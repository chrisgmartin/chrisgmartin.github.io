Product Surface

Pods, serverless endpoints, persistent volumes, templates, the CLI, the API. RunPod's developer-experience-led identity shows up most concretely here.

Pods

A "pod" in RunPod terminology is a running container with attached GPU(s). The fundamental product unit. A pod is created with:

  • A container image (RunPod-provided templates or your own).
  • A GPU type and count.
  • A region / cloud-type (Community or Secure).
  • Optionally, attached persistent volumes for storage that survives pod termination.

Pods boot in seconds-to-minutes depending on the template and image. The pod model is friendlier than raw VM provisioning — there's no OS installation, no driver configuration, no PyTorch setup. Users go from "I need a GPU" to "I have a running Jupyter notebook" in under five minutes for most workflows.

Serverless

RunPod Serverless is a managed inference / function service. Customers deploy a model or a function; RunPod runs it on demand and bills per second of worker time, covering cold start, execution and idle wait. Cold start time depends on model size, because larger models take longer to load into GPU memory.

Use cases:

  • Inference APIs that need to scale to zero between requests.
  • Workloads where you don't want to keep a pod running 24/7.
  • Spiky traffic patterns where dedicated capacity would be wasteful.

This is the product that competes most directly with Together.AI / Fireworks / Modal / Replicate. The user experience is similar — deploy a function, get an HTTP endpoint, pay for the seconds a worker runs.

Serverless is also where RunPod's two-product synergy shows: the underlying compute can run on Community Cloud (cheap, variable) or Secure Cloud (reliable). Users mostly don't see the distinction; RunPod's orchestrator handles routing.

Persistent volumes

By default, pod local storage disappears when the pod is terminated. Persistent volumes (network-attached, persistent block storage) survive pod lifecycle and attach to subsequent pods.

Useful for:

  • Training datasets you want to reuse across runs.
  • Model weights that exceed reasonable image sizes.
  • Checkpoints that need to outlive a single pod.

The pricing is separate from compute. As of November 2026, network volumes cost $0.07 per GB per month under 1 TB and $0.05 above, and a volume disk costs $0.10 per GB per month while the pod runs. The performance is network-attached storage, not local NVMe, so for performance-critical I/O you want to copy data to local storage at job start.

Templates

Pre-built container images for common workloads:

  • PyTorch + Jupyter for general ML.
  • Stable Diffusion variants (Automatic1111, ComfyUI, etc.) for image generation.
  • Text-generation web UIs for LLM experimentation.
  • vLLM for inference deployment.
  • Specific model-server templates (Llama, Mistral, etc.).

Templates lower the barrier to entry. A user who couldn't set up CUDA + drivers + their framework themselves can still spin up a working pod from a template.

CLI & API

RunPod's CLI and HTTP API let users automate everything the web UI does:

import runpod

runpod.api_key = "..."

pod = runpod.create_pod(
    name="training-run-42",
    image_name="runpod/pytorch:latest",
    gpu_type_id="NVIDIA RTX 4090",
    cloud_type="COMMUNITY",
    volume_in_gb=100,
)
# pod.id, pod.public_ip, etc.

The CLI mirrors the API. Power users orchestrate dozens of pods programmatically; SDKs in Python and JavaScript exist; integrations with workflow tools (Prefect, Dagster, etc.) are community-driven.

Networking

Pod networking varies by cloud type:

  • Community Cloud: Public IP, port forwarding to specific services. Variable bandwidth.
  • Global networking links Pods in one account at 100 Mbps, in 17 listed data centers, for NVIDIA GPU Pods only. It suits light traffic, not training.
  • Secure Cloud: Public IP optional. Inter-pod networking within a region available. More consistent bandwidth.

Multi-pod distributed training: possible but constrained. Instant Clusters support it, with 1600 to 3200 Gbps between nodes across 2 to 8 nodes, which is 16 to 64 GPUs. Community Cloud generally doesn't — pods are on different providers' hardware with no high-speed interconnect.

Developer experience

The DX is the single biggest reason customers choose RunPod over Vast. Concretely:

  • Faster onboarding (template-driven).
  • More polished web UI.
  • Cleaner CLI / API surface.
  • Better documentation.
  • More active community and company-staffed support channels.
  • Serverless option that Vast doesn't have.

The trade-off: prices are typically a bit higher than Vast for the same nominal hardware, and the supply pool is smaller. Users who prioritize DX over absolute lowest price come to RunPod; users who prioritize price over polish often pick Vast.

✓ Check yourself

Answer from memory before opening each one.

  1. Why can a new user go from needing a GPU to a running notebook in minutes on RunPod?

    Show answer

    A pod is a container with attached GPUs and templates bundle the framework, drivers and tools, so there is no OS install or CUDA setup. See pods and templates.

  2. You terminated a pod and lost the training checkpoints. What did you miss and how do you avoid it?

    Show answer

    By default local pod storage disappears on termination. Attach a persistent volume that outlives the pod and write checkpoints there. See persistent volumes.

  3. When does Serverless beat a pod, and when does the pod win?

    Show answer

    Serverless wins for sparse or spiky traffic that should scale to zero. A pod wins for sustained load where per-hour dedicated pricing is cheaper than paying per active second. See Serverless.

  4. Why is distributed training a poor fit for Community Cloud but workable on Secure Cloud?

    Show answer

    Community pods sit on different providers' hardware with no high-speed interconnect. Instant Clusters connect nodes at 1600 to 3200 Gbps, and global networking runs at only 100 Mbps. See networking.

  5. Your job reads a large dataset from a network volume and runs slowly. What do you change?

    Show answer

    Network volumes are network-attached, not local NVMe, so copy the data to local storage at job start for I/O-heavy work. See persistent volumes.

Takeaway

  • A pod is a running container with attached GPUs, created from a template or your own image.
  • Pod local storage is lost on termination; persistent volumes survive but are network-attached.
  • Serverless scales to zero and bills per second of worker time, suiting spiky inference.
  • Templates, the CLI and the API are what justify the price premium over Vast.
  • Distributed training runs on Instant Clusters, 2 to 8 nodes, and generally not on Community Cloud.
