Cloudflare security-audit

The skill that seeded Cloudflare's vulnerability-discovery harness — six phases, isolated hunters, and a rule that the agent which checks a finding is never the agent that found it.

by Cloudflarerepo github.com/cloudflare/security-audit-skilllicense MITskills 1 + 14 referenceschecked September 2026

What it is

One skill, but not a small one: a SKILL.md plus fourteen reference documents, a JSON report schema and two zero-dependency Node validators. It turns a coding agent into a security auditor that orchestrates other agents — isolated hunters working assigned units of a coverage ledger, then fresh verifiers whose job is to disprove what the hunters found. Cloudflare describe it as the single-repo starting point their fleet-wide harness evolved from, written up in Build your own vulnerability harness.

The six phases

The parent agent orchestrates; the work happens in isolated children. Validators run between phases, not just at the end.

PhaseWhat happens
1 · ReconnaissanceMap architecture, trust boundaries, input surfaces and prior evidence into architecture.md and a deterministic coverage-ledger.json.
2 · HuntingCoverage-led: hunters are assigned units from the ledger, record their checks, and coverage critics look for the gaps they left.
3 · ValidationEvery unique candidate goes to a fresh verifier that tries to disprove it.
4 · Structured outputconfirmed, needs_validation and rejected records written to findings.json and checked against report-schema.json.
5 · Record verificationFresh agents verify the final source claims; a material replacement gets yet another independent verifier.
6 · ReportingTarget-neutral REPORT.md, FINDINGS-DETAIL.md and NEEDS-VALIDATION.md derived from verified records and the ledger.

The three verdicts are deliberately distinct: confirmed carries a complete source trace and a bounded observed result; needs_validation names an exact unresolved fact and gets no severity; rejected records a candidate that was disproved.

Running it

Point your agent at the codebase and ask in plain language — there is no slash command.

prompt
security audit this codebase
find security vulnerabilities in ./src
do a security review, output to ~/audits/my-project
Where it writes

In full audit mode an unspecified output directory defaults to ~/security-audit-skill/<repo-name>/run-<N>. It writes inside the target repository only when you explicitly choose a directory that version control ignores — so an audit does not quietly turn into a dirty working tree.

Runs are additive. A second pass reads the prior ledger and findings to target gaps, revalidate changed source and carry forward current-source evidence, without treating stale or unresolved work as covered. Cloudflare's own number: a single run found roughly half the vulnerabilities that repeated runs found in total.

What it refuses to confirm

The design principles are the interesting part, because most of them are subtractive — rules about what not to call a finding:

  • Only established boundary failures get confirmed. A source-grounded lead it could not finish stays needs_validation with the exact unresolved fact attached, rather than being promoted on vibes.
  • Adversarial validation. The agent that checks a finding is never the agent that found it — the single rule most of the architecture exists to enforce.
  • Severity requires impact. Likelihood × impact, not deviation from a checklist.
  • Defense-in-depth gaps are not vulnerabilities. If layer A already prevents the attack, the absence of layer B is a hardening note.
Sandbox or it stays unvalidated

Executing target-controlled builds, tests, browsers, emulators, fuzzers and fixtures requires an OS-enforced sandbox: external networking disabled, a sanitized allowlisted environment, resource limits, and writes confined to assigned scratch paths. Without those controls the workflow does not improvise — it leaves the lead as needs_validation instead of running the target's code.
