Entity Identity and Resolution

One identity for a machine that twelve systems name differently: keys, crosswalks, probabilistic matching, survivorship, and what to do when the match is wrong.

Six systems, six names for one server

The previous chapter ended on a server that every system names differently. Take the Reserved server with serial GD-7F21, as GridDP's illustrative fixture, and follow its life through the records that mention it.

StageSystemWhat the record calls itWhat the key actually identifies
DesignGoogle DriveBOM revision BA server type, never one machine
OrderNetSuitePO 4471, line 3A quantity of units; no serial until the vendor ships
DeliveryCarrier trackingShipment 1Z-…-88A package or pallet that holds several servers
DeploymentNetBoxDevice 5519, rack R12, U31, hostname reno-r12-31One device, with a serial typed by a person at rack-in
OperationTelemetry storeinstance="10.4.12.31:9400"An address and port, which outlives the machine behind it
FailureJira Service ManagementINC-2093, DIMM failure, 2026-10-14A ticket whose text names the machine by whatever the reporter typed

Read the last column, because it is the real problem. Only one of these keys identifies a single machine, and that one was typed by hand. The BOM key names a type, the PO key a quantity, the shipment key a box, and the telemetry key an address that will be reassigned when the server leaves for RMA and another takes its slot. Joining on "the ID" does not work because the IDs are not about the same kind of thing.

That gives the design its shape. The ontology issues its own identifier for each server, one per physical machine, and records which native keys point at it, how it knows and how sure it is. The rest of the chapter is how that table is filled and kept honest.

Deterministic keys first

Start with exact matches and a crosswalk table. A crosswalk row says that in system S, native key K refers to entity E, and says how that was established. It is cheap, explainable and fast, and for a fleet of 600 servers it settles most of the work.

identity/crosswalk.sql (sketch)
create table entity (
  entity_id   text primary key,          -- issued by the identity service, never reused
  entity_type text not null,             -- 'server', 'rack', 'shipment', ...
  created_at  timestamptz not null
);

create table crosswalk (
  system      text not null,             -- 'netbox', 'netsuite', 'prometheus', 'jira', ...
  native_key  text not null,             -- '5519', '4471/3', '10.4.12.31:9400', 'INC-2093'
  entity_id   text not null references entity,
  method      text not null,             -- 'exact_serial', 'manual', 'linkage', 'mention'
  confidence  real not null,             -- 1.0 for exact, a match probability otherwise
  valid_from  timestamptz not null,
  valid_to    timestamptz,               -- null while the mapping holds
  primary key (system, native_key, valid_from)
);

Two columns carry the lessons of the table above. valid_to exists because addresses, hostnames and asset tags are reused. The mapping from 10.4.12.31:9400 to GD-7F21 holds from rack-in until the server leaves for RMA; afterwards the same address belongs to a different entity, and a join that ignores time will blame the old server for the new one's metrics. The pattern is the same one the curriculum covers for slowly changing dimensions, applied to keys instead of attributes. And method exists because later chapters need to know whether a link was asserted by a person, matched exactly or inferred.

Deterministic rules run in a fixed order, strongest first: a serial that matches exactly, then a NetBox device ID carried in the telemetry labels, then a hostname that follows the naming convention. Each rule writes its own method, so a bad rule can be found and reverted. For hostname, add a guard: reno-r12-31 is a position in a rack, so it is only a valid key while the NetBox record for that position names the same server.

The recommendation is to stay deterministic as long as exact keys exist. It flips when keys are missing or unreliable on a large population, which is exactly what the table showed for PO lines and shipments, and what is true of provider machines on the marketplace, where owners enter their own labels.

Probabilistic linkage for the rest

When no key links two records, the evidence is partial: a similar hostname, the same site, a close date. Fellegi and Sunter's 1969 paper, "A Theory for Record Linkage" in the Journal of the American Statistical Association, gives the standard answer. Compare each pair field by field, and ask how much more likely the observed agreement is if the pair is a true match than if it is not. Splink, the open-source implementation GridDP would use, states the same basis: its "core linkage algorithm is based on Fellegi-Sunter's model of record linkage."

Two probabilities per field carry the model. As Splink's documentation puts it, the m probability is the probability of an observation given the records are a match, and the u probability is the probability of the observation given they are not. Their ratio, K = m / u, is the Bayes factor, and its base-2 logarithm is the match weight. Weights add across fields and with a prior, and a total weight converts to a probability as 2w / (1 + 2w).

A worked case, all numbers illustrative. Link NetBox devices to PO shipment lines, 600 records on each side, so a random pair matches with probability λ of about 1 in 600. The prior weight is log₂(λ / (1 − λ)) = log₂(1/599) = −9.23.

  • Serial agrees: m = 0.9 and u = 0.00002, so K = 45,000 and the weight is +15.46.
  • Hostname is similar: m = 0.8 and u = 0.01, so K = 80 and the weight is +6.32.

With both: −9.23 + 15.46 + 6.32 = 12.55, a probability of 0.9998. With hostname alone, because the serial is missing on the PO side: −9.23 + 6.32 = −2.91, a probability of about 0.12. The first pair is a match for practical purposes. The second is neither a match nor a non-match, and that middle ground is where policy lives.

Set two thresholds, not one. Above +8, a probability near 0.996, link automatically. Below −4, a probability near 0.06, discard. Between them, put the pair in a review queue for a person in procurement or site operations. Where the thresholds sit is a business decision about the relative cost of a wrong merge and a missed one, and the next sections explain why the first is the costlier.

The comparison count is why blocking exists. Splink's guide notes that the number of pairwise comparisons grows "with (approximately) the square of the number of records," and that "a dataset of 1 million input records would generate around 500 billion pairwise record comparisons." GridDP's 600 Reserved servers produce 600 × 599 / 2 = 179,700 pairs, which needs no blocking. The roughly 40,600 machine records across marketplace and fleet produce about 824 million, which does. A blocking rule such as "same site and same vendor" keeps only the pairs worth scoring. As of November 2026 the Splink 5 documentation claims it is "capable of linking a million records on a laptop in approximately one minute," runs on DuckDB, scales to Spark "for 100+ million records," and needs no labelled data, since "models can be trained using an unsupervised approach."

Linked pairs then become clusters, and clusters need a guard. If A matches B at 0.9 and B matches C at 0.9, a naive connected-components pass puts A and C together even when they carry different serials. Add a cannot-link rule: two distinct, non-empty serials in one cluster is a violation, and the cluster goes to review whole instead of being merged.

Survivorship: which system wins which attribute

Once six records are one entity, each attribute still has up to six candidate values. A survivorship rule says which one is shown by default, per attribute, with a reason.

AttributeWinsWhy
SerialVendor packing data, then NetBoxTyped by a machine at the source; NetBox is typed by a person
Rack, unit, hostnameNetBoxIt is the system of record for placement
Delivery dateCarrier tracking over the PO dateAn observation beats a plan
Operational statusMost recent event across telemetry, Jira and PagerDutyNo single owner; recency decides

The tempting design stores only the winner and calls it the golden record. The better design keeps every candidate value as its own fact, with its source and confidence, and makes the golden record a view computed by the rules. The reason is correction: when a rule turns out wrong, or a source is retracted, the view recomputes. If only winners were stored, the losers are gone. Chapter 04 gives each candidate its provenance. The decision flips for consumers that cannot handle several values, such as a dashboard tile; materialise the golden record for them, as a derived table that can be rebuilt.

When the match is wrong

A false merge is worse than a missed one. A missed merge shows two objects where there is one, which is visible and annoying. A false merge fuses two servers, and the fused object inherits the facts and, through them, the permissions of both. If a Reno contractor's record merges with an Amsterdam server, a site-scoped permission now covers facts it should not. Chapter 05 returns to this; for now it is the reason to set the auto-link threshold high and to prefer the review queue to the optimistic merge.

Detection comes from three places: cannot-link violations such as two serials in one entity, a person flagging a bad merge from the review queue, and downstream anomalies such as a server reporting from two racks. The repair is a split, and a split must not rewrite history. The identity service never reuses or deletes an identifier. A split creates a new identifier for the part that was wrongly joined, closes the old crosswalk rows with a valid_to, writes new ones, and emits a split event. Every fact stores the native key it came from, so facts can be re-resolved under the corrected crosswalk instead of being edited by hand. That storage is what the lineage chapter of the ML data architecture guide calls identifiers stored on the downstream side, and the same discipline applies here.

A merge you cannot undo is a data loss

If the platform overwrites the losing record's key on merge, the split has nothing to restore from. Keep native keys on every fact and keep the crosswalk append-only with valid time.

Identity for documents and messages

A Slack thread about GD-7F21 is not a record in a source system, and it has no key. It has a mention. GridDP has about 150 Slack channels and 30,000 documents, and the platform links them by extracting mentions and resolving each against the crosswalk. The link is a fact with a confidence, not a merge: the thread does not become the server, it is evidence about it.

Scale decides the method. All pairs of documents against the 600 servers is 30,000 × 600 = 18 million candidate pairs, far too many for a fuzzy comparison on each and trivial for an index lookup of exact keys. So the first pass looks for strings that match the key formats: a serial, a hostname, a PO number, an incident ID.

identity/mentions.py
import re

SERIAL = re.compile(r"\bGD-[0-9A-F]{4}\b")
HOST = re.compile(r"\b(?:reno|dal|ams)-r\d{1,2}-\d{2}\b")

# Native keys the identity service already knows (illustrative).
KNOWN = {"GD-7F21": "ent_01JD7F21", "reno-r12-31": "ent_01JD7F21"}


def mentions(text):
    """Return (surface form, entity id or None, confidence) per match."""
    out = []
    for m in SERIAL.finditer(text):
        out.append((m.group(), KNOWN.get(m.group()), 0.99))
    for m in HOST.finditer(text):
        out.append((m.group(), KNOWN.get(m.group()), 0.95))
    return out


msg = "reno-r12-31 threw a DIMM error again, GD-7F21 needs the RMA before Friday"
print(mentions(msg))
print(mentions("the Reno box with the bad DIMM"))

The first message resolves to the entity twice, at 0.99 and 0.95. The second returns nothing, and that is the correct output: a description with no key is not a mention the platform can resolve with confidence. Do not send it to a language model and accept the answer as a link. Either leave it unlinked, or let a model propose a candidate that goes to the review queue below the auto-link line. The recommendation is exact keys at high confidence, proposals at low, and nothing silent in between. The exception is a source where the volume of unkeyed text is the point, such as an incident channel where nobody types serials; there the review queue will drown, and a model-proposed link with a visible confidence and a "proposed" method is the pragmatic choice, as long as method is never hidden from the consumer.

The identity service and what it promises

Everything above sits behind one narrow API, so that every other part of the platform asks the same questions the same way.

identity API (sketch)
resolve:   {system: netbox, native_key: "5519", as_of: 2026-10-14T09:00Z}
  returns: {entity_id: ent_01JD7F21, confidence: 1.0, method: exact_serial}
members:   {entity_id: ent_01JD7F21}
  returns: [{system, native_key, method, confidence, valid_from, valid_to}, ...]
changes:   stream of {merge | split | link | unlink, entity_ids, at, reason}

Five guarantees make the API safe to build on:

  1. An entity identifier is never reused, and never deleted. A merge leaves a redirect from the old identifier to the new one.
  2. The same inputs and the same rule versions return the same answer, so a replay rebuilds the same graph.
  3. Every mapping carries its method, confidence and validity interval.
  4. Writes are idempotent: registering the same native key twice does not create a second entity.
  5. Every merge or split is an event on the changes stream, so downstream tables can re-resolve instead of guessing.

Resolution sits on the ingestion path, so it has a latency budget. With peak change events of about 1,200 a second across all twelve systems, a lookup that adds 50 ms of serial delay per event caps one worker at 20 events a second and needs 60 workers to keep up; a cache of the crosswalk in memory, refreshed from the changes stream, turns that into microseconds. The cost is a staleness window after a merge, which is why the stream exists. Chapter 03 follows an event through that path and measures how late each hop makes it.

✓ Check yourself

Answer from memory before opening each one.

  1. A telemetry join on instance="10.4.12.31:9400" shows GD-7F21 running hot a week after it left for RMA. What went wrong in the identity design, and what column prevents it?

    Show answer

    The address was treated as a permanent key, but addresses are reused, so a replacement server took over the same address. The crosswalk's valid-to column closes the old mapping when the server leaves, and the join must respect it. See deterministic keys.

  2. A device and a PO line agree on hostname-like text, but the PO line has no serial. The total match weight is −2.9. Should the platform merge them, drop them or do something else, and why is the answer not a single cut-off?

    Show answer

    It belongs in the review queue: about 0.12 is too low to merge and too high to discard. Two thresholds leave the uncertain middle to a person, because the costs of a wrong merge and a missed one differ. See probabilistic linkage.

  3. The cluster A-B-C has links at 0.9 each, but A carries serial GD-7F21 and C carries GD-81C0. What do you do, and what is the tempting answer?

    Show answer

    Reject the merge and send the whole cluster to review. The tempting answer is to accept the chain because each link is strong, but transitive chaining joins records that two distinct serials prove are different machines. See probabilistic linkage.

  4. Why does a false merge cost more at GridDP than a missed merge, and what must the repair avoid doing?

    Show answer

    A merged entity inherits the facts and permissions of both parts, so a site-scoped restriction can cover facts it should not. The repair must not rewrite or delete identifiers; it issues a new one, closes crosswalk rows and re-resolves facts from their stored native keys. See when the match is wrong.

  5. Product wants a single "owner site" shown for every server, and engineering proposes storing only the winning value. Argue for or against, and name the case where you would concede.

    Show answer

    Keep every candidate value with its source and make the golden record a view, because a corrected rule or retracted source can then recompute it. Concede for a consumer that cannot show several values, and materialise a rebuildable table for it. See survivorship.

  6. A Slack message says "the Reno box with the bad DIMM is down again". A colleague wants a language model to link it to the server. What do you allow, and what do you refuse?

    Show answer

    Allow a proposed link with a visible low confidence and a method that says it is proposed, queued for review. Refuse a silent link at high confidence, since nothing in the text is an exact key. See identity for documents and messages.

Takeaway

  • Native keys often identify a type, a quantity, a box or an address, not a machine, so the ontology issues its own identifier per physical thing and records every native key that points at it.
  • A crosswalk with a validity interval and a method column handles reused addresses and tells later chapters how each link was established.
  • Run deterministic rules first and in order of strength; use probabilistic linkage only where exact keys are missing or unreliable, as with PO lines, shipments and provider machines.
  • Fellegi–Sunter match weights add across fields, and two thresholds with a review queue between them handle the pairs the arithmetic cannot settle.
  • A false merge costs more than a missed one because the merged object inherits both sides' permissions; guard clusters with cannot-link rules and split without rewriting history.
  • Keep every candidate value and compute the golden record as a view, so a corrected rule or a retracted source can change the answer.
  • Mentions in documents and messages are links with a confidence and a method, not merges.
