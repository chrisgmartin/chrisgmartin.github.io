Section C · Guard it

Deletions, Corrections and Replay

Propagating an erasure, a permission change or a corrected record through every derived table, index, cache and cited answer; replaying history without resurrecting what was removed.

Three triggers, three different jobs

Chapters 04 and 05 built a platform that remembers everything and shows each person only what they may see. Three events force it to stop doing one or both, and they ask for different work, so the first design step is to keep them apart.

  • Erasure. A person's personal data must be destroyed. GridDP holds some: contractor staff named in site access records, on-call engineers in PagerDuty, authors of Slack messages, people named in vendor emails.
  • Permission change. A contractor's engagement at Reno ends. Nothing is destroyed; every copy of every affected fact must stop being served to that person, quickly.
  • Source correction or retraction. A vendor withdraws a quote PDF, or NetSuite fixes a PO line. The platform did hold the old value and decisions were made on it, so history stays, but the old value must stop being served as current.

The legal text for the first is short. GDPR Article 17(1) gives the data subject the right to "the erasure of personal data concerning him or her without undue delay", on grounds that include data no longer needed for their purpose and withdrawn consent. Article 17(2) adds that where a controller "has made the personal data public", it shall "take reasonable steps, including technical measures, to inform controllers" processing it. An internal ontology rarely publishes, so that paragraph seldom bites, but Article 19 does: the controller "shall communicate any rectification or erasure" to each recipient of the data "unless this proves impossible or involves disproportionate effort", and tells the data subject who those recipients are on request. That means GridDP needs a register of what it sends where. Article 17(3) also lists limits, among them processing necessary "for compliance with a legal obligation" and "for the establishment, exercise or defence of legal claims", which is why an invoice naming a contractor is usually retained while their Slack messages are not. Which case applies is a decision for counsel, not for the pipeline; the pipeline's job is to carry out whatever the decision is, completely and provably. All GridDP figures in this chapter are illustrative.

Every place a fact lives

A fact written once is stored many times. The first design artefact is an inventory of copies, kept as a registry that each store's purge adapter is registered in, so adding a store without a purge path is a failed review and not a surprise in an audit.

The way to find the rows is provenance. Chapter 04 stores each derived fact's inputs; a forward walk over those edges from a source record or subject lists every derived fact, and each fact id keys its index entries, cache dependencies and citations. The purge is therefore a graph traversal from one root, followed by one delete per store using ids the traversal produced. Searching each store by name or text instead is how personal data survives in a store nobody remembered.

Two rows deserve a decision. The audit log from chapter 05 stores ids and not values, so it contains no personal content and survives intact, though a person's id in it is still a pointer, which is one more reason to keep names in a small separate identity table. Backups and fine-tuned models cannot be edited. The governance chapter of the ML data architecture guide says the same of weights: machine unlearning exists as research and is not something to promise a regulator. The only guarantees available are architectural: do not fine-tune on personal or restricted ontology facts, keep retrieval at query time, and bound backup retention so that the oldest copy ages out within a stated period. On restore, replay the erasure ledger described below before the system serves anything.

Deleting from the fact tables and logs

The Iceberg spec defines three row-level mechanisms. Position deletes "identify deleted rows by file and position in one or more data files". Equality deletes "identify deleted rows in a collection of data files by one or more column values", for example person_id = 5. Version 3 adds deletion vectors, where "at most one deletion vector is allowed per data file in a snapshot". All three mark a row as removed in a later snapshot. None of them touches the original data file, and the older snapshots still point to it, so the personal data is still on disk and still reachable by time travel.

The spec says when it leaves: "a file may be deleted from the file system when the snapshot in which it was deleted is garbage collected". The maintenance documentation says the same from the operator's side: expiring snapshots "removes them from metadata, so they are no longer available for time travel queries", and data files are not deleted "until they are no longer referenced by a snapshot that may be used for time travel or rollback". So the physical erasure sequence has four steps.

erase_subject.sql (sketch, Spark SQL with Iceberg procedures)
-- 1. Logical delete: rows are masked from new reads.
DELETE FROM ontology.person_facts WHERE person_id = 'person:8841';

-- 2. Rewrite: data files that held the rows are rewritten without them.
--    delete-ratio-threshold (default 0.3) would skip lightly affected files,
--    so force the rewrite for this purge.
CALL ontology.system.rewrite_data_files(
  table => 'ontology.person_facts',
  options => map('rewrite-all', 'true'));

-- 3. Expire: drop every snapshot older than the rewrite commit.
CALL ontology.system.expire_snapshots(
  table => 'ontology.person_facts',
  older_than => TIMESTAMP '2026-11-17 18:00:00',   -- time of step 2's commit
  retain_last => 1);

-- 4. Sweep unreferenced files left by failed jobs.
CALL ontology.system.remove_orphan_files(table => 'ontology.person_facts');

Three traps sit in that sequence. The expiry procedure's defaults are older_than five days ago and retain_last of 1, and snapshots "still referenced by branches or tags won't be removed", with branches and tags never expiring by default. A table that pins a snapshot by tag for an audit will keep the erased rows indefinitely, so the erasure job must list refs first. Expiring all older snapshots also removes the table's rollback and time-travel window, which chapter 04 said to use for reproducing past runs. The cost of that is real, so batch erasures, say once a day, and expire once per batch rather than once per request. And a fact table partitioned by recorded_at date, the usual layout for history, scatters one person's rows across every day's files, so a rewrite touches up to 365 partitions a year. The remedy is structural: keep names and other direct identifiers in a small identity table keyed by person_id, and let facts carry only the id. Erasure then rewrites one small table. Whether a surviving pseudonymous id counts as erased is a legal question; where it does not, the same rewrite is needed on the fact tables and is expensive.

The change log has its own version of the problem. Debezium's PostgreSQL connector follows a delete event "with a special tombstone event that has the same key but a null value", because "for Kafka to remove all messages that have that same key, the message value must be null", and tombstones.on.delete controls this and defaults to on (Debezium 3.7 documentation, as of November 2026). The consequence is narrow. Compaction removes earlier messages with the same key, so it helps only on topics that are compacted and keyed by the source row. A derived topic keyed by something else is not cleaned by a tombstone on the source, and a topic on time-based retention simply ages out. Inventory each topic's cleanup policy; do not assume.

Replay without resurrection

Replay is the safety net of the platform: fix a bug in the derivation rules, re-run history, get corrected facts. It is also how erased facts come back. The raw events still describe the person, and a rebuild that reads them faithfully writes the person into the new table.

The defence is an erasure ledger: an append-only record of subject keys and source references, each with the time it took effect and the scope of the erasure. Every replay and backfill job consults it at read time and drops matching events before any derivation runs. Permission changes follow the opposite rule from facts. A fact's valid and record times are historical and replay preserves them, but permission and erasure are current-state: a replay must evaluate audiences with today's tuples and today's ledger, never those of the replayed date.

# sketch: the filter every replay job wraps around its event source
def replayable(events, ledger):
    for ev in events:
        if ledger.erased(ev.subject_keys, ev.source_ref):
            continue                      # never rebuild an erased subject
        if ledger.retracted(ev.source_ref, ev.object_hash):
            continue                      # a retracted source stays out
        yield ev

Corrections replay the other way. A corrected source record becomes a new fact version that supersedes the old one under chapter 04's rule, so the rebuilt table shows the corrected value as current and the history still shows what was believed and when. The ledger therefore carries two kinds of entry that look alike but behave differently: erasures remove the data, retractions supersede it and stop it being served. Test the ledger the way the curriculum's data quality tests are written: a nightly check replays a sample window into a scratch table and fails if any ledger key appears.

Caches, indexes and answers that already left

A cached or stored answer is a derived fact with a shorter life and a worse paper trail, and the same provenance fix applies. Each answer records the fact ids it cites, which the retrieval path of chapter 07 produces anyway for citations. The cache keeps an inverted map from fact id to entries. A purge, retraction or permission event publishes the affected fact ids, and the cache evicts every entry that depends on one. The vector and full-text indexes use the same keys: all chunks of a withdrawn document share its document id, and a reconciliation sweep that lists ids present in the index but absent from the source catches the events that were lost. The RAG guide's section on deletes, tombstones and orphans describes that pairing; here it is driven from the platform's provenance and not from a document crawler.

Permission changes need one more rule. A cached answer built for one caller must not serve another, so the cache key includes the caller's audience, and a revocation evicts that caller's entries. Sharing entries across callers raises the hit rate and is safe only for facts that carry no restricted label. After a revocation the first read should also bypass any authorization cache, using the fresh-read mode chapter 05 reserved for this case.

Proving it happened

A claim that data was deleted needs evidence that does not itself contain the data. Each purge produces a receipt stored in the ledger: the request id, the scope as subject keys or hashes, the approver, and, per store, the method and the number of items removed. The receipt includes a verification result: after the purge, a probe queries every registered store for the keys. For the lakehouse the probe must read data files, not the masked table view, because the view hides rows that are still on disk. The expected answer is zero everywhere, and the receipt records the snapshot ids that no longer exist.

Receipts also serve Article 19: the register of recipients that had the data, and whether each was notified, is part of the same record. For recipients outside the platform, such as a vendor portal that received a contractor's name, the receipt records the notification and the response, or the reason it was judged impossible or disproportionate.

A masked row is not an erased row

A successful row delete is the first step of the purge, not the last. Until the rewrite and snapshot expiry complete and the probe reads zero from the data files, the receipt must say "masked", not "erased", and the clock for "without undue delay" is still running.

GridDP: a contractor leaves and a quote is retracted

The contractor. At 17:00 on a Friday the Reno vendor contractor's engagement ends. Nothing is destroyed. The group membership tuple is deleted; the next reads use fresh authorization state; cached answers keyed to that audience are evicted; the coarse site label in the search index is untouched because it describes the document, not the person; and the audit log shows the last time they read anything. Total work: one tuple, one eviction, one query for last access. The person's name in site access records is a separate matter, governed by the retention rule for those records, and an erasure request would start the sequence in the tables section.

The retracted quote. A vendor emails to withdraw the quote PDF it sent for GD-7F21's replacement DIMMs, saying the price was wrong. The platform's forward walk from the PDF's hash finds, for this example, three derived facts (a price comparison and two at-risk reasons that cited the quote), 31 chunks across the full-text and vector indexes, and two cached answers. The retraction rule supersedes the three facts, so history shows they were held from the quote's arrival until the retraction. Unsearchable flags go on the chunks. The cached answers are evicted. The raw object stays in the raw zone behind a restricted flag, since an audit may ask what the vendor sent, and the ledger gains a retraction entry so a replay does not bring the quote back. The flip is a retraction that says the document was sent in error and holds confidential data. Then it is an erasure of the object, with a hash-only stub left, and the whole sequence above applies.

✓ Check yourself

Answer from memory before opening each one.

  1. A contractor's engagement ends, and a different person asks for erasure of their Slack messages. Why are these different jobs, and what is destroyed in each?

    Show answer

    The permission change destroys nothing and must stop every copy being served to that person, quickly. Erasure destroys the personal data in every store, subject to legal limits that counsel decides. See Three triggers.

  2. A DELETE on the Iceberg person table succeeded an hour ago. The person's rows still come back from a time-travel query. Explain why and list what completes the erasure.

    Show answer

    A row-level delete only masks rows in later snapshots; the data files and older snapshots remain. Rewrite the affected files, expire snapshots older than the rewrite, and sweep orphans, after checking that no branch or tag pins an old snapshot. See Deleting from the fact tables and logs.

  3. You fix a bug in a derivation rule and replay a year of events. Two weeks later a subject erased last month reappears in the rebuilt table. What was missing, and where does it have to be consulted?

    Show answer

    An erasure ledger consulted by every replay and backfill before derivation. The raw events still described the person, and replaying faithfully rewrote them. See Replay without resurrection.

  4. The search index, the vector index and an answer cache all hold content from one retracted PDF. How do you find all three without searching them by text?

    Show answer

    Walk the provenance edges forward from the PDF's hash to derived fact ids, then purge each store by those ids: document id for the indexes, an inverted dependency map for the cache. A reconciliation sweep catches lost events. See Every place a fact lives and Caches, indexes and answers.

  5. A manager wants a receipt that says "erased" as soon as the delete statement returns. What do you tell them, and what must the receipt contain before it may say so?

    Show answer

    The row is only masked until rewrite and expiry finish. The receipt needs per-store methods and counts plus a probe reading zero from the data files, not the masked view, and records the expired snapshot ids. See Proving it happened.

  6. A vendor retracts a quote and asks you to delete it. When do you supersede and keep the raw object, and when do you destroy it?

    Show answer

    Supersede and keep it, restricted and unsearchable, when it is a wrong price that decisions were made on, so audits can show what was sent. Destroy it, leaving a hash stub, when it was sent in error and holds confidential data. See GridDP.

Takeaway

  • Erasure, permission change and source retraction are different jobs: destroy, stop serving and supersede. Treating them alike either loses history or leaves copies.
  • Keep a registry of every store that holds a fact, each with a purge adapter, and find what to purge by walking provenance edges forward from the root, never by searching stores.
  • An Iceberg row delete only masks. Physical erasure needs a rewrite, snapshot expiry that clears branches and tags too, and orphan removal; keep direct identifiers in a small table so the rewrite stays cheap.
  • A tombstone helps only on compacted topics keyed by the source row, so each topic's cleanup policy must be checked individually.
  • Replay must pass through an erasure and retraction ledger and use current permissions, or it brings deleted facts back.
  • A receipt says "erased" only after per-store counts and a probe that reads zero from the data files, and it must record Article 19 notifications.
