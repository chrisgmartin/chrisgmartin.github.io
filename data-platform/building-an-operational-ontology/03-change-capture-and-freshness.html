Change Capture and Freshness

Cutting the time from something happening to the platform knowing it: log-based CDC, event time against processing time, documents and conversations as change streams, freshness as a measured number.

The chain from event to knowing

Freshness is the age of what the platform knows, and that age is the sum of every hop between something happening and a person or agent being able to read it. The previous chapter gave each server one identity. This one asks how quickly a change to that server, a late shipment or a failing DIMM, reaches the graph that carries the identity. Nothing here improves by working on the hop that is already fast, so start by writing the hops down.

Take one telemetry-derived fact at GridDP, with all numbers illustrative. A GPU metric is emitted every 10 seconds, ingested within 5, resolved to its server within 2, aggregated over a 60-second window, turned into a derived fact such as "server health" within 30, and visible in the search index after another 30.

event source capture resolve window derive index happens ─▶ emit 10 s ─▶ ingest 5 s ─▶ identity 2 s ─▶ aggregate 60 s ─▶ derive 30 s ─▶ visible 30 s = 137 s target for telemetry-derived facts: 300 s slack: 163 s (54 %)

The sum is 10 + 5 + 2 + 60 + 30 + 30 = 137 seconds, which leaves 163 of the 300 seconds of the five-minute target. The window dominates: 60 seconds of the 137 are spent waiting for enough events to aggregate. Shaving the capture hop from 5 seconds to 1 gains almost nothing; shortening the window to 30 seconds gains 30. The lesson holds across the guide: measure each hop, then work on the largest one.

Capturing changes: log, poll or dual write

For a database you control, there are three ways to learn that a row changed, and they fail in different ways.

  • Polling queries the table on a schedule. It is simple and needs no special access. It adds half the interval on average, so a 5-minute poll adds about 2.5 minutes, and it cannot see changes that cancel out between polls or, without extra columns, hard deletes.
  • Dual writes make the application write to the database and to a queue. They look cheap and fail quietly: if the process dies between the two writes, the two stores disagree and nothing records it.
  • Log-based change data capture reads the database's own transaction log, so it sees what the database committed, in the order it committed it.

Debezium's features page, for version 3.7 as of November 2026, states the contrast directly: "Unlike other approaches, such as polling or dual writes, log-based CDC as implemented by Debezium ensures that all data changes are captured," and it "produces change events with a very low delay while avoiding increased CPU usage required for frequent polling." Its PostgreSQL connector takes "a consistent snapshot of all schemas" first, then "continues streaming changes from the exact point at which the snapshot was made." For tables too large to snapshot in one go, incremental snapshots are available and can be "triggered at connector runtime"; the connector "sorts each table by primary key and then splits the table into chunks," and uses watermarks to track its progress.

Two cautions from Debezium's own FAQ shape the design downstream. Delivery is exactly once only when everything stops gracefully; after a crash the application "sees every event at least once," and the FAQ adds that duplicates "will always be visible to downstream consuming applications." Plan for repeats, which the section on idempotent ingestion does.

At GridDP, only the marketplace Postgres is a database the platform team can read the log of; the other eleven systems are SaaS products, files or people. So the recommendation is log-based capture for the one source where it applies, and polling or events for the rest. The curriculum covers the mechanics of change data capture in detail, and the systems-design guide places it in the wider ingestion design. The recommendation flips for a small table that changes rarely, where a poll every few minutes is cheaper to run than a replication slot and a connector.

Event time, processing time and late data

A shipment scan has two times. The Dataflow Model paper, published at VLDB in 2015, defines them: event time is "the time at which the event itself actually occurred," and processing time is "the time at which an event is observed at any given point during processing within the pipeline." Event time of an event "essentially never changes," while processing time "changes constantly for each event as it flows through the pipeline." Between them sits an inherent and changing skew.

The distinction is not academic for GridDP. A carrier scans the pallet on Tuesday at 09:00, and the platform learns of it at 10:00 because the poll runs hourly. A fact stamped with the processing time says Tuesday 10:00; a fact stamped with the event time says 09:00. Compute "how long was the pallet at the depot" from the first and the answer is wrong by the polling interval, and wrong differently every day. The platform therefore stores both on every event, and uses event time for questions about the world and processing time for questions about itself, such as freshness.

Late data is what makes the two diverge widely. Some events arrive hours after they happened, and the paper's argument is that waiting for completeness is the wrong aim: "we will never know if or when we have seen all of our data, only that new data will arrive." A watermark is the practical device. The paper describes it as "a lower bound (often heuristically established) on event times that have been processed by the pipeline," and notes that "most watermarks must be heuristically defined," so it is an estimate of completeness, not a guarantee.

Set the allowed lateness per source, not globally. Telemetry from a rack can sensibly wait a couple of minutes before a window closes. A vendor PDF is routinely a day old before anyone mails it, and a window that waits for it would hold every dependent fact for 24 hours. The recommendation is to close windows on the watermark for streams with a short tail, and to accept late events as restatements for slow sources, writing a corrected fact with its event time and noting what was believed before. Chapter 04 shows how history records that restatement. The exception is any fact that triggers an irreversible action: gate such actions on the watermark passing, not on the first event.

Sources with no log

Webhooks fail silently when the receiver is down or the sender drops them, so treat a webhook as an accelerator and the poll as the source of truth. If the poll finds a record the webhook never delivered, count it: a rising rate is a freshness incident forming, and the measurement section below picks it up.

A PDF deserves one more note. Extraction produces a fact whose confidence is lower than a database row's, because a parser read a table. Keep the page and the extracted span with the fact. A later chapter uses them as evidence, and without them a wrong parse is unfindable.

Idempotent ingestion and ordering per key

Duplicates, retries and late arrivals are normal, so ingestion has to give the same state whether an event arrives once, twice or after its successor. Three rules do it.

  1. Give every event a stable identity made from the source, the native key and the source's own position, such as a log offset or a record version. Never use arrival time.
  2. Append the event to raw history once; a second copy with the same identity changes nothing.
  3. Update current state only if the incoming position is higher than the stored one. A late, older event still enters history but cannot overwrite a newer state.
ingest/apply.sql (sketch; the same logic ran in SQLite)
insert into raw_event (source, native_key, source_pos, event_time, payload)
values ($1, $2, $3, $4, $5)
on conflict do nothing;                      -- redelivery: no second row

insert into current_state (source, native_key, source_pos, payload)
values ($1, $2, $3, $5)
on conflict (source, native_key) do update
  set source_pos = excluded.source_pos, payload = excluded.payload
  where excluded.source_pos > current_state.source_pos;   -- older event: no overwrite

Run on a carrier record, an event at position 2 is applied, the same event redelivered is dropped as a duplicate, and an older event at position 1 arriving afterwards lands in history and leaves the state at position 2. Ordering per key matters here and ordering across keys does not, so route every event for one native key to one partition and let different keys run in parallel. That gives a sequence for each shipment without a global order across 1,200 events a second. The caveat: this only works while the source's position is trustworthy. For a spreadsheet diff there is no position, so use the file version and the row content hash, and accept that two edits between polls look like one.

Freshness as a measured number

"Real time" is not a number and cannot be tested. The Google SRE Workbook defines a service-level indicator as "the number of good events divided by the total number of events," and its table of indicators for different components gives the pipeline one: freshness, "the proportion of the data that was updated more recently than some time threshold." That definition is what to implement, per source and per derived fact.

Take 4,800 Reserved GPUs, each with a telemetry-derived fact and a five-minute threshold. If 48 of them have not been updated in the last five minutes, the indicator reads 4,752 / 4,800 = 99.0%. The metric counts every fact, not every arrival. That choice is the important one. A source that goes silent produces no late events to count, so a measure built on the events that did arrive stays green while the data rots. Counting every fact against its age catches the silence.

A derived fact is no fresher than its stalest input. The "server at risk" fact reads from the carrier, Salesforce, NetBox, telemetry and possibly a vendor PDF. Its freshness bound is that of the slowest input it actually uses: 24 hours if the PDF is required, 1 hour if it is not. Store the input ages with the fact so the bound can be shown to the reader. The SLO, the target and its window, and the error budget around this indicator are the subject of chapter 09.

GridDP's three tiers, with arithmetic

At a peak of about 1,200 change events a second, GridDP's platform handles 1,200 × 86,400 = 103.68 million events a day, and in a five-minute window 1,200 × 300 = 360,000. Treating all of them at the fastest tier would be wasteful. Freshness costs money, so the platform buys it only where a decision needs it.

  • Five minutes, telemetry-derived facts. A failing GPU or a rack going dark matters now. This tier needs streaming, windowing and an index refresh inside the 163 seconds of slack computed above.
  • One hour, ERP and ticketing. Purchase orders, incidents, commitments and shipments change on human timescales. A poll every 15 minutes leaves 45 minutes of budget for the rest of the chain.
  • Twenty-four hours, documents and Slack. 30,000 documents refreshed over a day is 1,250 an hour, about one every three seconds, which a batch job handles easily. A faster tier would cost more and change no decision.

The recommendation flips per source when a decision moves. If Slack becomes the place where site operators declare an outage, the Slack tier for that channel rises, and the cost of reading it faster is justified for that channel only. The curriculum's streaming fundamentals chapter covers the windowing and state that the five-minute tier needs.

A four-day delay, propagating

Return to GD-7F21. Shipment 1Z-…-88 slips four days, which is 96 hours. How soon the platform knows depends on which source reports it.

carrier scan, Tue 09:00 (event time) ├─ poll hourly ─▶ known by Tue 10:00 at worst 1 h = 1 % of the 96 h └─ vendor PDF, mailed next day ─▶ known by Wed 09:00 at worst 24 h = 25 % of the 96 h then, either way: shipment ─▶ identity (chapter 02) ─▶ server GD-7F21 ─▶ expected at Reno: +4 days ─▶ derived fact "late" updated within the 5-minute tier ─▶ commitment slack recomputed (chapter 08)

The carrier path spends about 1% of the delay before the platform knows; the PDF path spends 25%. That difference is the whole argument for polling the carrier hourly and for treating the vendor's mail as confirmation, not as the first signal. When both disagree, the fresher source wins on the date and the older one is kept as a candidate fact, as the survivorship rule in chapter 02 prescribes.

Note what propagates and what does not. The platform's event is the change to a date on one server, and everything downstream of that date is recomputed from it: the "late" flag, the slack against the November promise, the ranking of at-risk servers. The delay does not travel as a message to people. It travels as a fact, and the people and agents who ask the two recurring questions see it because the graph changed, not because someone remembered to tell them.

✓ Check yourself

Answer from memory before opening each one.

  1. A latency budget for a telemetry fact sums to 137 s against a 300 s target. An engineer proposes cutting ingest from 5 s to 1 s. What is wrong with spending effort there, and what would you change first?

    Show answer

    The ingest hop is 4 s of a 137 s chain, so the saving is under 3%. The 60 s aggregation window is the largest hop, so shorten it first if freshness is the problem, or accept the slack if it is not. See the chain.

  2. The team proposes dual writes from the marketplace application to Postgres and to a queue, because log-based CDC "needs a connector". What failure does the proposal accept, and when is a poll the better choice than either?

    Show answer

    A crash between the two writes leaves the stores disagreeing with no record of it. A poll is better for a small, slow-changing table where its delay is within the tier and a connector and replication slot cost more to run. See capturing changes.

  3. A carrier event happened at 09:00 and was ingested at 10:00. Which timestamp do you use to compute how long a pallet sat at a depot, which for how stale the platform's knowledge is, and why does storing only one fail?

    Show answer

    Event time for the depot duration, processing time for staleness. With only processing time, the duration is wrong by the poll interval and by a different amount each day. See event time and processing time.

  4. A carrier record at position 2 arrives, then the same record again, then an older record at position 1. What are the final contents of raw history and of current state, and why?

    Show answer

    History holds positions 1 and 2, once each; current state holds position 2. The duplicate is dropped on its identity and the older event cannot overwrite a higher position. See idempotent ingestion.

  5. A freshness dashboard built from the events that arrived shows 100% green for the PagerDuty source, yet nobody has been paged in a week during an outage. What did the measure miss, and how would you rebuild it?

    Show answer

    A silent source produces no late events, so a measure over arrivals stays green. Count every expected fact against its age, as the SRE Workbook's proportion of data updated within a threshold, so silence lowers the number. See freshness as a measured number.

  6. Finance asks that every source run at the five-minute tier "to be safe". Argue the cost, and name the condition under which you would raise one source's tier.

    Show answer

    Faster tiers cost streaming, state and index work for no change in any decision at sources like documents, at about 1,250 per hour. Raise a source when a decision depends on it, such as a Slack channel where outages are declared. See the three tiers.

Takeaway

  • Freshness is the sum of every hop from event to readable fact, so write the hops down, measure each one and work on the largest.
  • Log-based CDC captures all committed changes with low delay, but it applies only to a database you can read the log of, and its delivery can repeat after a failure.
  • Store event time and processing time on every event: the first answers questions about the world, the second questions about the platform's own lag.
  • Set allowed lateness per source, and accept late events from slow sources as restatements instead of holding every dependent fact.
  • Idempotent ingestion identifies events by source and position, appends history once and advances current state only on a higher position, with one partition per native key.
  • Freshness is the proportion of data updated within a threshold, counted over every expected fact, so a silent source lowers the number instead of hiding.
  • The three tiers of five minutes, one hour and 24 hours buy speed only where a decision needs it, and which source reports a delay decides how much of it passes before anyone knows.

Knowing quickly is not the same as being able to say where a fact came from and what was believed when, which is the job of the next chapter. → Provenance, History and Evidence
