Section D · Make it operational

Serving People and Agents

One query service for dashboards, people and agents: filter first, cite every fact, show its age, name the gaps.

One door

Every consumer reaches the ontology through one query service: a person in a dashboard, a Slack bot, an agent acting for a procurement lead. The reason is not tidiness. The four guarantees built so far (identity, freshness, provenance, permissions) can only be enforced at the point where data leaves the platform. A second door, such as a read replica handed to finance "for now", is a place where at least one of them is not enforced, and it is where the first leak appears.

The rule is "no door that skips the checks", not "one process". An analytics warehouse can stay a separate system if it is fed from the same permissioned facts and carries the same labels.

Facts and documents, joined on identity

The service answers from two stores with different characters. The fact store holds typed facts about objects: exact, filterable, traversable. "Which servers covered by commitment X have a shipment expected after 22 November?" is a walk across links with a filter, and the answer is right or wrong. The document index holds thirty thousand Drive files and the Slack history: approximate, ranked, and only as good as its parsing.

The join between them is the object identifier, never the text of a serial. Chapter 04 gave every document span a mentions link with a confidence. The link works both ways. From an object to documents: "find spans that mention GD-7F21 with confidence above 0.8, then rank them against the question". From documents to objects: a vendor email says the shipment is on time, and the service shows it beside the carrier fact that says it is four days late. That second direction is where the ontology earns its cost, because the disagreement is the finding.

Order the work so the exact store narrows the approximate one. For "why is the Reno batch late?", first find the shipments linked to PO 4471 whose expected date is past the plan, then search documents restricted to those shipments, their PO lines and their servers. A filter that turns thirty thousand documents into a few dozen costs little and improves precision more than a better ranker would.

Permissions before the model

Whatever reaches a model's context can reach the user, an injected instruction, or a log. An instruction such as "do not reveal finance documents" is a request to a text predictor, not an access control. So the service filters first, and the model only ever sees the filtered result.

The caller is resolved first: for an agent, the pair of agent and user, with the user's permissions as the ceiling. Then the service asks the permission graph what the caller may see and passes that into the queries as a filter. For GridDP's six hundred servers the visible set is small enough to list, so the structured query runs over exactly that list. For thirty thousand documents no caller's visible set can be listed; each indexed span instead carries a coarse audience label written at ingestion, search filters on the label, and the top results are checked exactly against the graph before anything is returned. The label is a hint; the check is the authority. A document that fails the check is dropped even if the index said yes.

A truncated list is a gap, not a verdict

If the permission lookup times out or hits a size cap, it returns fewer objects, never more. That fails safe for leaks and silently wrong for completeness: "no late servers" may mean "none among the first thousand". The service detects truncation, returns what it has and says the result may be incomplete. It never widens the filter to compensate.

An answer carries its evidence, its age and its holes

An answer from the ontology is more than prose. It has four parts: the text, the facts behind each claim, the age of each fact against its target, and the gaps the service knows about.

The citations come from the model: it is given the retrieved facts and spans as numbered documents and asked to cite them, and most model APIs now return the cited passage and its location so the service can map each citation back to a fact identifier. The rest cannot come from the model, because the model does not know what it was not given.

  • Age is computed by the service for each cited fact: now minus the recorded time, against the source's tier from chapter 05. A citation proves the text came from that source. It does not prove the source is current.
  • Gaps are computed by rule. For every object in the answer the service knows which sources are expected to speak. A shipment in transit should have a carrier scan each day; a last scan on Tuesday produces "no shipment update since Tuesday". The model might omit that line. The service cannot.
  • As-of is the time up to which the facts are complete, so a follow-up question can ask for nothing older.
  • The check is the identifier of the permission check that was run, as whom, so the answer can be audited.

Adding a source without adding a service

A vendor starts sending a nightly file of RMA statuses. If that needs a new service, the platform will not scale past twelve sources. It should need one registration, reviewed as a pull request, with four parts.

  • Shape. Which column becomes which property on which object type, and which column is the true-from time. Unmapped columns are kept raw, not dropped.
  • Identity. Which columns are keys (serial, PO line, RMA number) and which crosswalk they resolve against. Rows that do not resolve go to the review queue, not the bin.
  • Permissions. A default audience for the source and a column that maps each row to a site. A row without a mapping is visible only to the source's owners, so a mistake fails closed.
  • Provenance. File hash, row number and ingestion time stored with every fact.

The build runs the registration against a sample file and reports rows ingested, the share that resolved to an object, and any row with no audience. Sources that need real parsing (a new kind of scanned PDF) need code, and the registration then points at the parser.

The tool contract for agents

An agent reaches the service through tools. The Model Context Protocol is one way to describe them; any function-calling scheme has the same shape: a name, a description, a typed input, a typed output. The ontology's tools add four rules.

  • Identity from the credential, never from an argument. A tool with a "user" parameter lets the model, or an injected instruction, ask as someone else.
  • A consistency token goes in and out. The reply carries its as-of time; a follow-up call can pass it back as a minimum, so a second answer in one conversation is never based on older facts than the first.
  • Few tools, shaped as intent. Find objects, get an object, trace a fact to its sources, search documents, list gaps, and the named actions from chapter 07. No free-form query tool for agents.
  • Hidden means not found. An object the caller may not see returns the same answer as one that does not exist, so existence does not leak.

People doing exploratory analysis can have a query path through the same door with the same row filters. The difference is that a person can be trusted with a wide tool and an agent should not be.

✓ Check yourself

Answer from memory before opening each one.

  1. A colleague proposes a read replica of the fact store for finance's quarterly work. What do you ask before agreeing?

    Show answer

    Whether it applies the same permissions, carries provenance and shows age. A door that skips them is where the first leak appears. A separate analytics system is fine if it is fed from the permissioned facts with the same labels. See one door.

  2. The model's cited answer says the shipment is on time, citing a vendor email. The carrier says four days late. Which design element should have caught this, and why can the model not supply it?

    Show answer

    The join on identity shows both facts side by side, and the age check shows the email is older. The model sees only what it is given and cannot know what disagrees with it. See facts and documents and the answer envelope.

  3. A contractor's document search returns exactly the cap's worth of results and no error. What has happened and what does the service do?

    Show answer

    The permitted list was truncated. The service reports the result as possibly incomplete and never widens the filter. See permissions before the model.

  4. A vendor sends a weekly spreadsheet of quote revisions. Which part of the registration is most likely to cause an incident if done carelessly, and what default limits the harm?

    Show answer

    The permission mapping, since quotes are finance documents. Unmapped rows are visible only to the source's owners, so the mistake fails closed. See adding a source.

  5. Why does an agent get "find objects" and "trace a fact" but not a free-form query tool, when an analyst gets one?

    Show answer

    Each extra tool shape is another way for an injected instruction to over-reach, and an agent cannot be held responsible. A person can. Both go through the same door with the same row filters. See the tool contract.

Takeaway

  • Every consumer goes through one query service, because the four guarantees can only be enforced where data leaves.
  • The exact fact store narrows the approximate document search, joined on object identity. Disagreement between them is a finding.
  • Permissions are applied before the model sees anything. A truncated permitted list is reported as a gap and never widened.
  • The model writes the sentence; the service attaches citations resolved to facts, the age of each, the gaps, the as-of time and the permission check.
  • A new source is a four-part registration that fails closed. Agent tools take identity from the credential, carry a consistency token, and stay few.
