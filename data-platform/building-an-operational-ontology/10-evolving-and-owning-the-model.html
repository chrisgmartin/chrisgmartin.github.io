Evolving and Owning the Model

Who owns a definition, how the model changes without breaking its users, and what to do when facts must go.

Every type has an owner, and so does every definition

Chapter 02 gave every object type a system of record. That settles which value wins. It does not settle who decides what the type means. When procurement says a server is "delivered" at the dock and site operations say it is "delivered" when it is racked, no system can arbitrate. A person has to.

So every object type, link type and lifecycle state has a named owner: a person or a team, not a system. The owner decides the definition, approves changes to it, and is the one the platform team asks when two sources disagree in a way no rule covers. For GridDP:

OwnedOwnerTypical dispute
Server, Rack, Site, GPU, lifecycle statesSite operations leadWhen is a server "live": first telemetry, or customer acceptance?
PurchaseOrder, POLine, Vendor, ShipmentProcurement leadIs a partial delivery "delivered"?
Customer, Commitment, the covers linkHead of customer deliveryWhich servers count against which promise when a batch is split?
Incident, RMASite reliability leadDoes a GPU swap close the incident or open a new one?
Person, Document, audience labelsSecurity and the HR partnerWhat a contractor may see at a site they are visiting
Identity rules and thresholdsPlatform team, with the site operations leadWhere the auto-link line sits

Write the definitions down where the model lives, next to the types, in the owners' words. "Live: the customer has accepted the server in Salesforce, or fourteen days have passed since burn-in finished with no rejection." A definition the owner wrote is one the owner will defend.

Kinds of change, from cheap to expensive

The model will change. New sources arrive, the business renames things, a type turns out to be two. The cost of a change depends on what else has to move.

  • Add a property. A pull request. Nothing that exists changes.
  • Add a link type. A pull request plus a "proved by". Existing queries keep working; new ones can use it.
  • Add an object type. A design review. It needs an owner, identity rules, audience labels, a place in the picture, and a check that no existing type already covers it.
  • Rename. Keep the old name as an alias for a stated period and record who still uses it. A rename with no alias breaks every dashboard and agent tool at once.
  • Split or merge a type. The expensive one. Every object needs a new or merged identity, history has to be re-attributed, permissions re-derived, and every consumer updated. Do it rarely, with the owners in the room, and never in place: build the new types beside the old, migrate, then retire.

Two habits make all of these safer. Version the model: every change is a numbered revision, and every fact records the model version it was made under, so "what did Server mean in June?" is answerable. And keep a list of consumers per type (dashboards, tools, reports), so a change knows whom to tell.

When facts must go

Three events look like deletion and are three different jobs.

  • Erasure. A person asks for their data to go, and the law (GDPR Article 17 in Europe) says it must. GridDP holds personal data in site access records, PagerDuty rotations, Slack authorship and vendor emails. Erasure means destroying those values in every store that holds a copy, and keeping a receipt that proves it. Which exceptions apply (an invoice naming a contractor is usually retained) is a decision for counsel, not the pipeline.
  • Permission change. A contractor's engagement ends. Nothing is destroyed. Every copy of every affected fact must stop being served to that person, quickly, which is one edge removed in the permission graph plus the cache rule from chapter 06.
  • Correction or retraction. A vendor withdraws a quote, or NetSuite fixes a PO line. The platform did hold the old value and decisions were made on it, so history stays. The old value is superseded by a new version under chapter 05's rule and stops being served as current.

Erasure is the hard one, and the model helps more than the storage does. A fact written once is stored in several places: raw copies, fact tables, the search index, caches, and answers already given. The way to find every copy is provenance: walk forward from the person's identifier to every fact derived from their data, and each fact's identifier keys its index entries and cached answers. Searching stores by name is how personal data survives in a store nobody remembered.

Two structural choices make erasure cheap. Keep names and other direct identifiers in one small table keyed by person identifier, and let facts carry only the identifier, so erasure rewrites one small table rather than a year of partitions. And keep an append-only ledger of what was erased, consulted by every rebuild, so that replaying history to fix a bug does not quietly bring an erased person back. The storage mechanics (how a lakehouse table physically forgets a row) are the lakehouse chapter's job in the curriculum.

A hidden row is not an erased row

A delete statement on a lakehouse table masks the row from new reads. The bytes are still in the old files until those files are rewritten and the old snapshots expire. Until a probe reads zero from the files themselves, the receipt says "masked", not "erased", and the legal clock is still running.

What the ontology promises, in numbers

A model people act on needs stated guarantees, each with a number, or it is a hope. Three are enough.

  • Freshness. The share of facts younger than their tier's target, per tier, over a rolling four weeks. GridDP aims at 99 per cent for the five-minute tier, which allows about seven hours of the whole fleet being stale in a month. A two-hour source outage spends a third of that, which is why each tier gets its own number rather than one blended figure that averages a dead document feed against a healthy telemetry feed.
  • Correctness. A golden set of about sixty questions about specific servers, with answers written by site operations, re-run after every change. The share answered correctly with citations that resolve.
  • Permissions. Not a percentage. A leaked finance document is not a degraded answer, so this one is an invariant: every answer has a recorded permission check, a scheduled probe tries to read across sites as a contractor and expects zero results, and a revoked permission stops working within a stated minute. One violation stops changes until it is understood.

The form of these (indicators, windows, error budgets, what to do when a budget is spent) is the SRE Workbook's, and the systems-design guide's quality and observability chapter applies it to the platform as a whole. The ontology adds one habit: when an answer is wrong, trace it through its envelope first. Nine times in ten the model did what the facts told it, and the fault is a stale source, a survivorship rule that trusted the wrong system, or a definition two owners disagreed about.

The first ninety days after launch

What tends to happen, and what to do about it.

  • The review queue fills with the same mismatch. A source names things in a way no rule expected. Add the rule, record its method, and re-resolve. A queue that grows is a rule that is missing, not a person who is slow.
  • Two owners disagree about a state. Write both definitions down, pick one, and record the other as a second property if it answers a real question. "Delivered at dock" and "racked" can both exist.
  • Somebody asks for a thirteenth source. The registration from chapter 09 should take a week, including the review. If it takes a month, the model is missing a type, and that is the real request.
  • An agent gives a confident wrong answer. Trace the citation to the fact, the fact to its source and the rule that chose it. Fix the rule or the source, add the question to the golden set. Fine-tuning the model is almost never the fix.

✓ Check yourself

Answer from memory before opening each one.

  1. Procurement and site operations disagree about when a server is "delivered". Which rule in the model settles it, and if none does, what happens?

    Show answer

    None: this is a definition, not a value, so no system of record can decide. The named owner of the Server lifecycle decides, the definition is written down in their words, and if both meanings answer real questions, both become properties. See every type has an owner.

  2. Rank these by cost: rename Commitment to Promise; add a "warranty expiry" property to Server; split Document into File and Thread.

    Show answer

    The property is cheapest. The rename is next, and safe only with an alias. The split is most expensive: new identities, re-attributed history, re-derived permissions, every consumer updated. See kinds of change.

  3. A contractor leaves, and a different person asks for their Slack messages to be erased. Why are these different jobs?

    Show answer

    The leaver is a permission change: destroy nothing, stop serving. The erasure destroys values in every store, with a receipt, subject to the exceptions counsel decides. See when facts must go.

  4. You replay a year of history to fix a derivation bug. Two weeks later a person erased last month is back in the tables. What was missing?

    Show answer

    The erasure ledger, consulted by every rebuild before derivation. The raw events still described the person and a faithful replay rewrote them. See when facts must go.

  5. Why is permission correctness an invariant and not a 99.9 per cent target like freshness?

    Show answer

    A stale fact is a degraded answer; a leaked document is not. A percentage would allow a leak every thousand answers. So every answer records its check, probes expect zero leaks, and one violation stops changes. See what the ontology promises.

Takeaway

  • Systems of record settle values. People settle definitions. Every type, link and state has a named owner who writes its definition in their own words.
  • Changes range from a pull request (a property) to a migration with the owners in the room (a split). Version the model and keep a consumer list per type.
  • Erasure, a permission change and a correction are three jobs: destroy, stop serving, supersede. Find every copy by walking provenance, keep identifiers in one small table, and keep an erasure ledger that every rebuild consults.
  • Three promises with numbers: freshness per tier, correctness against a golden set, and permissions as an invariant with a recorded check on every answer.
  • When an answer is wrong, trace it through its envelope before blaming the model.
