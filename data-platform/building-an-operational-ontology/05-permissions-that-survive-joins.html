Section C · Guard it

Permissions That Survive Joins

Relationship-based access control over the object graph, source restrictions enforced in search and in derived answers, and what happens when an answer combines three systems with three policies.

Why a join breaks row-level security

Take the first of GridDP's questions: which Reserved servers promised to customer X for November are at risk, and why? The answer touches a Salesforce commitment, a NetSuite purchase order, a NetBox rack, a carrier delay, and a Slack thread where a site lead explained the delay. Each system has its own idea of who may read its rows. Row-level security in Postgres, a NetSuite role and a Slack private channel are each correct inside their own walls, and none of them can say what the join of the three may show to a vendor contractor at Reno.

The ontology has to hold one permission model of its own and map every source policy into it at ingestion. There is no alternative, because the join happens in the ontology and no source database can enforce a rule over rows it does not hold. The roles are fixed by the guide: procurement, site operations, finance, executives, vendor contractors (per site) and agents acting for a user. Site, rack and device inherit downwards; finance documents are limited to finance and executives; a contractor sees only their own site; an agent never sees more than its caller. All GridDP figures in this chapter are illustrative.

This chapter owns who may see which fact. It relies on the per-fact source and history of chapter 04, because a derived fact's audience is computed from its inputs, and it hands deletion on a permission change to chapter 06.

Relationships as the model

Google's Zanzibar paper (USENIX ATC 2019) gives the model most open implementations follow. Access control lists are stored as relation tuples such as doc:readme#parent@folder:A#..., meaning doc:readme is in folder:A, alongside group:eng#member@11, user 11 is a member of group:eng. A namespace configuration then rewrites relations: its Figure 1 makes owners editors, editors viewers, and "viewers of the parent folder are also viewers of the document". Permission is therefore a graph walk, not a per-object list, and one tuple, a document's parent, grants an audience that would take thousands of list entries to write out.

OpenFGA is the open-source implementation. Its documentation defines the pieces plainly: "a type is a string" naming a class of objects, "a relation is a string defined in the type definition of an authorization model", and "a relationship tuple is a base tuple/triplet consisting of a user, relation, and object". A Check "returns whether the user has a certain relationship"; ListObjects "returns all objects of a given type" the user relates to. Its JSON syntax "closely follows the original syntax in the Zanzibar Paper". The DSL below follows the configuration-language page's operators: from for inheritance from a related object, or and and for union and intersection. It is a sketch of GridDP's site tree and has not been run against a server.

griddp.fga (sketch, OpenFGA DSL)
model
  schema 1.1

type user
type group
  relations
    define member: [user]

type site
  relations
    define operator: [group#member]
    define contractor: [user]
    define can_view: operator or contractor

type rack
  relations
    define site: [site]
    define can_view: can_view from site

type device
  relations
    define rack: [rack]
    define can_view: can_view from rack

type document
  relations
    define site: [site]            # site plans, vendor quotes for a site
    define reader: [group#member]  # explicit audience, e.g. finance
    define can_view: reader or can_view from site

Three tuples then carry the contractor rule: site:reno#contractor@user:vendor-7, rack:r12#site@site:reno and device:5519#rack@rack:r12. A Check of vendor-7 on device 5519 walks device to rack to site and succeeds. The same vendor on a Dallas device finds no path and fails. Nothing was written for Dallas; the absence of an edge is the denial. Finance documents get a reader tuple naming the finance and executive groups and no site tuple, so no site relationship can reach them. Moving a rack between sites is one tuple change, and every device under it follows.

Zanzibar is also the source of the hard consistency requirement. The paper's "new enemy" problem has two cases: a user removed from a folder's list who can still see documents added to it afterwards, and a stale ACL applied to new content. Zanzibar prevents both with external consistency and snapshot reads, carried by an opaque token it calls a zookie. OpenFGA's consistency page offers a coarser tool: with caching enabled the default mode is that "OpenFGA will serve queries from the cache when possible", and HIGHER_CONSISTENCY skips the cache. The cost is stated: always using it "will have a significant impact in performance". GridDP should use the default for ordinary reads and force fresh reads on the path that follows a revocation, such as the minute after a contractor's access ends. That choice is the flip point for the whole system: if a stale grant can leak a vendor quote, the extra latency is cheap.

When attributes are the better tool

NIST SP 800-162 describes attribute-based access control as a "logical access control methodology where authorization to perform a set of operations is determined by evaluating attributes", of the user, the resource, the action and the environment. Relationships suit questions of structure: this rack is in that site, this person works for that contractor. Attributes suit questions of value or state: the quote is under a spending limit, the grant has not expired, the request comes from the site's network.

OpenFGA folds the second kind into the first through conditions: "a condition is a function composed of one or more parameters and an expression", attached to a tuple, with context merged from the tuple and the request, and the tuple's value winning on a clash. GridDP's use is time-boxed contractor access. The tuple for vendor-7 carries an expiry attribute (not shown in the sketch), the request supplies the current time, and the grant lapses without anyone deleting it.

Combine them in that order of preference: relationships for the structure that matches the org chart and the site tree, a condition for the time or value limit on a single edge. Pure attribute rules over many fields are harder to audit, because no one can list who may see a fact without evaluating every user; ListObjects and ListUsers are cheap questions only when access is relationships. The case where attributes should lead is a policy that does not follow an entity tree at all, such as "no one outside finance sees any amount over a threshold".

Derived facts: the most restrictive source wins

A derived fact is readable only by someone who may read everything it was derived from. The reasoning is mechanical: if the audience of a derived fact were wider than that of any input, the fact would be a side channel for the input. A "reorder at risk" fact computed from a PO's unit price leaks that price to anyone who can see the flag.

The model above cannot express this directly for variable inputs, because and joins a fixed set of relations. The workable design uses policy labels. Every source field is mapped at ingestion to a small set of labels such as finance or site:reno. Every derived fact stores the union of its inputs' labels, computed at derivation and carried beside the inputs array from chapter 04. A caller may read the fact when a Check passes for every label on it. Labels number in the tens, so the check is a few calls; the label set is far smaller than the input set.

Label the field, not the record. A PO's delivery date belongs to procurement and site operations, and its unit price to finance. A "late" flag derived from the date alone carries no finance label, so site operations can act on it. Record-level labels would hide it from them and turn the permission system into the thing that blinds the people closest to the problem.

There are two honest exceptions. A rule may declassify, for example publishing to executives a count of at-risk servers per site that omits amounts. A declassification is an Activity in chapter 04's sense: a named rule, a named approver, a version, and an agent on record, so that widening an audience leaves evidence. And a few facts are open to every employee by policy, such as a hostname. Without these two escapes the rule produces answers nobody may see, and people respond by exporting data to spreadsheets, where no label follows it.

A summary is a derived fact too

Counts, rankings and "top reasons" computed over restricted rows inherit the restriction unless a declassification rule says otherwise. The helpful aggregate is an easy path to a leak, because nobody thinks of it as data.

Filtering results: before or after the query

There are two ways to apply permissions to a result set. Pre-filtering asks the permission system for the objects the user may see, then restricts the query to them. Post-filtering runs the query, then Checks each result. OpenFGA's relationship-queries page positions ListObjects for "access-aware filtering on small object collections" and states its limits: results come back only if found within listObjectsDeadline, default 3 seconds, and are capped by listObjectsMaxResults, default 1,000.

Those limits sort GridDP's collections. A site operator's visible Reserved servers number at most 600, growing by about 200 a quarter, so ListObjects returns the whole set under the default cap for about two more quarters; raise the cap or move to the next scheme before then. The marketplace's 40,000 machines and the 30,000 documents are over the cap by a wide margin, and a finance user may legitimately see all of them.

Pre-filter (ListObjects)Post-filter (Check per result)
SuitsVisible set under the cap, structured queriesSearch, ranking, large visible sets
CostOne call, but cap and deadline applyOne Check per candidate
FailureSilent truncation past the capPages that come back short

Post-filtering has the arithmetic problem. If a contractor may see 2% of the documents that match a query and the page size is 10, the search must fetch about 10 ÷ 0.02 = 500 candidates to fill one page, then run 500 Checks. At an assumed 5 ms each, done one after another, that is 2.5 seconds, so the Checks must run in parallel or in batches. The standard answer is to do both. Copy a coarse label, such as site and audience group, into each search document as a filter field so the index discards most candidates cheaply, then Check the surviving top results exactly. The coarse label is only a hint; the Check is the authority, so a stale label causes a short page and never a leak. The cost is a second copy of the permission to keep current, which chapter 06 treats as one more place a revocation must reach.

Documents, spans and the lag problem

A document's audience is the source's own: a Drive file's sharing list, a Slack channel's membership. Ingestion syncs these into tuples, and a span cited as evidence inherits its document's audience. This makes permission lag the sharp edge. GridDP's freshness target for documents and Slack is 24 hours, which is acceptable for content. It is not acceptable for permissions, where a person removed from a private channel at 10:00 must stop seeing its messages at once. Sync permissions on their own faster path, minutes and not a day, and fail closed: when the permission sync for a source is older than its limit, deny that source's documents and report the gap.

A fact can be broader than its evidence. The fact "GD-7F21 shipment delayed four days" may be visible to site operations while the vendor PDF it came from is finance-only. Chapter 04 stores a short quote with each evidence link; decide per source whether the quote may travel. The default that holds up is to show the fact, show that evidence exists and is restricted, and name who can open it. Hiding the fact is the right answer only when the fact itself would reveal what the document says, as with a negotiated price.

Agents and audit

An agent acts for a user and may not exceed that user. The query service therefore authenticates the caller by a token that names both the user and the agent, runs every Check and ListObjects as the user, and treats the agent's identity as extra restriction: a tool may narrow what the user can reach, never widen it. This is the confused-deputy defence that the least-privilege section of the LLM security guide develops for tools, applied here to the data layer. The model must never be asked to filter; filtering is done before data reaches it, which chapter 07 builds into the retrieval path. The same separation appears in the RAG guide's treatment of access control in retrieval.

Audit is one record per answer: request id, user, agent, the authorization model version, the fact ids returned, and each Check's result. Store ids and not values, so the audit log is not a second copy of the restricted data. A weekly question, "which contractor accounts read finance-labelled facts", becomes a query. At an illustrative 10,000 answers a day with about 50 ids each, that is 500,000 rows a day, a small table beside the fact history of chapter 04. The audit log needs the same retention and erasure thinking as everything else, which chapter 06 takes up. The broader governance context sits in the governance chapter of the systems-design guide.

✓ Check yourself

Answer from memory before opening each one.

  1. Postgres row-level security, a NetSuite role and a Slack channel list are each configured correctly. Why does that not settle who may see an answer that joins all three?

    Show answer

    The join happens in the ontology, over rows no source database holds, so no source can enforce a rule on the combination. The ontology needs its own permission model with source policies mapped in at ingestion. See Why a join breaks row-level security.

  2. A vendor contractor works at Reno and a new rack is added there. What must be written for the contractor to see its devices, and what must be written to keep them out of Dallas?

    Show answer

    Only the rack's site tuple, since devices inherit through rack to site. Nothing is written for Dallas: the denial is the absence of a path. See Relationships as the model.

  3. A "reorder at risk" flag is derived from a PO's delivery date and its unit price. Site operations cannot see it. Which design choice caused that, and how would you fix it without exposing the price?

    Show answer

    Record-level labels. Label fields, so a flag derived from the date alone carries no finance label; if the flag really uses the price, a declassification rule with a named approver can release the flag. See Derived facts.

  4. A contractor may see 2% of the documents matching a query, and a page holds 10 results. Estimate the work of post-filtering and say what you would change.

    Show answer

    About 500 candidates and 500 Checks per page. Add a coarse site and audience label to the index as a filter and Check only the top results exactly, keeping the Check as the authority. See Filtering results.

  5. Document content is refreshed every 24 hours. A reviewer proposes syncing permissions on the same schedule. What is wrong, and what should the system do when the sync falls behind?

    Show answer

    A removal would stay effective for up to a day. Sync permissions separately and fast, and fail closed: deny that source's documents past the sync limit and report the gap. See Documents, spans and the lag problem.

  6. Argue whether an agent should hold its own grants or run every check as its caller. Say when your answer changes.

    Show answer

    Run as the caller, with the agent's identity only narrowing scope, so it can never exceed the user. A background agent with no user, such as a nightly report, needs its own narrowly scoped grants and its own owner. See Agents and audit.

Takeaway

  • Source-system permissions cannot govern a join, so the ontology holds its own permission model and maps every source policy into it at ingestion.
  • Relationship-based control models structure well: one tuple per edge, inheritance by walking the graph, and denial by the absence of a path. Attributes, through conditions, handle limits such as expiry on a single edge.
  • A derived fact is readable only by someone who may read all its inputs. Carry field-level policy labels on each fact and Check each; allow declassification only through a named, recorded rule.
  • Pre-filter with ListObjects when the visible set is small and under the cap; for search and large sets, filter coarsely in the index and Check the top results exactly.
  • Permission sync must be faster than content sync and fail closed, and after a revocation reads should bypass caches.
  • Agents run as their caller and may only narrow access. Every answer records who asked, which ids came back and which checks passed.
