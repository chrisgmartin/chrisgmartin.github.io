Section D · Make it operational

Actions and Write-back

The part that makes the model operational: changing the world through the same door you read it from.

Why actions are the point

Everything so far reads the world. A model that only reads is a very good map. Operations teams do not need a map; they need to do things. Raise a return on a failing server. Reassign a server from one commitment to another. Confirm that a delivery landed. Move a rack. Today each of those happens inside one source system, by hand, by someone who has just looked at three other systems to decide.

An action is a change to the world made through the model. It is defined on an object type (RaiseRMA on Server, Reallocate on Commitment), it takes typed inputs, it checks who is asking and what they may change, it writes back to the source systems that own the affected properties, and it records all of that as facts. The same door that serves reads serves writes.

This is what Palantir means by calling the ontology "operational", and it is the part most hand-built ontologies never reach. It is also the part that turns an agent from a question-answerer into something that can be trusted to act, because the checks it passes are the same ones a person passes.

What an action is made of

Take RaiseRMA, the action behind GD-7F21's return on 14 October.

PartFor RaiseRMA
Defined onServer
Inputsthe server, the incident that justifies it, a reason code, the person or agent asking
Preconditionsthe server's state is racked, burn-in or live; the incident is open and affects this server; the incident fact is less than an hour old
Permissionthe caller may act on this server (site operations for its site) and may read the incident
Writesa return ticket in Jira; a return authorisation request to the vendor through the procurement tool; the server's state to in RMA in NetBox
Facts recordeda new RMA object; the server's state change, with source "action 7731"; the action itself: who, when, inputs, what was written where, and the result of each write

Two of the steps are where hand-built write-backs go wrong. The permission check is obvious once named and skipped surprisingly often: a script that raises returns "as the integration user" can be driven by anyone who can call it. The freshness check is less obvious. An action taken on a stale fact is an action taken on a guess, so the action's preconditions name the facts it depends on and the maximum age it accepts.

Writing back to systems that own the truth

The ontology does not become the system of record. NetBox still owns placement, Jira still owns tickets, NetSuite still owns orders. An action writes to those systems through their own interfaces, and the fact that results is read back from them like any other change. That way the people who still live in Jira see the same ticket, and the ontology's fact about it has Jira as its source, with the action as the reason.

Three rules keep this honest.

  • One writer per property. The action writes a property to its owning system and nowhere else. If NetBox owns state, the action updates NetBox and waits for the change to come back, rather than updating the ontology's copy directly. A short delay is the price of never having two versions of the truth.
  • Partial failure is recorded, not hidden. RaiseRMA writes to three systems. If the Jira ticket is created and the vendor request fails, the action record says so, the ticket says so, and the retry is explicit. An action that reports success after two of three writes is worse than one that fails loudly.
  • The action is a fact. Who, when, with which inputs, what was written where, and what came back. It carries the same envelope as every other fact, and it is how "who changed this and why?" is answered.

Agents that act

An agent can call RaiseRMA with exactly the rights of the person it acts for, and no more. That follows from chapter 06. Three further rules apply to actions in particular.

  • The caller's identity comes from the credential, never from an argument. A tool with a "user" parameter lets an injected instruction act as someone else.
  • Actions with consequences outside the platform need a person in the loop until proven otherwise. Raising a return sends a server to a vendor. Start with the agent proposing and a person approving; log how often the approval is a rubber stamp; remove the step for that action only when the record justifies it.
  • Actions are few and named. An agent gets RaiseRMA, Reallocate and ConfirmDelivery. It does not get "update any field on any object". Each extra shape is another way to over-reach.

The attack side of this (what happens when a document the agent reads contains an instruction) is the excessive agency chapter of the LLM security guide. The design here is the defence: permissions from the credential, filtering before the model, few named actions, a person in the loop for anything irreversible.

Build actions last, design them first

Actions depend on everything before them. An action on a server needs the server's identity to be right, the facts it reads to be fresh and sourced, and the caller's permission on that server to be decided. A write-back that bypasses any of those is worse than no write-back, because it looks trustworthy and is not. So the first release of GridDP's ontology is read-only: objects, links and facts. Actions come once identity, provenance and permissions hold.

Design them from the start, though, because they change the model. Knowing that RaiseRMA exists tells you RMA is an object type, that Incident needs an "affects" link, and that Server needs a state that includes in RMA. Knowing that Reallocate exists tells you the covers link needs a dated history. The actions are the verbs in the questions people ask; the model has to be shaped to receive them.

The exception: when people are already writing by hand

If site operations already change NetBox and Jira under pressure, and the ontology cannot raise the return, they will keep doing it in Jira and the two will drift. In that case ship one action early, with its checks, rather than none. The cost of drift is higher than the cost of one well-guarded write path.

✓ Check yourself

Answer from memory before opening each one.

  1. What makes a model "operational" rather than a very good dashboard?

    Show answer

    Actions: typed changes to the world, made through the model, with the same identity, permission and audit checks that reads get, written back to the systems that own each property. See why actions are the point.

  2. RaiseRMA creates the Jira ticket, then the vendor request fails. What does the action record say, and what must it not say?

    Show answer

    It records each write and its result: ticket created, vendor request failed, NetBox not yet updated, retry pending. It must not report success. See writing back.

  3. Why does an action's precondition include the age of the facts it depends on?

    Show answer

    An action on a stale fact is an action on a guess. If the incident fact is a day old, the server may already be repaired. Naming the facts and their maximum age makes the action refuse rather than act wrongly. See what an action is made of.

  4. An agent tool for RaiseRMA takes the arguments user, server and incident. What is wrong, and what is the redesign?

    Show answer

    The user argument lets an injected instruction act as someone else. Identity comes from the credential; the tool takes only server and incident. See agents that act.

  5. Why ship read-only first, and when would you ship an action in the first release anyway?

    Show answer

    Actions depend on identity, freshness and permissions being right, and a write-back that skips them is worse than none. Ship one early if operators already change source systems by hand, because drift costs more than one guarded write path. See build actions last.

Takeaway

  • An action is a typed change to the world made through the model: defined on an object type, with inputs, preconditions, a permission check, writes to the owning systems, and a record.
  • Reads and writes go through the same door, so an agent that acts passes the same checks as a person.
  • Write to the system that owns each property and read the change back; record partial failure; treat the action itself as a fact.
  • Agents act as their user, from the credential, with few named actions and a person in the loop for anything irreversible until the record says otherwise.
  • Build actions last, but design them first, because the verbs shape the model.
