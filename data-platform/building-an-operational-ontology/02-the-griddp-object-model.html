The GridDP Object Model

The whole model on one page: fourteen object types, their properties and links, and which system owns each.

The model on one page

This is the chapter the rest of the guide hangs off. Before any identity rule, any permission or any pipeline, here is what GridDP's ontology says exists. Fourteen object types in three groups: the plans and commerce on top, the physical fleet in the middle, the people and evidence underneath. Each box names the system that owns it.

Three things to notice. First, the model is small. Fourteen types cover a fleet, its supply chain, its customers and its incidents, and the first release could ship with nine. Second, every type has an owner. When two sources disagree about a server's rack, NetBox wins, because the box says so. Third, Server is the only type whose identity the ontology issues itself. Every other type can borrow its source's key. Servers cannot, for the reasons chapter 01 drew.

Two types deserve a word. Commitment is the promise, separate from the Customer who holds it, because one customer holds several promises with different dates and the question "what is at risk?" is about promises. Document is an object so that a quote, a site plan or a thread can be linked to the servers it mentions. The text inside a document is not an object; it is evidence, and chapter 05 shows how a sentence inside a PDF becomes the source of a fact.

The link types

A link is a typed edge between two object types. It has a direction, a cardinality and, like everything else here, a source that proves it. Links are where the ontology earns its keep: they are the joins nobody could write before, because no single system holds both ends.

Look at the "proved by" column for fulfilled by and covers. Neither is a field in any system. One comes from matching a packing list against serials, the other from a decision someone records when they allocate servers to a promise. These two links are the reason the November question could not be answered before, and they are where the modelling effort pays off most.

Walking the two questions

A model is only as good as the questions it answers. Trace both of the guide's questions across the picture.

"Which servers promised for November are at risk, and why?" Start at the Commitment due 30 November. Follow covers to its servers. For each server follow fulfilled by back to its PO line, and carries to its shipment. Compare the shipment's expected date with the date that still leaves time for racking and burn-in. Any server whose shipment is too late is at risk, and the reason is the shipment. Seven object types, four links, one query. Chapter 08 turns this into arithmetic.

"Show me everything about GD-7F21." Start at the Server. Every link that touches it is one line of the answer: its rack, its PO line, its shipment, its commitment, its incidents, its RMA, the documents that mention it. Every property is another line. Each line carries its source. This is the question identity (chapter 04) and provenance (chapter 05) exist for.

If a question does not trace, the model is missing something

Write down the ten questions the operations team asks most, and trace each one across the picture. A question that needs a link you have not drawn, or an object type that is really two, shows up at this stage for the cost of a whiteboard. After launch the same discovery costs a migration.

One interface: things that can be rented

GridDP has two kinds of machine a customer can rent: a Server in the reserved fleet and a provider's machine on the marketplace. They are different object types with different owners, different properties and different lifecycles. Yet a question like "how much H100 capacity is free in Europe?" should not have to know which kind it is looking at.

An interface solves this. It names the shape both types share (a GPU model, a count, a location, an availability state) and lets a query ask for "anything rentable". Foundry has this idea under the same name; in a hand-built system it is a view or a union with a type column. Add an interface when the second similar type arrives, not before. GridDP's model has exactly one, and the marketplace side of it is out of scope for this guide.

What is deliberately left out

  • Telemetry samples. A GPU's temperature every ten seconds is not a fact about an object; it is a stream. The ontology holds the GPU and its current health state. The samples stay in the telemetry store, which is built for them.
  • Every Slack message. A thread is a Document. A single message is a span inside it, cited as evidence when it supports a fact. Making each message an object would add millions of objects and no questions.
  • Invoices and payments. Finance's questions are aggregate and historical. They stay in NetSuite and the warehouse. The model holds the PO and its lines because delivery depends on them, and stops there.
  • The marketplace's provider machines. Forty thousand of them, with their own guide. The interface above is the only point of contact.

Leaving things out is a modelling decision, not an omission. The next chapter is about how to make those decisions.

✓ Check yourself

Answer from memory before opening each one.

  1. Why is Commitment a separate object type from Customer?

    Show answer

    One customer holds several promises with different dates, sites and penalties, and the at-risk question is about promises, not customers. A property on Customer could not hold several of them with their own links to servers. See the object types.

  2. Which two links in the model are proved by no field in any system, and why do they matter most?

    Show answer

    Fulfilled by (PO line to server, matched through the packing list) and covers (commitment to server, a recorded allocation decision). They connect the supply chain to the promise, which is the join nobody could write before. See the link types.

  3. Trace "which servers promised for November are at risk?" across the picture. Name the object types and links the query touches.

    Show answer

    Commitment, covers, Server, fulfilled by, POLine, ships in or carries, Shipment, then compare the shipment's expected date with the latest date that keeps the promise. See walking the two questions.

  4. A colleague wants each Slack message to be an object so that agents can "see everything". What do you say?

    Show answer

    A thread is a Document; a message is a span inside it, cited as evidence for a fact. Millions of message objects answer no question that a mention link plus evidence does not, and they would swamp identity and permissions. See what is deliberately left out.

  5. When should GridDP add the Rentable interface, and what is it in a hand-built system?

    Show answer

    When the second rentable type exists and a question needs to span both, which for GridDP is from day one because of the marketplace. In a hand-built system it is a union view with a type column over the shared properties. See one interface.

Takeaway

  • GridDP's model is fourteen object types in three groups: plans and commerce, the physical fleet, people and evidence. Each type has one owning system.
  • Server is the only type whose identity the ontology issues itself; every other type can borrow its source's key.
  • Links are typed, directed, counted and proved. The two links no system holds, fulfilled by and covers, are the ones that make the November question answerable.
  • Trace the top questions across the picture before building. A missing link found on a whiteboard is cheap; found after launch it is a migration.
  • Telemetry samples, single messages, invoices and the marketplace's machines are left out on purpose.
