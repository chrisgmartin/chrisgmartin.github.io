Provenance, History and Evidence

Every fact keeps its source row, document span, time and transformation; bitemporal history; the model that makes 'show me why' a query.

The two questions that define the job

The guide's two recurring questions are both provenance questions in disguise. "Show me everything about GD-7F21 and where each fact came from" asks for evidence. "Which Reserved servers promised to customer X for November are at risk, and why?" asks for a derivation that a person can inspect and dispute. A third question arrives within a month of launch, from finance or from a customer: what did the platform believe about GD-7F21 on 14 October, and who acted on it? That one needs history that records what the platform knew, not only what was true.

This chapter builds the storage and model that answer all three. It assumes the identity work of chapter 02, so that GD-7F21 is one entity with one id, and the freshness work of chapter 03, so that each event carries the time it happened and the time the platform saw it. GridDP's figures here are illustrative teaching fixtures, not measurements.

Provenance is stored per fact, not reconstructed per incident

A platform that records lineage only between pipelines can say which job wrote a table. It cannot say which Jira event made one row say "faulted". If the evidence is not written at the moment the fact is made, no later effort recovers it reliably, because the raw record, the code version and the identity mapping have all moved on.

What a fact carries

The W3C PROV-O Recommendation of 30 April 2013 supplies the vocabulary, and it is worth borrowing whole rather than inventing a private one. PROV-O defines an Entity as "a physical, digital, conceptual, or other kind of thing with some fixed aspects", an Activity as "something that occurs over a period of time and acts upon or with entities", and an Agent as "something that bears some form of responsibility for an activity taking place". Its core relations are wasGeneratedBy, used, wasDerivedFrom, wasAttributedTo and wasAssociatedWith.

Mapped to GridDP, a single fact version is an Entity. The ingestion run or derivation job that made it is an Activity, and the fact was generated by it. The source record the job read is an Entity the Activity used. The pipeline, rule set or model that did the work is an Agent. A derived fact is wasDerivedFrom the facts that fed it. PROV-O adds generatedAtTime and invalidatedAtTime, which bound the start and end of an entity's existence; they give the transaction-time pair below a standard name, though the mapping is a design choice and not something PROV-O prescribes.

In a table this becomes one row per fact version, with the PROV relations stored as columns rather than as a separate graph.

Two columns need a decision. confidence is not part of PROV-O, so it is an extension, and it should come from the stage that produced the uncertainty: the identity linker from chapter 02, or the extractor that read a PDF. A derived fact's confidence is not the product of its inputs' by default; state the rule per derivation, because "worst input wins" and "product" give different numbers and different alerts. Keep inputs as an array for the walk back to parents, and mirror it in an edge table if the reverse walk matters.

Two clocks: valid time and record time

A fact has one clock for the world and one for the platform's knowledge. Martin Fowler's "Bitemporal History" (7 April 2021) names them with a payroll example: the "actual history" of a salary and "our record of the history". He adds that the first is also called valid or effective time and the second transaction time. His example is a correction. On 15 March HR's letter says a raise took effect on 15 February. On 5 April HR corrects the amount, after payroll has already run. The world did not change on 5 April. The platform's knowledge did.

GridDP meets this constantly. Shipment 1Z-…-88 for GD-7F21 was promised for a Monday, and the carrier's tracking system shows a four-day delay, but the carrier posts the exception on Wednesday. The delay is valid from Monday, because that is when the server should have arrived and did not. It is recorded on Wednesday. Anything that ran on Tuesday used the old belief, and a customer-facing promise made on Tuesday was a reasonable decision on the facts then held. A model with one timestamp cannot say both things. It overwrites Monday with Wednesday's knowledge, and the platform can no longer show that Tuesday's promise was sound.

The same split settles the 14 October question. Memory errors on GD-7F21 began at 03:12, which is valid time. The incident INC-2093 was opened and linked at 09:41, which is record time. A review at 08:00 would show the server healthy, correctly, because that is what the platform knew. A review of what was true at 08:00 shows it already faulted. The two queries below differ by one predicate, and the difference is the audit.

as_of_queries.sql (sketch, Spark SQL over Iceberg)
-- What did the platform believe at 08:00 on 14 October about GD-7F21's health?
SELECT value, confidence, source_ref
FROM ontology.facts
WHERE subject = 'server:GD-7F21' AND predicate = 'health_state'
  AND recorded_at   <= TIMESTAMP '2026-10-14 08:00:00'
  AND (superseded_at IS NULL OR superseded_at > TIMESTAMP '2026-10-14 08:00:00')
  AND valid_from    <= TIMESTAMP '2026-10-14 08:00:00'
  AND (valid_to IS NULL OR valid_to > TIMESTAMP '2026-10-14 08:00:00');

-- What does the platform now believe was true at 08:00 on 14 October?
SELECT value, confidence, source_ref
FROM ontology.facts
WHERE subject = 'server:GD-7F21' AND predicate = 'health_state'
  AND superseded_at IS NULL                      -- current knowledge only
  AND valid_from    <= TIMESTAMP '2026-10-14 08:00:00'
  AND (valid_to IS NULL OR valid_to > TIMESTAMP '2026-10-14 08:00:00');

Writes follow one rule: never update a row's claim. A correction closes the old version by setting superseded_at and inserts a new version with its own recorded_at. If the new version also changes when the claim became true, it carries a different valid_from. The slowly-changing-dimension pattern in the as-of join section of the curriculum is the one-clock version of this; the second clock is what makes retroactive corrections safe.

The recommendation flips for facts nobody will ever audit retroactively. A per-GPU temperature reading is valid at its sample time and is never corrected, so a single timestamp suffices. Keep the two clocks for facts that people decide on and that sources revise: status, location, dates, owner, commitments.

Evidence: from a fact to the original page

A source_ref that says "jira" is a label. Evidence is a locator that opens the original and a check that it is the same original. For structured sources the locator is the source's own key plus the change identifier: a Jira issue key and changelog id, a NetSuite internal id and its last-modified stamp, a Postgres primary key with the log position from the change stream of chapter 03. For documents and messages it must go finer than the file.

evidence.json (sketch)
{
  "kind": "document_span",
  "object": "s3://griddp-raw/vendor-portal/2026-10-09/status-4471.pdf",
  "object_sha256": "9b1c…e04a",
  "locator": {"page": 2, "char_start": 1840, "char_end": 1902},
  "quote": "Line 3: dispatch moved to 13 Oct",
  "extractor": {"name": "vendor-pdf-parse", "version": "2.3.1"},
  "observed_at": "2026-10-09T07:14:00Z"
}

Three details carry the weight. The object is in a raw zone that is immutable and addressed by hash, so the evidence cannot drift when someone re-uploads the vendor's file under the same name. The locator is a page and a character range, or for Slack a channel id and message timestamp, so a reviewer lands on the sentence and not on a 40-page quote. And the short quote is stored so that a human sees the claim's basis without opening the object, which matters when permissions on the object are stricter than on the fact; chapter 05 covers what to do when they differ.

Extracted facts need the extractor's version because extraction is a transformation that can be wrong in a repeatable way. If vendor-pdf-parse 2.3.1 misreads a column, the fix is to find every fact whose activity_version names it and re-derive them. Without the version column that query does not exist, and the repair becomes a manual search.

A quote without an object hash proves nothing

If the evidence is a URL to a living Drive file, the file can be edited after the fact was made, and the link then supports a different claim than the one stored. Snapshot the object into the raw zone at ingestion and hash it. The cost is storage for 30,000 documents, which is small beside the cost of a disputed vendor quote that no one can reproduce.

Pipeline lineage and fact provenance are different graphs

OpenLineage describes itself as "an open framework for data lineage collection and analysis". Its core entities are Job, Run and Dataset, extended through facets, which it describes as user-defined metadata attached to those entities. That is a pipeline-level model. It answers "which run of which job wrote this table, from which input tables", and it is the right tool for it. The lineage chapter of the ML data architecture guide builds that graph from model run back to source tables, and GridDP should have it.

It cannot answer the ontology's questions, because the unit of those questions is a fact. A dataset-level edge says the server_health table was built from the jira_events table by run 7c2e. It does not say that the row for GD-7F21 came from changelog 88104, and the run that wrote one million rows is the same run whether one of them is wrong or none are. The two graphs join on the run: each fact's activity_id is an OpenLineage run id. That gives the full chain, and each graph stays at its own grain.

Keep fact-level provenance to the ontology's fact tables; per-row provenance on every staging table costs more than anyone will use. The exception is a regulated figure such as an invoice total.

fact row (GD-7F21, health_state = faulted) │ activity_id = run 7c2e ← fact-level provenance (this chapter) ▼ OpenLineage run 7c2e of job derive_health │ inputs: jira.issue_events, telemetry.ecc_5m ← pipeline-level lineage ▼ source tables → CDC log position → raw object (hash)

Storage: what history costs and where Iceberg fits

The Apache Iceberg table spec says "a snapshot represents the state of a table at some time", and the maintenance documentation adds that "each write to an Iceberg table creates a new snapshot, or version, of a table", usable for time-travel queries or rollback. Spark reads an older state with TIMESTAMP AS OF or VERSION AS OF. This is a storage-level history, and it is tempting to treat it as the bitemporal answer. It is not, for two reasons.

First, snapshots record when a commit landed, not when the platform learned a fact. A batch that loads Wednesday's carrier exceptions writes one snapshot, and the table's own history cannot tell you which of its rows were known on Tuesday if the load back-dated them. Record time must be a column the pipeline sets from the event, as in the table above. Second, snapshots are meant to expire. Per the maintenance guide, "expiring old snapshots removes them from metadata, so they are no longer available for time travel queries", and "regularly expiring snapshots is recommended to delete data files that are no longer needed". A history that exists only as snapshots has a retention window set by a cost decision, which is the wrong owner for an audit window.

The split that works is to keep business history in the columns, valid_* and recorded_at or superseded_at, and to use snapshots for what they are good at: reproducing a table exactly as a past run read it, recovering from a bad write, and giving the lineage graph a stable table version to name. Expire snapshots on a schedule that serves those uses, and treat the interaction with erasure as chapter 06's problem, because an expired snapshot is also how deleted data physically leaves.

The cost of the columns is simple arithmetic. Assume the 1,200 change events a second at peak is a quarter of the day's mean, so a mean of 300 a second:

300 facts/s × 86,400 s/day = 25.9 million fact versions per day 25.9 M × 500 B (with provenance) = 13 GB per day raw 13 GB ÷ 4 (assumed columnar compression) = 3.2 GB per day 3.2 GB × 365 = about 1.2 TB per year

About 1.2 TB a year of illustrative storage is small next to the 30,000 documents and the raw telemetry, so full history for decision-relevant facts is affordable at this scale. It stops being so when a fact changes on every sample. Telemetry-derived health that flips on each five-minute window would add 12 versions an hour per server per predicate. Version such facts only on a change of state, with a hysteresis rule, and leave the sample stream in the telemetry store where the lakehouse chapter already puts it.

Tracing GD-7F21's incident fact

On 14 October the server's health fact reads faulted. A reviewer asks why, and the walk is five lookups, each by id.

  1. The fact row for (GD-7F21, health_state) with recorded_at 09:41 gives activity_id run 7c2e, rules version 14, and an inputs array of three fact ids.
  2. Two input facts are memory-error counts for the host, derived from the telemetry store, valid from 03:12. Their evidence is a metric query and a time range, with the scrape target label recorded as the identity link from chapter 02.
  3. The third input is the incident fact, whose source_ref is INC-2093 and a Jira changelog id, with the issue's type "incident" and its priority as source fields.
  4. The changelog id opens the Jira event in the raw zone, with its hash, so the reviewer sees the status change as it was on 14 October and not as the issue reads today.
  5. The rules version points at the code that turned the three inputs into "faulted", and the run id opens the OpenLineage record for the job.

Two further answers fall out of the same rows. Setting the query to 08:00 shows no faulted fact, which explains why the earlier promise review passed. And a search on activity_version for rules v14 lists every health fact it produced, which is the blast radius if the rule turns out to be wrong. That is what "where each fact came from" means in operation: a path of identifiers, each resolvable, ending at an object that has not changed.

✓ Check yourself

Answer from memory before opening each one.

  1. A carrier posts on Wednesday that shipment 1Z-…-88 has been late since Monday. Which timestamps does the delay fact carry, and what can a Tuesday review still show?

    Show answer

    Valid from Monday and recorded on Wednesday. Filtering on record time up to Tuesday shows the pre-delay belief, so the promise made then can be judged on what was known. A single timestamp would overwrite Monday with Wednesday and lose that. See Two clocks.

  2. A colleague proposes Iceberg time travel as the whole history layer, since every commit is already a snapshot. What two things break?

    Show answer

    Snapshots record when a commit landed, not when the platform learned a fact, so back-dated loads blur record time. And snapshots are expired to save storage, which sets the audit window by cost. Keep business history in columns and use snapshots for table reproduction. See Storage.

  3. The lineage tool shows that run 7c2e of one job built the health table, yet a reviewer still cannot say why GD-7F21 reads faulted. What is missing, and how do the two graphs join?

    Show answer

    Fact-level provenance: the source record, input facts and rule version for that row. Pipeline lineage stops at the dataset. The join is the run id stored on each fact. See Pipeline lineage and fact provenance.

  4. The PDF parser used for vendor status emails turns out to have mis-read a date column since September. What must the fact table already hold for the repair to be a query, and what is the query?

    Show answer

    The extractor name and version on each fact, plus the evidence object hash and locator. Select facts whose activity version names the bad parser release, re-extract from the hashed raw objects, and write corrections as new versions. See Evidence.

  5. Per-GPU temperature facts are proposed for the two-clock table at one version per five-minute window. Argue for or against, with the arithmetic.

    Show answer

    Against. That is 12 versions an hour per server per predicate and nobody corrects a sample retroactively, so one timestamp and the telemetry store suffice. Version derived state, such as "overheating", on change only. The two clocks pay off for facts that people decide on and sources revise. See Storage.

Takeaway

  • A fact is stored with its source locator, producing run and code version, input facts and confidence, so "where did this come from" is a lookup and not an investigation.
  • PROV-O's Entity, Activity and Agent, with used, wasGeneratedBy and wasDerivedFrom, are enough vocabulary for fact provenance; confidence is a local extension.
  • Two clocks are needed: valid time for when the claim was true, record time for when the platform held it. Corrections close a version and insert a new one, and never update in place.
  • Evidence means an immutable, hash-addressed raw object plus a page, range or message locator and the extractor's version.
  • Pipeline lineage and fact provenance are different graphs that join on the run id, and each stays at its own grain.
  • Iceberg snapshots reproduce table states but expire by design, so business history lives in columns and snapshot retention is a separate, cost-driven choice.
