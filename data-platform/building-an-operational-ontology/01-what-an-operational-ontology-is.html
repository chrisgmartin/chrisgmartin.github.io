What an Operational Ontology Is

Objects, links and actions over live systems; what it adds to a warehouse, and when a warehouse is enough.

The problem in one picture

Ask GridDP's systems about the server with serial GD-7F21 and you get six answers from six places. Google Drive has the design it was built to. NetSuite has the order line it was bought on. The carrier has the pallet it travelled in. NetBox has the rack it sits in. The telemetry store has the network address it reports from. Jira has the incident that took it down.

None of these records is wrong. They are about different kinds of thing. A bill of materials describes a design that forty servers were built to. A purchase order line is a quantity. A pallet holds several machines. A network address outlives the machine behind it. You cannot join these on "the ID", because there is no shared ID and no shared idea of what the ID points at.

An operational ontology is the layer that fixes this. It says: there is a thing called a Server. This one is GD-7F21. Here is every record that is about it, here is how we know, and here is what each record tells us. Then it does the same for racks, orders, shipments, incidents and people, and it draws the links between them.

Two meanings of one word

"Ontology" means two different things, and mixing them up wastes months.

In research, an ontology is a formal vocabulary: the concepts in a field and the logical rules that connect them. Gruber's definition from 1993 is the one everyone cites, "an explicit specification of a conceptualization". The W3C's OWL language is built for this meaning. It answers the question "what exists, and what follows from that?" A team that takes this meaning builds a reasoning engine nobody asked for.

In software products, an ontology is a working model of an organisation over its live systems. Palantir's Foundry documentation calls it "an operational layer for the organization", built from object types, properties, links and actions mapped onto existing data sources. It answers the question "what is happening right now, to which things, and what may someone do about it?"

This guide uses the second meaning, and borrows one habit from the first: name what exists before you wire anything to it. The vocabulary is portable. You do not need Foundry or any product to build what follows.

What it is made of

Four kinds of thing, and that is the whole vocabulary.

  • Object types are the nouns: Server, Rack, Site, PurchaseOrder, Shipment, Incident, Person. An object is one instance: the server GD-7F21.
  • Properties are what an object says about itself: a serial number, a hostname, a lifecycle state, a planned delivery date.
  • Links connect objects: this server sits in that rack, was bought on that order line, was hit by that incident. Links are what let a question walk from a server to its purchase order to its customer.
  • Actions change things: raise a return, reassign a rack, confirm a delivery. An action writes back to the source systems, through the model, with the same identity and permission checks that reads get.

Objects and links make a map. Actions make it operational. A model without actions describes the organisation; a model with them lets the organisation run through it. That is the difference between a very good dashboard and the thing this guide is about. Actions come last in the build order, for reasons chapter 07 explains, but they are in the design from the start.

What it adds to a warehouse

A good warehouse already has tables, history and a way to aggregate. An operational ontology adds four obligations on top, and every one of them is a question you can ask of a design review.

  1. Identity. Which records are the same thing? One identifier per physical server, with a record of every native key that maps to it and how sure that mapping is. Chapter 04.
  2. Freshness. How old is this fact, in minutes? Not "real time", which is a hope, but a number per fact that can be compared with a target. Chapter 05.
  3. Provenance. Where did it come from? The row, document page or message each fact was read from, so "show me why" is a click. Also chapter 05.
  4. Permissions. Who may see it, after the join? An answer built from three systems carries the restrictions of all three. Chapter 06.

Drop any one of these and the result is a reporting layer. Reporting layers are useful. They are not something a site operator or a software agent can act on at nine in the morning with a truck waiting.

Things it gets confused with

Looks similarWhat it is forWhere it stops
Semantic layer (dbt MetricFlow and similar)One definition of each metric over tables that already agree on their keysCannot say that a PO line, a pallet and a NetBox device are the same server. It starts one step after the identity problem.
Warehouse star schemaHistory and aggregates for analysisLoaded in batches, so hours old by design. No actions. Permissions by table, not by fact.
Knowledge graph, research senseFormal concepts and what follows from themNobody designs it to take a thousand changes a second or to hide a finance document from a contractor.
CMDB or inventory (NetBox)What is installed whereKnows the rack. Knows nothing about the order, the promise, or the page.
A graph databaseA storage engine with good traversalA technology choice, not a model. You can build an ontology on a graph database, on relational tables, or on both.

The semantic layer is the one most often mistaken for it, because both "define things once". The difference is what they define. A semantic layer defines metrics. An ontology defines the things the metrics are about. GridDP keeps both: the ontology says which servers exist and what state each is in, and the semantic layer counts them. Chapter 08 shows the two working together.

When you need one, and when you do not

Start with arithmetic. Reconciling twelve systems pairwise needs 66 mappings, and each new tool adds eleven more. One identity layer needs twelve, one per system, and a new tool adds one. A company with three systems can live on SQL views. A company with a dozen cannot, and the gap widens every quarter.

Beyond the arithmetic, four conditions together make the case:

  • Several systems each own part of an object's life, and none holds the whole thing.
  • The operations are physical. Trucks are late, parts fail, hand-offs happen in the world and the data arrives afterwards in odd formats.
  • Someone must decide within hours, not at the monthly review.
  • Software agents will ask questions, so permissions and provenance cannot be left to the dashboard.

The case fails when the questions are aggregate and historical and a day-old answer is fine. "Deployed GPU capacity by site last quarter" is a warehouse query with a semantic layer on top, and should stay one. The test is simple: would a wrong answer, an hour late, make someone act wrongly? For the quarterly report, no. For "will the Reno rack be ready for the November promise?", yes.

A middle path is usually right

Keep the warehouse. Add identity and permissions as a thin layer over it. Grow towards objects, links and actions only where the operational questions are. Nothing in this guide needs the full build on day one. It does need identity and permissions designed before the second source arrives, because those two are the expensive ones to retrofit.

✓ Check yourself

Answer from memory before opening each one.

  1. A colleague says the semantic layer already gives GridDP "one definition of everything". Which question about GD-7F21 can it not answer, and why?

    Show answer

    It cannot say that the PO line, the pallet and the NetBox device are the same server. A semantic layer defines metrics over tables whose keys already agree. The ontology's job starts one step earlier, where the keys do not agree. See things it gets confused with.

  2. Look at the six-records figure. Which of the six keys identifies one physical machine, and what is the catch?

    Show answer

    Only the NetBox device record. Its serial was typed by a person at rack-in, so it can be wrong. The others name a design, a batch, a pallet, an address or a ticket. See the problem in one picture.

  3. The platform team proposes a graph database loaded nightly from the twelve systems. Which of the four obligations does it fail?

    Show answer

    At least freshness: nightly is a day old for facts that need to be an hour old. And a graph database is a storage choice, not a model; it says nothing about identity, provenance or permissions unless those are designed. See what it adds to a warehouse.

  4. Finance wants quarterly deployed capacity by site. A site lead wants to know if tomorrow's delivery will land. Which gets the ontology, and what decides it?

    Show answer

    The delivery question. The deciding test is whether an hour-old wrong answer makes someone act wrongly. The capacity report is aggregate and historical, so it stays a warehouse query. See when you need one.

Takeaway

  • Six systems hold six records about one server, and the records are about different kinds of thing. That is the problem an operational ontology solves.
  • The vocabulary is four words: object types, properties, links, actions. Actions are what make it operational.
  • On top of a warehouse it adds four obligations: identity, freshness, provenance and permissions. Each is a question a design review can ask.
  • A semantic layer defines metrics; an ontology defines the things the metrics are about. Keep both.
  • Build it when several systems own parts of a thing, operations are physical, decisions are urgent and agents will ask. Otherwise a warehouse is enough.
