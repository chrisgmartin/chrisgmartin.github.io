What an Operational Ontology Is

Objects, properties, links and actions over live systems; how it differs from a knowledge graph, a semantic layer, a data warehouse and a CMDB; when a company needs one.

One word, two meanings

A platform team that takes the research meaning of "ontology" builds a reasoner nobody asked for. A team that takes the product meaning without knowing it exists builds a graph database and wonders why nobody trusts it. The two meanings differ in what they are for.

The research meaning is about shared vocabulary. Gruber's 1993 paper on designing ontologies for knowledge sharing states it in one sentence: "An ontology is an explicit specification of a conceptualization." The conceptualization is "the objects, concepts, and other entities that are assumed to exist in some area of interest and the relationships that hold among them." The W3C's OWL 2 carries that line forward and describes itself as "an ontology language for the Semantic Web with formally defined meaning." The question that tradition answers is what exists in a domain and what follows logically from that.

The product meaning is about work. Palantir's Foundry documentation, as of November 2026, says: "The Palantir Ontology is an operational layer for the organization," and that in many settings it "serves as a digital twin of the organization." It is built by "mapping existing datasources into objects, properties, and links." Its action types "enable you to capture data from operators in your organization," and functions "provide a way to author and evolve business logic with arbitrary complexity." The question this tradition answers is what is happening now, to which things, and what a person or program may do about it.

This guide uses the second meaning and borrows the first one's discipline: name what exists before you wire anything to it. The vocabulary of object types, properties, links and actions is portable. The Foundry product is one implementation of it and nothing in this guide depends on it.

What it holds: objects, properties, links, actions

GridDP builds and runs its own Reserved fleet beside the marketplace, across three colocation sites: Dallas, Reno and Amsterdam. As an illustration, the fleet today is 600 servers and 4,800 GPUs, so eight GPUs a server, growing by about 200 servers a quarter. The case is the one set up in the systems-design guide; every GridDP figure in this chapter is a teaching fixture, not a fact about a real company.

One object type is Server. One object of that type is the server with serial GD-7F21. The pieces fit like this:

Server GD-7F21 object type: Server ├─ properties serial, hostname, status, site, rack, unit ├─ link installed_in ──▶ Rack R12, Reno ├─ link ordered_on ──▶ PO 4471, line 3 ├─ link shipped_in ──▶ Shipment 1Z-…-88 ├─ link promised_to ──▶ Customer commitment (November) ├─ link affected_by ──▶ Incident INC-2093 └─ action RaiseRMA(server, incident) writes back to Jira and NetSuite

Properties are what one object says about itself. Link types are the edges that let a question walk from a server to its rack, its purchase order and its customer. Action types are the part that makes the model operational. A read-only model describes the organisation. A model with actions lets an operator or an agent change it through one door, so the same identity, the same permission check and the same audit record apply to the read and to the write.

Foundry also names interfaces: "An interface is an Ontology type that describes the shape of an object type and its capabilities." For GridDP the use is concrete. A Reserved Server and a marketplace ProviderMachine are different object types with different owners, yet both can be rented, and a question about rentable capacity should not need to know which one it is looking at. An interface lets the query say "anything rentable" and keeps the two types separate. Add interfaces when the second similar type arrives, not before.

Actions are also the part to build last. A write-back that bypasses the checks in chapter 05 is worse than no write-back. The recommendation for a first release is read-only objects and links, with actions added once permissions and provenance hold. The exception is a team whose operators already change the source systems by hand under pressure: if the ontology cannot raise the RMA, they will keep doing it in Jira and the two will drift.

What it is not

Four neighbours get mistaken for it. Each does a real job, and each stops at a different place.

NeighbourWhat it modelsBuilt fromWhere it stops for GridDP
Knowledge graph, research senseConcepts and logical relations, with formal meaningA curated vocabulary, often OWL or RDFAnswers "what follows from this", not "what changed in Reno an hour ago"; no freshness, no per-source permissions
Semantic layerMetrics and the dimensions to slice them byModelled warehouse tablesGives one answer to "how many servers are deployed"; does not give one identity to GD-7F21
Warehouse star schemaFacts and dimensions for analysisBatch loads, history kept as slowly changing dimensionsHours old by design; no actions; permissions are table-level
CMDB or inventory (NetBox)What is installed whereEngineers' entries and discoveryKnows the rack and device; knows nothing of the purchase order, the promise or the page

The semantic layer is the neighbour most often confused with it, because both define things once. dbt's documentation describes MetricFlow as "a SQL query generation tool designed to streamline metric creation across different data dimensions." Its semantic models are "the starting points of your data and correspond to models in your dbt project," and its entities are "the join keys of your semantic model." The problem it names is that of "multiple analysts working on the same data, each using their own query method." That is a metric-consistency problem over tables that already exist and already agree on their keys. The ontology problem starts one step earlier: the tables do not agree on what a server is. The serving chapter of the systems-design guide covers the semantic layer, and chapter 08 shows where metrics sit on top of the object graph.

The warehouse star schema and the knowledge graph fail in opposite directions. The star schema is excellent at history and aggregation and poor at the present: it is loaded in batches, and its keys are whatever the load jobs agreed on. A research-style knowledge graph is excellent at stating what things mean and poor at keeping up: nobody designs it to ingest 1,200 change events a second, to age out a stale shipment date or to hide a finance document from a contractor. The operational ontology borrows the graph's habit of naming things and links carefully, and the warehouse's habit of keeping history, then adds the four properties below.

NetBox, the inventory GridDP runs for racks, devices and cables, is one source of the ontology. It is authoritative for where a device sits. It is silent about whether the device was late, who is waiting for it and whether it is failing.

The four properties that make it operational

Strip the product language away and four properties separate an operational ontology from a data model with a better name. Each one is a chapter of this guide, and a design that skips one will fail in a predictable way.

  1. Identity across systems. One stable identifier per thing, with a record of which native keys map to it, and a confidence on each mapping. Without it, every join is a guess. Chapter 02 builds it.
  2. Freshness, measured. A number per source and per derived fact for how old the platform's knowledge is, compared with a target. "Real time" is not a property. Chapter 03 builds it.
  3. Provenance per fact. Each fact keeps the row or document span it came from, when it was observed and what produced it. Without it, "show me where that came from" has no answer. Chapter 04 builds it.
  4. Permissions per fact. An answer built from three systems carries the restrictions of all three. Without it, the ontology becomes the place where access controls go to be bypassed. Chapter 05 builds it.
The properties are testable, which is the point

Each one can be checked with a question. Can you name every native key of this object? How old is this fact, in seconds? Which document produced it? Who may not see it? If a design review cannot answer all four for a sample of ten objects, the system is a graph, not an operational ontology.

When a company needs one, and when a warehouse is enough

The first argument is arithmetic. Twelve systems that must be reconciled pairwise need 12 × 11 / 2 = 66 mappings, and every new tool adds as many mappings as there are existing tools. One identity layer needs 12, one per system, and a new tool adds one. A company with three systems can live with pairwise mappings and a few SQL views. A company with a dozen cannot, and the effect grows with every quarter that adds a tool.

Four conditions, together, justify the build:

  • Many systems that each own part of an object's life. No source holds the whole server.
  • Physical operations. Delays, failures and hand-offs happen in the world, and the data arrives late and in odd formats.
  • Decisions under time pressure. Someone must act within hours, not at the next monthly review.
  • Agents as consumers. A program asking questions in natural language will use whatever it can reach, so the permission and provenance work cannot be deferred to a dashboard.

The recommendation flips when the questions are aggregate and historical, the humans reading the answers are analysts, and a day-old answer is acceptable. "What was deployed GPU capacity by site last quarter" is a warehouse query with a semantic layer on top, and it should stay one. Building an ontology for it adds a freshness guarantee nobody needs. The test is whether a wrong answer, an hour late, causes someone to act wrongly. For the monthly capacity report, no. For "is the Reno rack going to be late for the November promise", yes.

A third path is common and often right: keep the warehouse, add identity and permissions as a thin layer, and grow towards objects and actions only where the operational questions are. Nothing in this guide requires the full build on day one. It does require that identity and permissions are designed before the second source arrives, because they are the two properties that are expensive to retrofit.

GridDP's reasons, system by system

GridDP lists about 40,000 provider machines on the marketplace and operates its own 600-server Reserved fleet. At the current growth of 200 servers a quarter, the fleet reaches 1,400 servers and 11,200 GPUs in four quarters, with a new site or two along the way. Twelve source systems hold facts about it.

The table maps the freshness tiers the guide uses throughout: 5 minutes for telemetry-derived facts, 1 hour for ERP and ticketing, 24 hours for documents and Slack. Chapter 03 explains why each source gets the tier it gets.

Two questions drive the design. The first: which Reserved servers promised to customer X for November are at risk, and why? It needs the promise from Salesforce, the order from NetSuite, the vendor's status from a PDF, the shipment from the carrier, the rack from NetBox, the health from telemetry and the incident from Jira. That is at least seven of the twelve systems, and a warehouse can join them only after someone has decided that a PO line and a NetBox device are the same server. The second: show me everything about GD-7F21 and where each fact came from. Its answer is the six records that name one server six ways, and a source for each.

Both questions are asked under time pressure, by people in procurement and site operations, and increasingly by agents acting for them. They are also asked by people who must not see everything: a contractor at Reno sees Reno, and an agent sees no more than its caller. That combination, many systems, physical delay, urgency, agents and per-person visibility, is what makes this an operational ontology problem and not a warehouse problem. The next chapter starts where the first question breaks: with six records that all mean GD-7F21 and no key that says so.

✓ Check yourself

Answer from memory before opening each one.

  1. A colleague says the dbt semantic layer already gives GridDP "one definition of everything". Which question about GD-7F21 can it not answer, and why?

    Show answer

    It cannot say that the PO line, the shipment and the NetBox device are the same server. A semantic layer defines metrics over models whose join keys already agree; the identity problem comes first. See what it is not.

  2. The platform team proposes a graph database loaded nightly from the twelve systems, with no per-fact source record. Which of the four properties does it fail, and what does an operator notice first?

    Show answer

    It fails freshness, since nightly is a 24-hour tier for facts that need 1 hour or 5 minutes, and provenance, since no fact names its source. The operator notices when a shipment slips four days and the graph still shows the old date, with no way to see who said so. See the four properties.

  3. GridDP adds a thirteenth system. Pairwise reconciliation and a shared identity layer now cost how many new mappings each, and what does that say about when to build the layer?

    Show answer

    Pairwise adds 12 new mappings, one to each existing system; a shared layer adds 1. The gap widens with every system, so build the layer before the count is large, because retrofitting identity after dozens of views exist is the expensive case. See when a company needs one.

  4. A finance analyst wants quarterly deployed capacity by site, and a site lead wants to know if tomorrow's delivery to Reno will land. Which gets an ontology and which a warehouse query, and what decides it?

    Show answer

    The capacity report is a warehouse and semantic-layer query: aggregate, historical, tolerant of a day's delay. The delivery question needs fresh, joined, per-object facts, so it needs the ontology. The deciding test is whether an answer that is an hour old makes someone act wrongly. See when a company needs one.

  5. Why does this guide recommend shipping objects and links before action types, and in what situation would you ship an action first?

    Show answer

    A write-back that skips the permission and audit checks is worse than none, and those checks are built after identity and provenance. Ship an action first only if operators already change source systems by hand under pressure, so the ontology's absence causes drift. See what it holds.

Takeaway

  • "Ontology" has a research meaning, a shared vocabulary with formal semantics, and a product meaning, an operational layer of objects, links and actions over live systems; this guide builds the second.
  • An action type is what makes the model operational, because reads and writes pass through one door with one identity and one permission check.
  • A semantic layer standardises metrics over tables that already agree on their keys; an operational ontology exists because the sources do not agree on what a thing is.
  • A CMDB such as NetBox is one source of the ontology, authoritative for placement and silent about orders, promises and incidents.
  • The four tests are identity across systems, freshness as a number, provenance per fact and permissions per fact; a design that fails any one is a graph, not an operational ontology.
  • A warehouse with a semantic layer is enough when questions are aggregate and historical and a day-old answer is fine; the ontology earns its cost when an hour-old answer makes someone act wrongly.
