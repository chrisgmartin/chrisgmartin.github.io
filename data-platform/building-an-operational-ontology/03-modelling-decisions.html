Modelling Decisions

Object or property, type or instance, state or event: the choices that shape the model, and how to make them.

Start from questions, not from systems

The wrong way to build the model is to open each source system and turn its tables into object types. You get twelve systems' worth of nouns, most of them duplicates, and a model shaped like the vendors' products rather than like the company.

The better way takes an afternoon with the people who will use it. Write down the questions they ask most. For GridDP's site and procurement teams the list starts with the two this guide follows, and continues with "which racks have free units at Reno?", "who touched this server last?", "which vendor is late most often?" and "what did we tell the customer in October?" Then:

  1. Underline the nouns. Server, rack, vendor, customer, promise, incident. Those are candidate object types.
  2. Underline the verbs between nouns. Promised to, shipped in, sits in, affected by. Those are candidate links.
  3. For each noun ask who owns it. If the answer is "two systems", you have found either a type that needs an ontology-issued identity (Server) or two types you were about to merge (Commitment and Customer).
  4. Trace every question across the result. A question that cannot be traced means a missing noun or verb.

The output is the picture in chapter 02. The rest of this chapter is the decisions you make while drawing it.

Object or property?

The commonest decision. Is a GPU an object, or is "8 GPUs" a property of Server? Is a rack unit an object, or is "unit 31" a property?

A GPU fails on its own, reports its own telemetry and gets swapped as a part. Incidents point at it. It is an object. A rack unit is a position. Nothing happens to position 31 that does not happen to whatever sits in it, and nobody owns it. It is a property of the server, or of the rack's holds link. A serial number identifies a server and never changes, so it is a property, and the most important one.

When you are unsure, start as a property. Promoting a property to an object later means adding a type and moving a column. Demoting an object back to a property means deleting identities that other things may link to, which is a migration with history attached.

Type or instance?

The second decision hides inside the first. Several of GridDP's source records look like servers and are not. A bill of materials is a design that forty servers were built to. A purchase order line is a batch of forty. Neither record is about one machine.

The model keeps both as their own objects: the BOM as a Design type if design questions matter, and the POLine as it is. The link from a PO line to its forty servers is fulfilled by, and it is filled in as serials arrive from the vendor's packing list. Before the servers ship, the PO line has a quantity and no servers; after rack-in it has forty. The question "is the order late?" is about the line. The question "is this server late?" is about one machine, through the line and the shipment. Keeping the types apart lets both questions be asked.

State or event?

A server is ordered, then shipped, racked, burned in, live, maybe returned, and eventually retired. Is "lifecycle state" a property that changes, or is each step an object?

Both, in a specific way. The current state is a property on Server, with a closed list of allowed values, because every consumer wants to filter on it. Each change of state is kept as an event with a time and a source, because "when did it go live?" and "how long was it in transit?" are history questions. Chapter 05 shows that keeping every fact with its times gives you this for free: the state history is simply all the state facts about one server, in order.

Events that have their own identity in a source system (an incident, an RMA) are objects, because people refer to them by key and attach things to them. Events that do not (a carrier scan, a NetBox status change) are facts with a time, not objects.

How fine to go

The model could go down to DIMMs and fans. It stops at GPUs. The rule: model to the level at which a decision is made or a thing is swapped. GPUs are swapped and have per-unit telemetry, so they are objects. A DIMM failure is recorded as an incident on the server with the slot in the incident's text. If GridDP started tracking DIMMs as parts with their own RMAs, they would become objects then.

Going too fine costs identity work and permission work for every extra type, and produces objects nobody asks about. Going too coarse hides the thing people act on. When in doubt, look at the ticket queue: the nouns in incident titles are the level operators think at.

Naming and cardinality

Three habits save arguments later.

  • Name types in the singular, in the team's words. Server, not Servers or Asset or Node. If site operations say "box", the type can still be Server, but write "box" in its description so search finds it.
  • Name links as verbs read from source to target. Rack holds Server. PO line fulfilled by Server. A link whose name reads both ways ("related to") is a sign you have not decided what it means.
  • Write the cardinality down, with the exception. A rack holds many servers; a server is in one rack at a time. That last phrase is a date range on the link, and it is what lets a move be recorded without losing where the server used to be.
A link with no owner is a link that will drift

Every link in chapter 02's table has a "proved by" column. If you cannot fill it, the link will be set once by hand and never updated. Either find the source that proves it, or make it an action (chapter 07) so that changing it is a recorded decision.

What to leave out, and how to say so

A model is also a list of refusals. Telemetry samples, single messages, invoices and the marketplace's forty thousand machines are outside GridDP's model, and chapter 02 says so in writing. Write the refusals down next to the types, with the reason, so the next person does not add a Message type in good faith and double the identity work.

The same page should say what the model does not promise. GridDP's ontology does not tell you what a server cost; that is finance's question, in NetSuite. It does not tell you what temperature a GPU is right now; that is the telemetry store's. It tells you what the server is, where it is, what state it is in, what it was promised for and what has happened to it. A model that knows its edges is one people trust at the edges.

✓ Check yourself

Answer from memory before opening each one.

  1. Site operations want "rack unit" to be an object so they can see what has been in unit 31 over time. Object or property, and how do you give them the history anyway?

    Show answer

    Property. Nothing happens to a position on its own. The history they want is the dated holds link between rack and server: every server that occupied unit 31, with start and end dates. See object or property.

  2. A PO line for 40 servers has no serials yet. What does the model hold about those servers, and when does it change?

    Show answer

    Nothing about individual servers: the line holds a quantity and a promised date. Server objects are created and linked through fulfilled by as serials arrive on the packing list. See type or instance.

  3. Is "racked on 3 October" a property, an event or an object?

    Show answer

    An event: a state fact about the server with a time and a source (NetBox). Current state is the property; the dated fact is the history. It is not an object, because nothing in any system refers to it by key. See state or event.

  4. Why does the model stop at GPUs and not go down to memory modules?

    Show answer

    Model to the level at which a decision is made or a part is swapped. GPUs are swapped and have their own telemetry. DIMMs are, for now, text in an incident. See how fine to go.

  5. A proposed link is called "related to" and runs between Document and Server. What is wrong with it?

    Show answer

    The name does not say what the link means or which way to read it, and there is no "proved by". Name it mentions, direct it Document to Server, and prove it by text extraction with a confidence. See naming and cardinality.

Takeaway

  • Build the model from the questions people ask, not from the tables the systems have. Nouns become types, verbs become links, and every question must trace.
  • Something is an object if it has a life of its own: events happen to it, someone owns it, other things point at it. Otherwise it is a property. Start as a property when unsure.
  • A design and an order line are not servers. Keep types apart and link them; the link fills in as the world catches up.
  • Current state is a property; each change of state is a dated fact. Events with keys in a source (incidents, RMAs) are objects; events without (scans) are facts.
  • Model to the level where decisions are made or parts are swapped. Name types in the singular, links as directed verbs, and write cardinality down with its exception.
  • Write the refusals down. A model that knows its edges is trusted at the edges.
