One Identity Across Systems

Six records that all mean one server: how the ontology gives it one identifier and keeps the mapping honest.

Six records, one server

Chapter 01 showed six records about GD-7F21, each with a different key. Here is what each key really points at.

StageSystemThe keyWhat it identifies
DesignGoogle DriveBOM revision BA design, built forty times
OrderNetSuitePO 4471, line 3A batch of forty; no serials until the vendor ships
DeliveryCarrier1Z-…-88A pallet holding several servers
Rack-inNetBoxdevice 5519, hostname reno-r12-31One device, serial typed by a person
OperationTelemetry10.4.12.31:9400An address, reused by the next server in that slot
FailureJiraINC-2093A ticket whose text names the server however the reporter typed it

So the ontology issues its own identifier for each physical server, and keeps a table of which native keys point at it, how it knows, and how sure it is. That table is called a crosswalk, and it is the single most important table in the system.

The crosswalk

A crosswalk row says: in system S, native key K refers to entity E, established by method M with confidence C, from date A until date B. Six columns, and each one earns its place.

  • Method says how the link was made: an exact serial match, a person's assertion, a probabilistic match, a mention in text. Later chapters need this to decide how much to trust a fact, and you need it to find every link a bad rule produced.
  • Confidence is 1.0 for an exact key and a probability otherwise. It travels with every fact that uses the link.
  • Valid from and valid to exist because keys get reused. The telemetry address 10.4.12.31:9400 belongs to GD-7F21 from rack-in until it leaves for repair. After that, the same address belongs to the replacement. A join that ignores dates blames the old server for the new one's metrics.

Two rules make the identifier safe to build on. It is never reused. And it is never deleted: when two identifiers turn out to be one server, one is kept and the other becomes a redirect to it, so anything that stored the old identifier still resolves.

Exact keys first

Most of the crosswalk is filled by exact matches, in a fixed order from strongest to weakest: a serial that matches exactly, then a NetBox device identifier carried in the telemetry labels, then a hostname that follows the naming rule. Each rule writes its own method, so a rule that turns out wrong can be found and reverted. For a fleet of 600 servers, exact keys settle almost everything about the fleet itself.

The hostname rule needs a guard. reno-r12-31 is a position, not a machine. It is a valid key for a server only while NetBox says that server is in that position. Encode that as the valid-to date on the row.

When there is no exact key

Linking a PO line to the servers it produced has no exact key until the packing list arrives, and the packing list is a PDF a vendor emailed. Linking a shipment to its servers is the same. Here the evidence is partial: a similar hostname, the same site, a close date, a serial that is present on one side and missing on the other.

The standard method is record linkage as Fellegi and Sunter set it out in 1969, and as the open-source tool Splink implements it. The idea fits in a sentence: compare two records field by field, and for each field ask how much more likely that agreement is if the records are the same thing than if they are not. Agreements on rare values (a serial) count for a lot; agreements on common values (a site) count for little. The scores add up to a probability.

The important design choice is not the model; it is that there are two thresholds. Above the upper line the platform links on its own. Below the lower line it discards. Between them it puts the pair in a review queue for someone in procurement or site operations. A pair that agrees on a serial and a hostname is a near-certain match and links itself. A pair that agrees only on a hostname-shaped string is a maybe, and a maybe goes to a person.

For GridDP's 600 servers the whole queue is a few items a week. For the marketplace's forty thousand provider machines, where owners type their own labels, it is a job, and that is why the marketplace is out of this guide's scope.

When the match is wrong

Two kinds of mistake, and they cost very different amounts.

A missed merge shows two objects where there is one. Someone notices a server that appears twice, and it is annoying. A false merge fuses two servers into one object. The fused object inherits the facts of both, and through the facts, the permissions of both. If a Reno server merges with a Dallas one, a Reno contractor can now see Dallas facts. That is why the upper threshold sits high and the review queue is preferred to the optimistic merge.

Detection comes from three places: a rule that says two different serials can never share an identity, a person flagging a bad merge, and a downstream oddity such as a server reporting from two racks. Repair is a split, and a split must not rewrite history. The identity service creates a new identifier for the part that was wrongly joined, closes the old crosswalk rows with an end date, writes new ones, and announces the change so every table that stored the old identifier can re-resolve.

A merge you cannot undo is data loss

If the platform overwrites the losing record's key when it merges, the split has nothing to restore from. Keep the native key on every fact, and keep the crosswalk append-only with dates.

When sources disagree: who wins

Once six records are one server, each property may still have six candidate values. Chapter 02's "owner" column is the rule: for placement NetBox wins, for the serial the vendor's packing data wins over a hand-typed value, for a delivery date an observation (a carrier scan) beats a plan (the PO date), and for operational state the most recent event wins across telemetry, Jira and PagerDuty.

Keep every candidate value as its own fact with its source, and compute the winner as a view. The reason is correction: when a rule turns out wrong or a source is retracted, the view recomputes. If only winners were stored, the losers are gone. The dashboard that cannot show several values gets a materialised copy of the view, rebuilt whenever the rules change.

Documents and messages

A Slack thread about GD-7F21 has no key. It has a mention. The platform scans text for strings that look like keys (a serial, a hostname, a PO number, an incident key), looks each one up in the crosswalk, and writes a mentions link with a confidence. The thread does not become the server. It becomes evidence about it.

A message that says "the Reno box with the bad DIMM" contains no key, and the right output is no link. Do not send it to a language model and accept the answer as a fact. Either leave it unlinked, or let a model propose a candidate that goes into the review queue with a visible "proposed" method and a low confidence. Exact keys at high confidence, proposals at low, and nothing silent in between.

The identity service

All of this sits behind one small interface, so every other part of the platform asks the same questions in the same way: resolve a native key to an identifier as of a date, list the native keys of an identifier, and subscribe to merges and splits. Five promises make it safe to build on: identifiers are never reused or deleted; the same inputs and rules give the same answer; every mapping carries its method, confidence and dates; registering the same key twice does not create a second identity; and every merge or split is announced.

Resolution runs on the path where changes arrive, so it has to be fast. A copy of the crosswalk in memory, refreshed from the merge-and-split stream, answers in microseconds. The cost is a short window after a merge where a worker may still hold the old answer, which is why the stream exists.

✓ Check yourself

Answer from memory before opening each one.

  1. Telemetry shows GD-7F21 running hot a week after it left for repair. What went wrong, and which crosswalk column prevents it?

    Show answer

    The network address was treated as permanent, and the replacement server took it over. The valid-to date closes the old mapping when the server leaves, and the join has to respect it. See the crosswalk.

  2. A PO line and a NetBox device share a hostname-shaped string but the PO side has no serial. The match probability is low but not negligible. What happens to the pair?

    Show answer

    It goes to the review queue. It is too weak to link and too strong to discard, and a person decides. Two thresholds exist so that the uncertain middle is never decided silently. See when there is no exact key.

  3. Why is a false merge worse than a missed one at GridDP, and what must the repair never do?

    Show answer

    A merged object inherits both sides' facts and permissions, so a site-scoped contractor can see the other site. The repair issues a new identifier, closes crosswalk rows and re-resolves facts from their native keys; it never rewrites or deletes identifiers. See when the match is wrong.

  4. Product wants one "owner site" per server and engineering proposes storing only the winning value. Argue against, and name the case where you would agree.

    Show answer

    Store every candidate with its source and compute the winner, so a corrected rule or a retracted source recomputes it. Agree only for a consumer that cannot show several values, and give it a rebuildable materialised copy. See who wins.

  5. A colleague wants a language model to link "the Reno box with the bad DIMM" to a server. What do you allow and what do you refuse?

    Show answer

    Allow a proposed link with a visible low confidence and a "proposed" method, queued for a person. Refuse a silent high-confidence link, because nothing in the text is a key. See documents and messages.

Takeaway

  • Native keys name designs, batches, pallets and addresses, not machines. The ontology issues its own identifier per physical server and records every key that points at it.
  • The crosswalk carries method, confidence and dates on every row. Identifiers are never reused and never deleted, only redirected.
  • Exact keys first, in order of strength. Probabilistic matching only where exact keys are missing, with two thresholds and a review queue between them.
  • A false merge leaks permissions; a missed merge is merely untidy. Set the auto-link line high, and split without rewriting history.
  • Keep every candidate value and compute the winner as a view. Mentions in text are links with a confidence, never merges.
