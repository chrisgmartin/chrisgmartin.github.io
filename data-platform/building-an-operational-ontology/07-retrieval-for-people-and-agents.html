Section D · Serve it

Retrieval for People and Agents

Query and retrieval services that check the caller's permissions before data reaches a model, answer with citations, freshness and gaps, and let a new source be added without a new service.

One door, four guarantees

GridDP's ontology holds facts about 600 Reserved servers, a marketplace of about 40,000 provider machines and 30,000 documents. Every consumer reaches them through one query service: a person in a dashboard, a Slack bot, an agent acting for a procurement lead. The reason is not tidiness. Four guarantees built in earlier chapters can only be enforced at the point where data leaves the platform: identity (one ID per server), freshness (how old each fact is), provenance (where each fact came from) and permissions (who may see it). A second door, such as a read replica handed to finance "for now", is a place where at least one of the four is not enforced.

The rule is "no door that skips the checks", not "one process". An analytics warehouse can stay a separate system if it is fed from the same permissioned facts and carries the same restrictions. All GridDP figures in this chapter are illustrative.

Structured facts and documents, joined on identity

The service answers from two stores with different behaviour. The fact store holds typed facts about objects: exact, filterable, traversable. A question such as "which Reserved servers allocated to customer X for November are late" is a graph traversal with filters, and the answer is either right or wrong. The document index holds the 30,000 Drive files and the Slack history: approximate, ranked, and only as good as its parsing. Lexical and dense ranking is covered in Production RAG and is not repeated here.

The join between the two is the entity ID, never the text of a serial. Chapter 02 gave every document span mentions linked to entities, each with a confidence. That link works in both directions. From an object to documents: "find spans that mention GD-7F21 with confidence of at least 0.8, then rank them against the question". From documents to objects: a vendor email says the shipment is on time, and the service shows it beside the carrier-tracking fact that says it is four days late. The second direction is where the ontology earns its cost, because the disagreement is the finding.

Order the work so the exact store narrows the approximate one. For "why is the Reno batch late", the service first finds the shipments linked to PO 4471 whose observed date is later than the planned date. It then runs document search restricted to the entity IDs of those shipments, their purchase-order lines and their servers. A filter that turns 30,000 documents into a few dozen costs little and improves precision more than a better ranker would. The case where this flips is an open question with no entity in it; there the search is unfiltered, and the answer says so.

Permissions before the model, not after

Whatever reaches the model's context can reach the user, an injected instruction, or a log. An instruction such as "do not reveal finance documents" is a request to a text predictor, not an access control. OWASP's guidance on excessive agency says the same about actions: authorisation is enforced downstream, in the context of the specific user, and the model is not asked to decide whether something is allowed. For reads the consequence is a pipeline where the service filters first and the model only ever sees the filtered result. The agents chapter of the security guide covers the attack side.

The caller is resolved first. For an agent that is the pair (agent, user), and the effective permission is the user's: an agent never sees more than its caller. Then the service asks the permission graph what the caller may see and passes the answer into the queries as a filter. In OpenFGA the call for that is ListObjects, which returns the objects of one type that a user has a given relationship with. Two limits in its documentation decide how far it carries. The response holds "the results found within the time allotted", set by listObjectsDeadline with a default of 3 seconds, and it is capped by listObjectsMaxResults, default 1,000. The page describes it as a fit for "access-aware filtering on small object collections" (as of November 2026).

Those limits split GridDP's data cleanly:

  • Devices and servers. 600 servers and their racks and sites fit under the 1,000 cap for any caller, so the service pre-filters: ListObjects first, then the structured query runs over exactly that set.
  • Documents. 30,000 documents exceed the cap, so no caller's visible set can be listed. Each indexed span instead carries an access label written at ingestion, such as the site and a restriction class, and search pre-filters on the label. The top 20 results then go through one batch check against the graph before anything is returned. OpenFGA's docs point to Batch Check for many checks at once.

The label and the graph can disagree after a permission change, until the change has propagated (chapter 06). So the label is a cheap pre-filter and the check against the graph is the authority. A document that fails the check is dropped even if the index said yes.

A truncated list is a gap, not a verdict

If ListObjects hits its deadline or its cap, it returns fewer objects, never more. That fails safe for leaks but silently wrong for completeness: "no late servers" may mean "none among the 1,000 found". The service must detect truncation, return what it has and say the result may be incomplete. It must never widen the filter to compensate.

An answer carries its evidence, its age and its holes

An answer from the ontology is more than prose. It has four parts: the text, the citations behind each claim, the freshness of each cited fact and the gaps the service knows about. Anthropic's citations feature, one mechanism among several, shows how the first part works. The service passes retrieved facts and spans as document blocks in the request. Each text block in the reply then carries citations with the document index, the exact cited_text and a location: char_location for plain text, page_location for PDFs and content_block_location for custom content. The docs state that cited_text does not count toward output tokens and that citations are guaranteed to contain valid pointers to the documents provided. The service maps each document index to a fact ID, so a citation resolves through the provenance model to a Jira event or a PDF page.

A citation proves that the text came from that source. It does not prove the source is current. Freshness is therefore a separate field, computed by the service: for each cited fact, the age (now minus observed time) against the source's freshness target of 5 minutes, 1 hour or 24 hours. A hole is also computed by rule, not by the model. For every entity in the answer the service knows which sources are expected to speak. If shipment 1Z-…-88 is in transit and carrier tracking is expected to report at least one scan a day (an illustrative rule), a last scan on Tuesday produces the line "no shipment update since Tuesday". The model could omit that line without noticing; the service cannot.

The same docs say citations cannot be combined with structured outputs, because citations interleave with text. The design follows: ask the model for cited prose, and assemble the envelope around it in code.

answer envelope (sketch)
{
  "answer": "Shipment 1Z-…-88 carries GD-7F21's batch and is 4 days behind plan [1][2].",
  "citations": [
    {"n": 1, "fact": "f-88231", "source": "carrier:1Z-…-88", "observed": "2026-10-06T09:12Z",
     "freshness": {"age": "26h", "target": "24h", "status": "stale"}},
    {"n": 2, "fact": "f-77102", "source": "netsuite:PO-4471/line-3", "observed": "2026-10-07T04:00Z",
     "freshness": {"age": "5h", "target": "1h", "status": "stale"}}
  ],
  "gaps": ["no carrier scan since Tuesday"],
  "as_of_watermark": "2026-10-07T09:30Z",
  "permission_check": "chk-5f3a1"
}

Production RAG's context assembly chapter treats citations from the retrieval side. Here the extra step is that every citation also resolves to a fact with a time and a permission.

Adding a source without adding a service

Suppose a vendor starts sending a nightly CSV of RMA statuses. If this needs a new service, the platform will not scale past twelve sources. It should need one registration with four parts, reviewed as a pull request:

  1. Schema. Each column maps to a fact predicate with a type and unit, and one column is named as the valid-time column. Unmapped columns are kept in the raw layer, not dropped.
  2. Identity mapping. Which columns are keys (serial, PO line, RMA number) and which crosswalk they resolve against. Rows that do not resolve go to the review queue from chapter 02 and are not discarded.
  3. Permission mapping. A default restriction for the source and a column that maps each row to a site. RMA data here is visible to procurement and to site operations for that site. A row without a mapping is visible only to the source's owners, so a mistake fails closed.
  4. Provenance capture. File hash, row number and ingestion time stored with every fact, so any answer traces to a line in a file.
sources/vendor_rma_csv.yaml (sketch)
source: vendor_rma_csv
freshness_target: 24h
facts:
  - column: rma_status
    predicate: rma.status
    type: enum[opened, shipped, received, closed]
    valid_time: status_date
identity:
  - column: serial
    crosswalk: server.serial
  - column: po_line
    crosswalk: purchase_order.line
permissions:
  default: [procurement, site_ops]
  site_column: site_code
  unmapped_row: owners_only
provenance: [file_sha256, row_number, ingested_at]

CI runs the registration against a sample file and reports rows ingested, the share of rows that resolved to an entity, and any row with no permission mapping. The recommendation flips for sources that need entity extraction, such as a new type of scanned PDF. They need parsing code, not configuration, and the registration then points at that parser.

The tool contract for agents

An agent reaches the service through a tool interface. The Model Context Protocol is one; any function-calling scheme has the same shape. The MCP specification (version 2026-07-28 shown, as of November 2026) defines a tool by a name, a description and a JSON Schema for inputs, with an optional output schema for structured results. Tool execution errors return with isError set, so the model can see them and retry. Its security section says servers must validate all inputs, implement access controls, rate limit and sanitise outputs, and that clients should log tool usage for audit. It also notes that the list of tools a server returns may vary with the authorisation presented on the request.

For the ontology, the contract adds four decisions:

  • Caller identity comes from the credential, never from an argument. A tool with a user parameter lets the model, or an injected instruction, ask as someone else. The service reads the identity from the transport and computes the effective permission.
  • A consistency token goes in and out. The reply carries as_of_watermark, the time up to which the facts are complete. A follow-up call may pass it as a minimum, so a second answer in the same conversation is never based on older state than the first. This is a design choice for the service; MCP does not define it.
  • Tools are few and expressed as intent: find entities, get an object, trace a fact to its sources, search documents, list gaps. Each has an output schema. There is no free-form SQL tool for agents, since each extra shape is another route to over-reach.
  • Hidden means not found. For an object the caller may not see, the answer is "not found", the same as for an object that does not exist, so existence does not leak.

The spec's guidance on stateful tools applies to any handle the service issues: a handle is a name, not a capability, and authorisation is checked on every call. Humans doing exploratory analysis can have a SQL path through the same door with the same row filters. The security guide's MCP section and the agent or workflow chapter cover the agent side of the same boundary.

The latency budget of one agent turn

An agent turn makes several tool calls, one after the other, because each call depends on the last. The service's share is therefore multiplied. GridDP's illustrative budget for one tool call:

StepBudget
Resolve caller, check token20 ms
ListObjects for the caller150 ms
Structured query, with the filter200 ms
Document search, with the label filter250 ms
Batch check on the top 2050 ms
Assemble citations, freshness, gaps30 ms

Run in sequence that sums to 700 ms. The structured query and the search depend only on the filter, so they run in parallel and the critical path is 20 + 150 + 250 + 50 + 30 = 500 ms. Three sequential calls in a turn then cost 1.5 s of tool time before the model's own time. The default ListObjects deadline of 3 s is six times the whole call budget, so the deadline is set to match it, and a timeout is reported as a gap under the rule above. A per-caller cache of permission sets removes the 150 ms step, but its lifetime must be shorter than the revocation target from chapter 06. With a 60 s target a 30 s time to live is safe; a 5 min cache is a standing breach of it.

✓ Check yourself

Answer from memory before opening each one.

  1. A colleague proposes giving the finance team a read replica of the fact store, because the query service is slow for their quarterly work. What do you ask before agreeing?

    Show answer

    Whether the replica applies the same permissions, carries provenance and shows freshness. A door that skips them is where the first leak appears. A separate analytics system is fine if it is fed from the permissioned facts with the same restrictions. See one door.

  2. A contractor at Dallas searches for "rack power plan". ListObjects over documents returns exactly 1,000 results and no error. What has happened, and what does the service do?

    Show answer

    The cap was reached, so the list is incomplete. At GridDP's 30,000 documents no caller's visible set is listable. Documents are pre-filtered by an access label and then checked in a batch on the top results. Truncation is reported as a gap and never widened. See permissions before the model.

  3. The model's cited answer says GD-7F21's shipment is on time, citing a vendor email. The carrier shows it four days late. Which design element should have prevented a confident wrong answer, and why can the model not supply it?

    Show answer

    Citations show where text came from, not that it is current or that other sources agree. The service computes freshness and disagreement from fact metadata and the identity join. The model sees only what it is given and does not know what is missing. See the answer contract.

  4. A vendor sends a weekly spreadsheet of quote revisions. Which of the four registration parts is most likely to cause a security incident if done carelessly, and what default limits the harm?

    Show answer

    The permission mapping. Quotes are finance documents, so a missing mapping could expose them. Unmapped rows are visible only to the source's owners, so the error fails closed. See adding a source.

  5. An agent tool takes the arguments user and query. Describe an attack and the redesign.

    Show answer

    An injected instruction in a document tells the agent to call the tool with a different user. The identity belongs in the credential, with the effective permission the intersection of agent and caller. The tool then has only a query argument. See the tool contract.

  6. Your permission cache has a five-minute lifetime and the revocation target is one minute. Argue for lengthening the cache, then say what would have to be true for that to be acceptable.

    Show answer

    A longer cache saves about 150 ms per call and load on the permission store. It is acceptable only if revocations are pushed to the cache as invalidations, so staleness is bounded by propagation and not by the lifetime, or if the revocation target is relaxed with the owner's agreement. Otherwise the cache silently breaks the guarantee. See the latency budget.

Takeaway

  • Every consumer reaches facts through the query service, because identity, freshness, provenance and permissions can only be enforced where data leaves.
  • The exact fact store narrows the approximate document search, and the join between them is the entity ID.
  • Permissions are applied before data reaches a model: pre-filter where the visible set is small enough to list, label and check where it is not.
  • A truncated permission list is reported as a gap. It is never widened.
  • The service, not the model, computes freshness per cited fact and the explicit gaps, and cites facts that resolve to provenance.
  • A new source is a four-part registration, and an unmapped row fails closed.
  • Agent tools take identity from the credential, return a consistency token and stay few and intent-shaped.
