The Method: Five Moves for Any ML Data Design Question

A repeatable structure for the design round — requirements and the signal, sources and labels, the offline path, the online path, operating it — with the estimates, the board layout, and the narration that make it land in 45 minutes.

Why a method

ML data design prompts are open: "design the data platform for our recommendation system." Candidates fail in two symmetrical ways — freezing, because there is no obvious first line to draw, or rambling, because there are too many. A fixed sequence of moves solves both. It also matches how the graders think: they are checking that you covered both paths (training and serving), that you handled time correctly, and that you can run it. The five moves below are ordered so that each one produces the inputs the next one needs, and so that the two things most candidates forget — labels and operations — have a reserved slot.

Run the moves in roughly these proportions in a 45-minute round: requirements and signal 6–8 min, sources and labels 5 min, offline path 10–12 min, online path 8–10 min, operate 5–7 min, with the remainder for the interviewer's deep dive. If the round is 60 minutes, the deep dive grows; the moves don't.

Move 1 · Requirements & the signal

Before drawing, establish what the model does and what that demands of the data. The word to use is signal: which decision does a prediction drive, and what does that decision need from us?

  • The decision. Block this payment? Rank these 200 listings? Forecast next week's capacity? The decision fixes the latency budget and the cost of being wrong.
  • Latency of a prediction. Synchronous in the request path (tens of ms), near-real-time (seconds), or batch (nightly scores written to a table)? This single answer decides whether an online store exists at all.
  • Freshness of the inputs. How stale can a feature be before the prediction degrades? "Transactions in the last five minutes" is a streaming feature; "average order value over 90 days" is a nightly batch one. Most systems have both.
  • Volume. Predictions per second, entities (users, items, accounts), features per entity, event rate feeding features. Get orders of magnitude, not precision.
  • Labels. What is ground truth and when does it arrive? (Move 2 goes deep; here you just flag the delay.)
  • Correctness bar and constraints. Regulated? Explainability required (which forces feature logging)? PII in the inputs? Budget and team size?
Ask these five, always

"What decision does the prediction drive? Is it made in the request path or in batch? How fresh do the inputs have to be? Roughly how many entities and predictions a day? And when do we find out whether a prediction was right?" Five questions, two minutes, and you now have the shape of the entire system.

Move 2 · Sources & labels

List the raw data and, separately, the ground truth. Candidates who skip labels design a beautiful pipeline that cannot evaluate or retrain its own model.

  • Sources. Transactional tables (via CDC), event streams (clicks, transactions, telemetry), third-party enrichments, documents or media for embedding. For each: owner, rate, arrival pattern, and whether it changes after the fact (late events, corrections, deletes).
  • Labels. Where does the outcome come from — a chargeback system, a "purchased" event, a human review queue, a future value of a metric? What is the label delay (seconds for clicks, weeks for fraud, months for churn)? Is the label noisy or partial (only reviewed cases get labelled)? Does it get revised?
  • The join key and time. How does a prediction get joined back to its label — by request id, by entity and window? This join is the spine of the training set and of every evaluation.

Say the label delay out loud and draw it as a number on the board ("labels arrive T+30d"). It drives how far back your training window must start, how you evaluate a freshly deployed model, and whether you can retrain weekly at all. Depth: Deep dive 03 · Labels, Ground Truth & Feedback Loops.

Move 3 · The offline path

The path from raw data to a training set. Draw it left to right: raw → curated entity tables → feature computation → offline feature store (or feature tables) → point-in-time training set → versioned dataset → training job.

  • Feature definitions. One definition per feature, owned, versioned, with an entity key and an event-time semantics ("sum of transaction amounts in the trailing 7 days, as of event time"). This is the artifact both paths share.
  • Point-in-time correctness. Every feature value in the training set must be the value that was knowable at the prediction time of that row. That means an as-of join between the label/prediction timestamps and the feature history — never a join to "current" values. Draw the as-of join explicitly; it is the single most tested mechanism in these loops.
  • Backfills. A new feature needs history. Say how you compute it for the past (from raw events, idempotently, by partition) and how you keep backfilled history distinct from live values.
  • Dataset versioning. The training set is an immutable, addressable artifact — a table snapshot, a manifest of file hashes, a tagged commit in a versioned lake. The model registry points at it.
  • Splits and leakage. Time-based splits for anything with drift; entity-disjoint splits when entities repeat; leakage checks for features that encode the label.

Move 4 · The online path

Only if Move 1 said predictions happen at request time. The path from live events to the features a model reads in milliseconds.

  • Online store. A low-latency key-value view of the latest feature values per entity — Redis, DynamoDB, Cassandra, or a purpose-built store. Sized by entities × features × bytes, with a TTL.
  • Materialisation. Batch features are pushed from the offline store on a schedule; streaming features are computed by a stream processor (Flink, Spark Structured Streaming, a Kafka Streams app) and written directly. Both write the same feature names with the same semantics.
  • Request-time assembly. The service looks up features by entity key, adds request-only features (the current basket, the query), and calls the model. State the latency budget: total, and the slice feature retrieval gets.
  • Feature logging. Log the exact feature vector the model saw, keyed by request id. This is how you build the next training set without recomputation, how you debug a prediction, and how you measure skew.
  • Skew. The offline value for (entity, time) and the online value the model saw should agree. Name the mechanism that keeps them agreeing (one definition compiled to both paths, or the same code) and the reconciliation job that checks it.

Depth: Deep dive 06, 08.

Move 5 · Operate

The move most candidates never reach and the one that most reliably marks a senior. Five words on the board: quality, drift, lineage, cost, governance.

  • Quality gates. Schema and distribution checks on features before they reach training or the online store; a bad batch is quarantined, not served.
  • Drift and skew monitoring. Feature distributions over time versus the training baseline; online-vs-offline reconciliation; prediction distribution; label-arrival lag.
  • Lineage and reproducibility. Model version → dataset version → feature definitions → raw partitions and code commit. "Can we rebuild model v14 from scratch?"
  • Cost. Storage of feature history and training sets, compute for backfills, the online store's memory, egress to training clusters. Name the biggest line and how you'd cap it.
  • Governance. PII in training data, consent and retention, the right to erasure propagating into datasets already trained on, access control on features, audit for regulated decisions.

Numbers you should be able to produce in under a minute. Precision is irrelevant; the order of magnitude decides the architecture.

"1,000 predictions/s at 80 ms with five-minute freshness" makes streaming features and an online store mandatory. "Nightly scores for 2M customers" makes both unnecessary — a warehouse job and a table do it. Say the number, then say the consequence.

The board layout

Draw two horizontal lanes that share a spine. The spine is the feature definitions; the lanes are the offline and online paths; operations sit underneath as a band. Every drill in this guide uses this layout.

ml-data-board.txt
  SOURCES                 OFFLINE PATH (training)
  ┌──────────┐   CDC   ┌────────────┐  ┌──────────────┐  ┌────────────────┐  ┌─────────┐
  │ OLTP DBs │───────▶ │ raw / lake │─▶│ feature jobs │─▶│ offline store  │─▶│ as-of   │──▶ dataset vN ──▶ train
  ├──────────┤ stream  │ (Iceberg)  │  │ (batch)      │  │ (history, PIT) │  │ join    │        │
  │ events   │───┬───▶ └────────────┘  └──────────────┘  └───────┬────────┘  └────▲────┘   model registry
  ├──────────┤   │                                    materialise │              │  labels (T+delay)
  │ labels   │───┼─────────────────────────────────────────────── ┼ ─────────────┘
  └──────────┘   │      ONLINE PATH (serving)                      ▼
                 │     ┌──────────────┐    ┌──────────────┐   ┌────────┐   ┌───────────┐
                 └───▶ │ stream jobs  │───▶│ online store │◀──│ model  │◀──│ request   │
                       │ (Flink)      │    │ (Redis/KV)   │   │ service│   │ + logging │
                       └──────────────┘    └──────────────┘   └───┬────┘   └───────────┘
                                                                  └──▶ feature log ──▶ back to offline
  ────────────────────────────────────────────────────────────────────────────────────────
   OPERATE:  quality gates ◆   drift & skew ◆   lineage ◆   cost ◆   governance/PII ◆
  ────────────────────────────────────────────────────────────────────────────────────────
   SPINE: feature definitions (name · entity · event-time semantics · owner · version)

Mark the decision points with a ◆ as you go — batch vs streaming for each feature group, buy vs build the store, warehouse vs lakehouse for history, which online store. Those marks are your invitations for the deep dive; you are choosing where the interviewer digs.

Narrating it

The method is also a script. A strong opening sounds like this:

The first ninety seconds

"Let me start with what the model is for and what that demands of the data, then the sources and — importantly — the labels, then I'll draw the training path, then the serving path, and I'll finish with how we operate it: quality, drift, lineage, cost and privacy. At each real decision I'll flag it and we can go deeper wherever you like. First, the decision this prediction drives…"

Two habits carry the round. First, the decision sentence at every fork: "Given [requirement], I'd choose [option] over [alternative] because [fit]; the cost is [downside], and I'd revisit if [condition]." Second, hand over the wheel at the end of each move: "That's the offline path — the interesting decisions were the as-of join and the versioning. Want to go deeper there, or shall I draw serving?" Driving the structure while letting the interviewer pick the depth is what a senior discussion feels like from their side of the table.

The method at four levels

What each level does with the same five moves
  • L1 · Foundational. Draws sources → features → model. One path. No labels, no numbers, no operations.
  • L2 · Practitioner. Draws training and serving separately; names an offline and an online store; computes batch features nightly. Time correctness and skew appear only when the interviewer asks.
  • L3 · Senior. Runs all five moves unprompted. Leads with label delay and the as-of join, sizes the online store, sets a latency budget, logs features at serving time, names the reconciliation job, and makes each fork a decision sentence with a flip condition.
  • L4 · Staff. All of L3, plus: feature definitions as contracts owned by producers and consumed by many teams; cost per prediction and per training run with a cap; PII lifecycle through training sets; a migration path from "warehouse tables + nightly jobs" to a feature platform, and the honest statement of when the latter is not worth it.
