Drill: Design a Feature Store

The question you will almost certainly get in some form. Worked end to end with the five moves: the prompt, the clarifying questions, the estimate, the board, the components and what each is actually for, point-in-time retrieval, the trade-offs, the probes, and the answer at four levels.

The prompt

As the interviewer says it

"We're a marketplace. We have a handful of models — search ranking, a recommendations model on the home page, and a seller-risk model — and each team is computing its own features in its own notebooks and pipelines. Training-serving mismatches keep biting us. Design a feature store for us."

Notice what the prompt contains: multiple models, multiple teams, an explicit pain (mismatch), and no numbers. Your first job is to convert it into requirements; your second is to resist saying "Feast" for at least ten minutes.

Clarifying questions

Ask these, in roughly this order, and write the answers on the board as you get them.

  • Which predictions are online? "Ranking and recommendations are in the request path; seller risk runs nightly." → Two models need an online store; one doesn't.
  • Latency budget? "Search has 100 ms end to end." → Feature retrieval gets a slice, say ≤ 15 ms p99.
  • Freshness? "Ranking wants the last few clicks; most other features can be a day old." → A small set of streaming features, a large set of batch features.
  • Scale? "10M active buyers, 500k sellers, 50M listings; ~2,000 search requests/s peak." → Sizes the online store and the retrieval fan-out.
  • Who defines features today, and who should? "Each team; we want sharing." → Feature definitions are a shared, owned artifact — a registry with ownership is a requirement, not a nicety.
  • What does the training side look like? "Nightly retrains from the warehouse, weekly for risk." → The offline store lives beside the warehouse; point-in-time retrieval is needed.
  • Where is data today? "Snowflake plus Kafka for events." → Build the offline store on the warehouse; streaming features from Kafka.

Say the consequence column out loud. It is the argument for everything you draw next.

Move 2 · Sources & labels

Sources: the listings and orders databases via CDC (Postgres → Debezium → Kafka), clickstream and search events from the web/mobile clients (Kafka), and a seller-verification service. Labels: for ranking, clicks and purchases joined to the search request id (delay seconds to hours); for recommendations, the same; for seller risk, chargebacks and policy actions (delay ~14 days, revised on appeal). Draw the label delay next to each model. The feature store does not own labels, but the training-set builder that sits on top of it does the join, so the entity keys and timestamps must line up.

The components, and what each is for

Weak answers list the boxes; strong answers say the problem each box exists to solve.

  • Registry. The shared definition of every feature: name, entity, source, transformation, event-time semantics, owner, version, freshness SLA. It exists so that "buyer_7d_purchases" means one thing in the ranking model and the risk model, and so that two teams don't compute it twice. It is also the thing that compiles to both paths — the same definition drives the batch job and the stream job. Without it a feature store is just two databases.
  • Offline store. Full feature history — every value with the timestamp it became true — in the warehouse or lakehouse. Exists for point-in-time training sets and backfills. Big, cheap, columnar.
  • Online store. The latest value per entity, in memory, with a TTL. Exists for the request path. Small, fast, expensive per byte. It holds only the features online models read — a subset of the registry.
  • Materialisation. The scheduled push of batch features from offline to online, and the stream jobs writing fresh features straight to online. Exists so the model reads yesterday's batch values and this second's streaming values through one interface.
  • Training-set builder. Takes a labelled "spine" (entity, timestamp, label) and joins features as of each timestamp. Exists to prevent leakage. Output is a versioned dataset artifact.
  • Serving SDK / API. get_online_features(entity_keys, feature_list) with batched multi-get, and get_historical_features(spine, feature_list) for training. Exists so consumers never touch the stores directly.
  • Feature logging. The vector the model actually saw, keyed by request id. Exists for skew measurement, debugging, and cheap training-set construction.
Say the sentence

"A feature store is a registry plus two stores plus the code that keeps them consistent. The registry is the product; the stores are implementation." Interviewers who have run one will nod; the ones who haven't will learn something.

Point-in-time retrieval

This is where the round is won. The training-set builder must, for each labelled row at time t, fetch the feature value that was current at t — not the latest, not the value at the end of the day. In SQL that is an as-of join against the feature history:

point_in_time_join.sql
-- spine: one row per (buyer_id, search_ts, label)
-- fh:    feature history, one row per (buyer_id, feature_ts) with values valid from feature_ts
SELECT s.buyer_id, s.search_ts, s.label,
       f.buyer_7d_purchases, f.buyer_30d_gmv
FROM spine s
ASOF JOIN feature_history f
  MATCH_CONDITION (s.search_ts >= f.feature_ts)     -- the latest value at or before the search
  ON s.buyer_id = f.buyer_id;

-- engines without ASOF: window over the union, or a lateral "latest row where ts <= t"
-- Either way the invariant is the same: feature_ts <= search_ts, and strictly the newest such row.

Two refinements mark a senior answer. First, a maximum staleness: a value from 40 days ago should not be "the latest" for a 7-day feature — enforce search_ts − feature_ts ≤ ttl and treat the rest as null. Second, event time vs availability time: if a feature computed at 02:00 describes yesterday, its value was not knowable until 02:00, so the as-of comparison must use the time it became available, or the training set will contain values the model could not have had. What the interviewer is listening for

  • That you separated the registry (the product) from the stores (the implementation).
  • The as-of join, unprompted, with the staleness bound and the availability-time subtlety.
  • An online-store size and a latency budget with numbers.
  • Only the features that need it are streamed; the rest are batch. No cargo-cult Flink.
  • Feature logging at serving time, and a reconciliation job that turns "training-serving mismatch" from an anecdote into a metric.
  • A build-vs-buy decision with a flip condition, and an honest "you might not need this yet" for the nightly risk model.

Follow-up probes

  • "A team adds a new feature and needs two years of history. What happens?" — A backfill: run the definition over raw history partition by partition, idempotently, writing to the offline store with the correct event timestamps; flag the rows as backfilled; do not push to online until the live job is producing. Cost is the raw scan; cap it by computing from curated entity tables where possible.
  • "How do you know online and offline agree?" — Log the served vector by request id; nightly, recompute the same features offline as-of the request time and diff; alert on drift above a per-feature threshold. Root causes are almost always time-window edges or a UDF that diverged between engines.
  • "Redis goes down." — The model service degrades: default values or last-known from a local cache for batch features, skip streaming features, and log that it did. Ranking gets worse, not broken. Rehydrate from the offline store's latest snapshot; streaming features catch up from Kafka offsets.
  • "Two teams want different definitions of buyer_7d_purchases." — They get two names, or one versioned definition; the registry enforces uniqueness and ownership. This is a governance question wearing a technical hat.
  • "Why not just query Snowflake at request time?" — Latency and cost: warehouse queries are hundreds of ms to seconds and priced per scan; 2,500 req/s would be ruinous. The online store is a cache with a contract.

The answer at four levels

Feature store, L1 → L4
  • L1 · Foundational. "Put features in a feature store so teams can share them." Names Feast. No stores distinguished, no time semantics.
  • L2 · Practitioner. Offline store in the warehouse, online store in Redis, nightly materialisation, a Python SDK. Training sets built by joining current features to labels — the leakage bug, until prompted.
  • L3 · Senior. Registry as the spine; as-of joins with staleness bounds and availability time; streaming for only the features that need it, sized and budgeted; feature logging and a reconciliation job; build-vs-buy with a flip condition; degradation story for the online store.
  • L4 · Staff. All of L3, plus: definitions as owned contracts with SLAs and deprecation; cost per feature per team; a migration path from notebooks to the registry (adapters first, enforcement later); the honest scoping — nightly risk stays on warehouse tables; and the platform's metric: mismatch incidents per quarter, trending to zero.
