Section B · Drills

Drill: Embedding & RAG Data Infrastructure

The 2024-onward classic: design the data plane that turns a corpus into embeddings, keeps them fresh, and serves retrieval for a product feature — with the freshness, cost and evaluation questions that separate a demo from a platform.

The prompt

As the interviewer would say it:

Prompt

"We have a knowledge base of about two million documents — support articles, product manuals, internal runbooks — that changes daily. Product wants an assistant that answers customer questions grounded in that content, and later wants the same retrieval to power search and recommendations. Design the data infrastructure: how the documents become embeddings, how they stay current, how retrieval is served at scale, and how you'd know it's working. Assume you can call any embedding model."

Notice what the prompt is not: it isn't "pick a vector database". A candidate who opens with "I'd use Pinecone" has skipped four of the five moves. The interviewer wants to see the pipeline as a pipeline — sources, chunking, embedding as a versioned transformation, an index that is a derived artifact of a model version, serving with a latency budget, and an evaluation loop. The deep-dive treatment is in 07 · Embeddings & Vector Data; this chapter is how you say it in the room.

Clarifying questions

Spend two minutes here. Each question below moves a real design decision, and saying why you're asking is part of the score.

  • Corpus shape. "Two million documents — what's the size distribution? A 400-word article chunks very differently from a 90-page manual." Drives chunking strategy and index size.
  • Change rate and freshness. "What fraction changes per day, and how quickly must an edit be reflected — minutes, or is next-day fine?" Drives batch vs incremental embedding and whether you need CDC on the source.
  • Query load and latency. "Peak QPS on the assistant, and the retrieval budget inside the end-to-end response — say 50 ms of a 2 s budget?" Drives index type, replication, caching.
  • Access control. "Are any documents restricted — internal runbooks visible only to staff, per-tenant content?" Drives metadata filtering and whether you need per-tenant indexes. This is the one most candidates forget.
  • Modalities and languages. "Text only? Tables, images, PDFs with layout? Multiple languages?" Drives the parsing layer and model choice.
  • Model ownership. "Hosted embedding API or self-hosted? Any constraint on sending content to a third party?" Drives cost, throughput and the compliance answer.

Pin assumptions if they say "you decide": 2M docs averaging 1,500 tokens → ~6M chunks at ~500 tokens with overlap; 2% daily churn (~40k docs); 200 QPS peak; 50 ms retrieval budget; some content is tenant-restricted. Say the numbers back so everything after is anchored.

The five moves, applied

Run the method from 02 · The Method out loud. The order matters: requirements and signal first, then data, then the offline path, then the online path, then how you operate it.

1 · Requirements & signal

The signal you're optimising is retrieval quality for a downstream generator, not vector similarity. Name the functional requirements (grounded answers with citations; freshness within an hour for edited articles; per-tenant isolation; three consumers — assistant, search, recs) and the non-functional ones (p95 retrieval ≤ 50 ms; 200 QPS peak with 5× headroom; cost ceiling; audit trail of which version of which document answered a question). Then estimate: 6M chunks × 1,536-dim float32 ≈ 6M × 6 KB ≈ 37 GB of raw vectors; with int8 quantisation ~9 GB; an HNSW index adds ~1.5–2× overhead. That's one large node or a small cluster — not a "big data" problem, which changes the conversation about tooling.

2 · Sources & labels

Sources: a CMS with an API and change events, a document store of PDFs, a wiki. Each needs a parser (HTML → text, PDF with layout awareness, tables preserved as tables) and a stable document identity plus a content hash — the hash is what makes incremental re-embedding cheap. The "labels" in a RAG system are the evaluation set: a few hundred real questions with known good passages and answers, built from support tickets and curated by the people who own the content. Say early that you'd build this set in week one, because without it every later tuning decision is a guess. Deep dive: 03 · Labels & Feedback Loops.

3 · The offline path

Ingest → parse → chunk → embed → index, as a versioned pipeline:

  • Land raw documents in object storage with metadata (source, tenant, ACL, updated_at, content hash). This is the system of record for "what did the assistant know at time T".
  • Chunk deterministically — a chunker version is part of the lineage. Semantic or heading-aware chunking beats fixed windows for manuals; fixed windows with overlap are fine for articles. Store chunks as rows in a lakehouse table (Lance or Iceberg) keyed by (doc_id, chunk_idx, chunker_version).
  • Embed in batch with the embedding-model version in the key. Throughput math: 6M chunks on a hosted API at ~1,000 chunks/s aggregate is ~100 minutes for a full rebuild; a self-hosted model on one GPU does ~200–500 chunks/s. Incremental daily load is ~120k chunks — trivial either way. The full rebuild is the scenario you size for, because a model upgrade forces it.
  • Build the index as a derived artifact — the vector index is to the chunk table what a warehouse mart is to bronze data. It has a version, it can be rebuilt from the table, and you swap it atomically (blue/green) rather than mutating it in place during a model migration.

4 · The online path

Query → embed the query (same model version as the index, non-negotiable) → ANN search with metadata filters (tenant, ACL, doc type) → optional rerank with a cross-encoder on the top 50 → return top-k with citations. Latency budget: query embedding 10–15 ms, ANN 5–15 ms, rerank 20–30 ms — it fits in 50 ms only if the reranker is small or skipped for search. Filters are the design trap: post-filtering after ANN destroys recall for small tenants, so you either pre-filter (partitioned index per tenant when tenants are large and few) or use an engine that filters during traversal. Serving detail lives in 08 · Serving Architectures.

5 · Operate

Freshness: CDC or webhooks from the CMS feed a small streaming job that re-parses, re-chunks and re-embeds changed documents within minutes, and tombstones deleted ones — a stale-but-present chunk is worse than a missing one when the answer is a citation. Evaluation: retrieval recall@k and answer faithfulness on the golden set, run on every model/chunker change and nightly against a sampled live traffic replay. Monitoring: index size, embed lag, filter-hit ratios, share of queries with low top-1 similarity (the "we don't know" signal). Cost: embedding calls and reranking dominate the API bill; vectors are cheap to store.

Say the seam out loud

"The index is a derived artifact of the chunk table and a model version. When we upgrade the embedding model, we rebuild into a second index, run the golden set against both, and cut over — we never query an index with a mismatched model." That sentence answers three follow-ups before they're asked.

What the interviewer is listening for

  • Versioning discipline. Chunker version, model version, index version — and that a model change means a rebuild and a cut-over, not an in-place mutation.
  • Deletes and ACLs. Tombstoning removed content and enforcing tenant/ACL filters at retrieval. Leaking a restricted runbook into a customer answer is the failure that ends a project.
  • An evaluation loop that exists before tuning starts. A golden set, recall@k and faithfulness, run automatically.
  • Sizing that shows the problem is small. 37 GB of vectors is a node, not a cluster — a candidate who reaches for a distributed system reflexively has not done the arithmetic.
  • The reuse story. Search and recommendations reuse the chunk table and index, not a second pipeline.

Follow-up probes

Expect three or four of these. Each strong answer is a sentence or two, then an offer to go deeper.

  • "The embedding model vendor releases a better model. Walk me through the migration." — Full re-embed into a new index version (about 100 minutes for 6M chunks at 1k/s), evaluate both on the golden set plus a shadow read on live traffic, cut over behind a flag, keep the old index for a week for rollback. Query embedding and index version are pinned together in config so they can't drift.
  • "A customer asks a question and gets an answer from a document that was deleted yesterday." — Deletion path is broken or too slow: the source emits deletes as tombstones, the incremental job removes the chunks and the index entries, and there's an alert on "deleted docs still present in index" reconciled nightly against the source. I'd also add the document's updated_at to the citation so staleness is visible.
  • "How do you know retrieval is good enough — not the LLM, the retrieval?" — Separate metrics: recall@k and MRR on the golden set for retrieval; faithfulness and answer correctness for generation. Track them separately so a regression is attributable.
  • "Multi-tenant: one index or many?" — Depends on tenant size distribution. Filtered search in one index for many small tenants; partitioned indexes for a handful of large ones or where isolation must be provable. Never post-filter after ANN for small tenants — recall collapses.
  • "Costs are 3× projection. Where's the money?" — Almost always embedding and rerank API calls, not storage: cache query embeddings for repeated questions, batch offline work, quantise vectors, skip reranking for the search surface, and check for a re-embed loop caused by hash instability.
  • "Tables and images inside the manuals?" — Parse tables into a structured text form or embed them separately with a table-aware model; images get captions or a multimodal embedding, stored as their own chunk type with a modality field so retrieval can route.

The answer at four levels

How the same design reads at L1 → L4
  • L1 · Foundational. Chunk documents, embed them, put them in a vector DB, do similarity search. Names a tool; no versions, no freshness story, no ACLs.
  • L2 · Practitioner. Adds a real pipeline: parsing, overlap chunking, batch embedding, a nightly refresh, metadata filters, and top-k with a reranker. Knows recall@k exists.
  • L3 · Senior. Sizes the corpus and shows it's one node; treats the index as a derived, versioned artifact with blue/green cut-over; incremental freshness via CDC with tombstones; pre-filtering for tenants; a golden set built before tuning; separates retrieval and generation metrics.
  • L4 · Staff. Frames it as a platform serving three consumers from one chunk table; reasons about cost drivers and when to self-host; designs the migration and rollback path; anticipates the ACL leak and the stale-citation failure as the two incidents that would kill trust, and puts monitors on both; knows when a plain Postgres + pgvector is the right answer.
