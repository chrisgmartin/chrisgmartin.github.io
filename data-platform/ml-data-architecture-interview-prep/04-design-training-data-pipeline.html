Section B · Drills

Drill: Training Data with Point-in-Time Correctness

"Our churn model looks great offline and falls over in production." Designing the pipeline that builds an honest training set — the spine, the as-of join, availability time, versioning, splits — and how to defend every part of it.

The prompt

As the interviewer says it

"We're a subscription business. Our churn model has 0.92 AUC offline and does nothing useful in production. Data science thinks it's the model. I think it's the data. Design the training-data pipeline for this model so that what we evaluate offline is what we'd get online."

The interviewer has told you the answer is leakage. Your job is to find where, design it out, and show that the design generalises to the next model.

Clarifying questions

  • What exactly is the prediction and when is it made? "On the 1st of each month, for every active subscriber: will they cancel within the next 30 days?" → Prediction time is fixed and periodic; label window is [t, t+30d].
  • How is churn recorded? "A cancelled_at on the subscription row, set when they cancel; sometimes backdated on refund." → Labels arrive up to 30 days late and can be revised.
  • What features do they use? "Usage in the last 30/90 days, support tickets, payment failures, plan, tenure, and a 'days since last login'." → Rolling windows over event data plus slowly-changing attributes.
  • Where do the features come from today? "A notebook querying the warehouse's current tables." → Almost certainly joins to current attribute values — the leak.
  • Scale? "2M subscribers, ~40 features, 24 months of history." → Small; correctness dominates, not throughput.
  • Retrain cadence? "Monthly." → The pipeline must produce a new versioned dataset each month with fully-matured labels.

Where leakage comes from

Name the specific mechanisms; each is a place the current notebook is probably wrong.

  • Current-state joins. Joining the training row for January to the subscriber's plan today. A subscriber who churned in February and downgraded to "free" in March now has "plan = free" as a feature for their January row. The model learns "free plan → churned" — which is the label, encoded.
  • Windows that cross the prediction time. "Usage in the last 30 days" computed over a calendar month that straddles the 1st — including days after the prediction. Or a feature refreshed daily at 06:00 used for a 00:00 prediction.
  • Label-derived features. days_since_last_login computed as of the dataset build date, not the prediction date: a churned user's last login is by definition before their cancel. Perfect predictor, zero value.
  • Immature labels. Including the most recent month, where most churn hasn't been recorded yet — the model learns that recent months don't churn.
  • Random splits on time-series. Training on March to predict February.
The tell

0.92 AUC offline on a churn problem is itself the evidence. Say so: "That number is too good; something in the features knows the future." Interviewers rate candidates who can smell leakage from the metric.

The spine and the as-of join

The design's centre is a spine: one row per (entity, prediction_time, label). Everything else is joined to the spine, as of its timestamp. Attributes come from an SCD2 history (what was the plan on the 1st of January), windows are computed from events with event_ts < t, and each feature carries two timestamps — when it was true (event time) and when it became available to the system (the job that produced it). The join uses the stricter of the two.

build_training_set.sql
-- 1. spine: subscribers active at t, with a matured label
WITH spine AS (
  SELECT h.subscriber_id, m.month_start AS t,
         CASE WHEN h2.cancelled_at > m.month_start
               AND h2.cancelled_at <= m.month_start + INTERVAL '30 days' THEN 1 ELSE 0 END AS label
  FROM months m
  JOIN subscription_history h
    ON h.valid_from <= m.month_start AND m.month_start < h.valid_to      -- state as of t (SCD2)
   AND h.status = 'active'
  LEFT JOIN subscription_current h2 ON h2.subscriber_id = h.subscriber_id
  WHERE m.month_start + INTERVAL '60 days' <= CURRENT_DATE                 -- label maturity gate
),
-- 2. windowed features from events strictly before t
usage AS (
  SELECT s.subscriber_id, s.t,
         COUNT(*) FILTER (WHERE e.event_ts >= s.t - INTERVAL '30 days') AS sessions_30d,
         COUNT(*) FILTER (WHERE e.event_ts >= s.t - INTERVAL '90 days') AS sessions_90d,
         s.t - MAX(e.event_ts)                                             AS days_since_login   -- as of t, not today
  FROM spine s LEFT JOIN usage_events e
    ON e.subscriber_id = s.subscriber_id AND e.event_ts < s.t
  GROUP BY 1,2
)
-- 3. slowly-changing attributes as of t, precomputed features as of availability
SELECT s.*, u.sessions_30d, u.sessions_90d, u.days_since_login,
       h.plan, h.region,
       f.payment_failures_90d
FROM spine s
JOIN usage u USING (subscriber_id, t)
JOIN subscription_history h
  ON h.subscriber_id = s.subscriber_id AND h.valid_from <= s.t AND s.t < h.valid_to
ASOF JOIN feature_history f
  MATCH_CONDITION (s.t >= f.available_ts)                                -- what the system KNEW at t
  ON s.subscriber_id = f.subscriber_id
WHERE s.t - f.feature_ts <= INTERVAL '7 days';                            -- staleness bound

Three lines carry the whole answer: the SCD2 range predicate, event_ts < s.t, and available_ts in the as-of join. Point at them. Depth: Deep dive 02.

Versioning the dataset

A training set is an artifact, not a query. The build job writes an immutable dataset — an Iceberg table snapshot, or Parquet files plus a manifest of paths and content hashes — tagged with the run (churn/v2026-09), the feature-definition versions, the label version, the code commit and the raw-partition watermarks it read. The model registry entry points at that tag. This is what makes "rebuild model v14" a command rather than an archaeology project, and what lets you diff two datasets when a metric moves. Because labels are revisable, the dataset records the label snapshot too; a later rebuild with corrected labels is a new version, never an in-place edit.

Why the raw layer must be immutable

Every guarantee above rests on being able to re-read the same raw partitions later. If the raw events table is compacted, deduplicated or "cleaned" in place, the dataset's watermarks point at data that no longer exists. Keep raw append-only; do all cleaning downstream and versioned.

Splits, sampling & the label delay

  • Time-based split. Train on months 1–18, validate on 19–21, test on 22–24. Never random. Report the gap between validation and test performance — that gap is the drift you will see in production.
  • Entity leakage across splits. The same subscriber appears in many months. Fine for a churn model where each month is a real prediction; wrong for a model that should generalise to unseen entities — then split by entity.
  • Label maturity. The last two months are excluded or held out with the caveat that labels are partial. Say the number: "fully-matured labels lag by 30 days, so the freshest training month is two months back."
  • Class balance. Monthly churn ~3%; keep all positives, sample negatives to a ratio, record the weights so probabilities can be recalibrated.
  • Leakage tests as gates. Automatically flag any feature with implausible univariate power, any feature whose max event time exceeds t, and any feature whose distribution differs between labelled and unlabelled rows.

What the interviewer is listening for

  • That you diagnosed the leak from the metric and named the mechanism before designing.
  • The spine as the organising idea; every feature joined as of the spine timestamp.
  • SCD2 for attributes, event-time windows strictly before t, availability time in the as-of join, a staleness bound.
  • Label maturity as a gate with a number; revisable labels versioned.
  • The dataset as an immutable, addressable artifact linked from the model registry.
  • Time-based splits and automated leakage checks — and the reusable step for the next three models.

Follow-up probes

  • "Data science wants to add a feature that needs 24 months of history. Tomorrow." — Backfill from raw events by month partition, idempotent, writing feature_history with correct feature_ts and an available_ts equal to the backfill time — and flag that the backfilled availability is a fiction: the model would not have had it then. Either accept the optimism knowingly, or set available_ts = feature_ts + normal job latency.
  • "Cancellations get backdated on refund. Does that break anything?" — It changes labels after the fact. Store the label snapshot per dataset version; rebuild as a new version; compare. Report label-revision rate as a metric.
  • "How would you prove to the scientists it was the data?" — Rebuild the dataset with the as-of pipeline, retrain the same model, show AUC drop to a plausible ~0.75 and the feature-importance shift away from the leaking columns. Then show that number holds in production. Evidence, not argument.
  • "This is 8 GB. Why not just do it in pandas?" — You can; the value is the discipline, not the engine. Do it in SQL on the warehouse so the same job runs monthly, is versioned, and the next model reuses the spine step.

The answer at four levels

Training data, L1 → L4
  • L1 · Foundational. "Join features to labels and train." Random split. Suggests "more regularisation" for the production gap.
  • L2 · Practitioner. Recognises leakage when prompted, adds a time-based split, computes windows before the prediction date — but still joins current attributes and includes immature months.
  • L3 · Senior. Diagnoses the leak from the metric; spine + as-of join with SCD2, event-time windows, availability time and staleness bounds; label-maturity gate; immutable versioned dataset linked from the registry; automated leakage checks; a reusable build step.
  • L4 · Staff. All of L3, plus: the backfill-availability caveat; label revision as a tracked metric; the dataset build as a platform capability shared across models with contracts on feature history; cost and retention policy for dataset versions; and the evidence-based path to convincing the scientists.
