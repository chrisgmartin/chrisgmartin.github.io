Section B · The data

Training-Data Pipelines & Point-in-Time Correctness

How a training set is actually built — the entity-timestamp spine, the point-in-time join that keeps the future out, the split and dedup rules that keep validation honest, and why a dataset is a versioned artifact rather than a query.

Why the join is the whole problem

Building a training set sounds like the easy part: take the labels, join the features, write Parquet. In practice it is where the most expensive ML bugs are born, because the join has a dimension analytics joins don't: time, as it was known to the system at a moment in the past. A fraud training row for a payment made on 3 March may only use feature values that existed on 3 March. Not the account's chargeback count as of today — that includes the very chargeback you are trying to predict.

Get this wrong and you get leakage: the training set contains information that would not have been available at prediction time. Leakage produces a model that looks superb offline (it is reading the answer) and useless in production (the answer isn't there). It is the single most common reason a model's offline AUC of 0.97 becomes a production precision of 0.4, and it is almost always a data-pipeline bug, not a modeling one.

The reframe

A training set is not a table. It is a set of snapshots: for each (entity, prediction time), the state of the world as of that instant, plus an outcome measured after it. Build it as a snapshot machine and leakage becomes structurally impossible rather than something you hope to catch in review.

The spine: entity, prediction time, label

Every training set starts from a spine — the list of examples, before any features. Each row is an entity key, a prediction timestamp, and (once known) a label. Everything else is joined onto the spine, never the other way round.

spine — fraud model
-- One row per decision the model would have made: a payment attempt.
-- prediction_ts is the instant the API would have called the model.
CREATE TABLE ml.fraud_spine_v14 AS
SELECT
  p.payment_id                         AS entity_id,
  p.account_id,
  p.attempted_at                       AS prediction_ts,
  -- label: a chargeback within 90 days. NULL if the 90d window hasn't closed yet.
  CASE WHEN p.attempted_at < now() - INTERVAL '90 days'
       THEN COALESCE(cb.chargeback_id IS NOT NULL, FALSE) END AS label_chargeback_90d
FROM  gold.fct_payment p
LEFT JOIN gold.fct_chargeback cb
       ON cb.payment_id = p.payment_id
      AND cb.filed_at <= p.attempted_at + INTERVAL '90 days'
WHERE p.attempted_at BETWEEN DATE '2025-01-01' AND DATE '2026-06-01'
  AND p.decision = 'approved';           -- ⚠ see ch. 03: declined payments have no label

Three decisions are baked into those twenty lines and each is an architectural choice: the grain (one row per payment attempt, not per account), the prediction time (attempt time, not settlement time), and the label window (90 days, and rows whose window hasn't closed are unlabeled, not negative). Write these down in the dataset's registry entry. They are the definition of the problem.

The point-in-time join

With the spine fixed, every feature is joined as of prediction_ts. The offline store (ch. 04) keeps feature history as intervals — each value with a valid_from and valid_to — so the join is "find the last value whose valid_from ≤ prediction_ts". Modern engines have an ASOF JOIN for exactly this; where they don't, it is a window over a union.

point-in-time join (DuckDB / Snowflake ASOF syntax)
SELECT
  s.entity_id, s.account_id, s.prediction_ts, s.label_chargeback_90d,
  f1.value AS acct_chargebacks_lifetime,     -- as of prediction_ts, NOT today
  f2.value AS acct_payment_velocity_1h,
  f3.value AS bin_country
FROM ml.fraud_spine_v14 s
ASOF JOIN fs.acct_chargebacks_lifetime f1
     MATCH_CONDITION (s.prediction_ts >= f1.valid_from) ON s.account_id = f1.account_id
ASOF JOIN fs.acct_payment_velocity_1h f2
     MATCH_CONDITION (s.prediction_ts >= f2.valid_from) ON s.account_id = f2.account_id
ASOF JOIN fs.card_bin_country f3
     MATCH_CONDITION (s.prediction_ts >= f3.valid_from) ON s.card_bin = f3.card_bin;

-- Spark / Trino without ASOF: window over the feature history
-- SELECT ... FROM spine s JOIN feat f ON keys AND f.valid_from <= s.prediction_ts
-- QUALIFY ROW_NUMBER() OVER (PARTITION BY s.entity_id, feature ORDER BY f.valid_from DESC) = 1

Two subtleties that separate a correct join from a plausible one:

  • Availability time vs event time. A feature computed nightly from yesterday's rentals is not known until the batch finishes at 06:00. Its valid_from must be the time the value became available to the online store, not the end of the window it summarises. Otherwise you train on a value the API could not have seen for six hours. Feature stores call this the materialisation timestamp; if yours doesn't track it, add a lag equal to the pipeline's cadence.
  • Late-arriving source data. If a telemetry sample for 09:00 lands at 09:40, a feature recomputed at 10:00 will differ from the one served at 09:05. Decide once whether the offline value reflects "as computed at the time" (correct for training) or "as recomputed with full data" (correct for analytics). For training, prefer the former — log the served value (ch. 08) and use it.
Classic leaks, by name
  • Target leak: a feature derived from the label (chargeback count including this one; "account status = banned").
  • Future leak: a feature computed over a window that ends after prediction_ts (a 7-day rolling sum aligned to calendar days).
  • Availability leak: a nightly feature joined by event time rather than availability time (the six-hour problem above).
  • Split leak: the same account in train and validation with a random split; the model memorises accounts.

Splits, dedup and sampling

A random 80/20 split is the right answer for i.i.d. tabular data and the wrong answer for nearly everything at GridDP, where rows are correlated by entity and by time.

StrategyUse whenWhy
Time-based split (train ≤ T, validate T…T+Δ)Fraud, pricing, forecasting — anything deployed into the futureMimics production: validation is literally "the next period". Reveals drift and label delay honestly.
Group split by entityRanking (many rows per renter), any model with repeated entitiesStops the model memorising an account/host and calling it generalisation.
Time + groupThe default for request-path modelsBoth leaks at once are the norm, not the exception.
Random splitGenuinely independent rows; one-off experimentsFine, but say why.

Dedup before splitting, keyed on (entity_id, prediction_ts); duplicate spine rows (a payment retried three times) will land on both sides of any split. Sampling is a cost lever — the 150 M-samples-a-day telemetry firehose cannot be a training set — but must be documented and, for rare positives like fraud (≈0.3% of payments), stratified: downsample negatives, keep every positive, and record the sampling weight so the model's calibration can be corrected.

The dataset is an artifact

The output of all this is not "a query you can re-run". Source tables change (late data, backfills, GDPR deletions), feature definitions get fixed, and a re-run six weeks later produces a different table with the same name. A training set must be materialised, immutable, hashed and registered, exactly like a model binary.

dataset manifest — fraud_train_v14.yaml
name: fraud_train
version: 14
spine: ml.fraud_spine_v14            # snapshot id: iceberg 7f3a…  (ch. 05)
prediction_window: [2025-01-01, 2026-06-01]
label: label_chargeback_90d          # censored after 2026-03-03 (window not closed)
features:                            # registry names + definition versions (ch. 04)
  - acct_chargebacks_lifetime@3
  - acct_payment_velocity_1h@2
  - card_bin_country@1
split: time; train < 2026-01-01; valid 2026-01-01..2026-03-01; group_by: account_id
sampling: negatives 1:20 stratified; weight column: sample_weight
rows: {train: 4_812_330, valid: 1_106_912}
storage: s3://griddp-ml/datasets/fraud_train/v14/   # parquet, immutable
sha256: 9c1e…                        # of the file list + manifest
built_by: dataset-builder 1.7.2, commit a41c0f, 2026-06-02T04:12Z

The model registry entry for fraud-xgb:2026-06-02 points at fraud_train@14, which points at Iceberg snapshot IDs and feature-definition versions. That chain — model → dataset → snapshots → definitions → code — is what "reproducible" means (ch. 09), and it is only possible because the dataset was frozen.

Tests that catch leakage before training does
  • For every feature, assert valid_from ≤ prediction_ts on the joined result (a leak shows up as a violation, not as a suspiciously high AUC).
  • Train a trivial model on each feature alone; any single feature with near-perfect separation is a target leak until proven otherwise.
  • Assert no account_id appears in both train and valid when the split is grouped.
  • Diff the label rate and feature means between the last dataset version and this one; a jump is a pipeline change or a world change, and you want to know which before training.

Worked example: the fraud set on each stack

On Stack A, the dataset builder is a Python job that reads the spine and feature tables from Iceberg via Spark, runs the window-based point-in-time join, writes Parquet to S3 and pins the Iceberg snapshot IDs it read in the manifest; Feast's get_historical_features() does the same join if the features are registered there. On Stack B, FeatureEngineeringClient.create_training_set() performs the point-in-time lookup against Delta feature tables with timestamp_lookup_key, and the Delta version is the snapshot. On Stack C, Snowflake's feature store generates the ASOF-joined dataset as a versioned Dataset object backed by an immutable stage. The primitives are the same everywhere: spine, interval-keyed feature history, as-of join, frozen output with a pointer back to what it read.

At GridDP's scale the fraud set is small (millions of rows). The capacity-forecasting set is not: 17,000 GPUs × hourly rollups × 18 months ≈ 220 M spine rows before features. That one is built incrementally — new months appended as new dataset versions that share earlier partitions — which is why chapter 05 cares so much about partition layout and snapshot semantics.

When to choose what

The training-data decision heuristic
  • Spine first, always. If you cannot state the grain, prediction time and label window in one sentence, you are not ready to join.
  • ASOF join from interval-keyed history whenever a feature changes over time — which is every feature except static attributes. Join by availability time, not event time.
  • Time-based split by default; add a group split when entities repeat. Random splits need a justification.
  • Freeze the output. Manifest + hash + snapshot IDs. If rebuilding it is a notebook, it is not a dataset.
  • Use the served vector when you have it (ch. 08): logging what the model actually saw sidesteps availability and late-data problems entirely for request-path models.

The mature answer names the flip condition: "For the nightly forecaster, a scheduled SQL job with interval-keyed rollups is enough. The moment a request-path model uses a feature refreshed more often than daily, I move dataset assembly onto logged served vectors, because reconstructing 'what the API knew at 09:05' from batch tables is a losing game."

Optional: the training-data answer at four levels
  • L1 · Foundational. Joins today's feature table to historical labels; random split; the notebook is the dataset.
  • L2 · Practitioner. Knows leakage exists and time-splits; joins on event time; versions the model but rebuilds the data from live tables.
  • L3 · Senior. Builds from a spine with an as-of join on availability time, group + time splits, stratified sampling with weights, and freezes the dataset with a manifest and snapshot pointers.
  • L4 · Staff. Designs assembly around logged served vectors for online models and incremental partitioned datasets for the firehose; puts leakage tests in CI; can explain censoring and label delay to a data scientist and a lawyer.
