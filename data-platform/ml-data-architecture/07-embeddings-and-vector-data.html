Section C · Moving & serving

Embeddings, Vector Data & RAG Pipelines

Embeddings are features whose definition is a model. That single fact drives everything — how the pipeline runs, why re-embedding is a migration, where vectors should live, and why "just add a vector database" is usually the wrong first move.

An embedding is a feature with a model inside it

A tabular feature like acct_rentals_30d has a definition you can read: count rentals, trailing 30 days. An embedding's definition is the weights of the model that produced it. Two vectors are only comparable if the same model, at the same version, with the same preprocessing, produced both. Change the model and every stored vector is silently obsolete — not wrong in a way a test catches, just no longer in the same space as the new queries.

That is the whole architecture in one sentence. An embedding pipeline is a feature pipeline where the "feature version" includes a model version; a vector store is an online store whose index must be rebuilt when that version changes; and retrieval quality is a data-quality problem, monitored like drift. At GridDP the honest starting point is that most models don't need this at all — ranking, fraud, forecasting and pricing are tabular problems where gradient-boosted trees win. Embeddings earn their place for three jobs: semantic search over free-text workload descriptions ("fine-tune a 70B model" → suitable GPU configurations), similarity over behavior (hosts whose telemetry signature looks alike, for reliability and fraud rings), and retrieval for the AI interfaces that answer questions over docs, runbooks and metric definitions.

The reframe

Treat (embedding_model, version, preprocessing_hash) as part of the vector's schema. Store it on every row. A vector store that mixes two model versions in one index is returning garbage with high confidence, and nothing downstream can tell.

The embedding pipeline: batch and incremental

The pipeline has four stages, and the interesting decisions are in how it runs, not what it does: select the rows or documents that need vectors → preprocess (clean, chunk, normalize) → embed (a hosted model, an API, or a GPU batch job) → write vectors plus metadata to the store and the lakehouse.

  • Batch (backfill and re-embed). Everything, once. This is a GPU job — a 7B-parameter embedding model over ten million support tickets is hours on a handful of GPUs, not minutes. Shard the input, checkpoint progress by shard, write to a new index version, and cut over atomically. At a neocloud this is the one ML data pipeline that competes with customers for the same hardware; schedule it on the marketplace's own idle capacity.
  • Incremental (steady state). New and changed rows only, driven by CDC or an event stream (chapter 06's machinery). Latency is usually minutes; a new listing should be findable soon, not instantly. Idempotent upsert keyed by (entity_id, chunk_id).
  • Deletes. The forgotten stage. A deleted listing, an erased account (GDPR), a retracted document must leave the index. CDC delete events → tombstone in the metadata table → delete from the vector store. Vector stores vary wildly in how cheaply they delete; check before choosing one.
embed_listings.py (incremental, idempotent)
# Incremental embedding of changed listings. Driven by the CDC topic; runs every 5 minutes.
MODEL_ID  = "bge-m3"                # embedding model
MODEL_VER = "2025-11"               # weights version — part of the vector schema
PREP_HASH = preprocess_hash()       # hash of chunking + cleaning code

changed = read_cdc("marketplace.listings", since=last_checkpoint())      # inserts, updates, deletes
docs    = [prepare(l) for l in changed if l.op != "delete"]              # title + description + specs
vecs    = embed_batch(docs, model=MODEL_ID, version=MODEL_VER)           # GPU or API, batched

rows = [dict(entity_id=d.listing_id, chunk_id=0, vector=v,
             model=MODEL_ID, model_version=MODEL_VER, prep_hash=PREP_HASH,
             gpu_model=d.gpu_model, region=d.region, price_hr=d.price_hr,  # filterable metadata
             embedded_at=now())
        for d, v in zip(docs, vecs)]

upsert("listings_v3", rows, key=("entity_id", "chunk_id"))               # vector store, index version v3
append_lakehouse("features.listing_embeddings", rows)                    # offline history for training/eval
tombstone([l.listing_id for l in changed if l.op == "delete"], "listings_v3")
commit_checkpoint()

Chunking & the document model

For RAG the unit of retrieval is a chunk, not a document, and chunking is where most retrieval quality is won or lost — before any vector store is involved. The decisions: chunk size (a few hundred tokens for Q&A over runbooks; larger for narrative docs), overlap (so a fact split across a boundary survives), structure-awareness (split on headings and tables, not on character counts), and what metadata rides along (source, section title, last-updated, access class). Each chunk is a row: (doc_id, chunk_id, text, vector, metadata). Store the text alongside the vector — a store that returns only IDs forces a second lookup in the latency path.

The document model also has to answer "what is the source of truth?" For GridDP's metric definitions the answer is the semantic layer, not a copied paragraph; for runbooks it is the wiki page at a version. Record it, because the AI interface will be asked "where did this come from?" and a chunk without provenance cannot answer.

Access control lives on the chunk

A vector index flattens every permission boundary you had in the source systems. If finance runbooks and public docs share an index, a retrieval query from an unprivileged user will happily surface the finance chunk. Carry the access class as filterable metadata and apply it as a pre-filter on every query. Post-filtering after retrieval is not enough — the sensitive chunk already left the store.

Where vectors live

The choice is about scale, filters and how many systems you want to run. Nearly every option now offers HNSW or IVF-style approximate-nearest-neighbour indexes; the differences are in what surrounds the index.

Whatever serves queries, the lakehouse keeps the history. Vectors written only to a vector database are unreproducible the day the index is rebuilt with a new model; the append to features.listing_embeddings in the pipeline above is what lets you evaluate old versus new retrieval on the same corpus.

Hybrid search & filters

Pure vector similarity is a poor search engine. It has no notion of exact match — a query for "H100 SXM 80GB" should not rank an "H100 PCIe 80GB" listing as its nearest neighbour just because the words are similar — and it cannot enforce hard constraints like region or price ceiling. Production retrieval is hybrid: a lexical component (BM25) for exact terms, a vector component for semantics, fused by rank (reciprocal rank fusion is the workhorse) or by a learned reranker; plus metadata pre-filters applied inside the index so the top-k is computed over eligible rows only. The GridDP semantic search pre-filters on region and GPU memory, fuses BM25 over specs with the vector score over the free-text description, then reranks the top 50 with a cross-encoder. The vector store contributed one of four stages.

Refresh, re-embedding & drift

Three things change under an embedding index, and each needs a plan.

  • The data changes. Handled by the incremental pipeline; measure the lag from source change to index visibility as a freshness SLA, like any feature.
  • The model changes. A new embedding model is a migration, not an update: re-embed the full corpus into a new index version, evaluate retrieval quality on a held-out query set (recall@k against labeled relevant chunks, plus an LLM-judged answer quality if it feeds RAG), then cut queries over and retire the old index. Never embed new rows with the new model into the old index.
  • The world changes. Query distribution drifts — a new GPU generation ships and nobody searched for "B200" during evaluation. Monitor the distribution of query embeddings and of top-k similarity scores over time; a falling median top-1 score means queries are landing in sparse regions of the index. Feed sampled queries back into the evaluation set monthly.

Worked example: GridDP

GridDP runs two embedding pipelines and, deliberately, no dedicated vector database. Listing embeddings (a few hundred thousand vectors, refreshed incrementally from the listings CDC topic) live in pgvector beside the listings table that marketplace search already queries — the pre-filters on region and GPU memory are ordinary SQL predicates, and hybrid search fuses pgvector similarity with Postgres full-text search. Internal-knowledge chunks for the AI interface (docs, runbooks, the semantic layer's metric definitions) live in LanceDB on object storage: low QPS, cheap, versioned per re-embedding, and readable directly by the evaluation notebooks. Both pipelines append to the lakehouse. The host-behavior embeddings for fraud-ring detection are computed weekly in batch and consumed as ordinary tabular features by the fraud model — they never see a vector index at all, because the consumer is a model, not a search box.

When to choose what

The vector-data heuristic
  • Do you have a similarity or retrieval problem? If the consumer is a tabular model, embeddings are features — store them as columns, no index needed.
  • Under a few million vectors, already on Postgres: pgvector. Embeddings as a versioned dataset, moderate QPS: Lance. Governed platform, SQL users: warehouse-native. You already run OpenSearch for search: its k-NN. Tens of millions of vectors at high QPS with tight recall targets: a dedicated store — and only then.
  • Always: model version on every row, history in the lakehouse, access class as a pre-filter, hybrid retrieval, a labeled eval set, and re-embedding as an index-version migration.
Optional: the embeddings answer at four levels
  • L1 · Foundational. "Embed everything, put it in a vector DB, query nearest neighbours"; no notion of model versioning or deletes.
  • L2 · Practitioner. Runs an incremental pipeline with metadata filters; knows chunking matters; picks a store by scale.
  • L3 · Senior. Versions the model with the vectors, treats re-embedding as a migration with an eval gate, does hybrid retrieval with pre-filters and access control, keeps history in the lakehouse, monitors query drift.
  • L4 · Staff. Says no to the vector database until there is a retrieval problem; designs the eval set and the cut-over process before the first index; can show the recall/latency/cost curve for each store option and explain why the fraud team's embeddings are features, not an index.
