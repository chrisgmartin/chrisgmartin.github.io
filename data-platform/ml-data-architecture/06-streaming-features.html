Section C · Moving & serving

Streaming Features & Real-Time Inference Data

The minority of features that must be seconds fresh, what it costs to compute them on a stream, how windows and watermarks keep them correct, and the discipline that stops your streaming features from disagreeing with the batch features the model trained on.

Which features actually need to stream

Streaming is the most over-prescribed component in ML data architecture. The reflex is "real-time inference needs real-time features", and it is wrong for most features: a ranking model scoring offers in 50 ms does not need host_reliability_7d recomputed since the last heartbeat — a value materialized an hour ago is indistinguishable from a live one. What it needs is fast reads, which is the online store's job (chapter 08), not a streaming pipeline's.

A feature earns a streaming pipeline when the value changes materially inside the batch interval and the model's decision depends on that change. At GridDP that is a short list: device/IP signup velocity in the last five minutes (fraud), live bid depth per GPU model (pricing), a host's last-heartbeat age (ranking's availability gate), and an account's actions in the current session (fraud, churn). Everything else — tenure, spend trends, benchmark scores, 30-day aggregates — is batch, and forcing it through Flink buys you cost and a second definition of the same feature to keep in sync.

The reframe

Freshness is a property of a feature, not of a system. Ask per feature: what is the cost of the model seeing a value that is N minutes stale? If the answer is "nothing" for N = 60, it is a batch feature served online. If the answer is "we approve a fraudulent signup" for N = 2, it streams.

Freshness SLAs, in numbers

Write the SLA down before choosing the engine, because the engine follows from it. Freshness is measured end to end — event occurs → feature value visible to the model — and it has three components: transport lag (producer to Kafka), compute lag (window close plus processing), and write lag (to the online store). A "sub-second feature" that sits behind a five-minute tumbling window is a five-minute feature.

Computing features on a stream

Three engine families cover nearly every streaming-feature pipeline. The choice is about state and latency, not brand.

  • Apache Flink. True event-at-a-time processing with keyed state, event-time windows, watermarks and exactly-once sinks. The right tool when latency is seconds, windows are sliding or session-shaped, and state (per-account counters, per-IP sets) must survive restarts. Flink SQL makes many feature definitions declarative.
  • Spark Structured Streaming. Micro-batches on a trigger; same API as the batch job, which is its superpower — the hourly feature and the two-minute feature can share code. Latency floors at the trigger interval; state handling is coarser than Flink's. The default in Stack B.
  • Kafka Streams / ksqlDB. Library-in-your-service model, no cluster to run. Good for a fraud service that owns its own velocity counters; awkward when the feature must also land in the lakehouse for training.

Managed offerings (Confluent Flink, Databricks streaming tables, Snowflake Dynamic Tables at minute lag, Tecton's streaming feature views) shift the operations, not the semantics. Whatever runs the job, the feature must be defined once — a name, an entity key, an aggregation over a window — and materialized to two places: the online store for inference and the offline store for training.

signup_velocity_5m.sql (Flink SQL)
-- Feature: signups from the same device fingerprint in the trailing 5 minutes.
-- Entity key: device_id. Event time from the producer, watermark tolerates 30s of lateness.
CREATE TABLE signup_events (
  device_id      STRING,
  account_id     STRING,
  ip_prefix      STRING,
  event_ts       TIMESTAMP(3),
  WATERMARK FOR event_ts AS event_ts - INTERVAL '30' SECOND
) WITH ('connector' = 'kafka', 'topic' = 'marketplace.signups', ...);

INSERT INTO online_features_signup_velocity   -- Redis sink, keyed by device_id, TTL 15m
SELECT
  device_id,
  COUNT(*)                        AS signups_5m,
  COUNT(DISTINCT ip_prefix)       AS distinct_ip_prefixes_5m,
  HOP_END(event_ts, INTERVAL '30' SECOND, INTERVAL '5' MINUTE) AS feature_ts
FROM signup_events
GROUP BY device_id,
         HOP(event_ts, INTERVAL '30' SECOND, INTERVAL '5' MINUTE);  -- sliding: 5m window, 30s slide

Windows, watermarks & late data

A streaming feature is an aggregate over a window, and every correctness question reduces to: which events are in the window, and when is the window's value final? Three window shapes cover the feature catalogue — tumbling (fixed, non-overlapping: bids per market per minute), sliding/hopping (overlapping: signups in the trailing 5 minutes, updated every 30 s), and session (gap-based: an account's actions until 20 minutes of silence). Sliding windows are the common choice for velocity features and the expensive one — each event lands in several windows, so state multiplies by window ÷ slide.

Event time versus processing time is the trap. The fraud feature must count signups by when they happened, not when the message reached the job — otherwise a Kafka partition that lags by two minutes makes a burst look spread out. Event-time processing needs a watermark: the job's declaration that "I have now seen everything up to time T, give or take my tolerance". Events arriving after the watermark passed their window are late, and the design decision is what to do with them: drop (simplest; fine for velocity counters where a 30-second-late event barely matters), update the emitted value (correct; requires the sink to accept upserts and consumers to tolerate change), or side-output to a reconciliation table (auditable; the batch path picks them up).

The watermark tolerance is a business decision

A 30-second watermark means a 5-minute feature is emitted ~30 seconds after the window closes. A 5-minute tolerance handles more late data and adds 5 minutes of latency to every value. There is no free setting — pick it from the producer's measured lateness distribution (p99 of event_ts vs arrival) and write it next to the feature definition, because the model's training data must be built with the same rule.

The online-store write path

Where the streamed value lands is half the design. The batch path materializes latest values into the online store on a schedule; the streaming job writes directly, continuously. The two paths meet in the same keyspace, which creates three rules:

  • Key by entity, version by time. Every write carries feature_ts. A slower batch materialization must not overwrite a fresher streamed value; compare timestamps on write (Redis Lua, DynamoDB condition expressions) or namespace the two paths and resolve at read.
  • TTL streamed features. A 5-minute velocity feature for a device that never signs up again should not live in Redis forever. Set TTLs to the window length plus margin; a missing key reads as zero, which is correct.
  • Dual-write to the offline store. The same job that writes Redis must append the emitted values (entity, feature_ts, value) to the lakehouse — Iceberg via Flink's sink, Delta via Structured Streaming — because that history is the only way to build a leakage-free training set for a streamed feature. Skip this and the feature is untrainable.

Stream–batch consistency: the second-definition problem

Here is the failure that actually ships. The training set for the fraud model is built in SQL over raw signup events, in batch, with a clean 5-minute window. The serving feature is computed in Flink, with a 30-second watermark, a hop of 30 seconds, and late events dropped. Same name, two definitions. Offline the feature is slightly "too complete" (it saw the late events); online it is slightly sparse. The model learns thresholds on the complete version and applies them to the sparse one. AUC drops from 0.94 offline to 0.85 in production, and nobody can find a bug because there isn't one — there are two correct implementations of different things.

Four ways out, in rising order of rigor:

  1. Log the served value. Have the inference service record the exact feature vector it scored; build the training set from those logs rather than recomputing. Cheapest fix, trains only on what the model would have seen, but you cannot backfill a new feature.
  2. One code path, two triggers. Structured Streaming lets the same query run as a micro-batch job and as a nightly batch over the lakehouse. Latency floors at the trigger, but the definition is shared.
  3. Replay the streaming job over history. Run the Flink job against the Kafka retention (or a lakehouse-backed replay) to produce the offline history with the exact same windowing and watermark. Needs long retention or Tiered Storage, and takes as long as the stream is long unless the job is parallelized.
  4. Reconcile continuously. Keep both paths but recompute the batch version of every streamed feature nightly, diff it against the streamed history, and alert on drift beyond a tolerance. This does not prevent the skew; it makes it visible within a day instead of at the next model review.
Say the number

"How do you guarantee the streaming feature matches training?" is the question that separates people who have run this from people who have read about it. The strong answer has a mechanism and a tolerance: "the serving path logs feature vectors, training reads those logs, and a nightly reconciliation recomputes the window from raw events and pages us if p99 disagreement exceeds 2%." Mechanism without tolerance is a hope; tolerance without mechanism is a dashboard.

Worked example: fraud velocity at GridDP

GridDP's fraud model scores every signup and every new listing. Its batch features (payment-method age, KYC outcome, chargeback history) come from the nightly materialization. Its two streamed features — signup_velocity_5m keyed by device fingerprint and listing_velocity_15m keyed by host — run in one Flink job reading the marketplace event topics with a 30-second watermark. The job writes Redis with a 15-minute TTL and appends to Iceberg. The nightly reconciliation recomputes both windows from the raw topic mirrored in the lake and diffs; tolerance is 2% at p99, and the one time it fired it caught a producer that had switched from event time to send time after a deploy.

Cost shape: the Flink job is two task managers and about 4 GB of keyed state; the Redis keyspace stays under a million entries because of the TTL; the Iceberg append is ~2 GB/day before compaction. The point is not that this is small — it is that it is small because only two features stream. The first design had eleven.

When to choose what

The streaming-feature heuristic
  • Default: batch-compute, materialize to the online store. Fast reads are not a streaming problem.
  • Stream only when a feature changes inside the batch interval and the decision depends on it. Write the freshness SLA in seconds next to the feature name.
  • Seconds and stateful: Flink (or a managed Flink). Minutes and shared code: Spark Structured Streaming micro-batches. Inside one service: Kafka Streams.
  • Always: event time with an explicit watermark; TTL the online keys; dual-write history to the offline store.
  • Consistency: log served feature vectors for training and reconcile nightly with a stated tolerance. Add replay when you need to backfill new streamed features.
Optional: the streaming-features answer at four levels
  • L1 · Foundational. "Real-time models need real-time features"; would stream everything; computes on processing time.
  • L2 · Practitioner. Separates fast reads from fresh values; uses event-time windows and knows what a watermark is; writes the online store from a streaming job.
  • L3 · Senior. Classifies features by freshness SLA and streams only the few that need it; picks the window shape and watermark from measured lateness; dual-writes history; has a concrete plan for stream–batch consistency.
  • L4 · Staff. Treats the second-definition problem as the central risk and designs around it (feature logging or shared code path), sets reconciliation tolerances, sizes state and TTLs, and can show the cost delta of moving a feature from hourly to seconds — and say no when the model gain doesn't cover it.
