Section B · The data

Storage for ML: Lakehouse, Formats & Dataset Versioning

Where training data actually lives, which file and table formats earn their keep for ML workloads, how to lay out object storage so GPUs don't starve, and the one rule that makes a model reproducible a year later: a dataset is an immutable artifact.

Why storage is an ML problem, not a storage problem

Analytics storage is judged on one axis: how cheaply can a query engine scan it. ML storage is judged on three. The training loop needs throughput — a GPU node reading Parquet at 200 MB/s will sit idle while the accelerator waits for the next batch. The feature pipeline needs time travel — "the value of host_reliability_7d as of March 1st" is a storage question before it is a join question. And the model needs reproducibility — six months after a fraud model ships, a regulator or an incident review will ask what rows it trained on, and "roughly the March extract" is not an answer.

The good news is that the lakehouse stack most platforms already run — columnar files on object storage, governed by a table format — gets you two of the three for free. This chapter is about the third axis, the places where ML diverges from analytics (unstructured data, tensor-shaped records, random-access reads), and the discipline of versioning that turns a pile of Parquet into a dataset.

The reframe

A table is a mutable thing that answers "what is true now". A dataset is an immutable thing that answers "what did the model see". The whole storage design for ML is about producing the second from the first — cheaply, repeatably, and with a name you can put in a model registry.

Table formats for ML: Parquet, Iceberg, Delta, Hudi

Start with the file layer. Parquet is the default for a reason: columnar, compressed, with per-row-group statistics so a reader can skip whole chunks. For tabular features — which is what ranking, fraud, churn, forecasting and pricing at GridDP all consume — nothing beats it for scan-heavy training reads. Its weaknesses show up at the edges: it is append-only at the file level (no in-place update), row-group granularity makes random access to a single record expensive, and it has no opinion about how many files make a table.

That last gap is what table formats fill. Iceberg, Delta Lake and Hudi all sit on top of Parquet and add a transaction log: which files belong to the table, what schema they carry, what snapshot they represent. For ML the three features that matter are snapshot isolation (a training job reads a consistent view while pipelines keep writing), time travel (query a past snapshot by ID or timestamp), and schema evolution (add a feature column without rewriting history).

The honest recommendation: pick the format your platform already governs with, and lean on its time travel for datasets. The mistake is not choosing "wrong" between these three; it is training from a table with no snapshot pinned at all, so that "the training set" silently changes every night the pipeline runs.

Snapshot expiry eats datasets

Every table format expires old snapshots to reclaim storage — Iceberg's expire_snapshots, Delta's VACUUM. Default retention is days, not years. A model registry that points at a snapshot the platform deleted in week two is a reproducibility promise you cannot keep. Either tag training snapshots (Iceberg branches/tags, Delta CLONE) or export the dataset to its own immutable location. Decide this before the first model ships, not at the first audit.

Tensors, images & text: when Parquet stops fitting

Tabular features are the easy case. The moment a model consumes images (a GPU benchmark screenshot classifier), long text (support-ticket embeddings), or pre-computed vectors, Parquet's row-group access pattern becomes a tax. A training loader wants to fetch row 4,183,022 and its 1,536-dimensional embedding in one seek; Parquet wants to hand you a 128 MB row group and let you find it.

Lance exists for exactly this. It is a columnar format with a fixed-size-list encoding for vectors, page-level random access, and a versioned dataset abstraction built in — you can append, add a column, and read any prior version without the table-format-on-top layer. LanceDB adds ANN indexes on the same files, which is why it shows up again in chapter 07. For multimodal training sets — image bytes alongside labels and metadata — the alternatives are WebDataset (tar shards streamed sequentially to GPU workers), TFRecord, or the "Parquet for metadata, object-store URIs for blobs" split.

Object-storage layout: feeding GPUs without starving them

S3, GCS and Azure Blob all have the same personality: high aggregate throughput, high per-request latency (tens of milliseconds), and a per-prefix request-rate ceiling. A training job that opens ten thousand 2 MB files will spend its life in request overhead; one that opens forty 512 MB files will saturate the network. The layout rules follow directly.

  • File size. Target 128–512 MB per Parquet file for training reads; compact small files produced by streaming writers before they reach a dataset. Table formats ship compaction jobs — schedule them.
  • Partitioning. Partition by what the training query filters on (usually event date and maybe entity type), never by high-cardinality keys. Over-partitioning recreates the small-file problem one directory at a time.
  • Sort within files. Sort by the entity key used in point-in-time joins (account_id, host_id) so row-group statistics prune, and so a loader reading one entity's history touches few pages.
  • Sharding for parallel loaders. A distributed training job with 8 workers wants at least 8×N roughly equal shards it can claim without coordination. WebDataset and Lance both make shard = file.
  • Locality and egress. Keep the dataset in the same region as the GPUs. Cross-region egress at training scale costs more than the storage; for a neocloud renting GPUs in several regions, replicate the dataset once per active region rather than pulling it per job.

Dataset versioning: the immutable-artifact rule

Here is the rule, and it is not negotiable for anything that ships: a model trains from a named, immutable dataset version, and the model registry records that name. Not "the features table", not "last night's run" — a version with a manifest. There are four ways to get there, and they differ mostly in where the version lives.

ApproachHow a version is expressedStrengthsWatch out for
Table-format snapshots (Iceberg tags/branches, Delta versions)Snapshot ID / version number on the governed tableZero copy, SQL-native, same access control as the tableRetention policy; snapshots on a hot table accumulate; cross-table consistency is on you
Exported dataset (copy to an immutable prefix)A prefix + manifest listing sources and snapshot IDsSurvives table churn, cheap to replicate to GPU regions, trivial to auditStorage cost per version; must record provenance in the manifest or it's just a copy
LakeFS (Git semantics over object storage)Branch / commit hash over the bucketAtomic multi-table commits, branches for experiments, zero-copyAnother service in the path of every read; teams must adopt the branch workflow

For a platform team the pragmatic pattern is the first two combined: pin snapshots for the point-in-time join, then export the joined, split training set to an immutable prefix with a manifest. The export is what the trainer reads (fast, sharded, regional) and what the registry names; the snapshot IDs in the manifest are what let you regenerate it if the export is ever lost.

Time-based splits, recorded in the manifest

Random splits leak for any problem with a time dimension — and at GridDP every problem has one. Split by time (train on January, validate on early February, test on late February) and write the boundaries into the manifest so nobody has to guess later whether validation rows post-date training rows. The manifest is also where the label delay lives: a fraud label confirmed 45 days after signup means the last 45 days of any window are unlabeled, and the split boundaries must respect that.

Worked example: GridDP's four models, four storage shapes

Map the storage decisions onto the models from the case study:

  • Ranking. Tabular features (DLPerf, reliability, price-vs-market) from Iceberg feature tables; nightly export of ~40 M offer-impression rows to a sharded Parquet dataset, sorted by offer_id. Snapshots tagged rank-train-2026-03-01 so the point-in-time join can be re-run.
  • Fraud. Smaller (a few million signups) but the manifest matters most here — a regulator may ask. Exported dataset with the label-delay window recorded; Iceberg snapshots retained 400 days on the feature tables that feed it.
  • Capacity forecasting. Trains on fct_telemetry_hourly — the firehose rolled up. This is the one place file layout dominates: partition by day, sort by (gpu_model, region, ts), compact to 256 MB files, and the forecaster reads two years of hourly rows in minutes instead of hours.
  • Dynamic pricing. Bid-event sequences as nested lists in Parquet, one row per market-hour, so a sequence model gets contiguous input. Lance for the market-state embeddings the pricing team experiments with, versioned in-format.

Four models, one governed lakehouse, one immutable-dataset bucket, one manifest schema. The variety is in the file layout, not in the process.

When to choose what

The storage-for-ML heuristic
  • Tabular features, any scale: Parquet under whichever table format your platform governs. Use its time travel; tag the snapshots you train on.
  • Vectors or random-access records: Lance. Parquet if you must, with fixed-size lists and an external index.
  • Images, audio, documents: blobs in object storage, a governed manifest table of URIs, WebDataset shards for the trainer.
  • Reproducibility bar is "audit": export each training set to an immutable prefix with a provenance manifest; do not rely on snapshot retention alone.
  • Several teams need atomic multi-table versions and branch-style experiments: LakeFS. Otherwise it is one more system to run.
  • GPUs in more than one region: replicate the dataset per version, never per job.

The mature answer names the seam: "Features live in Iceberg with SCD2 history and long snapshot retention; a training set is a point-in-time join pinned to snapshot IDs, exported as sharded Parquet to an immutable bucket with a manifest, and the manifest's version string is what the model registry records." Everything in the next nine chapters assumes that sentence.

Optional: the storage answer at four levels
  • L1 · Foundational. Knows training data is Parquet on S3; trains from "the features table" as it exists today; splits randomly.
  • L2 · Practitioner. Uses a table format and can query a past snapshot; splits by time; knows small files hurt throughput and compacts them.
  • L3 · Senior. Exports named, immutable dataset versions with a provenance manifest; records label delay and split boundaries; lays out files and partitions for the trainer's access pattern; picks Lance/WebDataset for non-tabular data.
  • L4 · Staff. Treats dataset versioning as a platform contract — registry names a dataset version, snapshot retention is set per table class, regional replication is part of the dataset lifecycle — and can explain the cost/reproducibility trade-off of each versioning approach to a finance partner and a regulator in the same meeting.
