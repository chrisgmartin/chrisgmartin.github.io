Section E · Putting it together

Reference Design for GridDP, Anti-patterns & Outlook

The capstone: the entire GridDP ML data plane on one canvas, one fraud decision traced from a payment event to a served score and back into a training row, the stack defended layer by layer, the team, the roadmap, the capacity math — then the mistakes that sink these systems and where the field is going.

The plane, in one breath

We began with the lifecycle and its two-speed problem: an offline path that must be correct and reproducible, an online path that must be fast and fresh, and the requirement that the two agree. We built training sets as point-in-time-correct, snapshot-pinned artifacts; treated labels as delayed, versioned data with their own pipelines; put a feature store — registry, offline history, online latest — at the centre; chose open formats with snapshots as the substrate; added a streaming lane for the few features that need seconds; gave embeddings the same discipline as tabular features; assembled serving so the model sees one feature vector regardless of path; made lineage the connective tissue; and wrapped it in quality, governance, and cost discipline. Chapter 13 settled the shape: lakehouse-centric with a streaming lane. This chapter draws it.

Read it as three horizontal bands. The analytics platform (left-centre) is the DPE guide's design and is the ML plane's upstream — every feature is derived from silver/gold or from the same Kafka topics. The ML data plane (centre-right) is this guide: registry, two stores, streaming lane, builder, training, model registry. The cross-cutting rail (bottom) — lineage, monitoring, governance, orchestration — wraps every box. The two structural decisions, visible as shapes: the streaming lane is a narrow lane for six features, not a second platform; and the served-feature log flows back into the lake, closing the loop that makes skew checks, audits and the next training set possible.

One fraud decision, end to end

Account acct_7a adds a new payment method and attempts a $1,800 reserved rental. Follow the data:

  1. T0 — events. payment_method.added and rental.requested land on Kafka; the payments webhook delivers the vendor's tokenized card reference and risk score.
  2. T0 + 200 ms — streaming features. Flink updates device_velocity_24h (3 → 4 accounts on this device fingerprint), ip_velocity_1h, and payment_method_age_d (0.0) in Redis, and appends the same values with event time to the lake.
  3. T0 + 250 ms — inference. The fraud service assembles the vector: streaming features from Redis; batch features (chargebacks_90d, kyc_outcome, acct_tenure_d) from Redis, materialized hourly from the offline store; two on-demand features computed from request context. Schema-validated by the Pandera contract. Model fraud_v22 scores 0.83 → review. The full vector, score, model version and request ID go to the served-feature log.
  4. T0 + 1 h — batch. The hourly Dagster run recomputes account aggregates from silver, materializes to Redis, and appends history to the offline store. Freshness and volume monitors pass; PSI on device_velocity_24h is 0.08.
  5. T0 + 1 d — skew check. The daily job recomputes yesterday's served vectors from the offline store: 99.4% match; the mismatch is entirely ip_velocity_1h late-arriving events, within the 2% SLO.
  6. T0 + 45 d — label. A chargeback arrives via the payments webhook → label_fraud_30d = 1 for the prediction at T0, written by the label pipeline with its own event time.
  7. T0 + 60 d — training. The monthly builder assembles the fraud training set: labels joined point-in-time to feature history (only values known at T0), consent and jurisdiction filters applied, the deletion list honoured, contract validated, dataset card written, shards streamed to the GPU region. fraud_v23 trains at 84% GPU utilization, is registered with its dataset snapshot and drift baseline, passes champion/challenger on matured labels, and deploys.
  8. T0 + 60 d + audit. A regulator asks why acct_7a was sent to review. The decision log returns the exact vector and model version; lineage walks each feature to its source columns; the dataset card for fraud_v22 shows the consent policy it was trained under. One query each.

Stack choices, defended

LayerChoiceWhy (and what we rejected)
Feature historyIceberg on S3 (the analytics lakehouse)One source of truth shared with analytics; snapshots give free dataset versioning. Rejected: a separate ML lake (two truths), warehouse-only (cost per experiment, poor dataloader).
Batch featuresdbt on Spark/Trino, incrementalSame tooling as the marts, same tests, same lineage. Rejected: notebook pipelines (no contracts).
Streaming featuresFlink, one job, six featuresOnly where seconds pay: pricing and fraud. Rejected: streaming everything (always-on cost, ops load).

Online storeRedis in the inference regionSingle-key reads at ≤ 5 ms; TTL per feature. Rejected: reading the lake online; cross-region KV.
Training dataSnapshot-pinned, sharded MDS/Parquet in the GPU regionStreams straight to the trainer, resumable on preemption. Rejected: warehouse queries per epoch.
Experiment / model registryMLflowDataset snapshot ↔ model version link; model cards. Rejected: spreadsheets, which is what "we'll add it later" means.
VectorsLance tables in the lake + a small serving indexEmbeddings governed like features. Rejected: a standalone vector DB as source of truth.
Lineage / catalogDataHub (Stack A) / Unity (Stack B)Column → feature → dataset → model → endpoint, both directions. Rejected: none — this is non-negotiable.
OrchestrationDagsterAsset-aware: features, datasets and retrains are assets with freshness policies. Airflow acceptable.

The team that runs it

The plane at GridDP scale is run by a small team with sharp boundaries. An ML platform engineer (one, later two) owns the registry, the stores, the builder, the loading path and the monitors — they are the DPE of the ML plane and sit with the data platform team. Data scientists / ML engineers (five-ish) own feature definitions, labels and models for their domain, and consume the platform through the registry and the builder; they never write to the online store directly. The data platform team owns everything upstream — silver, gold, Kafka, ClickHouse — and the contracts the ML plane depends on. Trust & safety and finance own label semantics (what counts as fraud, what counts as churn) and sign the model cards for their models. The failure mode to design against is the ML engineer who, under deadline, builds a private feature pipeline in a notebook; the platform's job is to make the registry path faster than the shortcut.

Sequence by risk, not by ambition

Reproducible training sets before a feature store; a feature store before streaming; monitoring before every one of them. Teams that start with the streaming lane end up with real-time features feeding a model nobody can retrain.

Capacity & cost math

Order-of-magnitude sizing for the plane described, at 17,000 GPUs, 200k accounts, five production models:

  • Offline store: ~40 tier-1 features × hourly grain × (17k GPUs + 200k accounts + 60k offers) ≈ 2.4B feature-rows/year ≈ 0.9 TB/year in Iceberg; 3-year retention ≈ 3 TB warm.
  • Online store: ~280k entities × ~40 features × ~80 bytes ≈ 1 GB; a small Redis with replicas. Peak reads: ranking at ~2k req/s × 20 features = 40k key reads/s — pipeline them, 5 ms budget.
  • Streaming lane: ~30M events/day on the relevant topics; one Flink job, 8–12 task slots, ~50 GB state; always-on cost ≈ $1.5–2.5k/month.
  • Training: monthly retrains of five models + experiments ≈ 900 GPU-hours/month at ≥ 80% utilization; datasets replicated once per version to the GPU region (~2 TB/month egress ≈ $150).
  • Served-feature log: ~5M predictions/day × ~2 KB ≈ 10 GB/day ≈ 3.6 TB/year; warm for 90 days, cool thereafter, decision records for money models archived five years.
  • Total ML data plane run-rate: roughly $8–12k/month excluding GPU time, dominated by the streaming lane and materialization compute; the GPU line is 3–4× that and is where the optimisation effort belongs.

Anti-patterns

  • The notebook feature pipeline. A feature computed in a notebook for training and re-implemented in a service for serving. The whole guide is the antidote.
  • Training on "now." Joining current feature values to historical labels. Every offline metric is a lie until the join is point-in-time.
  • The warehouse dataloader. Querying the warehouse per epoch. Pay once, write shards.
  • Streaming everything. An always-on Flink job for a churn feature that changes weekly.
  • A model with no baseline. If you did not record the training distribution, you cannot detect drift; you are waiting for a complaint.
  • The unowned label. Nobody can say precisely what "fraud" means in the label table, so the model learns the label pipeline's bugs.
  • Vector DB as source of truth. Embeddings that cannot be regenerated because the text was deleted and the model version was not recorded.
  • Deletion that stops at the tables. Erasure that never reaches the feature store, the served log, the vector index or the snapshots.
  • Two truths. A separate "ML lake" that drifts from the analytics lake until the churn feature and the churn dashboard disagree in a board meeting.
  • Unmeasured GPUs. Training jobs at 35% utilization for a year because nobody plotted dataloader wait time.

Where this is heading

Lakehouse-native ML. The gap between "the lake" and "the ML plane" is closing: table formats are growing vector and tensor types, catalogs are absorbing the feature and model registries, and the training-set builder is becoming a catalog operation rather than a separate tool. Expect the W-vs-L distinction to blur as warehouses adopt open formats and lakehouses adopt warehouse ergonomics.

Real-time by default, priced honestly. Streaming engines are getting cheaper to operate (serverless Flink, RisingWave, Materialize-style incremental views), so the "S lane" widens — but the discipline of asking which features actually pay for seconds will matter more, not less, as the default gets easier.

LLM and RAG data. The same architecture applies to retrieval corpora: chunk pipelines are feature pipelines, embeddings are features with a model version, retrieval logs are served-feature logs, and eval sets are training sets with point-in-time discipline. The teams treating RAG data as a side project are rebuilding this guide badly; the ones treating it as ML data are reusing it.

Agents as consumers and producers. Agentic systems will both consume the plane (feature and metric lookups as tools, governed by the same registry ACLs) and produce data for it (action logs, tool-call traces as training signal). The decision log becomes the central artifact — for audit, for training, and for the next generation of models learning from the last generation's decisions.

The constant through all of it is the thesis of this guide: a model is only as good as the data plane's ability to say, for any prediction, exactly what the model saw, why it was allowed to see it, and how to see it again.
