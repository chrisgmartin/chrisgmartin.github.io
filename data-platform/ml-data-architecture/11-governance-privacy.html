Section D · Operating it

Governance, Privacy & Compliance for ML Data

A model is a derived dataset that has been compressed into weights — every governance obligation on the data follows it there. This chapter is what that means in practice: which data may train which model, how you honour a deletion request against something you can't delete from, who may read what, and how you prove all of it to an auditor.

Why models change the rules

Governance on an analytics platform is about tables: who can read them, how long they are kept, which columns are sensitive. Governance for ML has to cover two more things. The first is derived artifacts: a training set is a copy of governed data, a feature table is a transformation of it, a model is a lossy compression of it, and each of those inherits the obligations of its source. The second is purpose: the same rental history that is legitimately used for billing may not be legitimately used to train a model that prices a customer differently, depending on what that customer consented to and what the regulator thinks a marketplace may do.

The practical consequence is that the ML data plane needs the same four instruments the rest of the platform has — classification, access control, lineage, and retention — applied one level further, to datasets, features, and models. The bad version of this chapter is a compliance checklist. The good version is a set of structural decisions that make the compliant thing the default thing.

The reframe

Think of a trained model as a materialized view over its training set with an unknown refresh function. Anything you would have to do to a materialized view when its source changes — rebuild it, restrict it, retire it — you have to be able to do to the model. Design the plane so those operations exist.

PII in training data

Start from classification, because nothing else works without it. Every column in silver and every feature in the registry carries a sensitivity tag — public, internal, confidential, pii, pii-special (financial account numbers, government IDs, KYC documents). Tags are set at the source contract and propagate through lineage, so a feature derived from a PII column is PII until someone explicitly declassifies it with a justification.

Then apply minimization at the feature boundary. Models rarely need the raw identifier; they need a signal derived from it. The pattern that keeps most training sets clean:

Two enforcement points make this real. The feature registry refuses to register a feature whose source columns are tagged pii-special unless a declassification review is attached. And the training-set builder refuses to run if any selected feature carries a tag above the model's approved tier. Both are simple policy checks against metadata you already have; they turn a memo into a build failure.

Embeddings are PII if the text was

An embedding of a support ticket that contains a name and an address is a transformation of PII, not an anonymization of it — inversion and membership-inference attacks are real. Redact before embedding, tag the vector table with the highest tag of its inputs, and put it under the same retention as the source text.

Consent & purpose limitation

GDPR, CCPA/CPRA, and most modern regimes tie data use to a purpose. Billing a rental is one purpose; training a dynamic-pricing model that may charge that customer more is a different one, and "improving our services" in a privacy policy does not automatically cover it. The engineering translation: consent is a feature of the entity, stored and versioned like any other, and it is a filter in every training-set builder.

training_set_builder.sql
-- Purpose-limited training set: only accounts whose consent state, AS OF the prediction time,
-- permitted use of their data for this model's registered purpose.
WITH consent_asof AS (
  SELECT l.account_id, l.prediction_ts, c.allows_model_training, c.jurisdiction
  FROM ml.churn_labels l
  ASOF JOIN silver.account_consent_history c
    MATCH_CONDITION (l.prediction_ts >= c.valid_from) ON l.account_id = c.account_id
)
SELECT ...
FROM consent_asof
WHERE allows_model_training = TRUE
  AND jurisdiction NOT IN (SELECT jurisdiction FROM policy.model_training_exclusions
                           WHERE model_purpose = 'churn_prediction');
-- The builder records: purpose, consent version, exclusion list version → model registry metadata.

Notice the join is point-in-time, like every other join in this guide. A customer who withdrew consent last week still legitimately appears in a training row from last year — the question is what was permitted then. And the builder records the consent-policy version it applied, so the model card can state exactly which population the model was allowed to learn from.

Retention & the deletion problem

A deletion request (GDPR Art. 17, CCPA deletion) is straightforward against tables: delete the rows, propagate through the lineage graph, expire the snapshots that still contain them. Against a model it is not: the account's data has been folded into weights and cannot be surgically removed. Machine unlearning exists as a research field and is not something you should promise a regulator. What you can do is architectural:

  • Bounded retention on training data. Training sets and feature history are kept for a declared window (say 24 months for behavioural features, 90 days for raw events). Every model trained on data past its window is retrained or retired. This bounds the exposure of any individual's data in any model.
  • Deletion propagates to derived sets on a clock. The deletion job removes the entity from silver, feature tables, the offline store, the online store, the served-feature log, and the vector store — then expires lakehouse snapshots older than the deletion so time travel cannot resurrect it. Iceberg and Delta both support this; you must actually schedule expire_snapshots or the data is still there.
  • Retrain cadence as the deletion SLA. If the fraud model is retrained monthly on a rolling window, an account deleted today is absent from every model within a month. Write that cadence down as the SLA and monitor it.
  • Exclusion lists for the interim. Between deletion and the next retrain, the entity is on a hard exclusion list at inference — no predictions are made about it and no features are read for it.
Lakehouse time travel is a liability here

The same snapshot history that gives you reproducible training sets (chapter 05) keeps deleted people alive. Pair every deletion job with a snapshot-expiry policy and a check that no pinned training snapshot older than the retention window is still referenced by a registered model. The tension between reproducibility and erasure is resolved by retention windows, not by hoping.

Access tiers & isolation

Access for ML follows the medallion tiers with two additions. Data scientists read gold and the feature store freely, silver with justification, bronze almost never — raw events are where the unredacted PII lives. The additions are per-feature access in the registry (a feature tagged pii is visible in the catalog to everyone but readable only by approved models and roles) and tenant isolation, which matters at GridDP because providers are businesses whose fleet telemetry is commercially sensitive.

Column masking and row-level security are catalog features in all three reference stacks (Unity Catalog, Snowflake Horizon, Polaris/Nessie + engine policies); the ML-specific work is making the feature registry and the model registry enforce the same tags rather than merely display them.

Audit for models

The auditor's questions are always the same four: what data trained this model, was that data permitted, who can read the outputs, and can you reproduce the decision it made for this person on this date. Answering them from memory is not an option; answer them from artifacts the platform produces automatically:

  • Dataset card — generated by the training-set builder: source tables and snapshot IDs, feature list with sensitivity tags, consent-policy version, row count, class balance, retention window, builder commit hash.
  • Model card — from the registry: dataset card reference, training code version, evaluation metrics by segment, intended purpose, approved tier, known limitations, the drift baseline.
  • Lineage — the graph from source column to feature to dataset to model to serving endpoint (chapter 09), queryable both ways: "which models used kyc_outcome?" and "what fed ranking_v14?".
  • Decision log — the served-feature log plus the prediction, request ID, model version and timestamp, retained for the regulatory window (five years for financial decisions is common). This is what lets you explain a specific fraud decline.

When these are produced by the pipeline rather than written by hand, an audit is a query. When they are not, an audit is a month.

Differential privacy & synthetic data, practically

Two techniques get invoked as magic words; both are useful in narrow places. Differential privacy adds calibrated noise so that any single individual's presence in a dataset has a bounded effect on the output. It is excellent for released aggregates — GridDP publishing regional utilization statistics to providers, or an internal dashboard exposed widely — and workable for training via DP-SGD when the model is small and the accuracy cost (which can be large) is acceptable. It is not something to bolt onto the ranking model to satisfy a policy; the utility loss on a high-cardinality tabular model is usually unacceptable, and a mis-set epsilon provides no real guarantee.

Synthetic data — generated to match the statistics of a real dataset — earns its keep for development environments (engineers build pipelines against realistic data without PII access), for sharing with vendors, and for augmenting rare classes. It does not earn its keep as a privacy substitute for training on the real thing: a generator overfit to a small population can reproduce real records. Rule of thumb: synthetic for non-production and for augmentation; real, minimized, purpose-checked data for the production model.

GridDP: KYC, crypto rails & payouts

GridDP's specifics sharpen every point above. KYC data — identity documents, vendor decisions — is pii-special; only the vendor outcome and score enter the platform, and the fraud model's dataset card must show it trained on outcomes, never documents. Crypto rails bring the Travel Rule and sanctions screening: wallet addresses are tokenized, screening results are features, and the transaction-monitoring model's decision log is retained for the AML window (five years) and queryable by transaction — that log is a regulatory record, not an ML convenience. Provider payouts make the fleet-telemetry isolation rule concrete: a capacity-forecasting feature like region_free_gpu_hours_7d is fine; a feature that reveals one identifiable provider's utilization to another is a commercial breach, so cross-provider features aggregate to at least k=5 hosts.

And the deletion story: an account requests erasure. The job removes it from silver and gold, the feature store (both stores), the served-feature log, the ticket-embedding vector store, and expires older snapshots; the account goes on the inference exclusion list; the next monthly retrain of churn, ranking and fraud drops it from the weights. Ledger entries and AML records are retained under the legal-hold exception and documented as such. The dataset cards for the next models show the deletion-list version they honoured.

When to choose what

The governance-for-ML heuristic
  • Always: sensitivity tags on every column and feature, propagated by lineage; minimize at the feature boundary; a retention window on training data with a retrain cadence that doubles as the deletion SLA; dataset and model cards generated by the pipeline.
  • When a model affects money or access (fraud, pricing, KYC): purpose-limited builders with consent as a point-in-time feature; a decision log retained for the regulatory window; feature-level ACLs enforced by the registry.
  • When you share data or aggregates externally: differential privacy on the aggregates; synthetic data for vendors and dev environments.
  • When someone proposes unlearning: say no; bound retention and retrain instead.
  • Multi-tenant supply data: row-level security on the owning entity and k-anonymity on cross-tenant features.
The answer at four levels
  • L1 · Foundational. Knows PII shouldn't be in training data; would drop obvious columns; treats deletion as a table operation.
  • L2 · Practitioner. Classifies columns, masks PII in silver, derives features instead of using raw identifiers, keeps a model registry with basic metadata, knows deletion must reach the feature store.
  • L3 · Senior. Propagates tags through lineage into the feature and model registries and enforces them at build time; purpose-limits training sets with point-in-time consent; bounds retention and ties deletion to retrain cadence with interim exclusion lists; expires lakehouse snapshots; generates dataset/model cards and a decision log; applies row-level isolation to tenant data.
  • L4 · Staff. Designs the plane so compliance is a build failure rather than a review — the registry, the builder and the deletion job share one policy engine; knows where DP and synthetic data genuinely help and where they are theatre; resolves the reproducibility-vs-erasure tension with explicit retention windows; can walk an auditor from a single fraud decline back to the source columns and consent version in one query.
