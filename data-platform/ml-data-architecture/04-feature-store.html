Section B · The data

Feature Engineering at Scale & the Feature Store

What a feature store actually is — a registry, an offline store and an online store bound by one definition — how entities, keys, point-in-time retrieval, backfills and on-demand features work, which products do what, and the honest answer to whether you need one at all.

Why feature stores exist

By the time GridDP had four models, it had four copies of host_reliability_7d: a dbt model for the forecaster, a pandas function in the ranking notebook, a Flink job for fraud, and a hand-written SQL string in the pricing service. They disagreed on the window boundary, on whether preempted rentals counted, and on what to do when a host had no rentals. Every model was trained on one definition and served with another. That is the problem a feature store solves, and it is worth being precise about how: a feature store is a registry of feature definitions, plus an offline store that keeps their history, plus an online store that keeps their latest values, with the guarantee that all three are produced from the same definition. Everything else — UIs, SDKs, monitoring — is convenience.

The reframe

A feature store is not a database. It is a contract enforcement mechanism: define once, compute from one source of truth, serve twice. If you have that contract without the product, you have a feature store. If you have the product without the contract (definitions duplicated outside it), you don't.

Entities, keys and feature views

Features attach to entities — the things you make predictions about — via a key. GridDP's entities are host, machine, gpu_model × region, account, payment, listing, and composite ones like (account, gpu_model). Get the entity model wrong and everything downstream fights it: a feature keyed on machine_id cannot be served for a listing until you know the mapping at request time, and that mapping had better be in the online store too.

A feature view (Feast's term; Tecton says feature view, Hopsworks says feature group, Databricks says feature table) groups features that share an entity, a source and a cadence — host_reliability_features holding host_reliability_7d, host_preempt_rate_30d, host_uptime_90d. Views are the unit of materialisation and of ownership. Keep them cohesive: one view per (entity, source, cadence), not one giant view per model.

feature view — Feast-style definition
host = Entity(name="host", join_keys=["host_id"])

host_reliability = FeatureView(
    name="host_reliability_features",
    entities=[host],
    ttl=timedelta(days=2),                     # online value older than this → null, not stale
    schema=[Field("host_reliability_7d", Float32),
            Field("host_preempt_rate_30d", Float32),
            Field("host_uptime_90d", Float32)],
    source=BatchSource(table="gold.host_reliability_daily",
                       timestamp_field="valid_from",      # availability time (ch. 02)
                       created_timestamp_column="materialized_at"),
    owner="supply-ml@griddp", tags={"tier": "1"},
)

# training:  fs.get_historical_features(entity_df=spine, features=[...])   → point-in-time join
# serving:   fs.get_online_features(entity_rows=[{"host_id": "h_9b2"}], features=[...])

The ttl line is doing quiet, important work: it defines how stale a served value may be before the store returns null rather than a value from three days ago. Pick it per view from the feature's cadence plus tolerance — and make sure the model's null handling is deliberate (ch. 08).

Point-in-time retrieval and backfills

The offline store is interval-keyed: each row is (entity, valid_from, values…), and valid_to is implied by the next row. get_historical_features is the ASOF join of chapter 02, executed by the store against a spine you provide. Two operations keep the history correct:

  • Backfill — computing a new or changed feature for the past, so models can train on it. A backfill must produce values as they would have been computed at each historical time, which means running the definition over historical source snapshots, not over today's tables. For definitions with late-arriving data, the backfilled value can legitimately differ from what was served at the time; record materialized_at so the training join can choose. Backfills are the most expensive operation in the store — a 7-day window over 18 months of the telemetry rollups is a full-table scan per day of history — so they are batched, incremental (only the changed feature), and scheduled off-peak.
  • Materialisation — pushing the latest offline values into the online store. Batch features materialise on the pipeline's cadence; the interval between the offline value existing and the online store having it is exactly the availability gap from chapter 02, so the store must record when each key was written.
Changing a definition changes history

Editing host_reliability_7d to exclude maintenance windows is a new version, not an edit. Old training sets reference version 2; new ones version 3; the offline store keeps both (or the backfill writes version 3 to a new column/view). Silently rewriting history invalidates every model trained on it and every skew comparison against it.

Streaming and on-demand features

Batch views cover anything with a daily-or-hourly cadence. Two other kinds cover the rest:

Streaming features are where a store proves its worth or its cost. The definition must be executable by both a batch engine (for backfills and training) and a stream engine (for serving). Products that own the transformation (Tecton, Hopsworks, Databricks with Spark Structured Streaming) can compile one definition to both; a registry-only product (Feast) leaves that consistency to you.

Worked example: GridDP's feature inventory

After consolidating the four copies, GridDP's registry has eleven feature views across six entities; roughly 60% of feature usage comes from four views (host_reliability_features, account_activity_features, market_depth_features, telemetry_rollup_features) — the reuse that justified the store. On Stack A: definitions in a feature_repo/ Git repo (Feast), batch views materialised by dbt + Dagster into Iceberg and pushed to DynamoDB hourly, three streaming views written by Flink to DynamoDB and appended to Iceberg, on-demand features as registered Python functions used by both the fraud API and the dataset builder. Online p99 is 6 ms for a 30-feature vector across three views; the fraud request budget is 100 ms, so 6 is comfortable. The costliest line item is not the store — it is the monthly backfill when a definition changes, which reads 14 TB of rollups. That number drove the partition layout in chapter 05.

When you need a feature store — and when you don't

The feature-store decision heuristic
  • You don't need one when: all models are batch-scored, features are computed by the same dbt models that produce the training data, and there is no online path. Versioned tables + a point-in-time SQL join + a YAML doc of definitions is the store. Don't add a platform to a problem you don't have.
  • You need the contract (Feast or built) when: one request-path model consumes batch features — the materialisation-to-KV step and the TTL semantics are where hand-rolled code goes wrong.
  • You need a product that owns computation (Tecton / Hopsworks / Databricks) when: streaming or on-demand features must be consistent across training and serving, more than two teams share features, or freshness SLAs are contractual. The consistency guarantee is what you are buying.
  • Stay inside the warehouse (Snowflake / Databricks native) when: you are already there and online latency budgets are lenient (> 50 ms) — governance and lineage come free.

The mature answer names the flip condition: "Today we have one nightly model; dbt tables and an ASOF join are the feature store. The day fraud needs acct_payment_velocity_1h in the request path, I introduce a registry and an online store — and if a second streaming feature follows, I'd rather buy the stream-batch consistency than build it."

Optional: the feature-store answer at four levels
  • L1 · Foundational. "A database of features"; features computed in the API and in notebooks separately; no history.
  • L2 · Practitioner. Uses Feast or a vendor; knows offline vs online; materialises batch features; hasn't thought about availability time or TTL semantics.
  • L3 · Senior. Registry as source of truth with owners and versions; interval-keyed offline history with materialized_at; TTLs per view; streaming views written to both stores; backfills as versioned, incremental jobs.
  • L4 · Staff. Chooses build vs buy on the consistency guarantee and team shape, not on features; designs the entity model first; treats definition changes as versioned events; can size backfill cost and online p99 from the feature inventory.
