The ML Data Lifecycle & Where It Breaks

The eight stages data passes through on its way to and from a model, the two speeds they run at, the roles that own them, and the specific place in each stage where production ML quietly goes wrong.

Eight stages, one loop

Analytics data has a direction: sources flow into a warehouse and out to dashboards. ML data has a loop, and the loop is why it needs its own architecture. Here are the stages, in the order data meets them at GridDP, with the artifact each one produces. Every later chapter is about one or two of these boxes.

Two things to notice. First, stages 1–5 are batch-shaped — they care about throughput and correctness across history — while stage 6 is request-shaped — it cares about milliseconds and freshness. Second, stage 8 closes the loop back to stage 1, which is the difference between a data pipeline and a control system. A model that ranks listings changes which listings get clicked, which changes the clicks that train the next ranker. Ignore the loop and you will train on your own predictions.

The two-speed problem

The defining architectural tension is that the same feature must exist at two speeds. Take bid_depth_5m — the number of interruptible bids on a GPU class in the last five minutes, used by both the pricing model and the fraud model.

DimensionOffline (training)Online (inference)
QuestionWhat was bid_depth_5m for every (GPU class, timestamp) in the last 18 months?What is bid_depth_5m for H100-80GB right now?
ShapeHundreds of millions of rows, window-aggregated over a history tableOne key lookup
Latency budgetMinutes to hours< 10 ms for the lookup, so the whole request stays < 100 ms
FreshnessWhatever the batch cadence is — the value as of each historical timestampSeconds — computed from the live bid stream
Computed bySQL / Spark window over fct_bid_eventFlink job keyed by GPU class, sliding window
Stored inLakehouse (Iceberg / Delta), full historyRedis / DynamoDB, latest value with a TTL

Two engines, two stores, two codepaths — and the model was trained on the left column and is served from the right. If the SQL window counts bids with status IN ('open','matched') and the Flink job counts only 'open', the model sees a systematically different world in production than it was trained on. That is training/serving skew, and it is invisible in every offline metric. Every architecture in this guide is, in part, a strategy for collapsing the two columns into one definition. Chapters 04 and 06 are the mechanics.

The skew you can't see

Skew never fails loudly. The API returns valid floats, the model returns valid scores, and precision drifts down 4 points over a quarter. The only defence is measurement: log the served feature vector alongside the prediction, replay the offline pipeline for the same entities and timestamps, and compare. Chapter 10 builds that comparison; chapter 08 explains why you must log the vector, not recompute it.

Who owns which stage

ML data architecture fails at seams between teams as often as at seams between systems. A workable division at a company of GridDP's size (tens to low hundreds of internal data users):

RoleOwnsTheir contract with the rest
Data platform engineeringCollect, the lakehouse, CDC/streaming, storage, governance, the feature store infrastructureFreshness and quality SLOs on silver/gold tables; the registry, offline/online stores and their SLAs
ML platform engineeringFeature pipeline framework, training-data assembly, registry, serving infrastructure, monitoring"Define a feature here and it will be served consistently"; reproducible training datasets
Data scientists / ML engineersFeature definitions, labels, models, evaluationFeatures registered with owner, entity, TTL, tests; labels documented with their delay
Product / domain teamsSource events and their schemas (data contracts)Don't change an event's meaning without a version bump; the ranker depends on it

The failure pattern is when the middle row is missing: data scientists each build their own feature pipelines from raw tables, the platform team has no idea what depends on fct_rental, and the first schema change breaks three models. The feature registry (ch. 04) is as much an organisational device as a technical one — it is the place where a feature acquires an owner.

Where each stage breaks

Each stage has a characteristic failure. Knowing them lets you diagnose a "the model is wrong" report in minutes instead of days, because you know which stage to interrogate first.

Worked example: the fraud model's first outage

Six weeks after GridDP's fraud model ships, chargebacks on approved payments double. The model's offline metrics are unchanged. The on-call ML engineer walks the stages:

  1. Collect. Volume and schema monitors on payments are green. The upstream payments provider did, however, start returning card_bin as an integer instead of a zero-padded string on 1 September.
  2. Features. bin_country is derived from a lookup on card_bin. Offline, the batch pipeline casts to string and pads — the lookup still works. Online, the Flink enrichment does a raw string match on "0412…" vs 412… — the lookup misses and the feature is served as null, which the model's imputer turns into "unknown country", a low-risk bucket.
  3. Serve. The null-rate on bin_country went from 0.3% to 41% on 1 September. There was no alert, because the null-rate monitor watched the offline table, which was fine.

Nothing about the model was wrong. The feature had two implementations (two-speed problem), the upstream contract changed (collect), and monitoring watched the wrong side of the seam (observe). Three chapters of this guide exist because of exactly this story.

The reframe

"The model is wrong" is almost never a modeling statement. It is a hypothesis to be falsified stage by stage, starting from the seams: offline vs online, then vs now, features vs labels. Build the plane so those comparisons are cheap.

When to choose what

How much of this plane do you need?
  • One batch model, scored nightly (capacity forecasting alone): you need stages 1–5 and 7. No online store, no streaming. A lakehouse, point-in-time-correct SQL, versioned datasets and a drift check are enough. Don't buy a feature store yet.
  • A request-path model with batch features (ranking with daily-refreshed features): add stage 6 with a materialised online store. Batch → KV sync is the whole "streaming" story.
  • A request-path model with fresh features (fraud with velocity features, pricing): now you need the streaming path, a registry that enforces one definition across engines, and skew monitoring. This is where a feature store earns its keep.
  • Several models sharing features across teams: the registry becomes organisational infrastructure; invest in discovery, ownership and tests (ch. 04, 09).
Optional: the lifecycle answer at four levels
  • L1 · Foundational. Describes ML data as "collect, clean, train, deploy"; doesn't distinguish offline from online; would recompute features in the API.
  • L2 · Practitioner. Names the offline/online split and training/serving skew; has hit leakage once; monitors model metrics but not feature distributions.
  • L3 · Senior. Walks the eight stages with the characteristic failure of each; designs the seams to be measurable (served-vector logging, replay); assigns ownership per stage.
  • L4 · Staff. Treats the loop as a control system — feedback, survivorship bias, exploration traffic — and sizes how much of the plane a given product needs, with the flip conditions for adding streaming and a registry.
