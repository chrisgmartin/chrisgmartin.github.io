Section B · Design & Orchestration

Orchestration

The layer that turns a pile of scripts into a system — scheduling, dependency resolution, retries, and backfills — worked through Airflow, then placed against the wider tool landscape.

What an orchestrator gives you

An orchestrator is not a compute engine and it's not a cron replacement — though people misuse it as both. It's the thing that runs your DAG (from Chapter 02) reliably. Concretely, it earns its keep by giving you:

  • Scheduling — run this graph on a cadence, or when an upstream dataset updates.
  • Dependency resolution — walk the DAG in topological order; run a task only once its upstreams succeed.
  • Retries & backoff — automatically re-run a failed task N times with increasing delay, so transient failures self-heal (which only works if the task is idempotent).
  • Backfill & catchup — run history: fill in the last 90 days of partitions on demand, or catch up runs missed while the scheduler was down.
  • Sensors / triggers — wait for an external condition (a file lands, a partition is ready, an API is healthy) before proceeding.
  • SLAs & observability — alert when a task misses its deadline; surface run history, logs, and durations.
  • Parameterization — bind each run to its data interval so tasks are functions of a date, not of "now."

That last point is the throughline from Chapter 02: the orchestrator's most valuable habit is handing every task the data interval it's responsible for, which is exactly what makes idempotent, backfillable pipelines possible.

Airflow, worked

Airflow is the default in most shops (and the one this company runs alongside dbt), so it's worth being fluent. A DAG is a Python file that declares tasks and their dependencies; the scheduler executes them. The modern idiom is TaskFlow — plain Python functions decorated into tasks, with return values passed as dependencies via XCom.

Here's a small, idempotent, backfill-safe DAG that waits for a source partition, then loads it — using the partition-overwrite pattern from Chapter 02:

orders_dag.py
from datetime import datetime
import pendulum
from airflow.decorators import dag, task
from airflow.sensors.external_task import ExternalTaskSensor

@dag(
    schedule="0 2 * * *",                     # daily at 02:00
    start_date=datetime(2026, 1, 1),
    catchup=False,                            # don't auto-run all history on deploy
    max_active_runs=1,                        # serialize runs so partitions don't race
    default_args={"retries": 3, "retry_exponential_backoff": True},
    tags=["orders", "elt"],
)
def orders_pipeline():

    # Deferrable sensor: releases the worker slot while waiting (no worker starvation).
    wait_for_raw = ExternalTaskSensor(
        task_id="wait_for_raw_orders",
        external_dag_id="ingest_raw_orders",
        deferrable=True,                      # async: frees the slot until the trigger fires
        timeout=60 * 60,
        poke_interval=120,
    )

    @task
    def load_partition(data_interval_start=None) -> int:
        # Parameterize on the RUN'S data interval, never on wall-clock "now".
        order_date = data_interval_start.date()
        # Idempotent: this run OWNS order_date's partition and overwrites it.
        return load_orders_partition(order_date)   # delete-then-insert in a txn

    @task
    def run_dbt_marts(rows_loaded: int) -> None:
        run_dbt(select="marts.orders+", vars={"min_rows": rows_loaded})

    wait_for_raw >> run_dbt_marts(load_partition())

orders_pipeline()

The pieces worth being able to explain out loud:

  • Data interval, not execution_date. Airflow schedules on interval end: the 02:00 run on the 11th processes the interval that ended then. Binding load_partition to data_interval_start is what makes it a pure function of a date — re-runnable and backfillable.
  • Deferrable sensor. A classic sensor occupies a worker slot the entire time it polls; a hundred of them can starve the pool. The deferrable=True / async version hands the wait to a lightweight triggerer and releases the slot — the standard fix for sensor starvation, and a sharp thing to name.
  • XCom for control flow, not data. Passing rows_loaded between tasks is fine; XCom has a small size limit (backed by the metadata DB), so never push a dataframe through it — pass a pointer (a path, a partition id) and let the task read the data itself.
  • Idempotent tasks + retries. retries=3 with exponential backoff only heals you because load_partition overwrites its partition. Retries on a non-idempotent append would multiply the damage.
  • Dynamic task mapping (not shown) lets you fan a task out over a runtime-determined list — e.g. one load task per source region — without hand-writing each one.

Scheduling correctness

Scheduling is where subtle, expensive bugs live, and interviewers probe it precisely because it separates people who've operated pipelines from people who've only written them.

  • The interval-end execution model. A daily DAG doesn't run "on" a day — it runs after the day's interval closes, to process the data that accumulated. Confusing the logical date with the wall-clock run time is the root of a whole class of off-by-one partition bugs.
  • Timezones & DST. Schedule in an explicit timezone (or UTC) and know what happens across daylight-saving transitions — a naive local schedule can skip or double a run twice a year. Pin it deliberately.
  • Late & missed runs. If the scheduler is down, what happens when it recovers? With catchup=True it replays every missed interval; with catchup=False it runs only the latest. Both are correct answers — for different pipelines. Choosing consciously is the signal.
Time-based deps are a smell

"Run B at 03:00 because A usually finishes by 02:45" is a race waiting to happen. Depend on the data — a sensor on A's output partition, or data-aware scheduling — not on a hopeful clock offset. If A runs long one night, a time-based B reads a half-built table and silently produces wrong numbers.

Catchup & backfill

The reason to invest in idempotent, interval-parameterized tasks is that it makes backfill trivial: to rebuild history, you just run the same task across a range of past intervals, each owning and overwriting its partition. No special code path.

  • Catchup is automatic history-filling by the scheduler between start_date and now. Leave it off (catchup=False) on deploy unless you actually want the whole backlog to fire — a surprise catchup storm is a common self-inflicted outage.
  • Backfill is a deliberate re-run of a date range (fixed a bug, or a source restated history). Because each run overwrites its partition, a backfill converges to the correct state with no double-counting.
  • Guardrails. Cap concurrency (max_active_runs, pools) so a 200-day backfill doesn't saturate the warehouse, and be aware that a backfill run and a scheduled run touching the same partition must be serialized. Backfills interact heavily with incremental logic and late data — the full treatment is Chapter 05.

Task-centric vs asset-centric

Chapter 02 introduced the two ways to express a DAG; orchestration is where the choice bites. Task-centric orchestration (classic Airflow) schedules operations — you tell it what to run and wire the edges. Asset-centric orchestration (Dagster's software-defined assets, dbt's model graph) schedules data artifacts — you declare the tables and their dependencies, and the framework derives the graph, tracks staleness, and knows lineage natively.

Airflow has met this world halfway with Datasets (data-aware scheduling): a DAG can be triggered by "dataset X was updated" instead of a clock, so downstream pipelines fire when their inputs are actually ready rather than on a hopeful schedule. That's the task-orchestrator borrowing the best idea from the asset-orchestrators. In an interview, being able to say "I'd move the cross-DAG dependency from a sensor to a dataset trigger" is a concrete maturity signal.

The reframe

Asset-centric orchestration matches ELT's grain: your dbt ref() graph already is the dependency DAG, so declaring assets removes a whole layer of hand-wired tasks and makes "is this table stale?" a first-class question. Task-centric orchestration is more flexible for arbitrary operations (a task that isn't a table — an API call, a training job). Most mature stacks end up asset-aware for the warehouse and task-based at the edges.

The tool landscape

Be tool-agnostic first, then place the tools. The honest summary: they differ mostly in what they treat as the primitive (task, asset, or durable workflow) and in developer ergonomics — not in whether they can schedule a DAG.

Antipatterns

Orchestration traps that read as junior
  • The giant monolithic DAG. One 400-task DAG for the whole warehouse — impossible to reason about, backfill, or own. Split by domain and wire with datasets.
  • Business logic inside operators. SQL and transformation logic buried in Python operators instead of version-controlled dbt/SQL. The orchestrator should invoke logic, not contain it.
  • Non-idempotent tasks. Tasks that append or depend on "now," so a retry corrupts state. Retries and backfills then become dangerous instead of routine.
  • Heavy work in top-level DAG code. Queries or API calls at module scope run on every scheduler parse (every few seconds), hammering sources and slowing the scheduler. Keep the top level cheap; do work inside tasks.
  • Time-based deps instead of data deps. "Run at 03:00, A's usually done" — replace with a sensor or dataset trigger on A's output.
  • Using the orchestrator as a compute engine. Pulling a million rows into the worker to transform in pandas. Push the compute to the warehouse/Spark; the orchestrator coordinates, it doesn't crunch.

Leveling ladder

Orchestration maturity is a clean ladder, and it's one interviewers climb quickly once they find your ceiling. Here's how the same "schedule the orders pipeline" answer grows.

LevelWhat you'd say / doWhat it signals
L1 · Foundational"A cron job runs the load script nightly. If it fails, someone re-runs it in the morning."Knows something schedules the work, but no dependency, retry, or recovery model.
L2 · Practitioner"An Airflow DAG with explicit task dependencies, retries with backoff, and idempotent tasks parameterized on the data interval, so retries and re-runs are safe."Uses the orchestrator correctly — dependencies, retries, idempotency by default.
L3 · Senior"Data-aware dependencies (sensors/datasets) instead of time offsets, deferrable sensors to avoid worker starvation, SLAs and alerting, and backfill-safe design so restating history is a routine re-run."Owns reliability and correctness of the schedule; designs for failure and backfill.
L4 · Staff"DAGs decomposed by domain with clear ownership, asset-centric lineage across teams, dataset-triggered handoffs between ingestion and dbt, pools/concurrency as cost controls, and orchestration standards other teams build on."Architects the orchestration layer across teams — lineage, ownership, cost, standards.
Level up

The rung interviewers reward most is L2 → L3: replacing time-based dependencies with data-aware ones. "I wouldn't run the marts at 03:00 hoping ingest finished — I'd trigger them off the dataset so they build when raw actually lands." That one move kills a whole class of silent-wrong-data bugs and shows you've operated pipelines, not just authored them.
