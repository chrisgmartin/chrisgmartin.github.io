Section C · The Hard Parts

Reconciliation & Validation

How you prove the numbers are right — source-to-target reconciliation, layered testing, data contracts, and the Write-Audit-Publish machinery that stops a bad batch before anyone sees it.

Reconciliation vs validation

This is one of the three named topics on the loop, and it's the one candidates hand-wave most. "I'd add some data quality checks" is a fail. The interviewer wants to know exactly what you'd check, how you'd stop a bad load, and how you'd prove to a finance stakeholder that the warehouse agrees with the system of record. Two distinct disciplines sit underneath that, and conflating them is the first mistake:

  • Validation asks "is this data well-formed and plausible on its own terms?" — no nulls in the primary key, amounts non-negative, status in an allowed set, row counts within a normal band. It's intrinsic. You can run it knowing nothing about any other system.
  • Reconciliation asks "does this data agree with the source of truth?" — does sum(amount) in the warehouse match the payments provider's daily settlement total, row for row, penny for penny. It's relational. It needs a second, trusted reference to compare against.

A dataset can pass every validation test and still be wrong: dropped ten thousand rows on ingest, all of them individually valid. Only reconciliation catches that. Conversely, reconciliation totals can tie out while individual rows are garbage (two errors that cancel). You need both, and you need to say so out loud.

The reframe that lands

Validation protects you from malformed data; reconciliation protects you from missing or duplicated data. Tests assert what each row should look like. Reconciliation asserts that the set is complete. In a financial pipeline the second is the one that gets people fired — lead with it.

The six data-quality dimensions

When an interviewer asks "how would you think about data quality here?", a vocabulary beats a list of ad-hoc checks. The standard six dimensions give you a checklist you can walk without missing a class of defect:

DimensionQuestion it answersTypical check
CompletenessIs anything missing?Row-count recon vs source; not_null on required columns; no missing partitions/days.
UniquenessAre there dupes?Unique/primary-key test on the grain; no duplicate natural keys after merge.
ValidityIs it well-formed?Type, range, regex, accepted_values, referential shape (status in a known set).
AccuracyDoes it match reality?Reconciliation against the system of record; control totals; hash-diff.
ConsistencyDoes it agree with itself & related tables?Referential integrity (relationships tests), debits = credits, fact rows point to real dims.
TimelinessIs it fresh enough?Freshness SLA — max(loaded_at) within threshold; partition for today exists by 6am.

Map each dimension to a concrete mechanism and you've turned "data quality" from a buzzword into an audit. Note that accuracy is the only one you generally can't test in isolation — it's where reconciliation lives. Timeliness ties directly into the freshness SLIs in Chapter 07.

Source-to-target reconciliation

Reconciliation is a comparison between two independent counts of the same thing. The design questions are: what do you compare, at what grain, how often, and with what tolerance.

  • Row counts — cheapest signal. Count source rows by day vs target rows by day. Catches wholesale drops and duplications.
  • Control totals / aggregate recon — sum a monetary or quantity column on both sides (sum(amount), count(distinct order_id)). Catches partial loss that row counts miss (right number of rows, wrong values).
  • Checksums / hash-diff — hash each row's business columns, aggregate the hashes per partition (e.g. sum(hash) or a bit-xor), and compare. Detects any field-level drift without shipping the full dataset across systems — the workhorse for column-level correctness at scale.
  • Financial reconciliation — the strict form: internal consistency (sum(debits) = sum(credits)) and external tie-out (warehouse settlement total = provider's reported total). Tolerance here is often exactly zero.

Sampling vs full, cadence, tolerance

Full reconciliation compares every partition; it's authoritative but can be expensive to pull from an OLTP source. Sampling (recon a random subset of days, or a statistical sample of keys) is a cheaper continuous signal with a periodic full recon as backstop. Cadence follows the money: financial pipelines reconcile every load and often re-reconcile a trailing window (late data mutates prior days — see Chapter 04); softer analytics can reconcile daily or weekly. Tolerance thresholds encode how exact the domain demands: revenue is usually a hard = 0 break; a distribution metric might tolerate ±0.5%. Set them explicitly per metric — an implicit tolerance of "looks about right" is not reconciliation.

Here's a recon query that compares source and target by day, computes absolute and relative variance, and flags anything outside tolerance. This is the kind of thing you'd whiteboard and then productionize as an audit table or a dbt test:

recon_orders_by_day.sql
-- Source-to-target reconciliation for the orders pipeline, by event date.
-- Compares row counts AND a monetary control total, and flags breaks
-- that exceed a per-metric tolerance. Runs after each load; a non-empty
-- result set with status='BREAK' is the circuit-breaker signal.

with source as (
    select
        order_date,
        count(*)                          as src_rows,
        count(distinct order_id)          as src_orders,
        sum(amount_cents)                 as src_amount_cents
    from raw.orders_source          -- e.g. a Fivetran/CDC landing of the OLTP table
    where order_date >= current_date - interval '7 days'   -- trailing recon window
    group by order_date
),

target as (
    select
        order_date,
        count(*)                          as tgt_rows,
        count(distinct order_id)          as tgt_orders,
        sum(amount_cents)                 as tgt_amount_cents
    from analytics.fct_orders
    where order_date >= current_date - interval '7 days'
    group by order_date
),

recon as (
    select
        coalesce(s.order_date, t.order_date)                        as order_date,
        s.src_rows,   t.tgt_rows,
        s.src_amount_cents, t.tgt_amount_cents,
        coalesce(t.tgt_rows,0)         - coalesce(s.src_rows,0)     as row_diff,
        coalesce(t.tgt_amount_cents,0) - coalesce(s.src_amount_cents,0) as amount_diff_cents,
        -- relative variance guards against divide-by-zero on empty days
        case when coalesce(s.src_amount_cents,0) = 0 then 0
             else abs(coalesce(t.tgt_amount_cents,0) - s.src_amount_cents)
                  / s.src_amount_cents::float
        end                                                          as amount_rel_var
    from source s
    full outer join target t on s.order_date = t.order_date
)

select
    order_date,
    src_rows, tgt_rows, row_diff,
    src_amount_cents, tgt_amount_cents, amount_diff_cents, amount_rel_var,
    case
        when row_diff <> 0            then 'BREAK'   -- counts must match exactly
        when amount_diff_cents <> 0    then 'BREAK'  -- money: zero tolerance
        else 'OK'
    end as status
from recon
where row_diff <> 0 or amount_diff_cents <> 0    -- only surface breaks
order by order_date;

Break investigation

A break is the start of an investigation, not the end. The disciplined path: (1) localize — which day, which metric, which direction (target high ⇒ duplication; target low ⇒ drops)? (2) bisect the pipeline — re-run the same recon at each stage (raw vs staging vs mart) to find the layer where the variance appears. (3) classify — is it a genuine data loss, a late-arriving-data timing artifact (source moved after your snapshot), a dedup bug, or a definitional mismatch (source counts refunds, target doesn't)? Timing artifacts are the most common false alarm, which is exactly why you recon a trailing window and re-check rather than paging on a single-run diff.

Testing layers

Reconciliation is one layer. Around it sits a stack of tests, cheapest and most local first. Name the layers as a pyramid — it shows you know where each tool earns its place:

LayerWhat it checksTooling
Schema / constraintsTypes, nullability, PK/FK at the warehouse levelDDL constraints, contract enforcement at ingest
Generic column testsnot_null, unique, accepted_values, relationshipsdbt generic tests, dbt_utils
Singular / expectation testsBespoke business rules, distribution & shapedbt singular tests, dbt_expectations, Great Expectations, Soda, Deequ
Unit testsTransformation logic against fixed input/expected rowsdbt unit tests, pytest on Python transforms
ReconciliationSet completeness & accuracy vs source of truthRecon queries, audit tables (above)
Contract testsProducer schema/semantics haven't broken consumersSchema registry, dbt contracts, CI checks

dbt tests come in two flavors. Generic tests are reusable and attach to columns in YAML; singular tests are a hand-written SQL query in tests/ that must return zero rows to pass. Packages extend the vocabulary: dbt_utils adds unique_combination_of_columns, recency, equal_rowcount; dbt_expectations ports Great Expectations' assertions (value ranges, distributions, regex, column types) into dbt. Here's a schema.yml showing generic tests plus dbt_expectations for shape, and a custom generic test you'd define once and reuse:

models/marts/fct_orders.yml
version: 2

models:
  - name: fct_orders
    description: One row per order at order grain.
    # A model-level contract: enforced at build time, not just tested after.
    config:
      contract:
        enforced: true
    columns:
      - name: order_id
        data_type: varchar
        constraints:
          - type: not_null
          - type: primary_key
        data_tests:
          - unique
          - not_null
      - name: amount_cents
        data_type: integer
        data_tests:
          - not_null
          # bespoke assertion from dbt_expectations: no negative money
          - dbt_expectations.expect_column_values_to_be_between:
              min_value: 0
              strictly: false
      - name: status
        data_type: varchar
        data_tests:
          - accepted_values:
              values: ['pending', 'paid', 'refunded', 'cancelled']
      - name: customer_id
        data_tests:
          # relationships = referential integrity to the dimension
          - relationships:
              to: ref('dim_customers')
              field: customer_id
    # model-level test: row volume shouldn't collapse or explode run-to-run
    data_tests:
      - dbt_expectations.expect_table_row_count_to_be_between:
          min_value: 1000
          max_value: 5000000
      # custom generic test defined below, reused here
      - reconciles_to_source:
          source_relation: source('oltp', 'orders')
          measure: amount_cents
          tolerance: 0

with target as (
    select sum({{ measure }}) as target_total
    from {{ model }}
),
source as (
    select sum({{ measure }}) as source_total
    from {{ source_relation }}
)
select
    source_total,
    target_total,
    abs(target_total - source_total) as variance
from target
cross join source
where abs(target_total - source_total) > {{ tolerance }}

{% endtest %}

dbt unit tests (GA in dbt 1.8+) are different in kind: they feed fixed mock input rows into a model's SQL and assert exact output rows, so you can test transformation logic — a tricky window function, a fiscal-week bucketing, a dedup rule — in CI without real data. Use them for the gnarly logic; use data tests for the runtime data. Outside dbt, Great Expectations (expectation suites + data docs), Soda (SodaCL checks, good for warehouse-native monitoring), and Deequ (Spark/Scala, constraint suggestion + verification at big-data scale) cover the same ideas for non-dbt or lakehouse stacks. Contract tests sit at the boundary and are the subject of the next section.

Data contracts

A data contract is an explicit, versioned agreement between a data producer and its consumers. It's the L4 move: instead of downstream teams reverse-engineering your table and silently breaking when you rename a column, the interface is declared and enforced. A real contract covers three things, not just schema:

  • Schema — column names, types, nullability, the grain, the primary key. The part everyone remembers.
  • Semantics — what the columns mean. Is amount gross or net? Cents or dollars? Does status='refunded' mean fully or partially? Allowed value sets, units, and definitions live here — this is where most "the data is wrong" incidents actually originate.
  • SLA — freshness (updated by 6am daily), completeness (≥ 99.9% of source rows), availability, and a deprecation/change policy (N days' notice, versioned rollout).

The contract is only real if it's enforced in two places: at CI, so a producer's PR that breaks the schema fails before merge (dbt's contract: enforced: true does exactly this — the build errors if the model's output diverges from the declared columns/types); and at ingest, so a producer emitting malformed events is rejected or quarantined at the door rather than corrupting the warehouse. A schema registry (Confluent, or JSON-Schema/Protobuf checks) enforces the event side; dbt contracts and CI enforce the transform side.

Say this in the room

"I'd publish a data contract — schema, semantics, and a freshness SLA — and enforce it both in CI on the producer's PR and at ingest, so a breaking change fails fast instead of showing up as a silent reconciliation break three days later." That one sentence signals staff-level thinking: you're designing the interface between teams, not just a table.

Write-Audit-Publish & circuit breakers

Tests that run after you've already overwritten the production table are a smoke alarm that goes off after the house is ash. The fix is to make validation a gate, not a report. Write-Audit-Publish (WAP) is the canonical pattern:

  1. Write — build the new data into a staging location (a temp/branch table, a separate partition, or an Iceberg/Delta branch) that consumers can't see.
  2. Audit — run all validation and reconciliation checks against the staged data.
  3. Publish — only if the audit passes, atomically swap the staged data into production (partition swap, ALTER TABLE ... SWAP, view repoint, or Iceberg branch fast-forward). If it fails, the swap never happens; production keeps serving the last-known-good data.

The publish step must be atomic — an all-or-nothing pointer flip — so consumers never see a half-written table. The check that decides whether to publish is the circuit breaker: a failed critical check halts promotion. Here it is as an Airflow flow; the shape is identical whether you orchestrate it in Airflow, Dagster, or a dbt build gate:

dags/orders_wap.py
from airflow.decorators import dag, task
from airflow.exceptions import AirflowFailException
from datetime import datetime

@dag(schedule="@daily", start_date=datetime(2026, 1, 1), catchup=False)
def orders_wap():

    @task
    def write_staging(ds=None):
        # Build into an isolated staging table consumers cannot read.
        run_sql(f"""
            create or replace table analytics.stg_fct_orders as
            select * from transform.fct_orders_build where order_date = '{ds}'
        """)

    @task
    def audit(ds=None):
        # 1) intrinsic validation, 2) source-to-target reconciliation.
        breaks = run_sql(f"""
            with recon as ( {RECON_ORDERS_BY_DAY} )     -- the query from earlier
            select * from recon where status = 'BREAK'
        """)
        null_keys = run_sql(
            "select count(*) from analytics.stg_fct_orders where order_id is null"
        )[0][0]

        if breaks or null_keys > 0:
            # Circuit breaker: raise, so publish never runs. Prod stays on
            # last-known-good; page on-call with the specific break rows.
            raise AirflowFailException(
                f"AUDIT FAILED: {len(breaks)} recon breaks, {null_keys} null keys"
            )

    @task
    def publish(ds=None):
        # Atomic swap -- consumers flip from old to new in one transaction.
        run_sql("""
            alter table analytics.fct_orders swap with analytics.stg_fct_orders
        """)

    write_staging() >> audit() >> publish()

orders_wap()

The equivalent in dbt is dbt build (which interleaves tests with model runs) plus a staging schema and a swap, or dbt Cloud's WAP-style deferral; on a lakehouse you'd stage on an Iceberg/Delta branch and fast-forward only on green. The pattern is what matters: nothing reaches consumers until it has passed audit.

Anomaly detection & the alert-vs-block trap

Explicit tests catch defects you thought to write a rule for. Anomaly detection catches the ones you didn't — by learning the normal behavior of a dataset and flagging deviation across four axes (the observability pillars, expanded in Chapter 07):

  • Volume — today's row count vs the trailing average / a control chart. Sudden 40% drop = upstream problem.
  • Freshness — how long since the table last updated vs its normal cadence.
  • Distribution — mean, null rate, cardinality, category mix drifting from history (a currency column that's suddenly 30% null).
  • Schema drift — a column added, dropped, or retyped upstream without notice.

Managed tools (Monte Carlo, Bigeye, Metaplane, Soda) do this out of the box; you can roll your own with control charts (flag > 3σ from a trailing window) stored in an audit table. The judgment call is what to do when something fires — and this is where candidates walk into a trap:

Trap: blocking on everything is as bad as blocking on nothing

If you block the pipeline on every check — including soft anomaly signals and non-critical columns — you'll halt production on a legitimate Black Friday volume spike or a noisy distribution wobble, erode trust, and train everyone to bypass the gate. If you only alert and never block, bad data reaches finance and the alert drowns in a channel no one reads. The answer is a severity tier, decided per check in advance: hard correctness checks (PK uniqueness, row-count/monetary reconciliation, not-null on keys) block via the WAP circuit breaker; soft plausibility signals (a 3σ volume blip, a distribution nudge) alert a human without halting. Wire the wrong check to the wrong action and you've either got a pipeline that cries wolf or one that ships corruption — name this trade-off explicitly and the interviewer knows you've run this in production.

SignalActionWhy
PK not unique; reconciliation break on moneyBlock (fail the WAP audit)Certain corruption; cost of shipping it > cost of delay.
not_null on a required key failsBlockBreaks downstream joins; unambiguously wrong.
Row volume 3σ above trailing meanAlert, don't blockOften a real event (promo, holiday); a human decides.
Null rate on a non-critical column ticks upAlert / warn severityWorth watching; not worth halting the business on.
New column appears upstream (schema drift)Alert + quarantine-on-ingest if contract-enforcedInvestigate; may be a breaking contract change.

dbt encodes this directly with test severity: error (block) vs severity: warn (surface but pass), and error_if/warn_if thresholds — the mechanism for the tiering above.

Quarantine, audit tables & dashboards

When validation finds bad rows mid-stream, you have a choice: fail the whole batch, or quarantine the offenders and let the good rows through. For high-volume ingestion, all-or-nothing is often too brittle — one malformed event shouldn't block a million good ones. The pattern is a dead-letter table (or dead-letter queue for streaming): route rows that fail validation into a side table with the failure reason and raw payload, publish the clean rows, and alert on the quarantine rate. Bad rows are preserved for investigation and replay after the upstream fix, rather than silently dropped.

quarantine_split.sql
-- Split a staged batch into clean rows (published) and bad rows
-- (dead-lettered with a reason) instead of failing the whole load.

insert into analytics.dead_letter_orders
select
    *,
    case
        when order_id is null            then 'null_order_id'
        when amount_cents < 0            then 'negative_amount'
        when status not in ('pending','paid','refunded','cancelled')
                                          then 'invalid_status'
    end                                   as reject_reason,
    current_timestamp                     as quarantined_at
from staging.orders_raw
where order_id is null
   or amount_cents < 0
   or status not in ('pending','paid','refunded','cancelled');

-- only the clean remainder proceeds to publish
insert into analytics.stg_fct_orders
select * from staging.orders_raw
where order_id is not null
  and amount_cents >= 0
  and status in ('pending','paid','refunded','cancelled');

Underpinning all of this are audit tables: a persistent log of every recon run — date, metric, source total, target total, variance, status, run id. They give you three things: an evidence trail a finance auditor can inspect, a time series to detect slow drift, and the raw data for reconciliation dashboards (green/red per feed per day, trending break rate, quarantine volume, freshness). A quarantine rate that's climbing over a week is a leading indicator of an upstream contract erosion you'd otherwise only catch when a total finally breaks. The dashboard is also your fastest answer to the stakeholder question that ends every one of these interviews: "how do you know the numbers are right?" — you point at the audit table.

The leveling ladder

Reconciliation & validation is a topic where the level gap is stark: L1 writes two dbt tests; L4 runs an org-wide contract-and-anomaly regime. Narrate the climb and you demonstrate three rungs in one answer.

LevelWhat you'd say / doWhat it signals
L1 · Foundational"I'd add not_null and unique tests on the primary key, and accepted_values on status." Knows dbt generic tests exist and runs them after the load.Knows validation vocabulary; catches malformed rows but not missing ones.
L2 · Practitioner"Plus a daily row-count and sum reconciliation against source with a tolerance, and a freshness check. Critical checks block the pipeline; I set test severity so soft signals only warn."Reconciles for completeness, thinks about timeliness, and knows the alert-vs-block distinction.
L3 · Senior"I'd wrap the build in Write-Audit-Publish with an atomic swap so a failed audit never reaches consumers, add tolerance thresholds per metric, publish a data contract, and quarantine bad rows to a dead-letter table instead of failing the batch."Makes validation a gate, owns the producer/consumer interface, designs for partial failure.
L4 · Staff"Org-wide: contracts enforced in CI and at ingest, anomaly detection on volume/freshness/distribution/schema, freshness & completeness SLAs with error budgets, audit tables + recon dashboards as the evidence trail, and automated break triage that localizes the failing layer before paging."Architects correctness as a platform capability across teams, with SLAs and automated diagnosis.
Level up

The jump from L2 to L3 is the single highest-value move in this topic: it's the shift from checking data after you've published it to gating publication on the checks (WAP + circuit breaker). Everything L4 adds — contracts, anomaly detection, SLAs — assumes that gate already exists. If you only level up one rung in the room, make it this one.
