Reliability & Observability

The difference between a pipeline that works on your laptop and one you can be paged for at 3am: delivery guarantees you can defend, failure that stays contained, and observability that tells you something broke before a consumer does.

Delivery semantics & effectively-once

Every hop in a pipeline — producer to queue, queue to consumer, consumer to warehouse — makes one of three promises about how many times a record is delivered. Interviewers use this vocabulary as a proxy for whether you actually understand distributed failure, so be precise.

GuaranteeWhat it meansFailure behaviorWhen it's acceptable
At-most-onceDeliver, don't retry. Ack before processing.Crash mid-process ⇒ record is lost.Lossy metrics, sampled telemetry — where a dropped row doesn't matter.
At-least-onceRetry until acked. Ack after processing.Crash after work, before ack ⇒ record is reprocessed ⇒ duplicates.The pragmatic default. Almost every durable pipeline.
Exactly-onceEach record affects the result once, no loss, no dup.Requires coordinated state (transactions, offsets, dedup).Rare end-to-end; expensive. Real inside one closed system (e.g. Flink→Kafka).

True end-to-end exactly-once across independent systems is mostly a myth — you can't atomically commit "I read this Kafka offset" and "I wrote this warehouse row" across two systems that don't share a transaction. What you can build, and what senior engineers actually say, is effectively-once: at-least-once delivery plus idempotent processing plus dedup. You accept that records may arrive twice; you make the second arrival a no-op.

The reframe that matters

Don't chase exactly-once delivery. Engineer at-least-once + idempotency so duplicates are harmless. This is the same property that makes a pipeline safe to re-run and safe to backfill — see idempotency & determinism in Chapter 02 and the incremental merge in Chapter 05. Reliability is idempotency wearing a different hat.

Idempotency keys & atomic swaps

Idempotency needs a key: a stable identifier that lets you recognize "I have already applied this." It should come from the data or the request, never from now() or a random UUID generated at processing time — those change on every retry and defeat the whole point.

idempotent_merge.sql
-- At-least-once delivery + a natural idempotency key (order_id) + a
-- source sequence (updated_at). Re-running with duplicate rows is a no-op,
-- and stale duplicates never clobber newer state.
MERGE INTO analytics.orders AS tgt
USING (
    SELECT order_id, status, amount_cents, updated_at,
           ROW_NUMBER() OVER (
               PARTITION BY order_id ORDER BY updated_at DESC
           ) AS rn
    FROM staging.orders_incoming        -- may contain dupes from retries
) AS src
ON tgt.order_id = src.order_id AND src.rn = 1
WHEN MATCHED AND src.updated_at > tgt.updated_at THEN UPDATE SET
    status = src.status, amount_cents = src.amount_cents,
    updated_at = src.updated_at
WHEN NOT MATCHED AND src.rn = 1 THEN INSERT
    (order_id, status, amount_cents, updated_at)
    VALUES (src.order_id, src.status, src.amount_cents, src.updated_at);

For file- and partition-based systems, the reliability primitive is the atomic swap: never mutate the live table in place. Write the new partition or table to a side location, validate it, then flip a pointer in a single metadata operation. Readers see either the old version or the new version, never a half-written one. This is exactly the Write-Audit-Publish flow from Chapter 06, and it's why table formats like Iceberg and Delta (Chapter 08) matter — the commit that swaps the manifest is atomic.

Say this in the room

"My write is a swap, not an update. I stage, validate, then atomically publish — so a crash mid-write leaves the live table untouched and the retry is clean." That one sentence signals you've operated pipelines, not just built them.

The dual-write problem & the outbox

Here's the trap that separates L2 from L4. Your service updates its own database and needs to emit an event ("order placed") so the pipeline picks it up. The naive code does both:

the_bug.py
# DUAL-WRITE BUG: two systems, no shared transaction.
def place_order(order):
    db.insert(order)              # commit #1: Postgres
    kafka.produce("orders", order)  # commit #2: Kafka
    # Crash between the two lines -> DB has the order, Kafka never
    # heard about it. Or Kafka succeeds and the DB txn rolls back ->
    # a phantom event for an order that doesn't exist. Silently wrong.

You cannot make two independent systems commit atomically. The fix is the transactional outbox: write the event into an outbox table in the same local transaction as the business change. Now there's one commit, so the state and the intent-to-publish succeed or fail together. A separate relay process (or log-based CDC — Chapter 05) reads the outbox and publishes downstream, marking rows sent.

outbox.sql
-- 1. One local transaction writes BOTH the state change and the event.
BEGIN;
  INSERT INTO orders (order_id, status, amount_cents)
  VALUES ('ord_123', 'placed', 4200);

  INSERT INTO outbox (event_id, aggregate_id, event_type, payload, created_at)
  VALUES (gen_random_uuid(), 'ord_123', 'order.placed',
          '{"order_id":"ord_123","amount_cents":4200}', now());
COMMIT;

-- 2. A relay (or Debezium CDC on the outbox table) publishes unsent rows,
--    at-least-once, then marks them. event_id is the idempotency key so
--    consumers dedup a re-published event safely.
SELECT event_id, event_type, payload
FROM   outbox
WHERE  published_at IS NULL
ORDER  BY created_at
LIMIT  500;
-- ...publish to Kafka... then:
UPDATE outbox SET published_at = now() WHERE event_id = ANY(:sent_ids);
Why this is the canonical answer

The outbox converts a distributed-transaction problem (impossible) into a local-transaction problem (trivial) plus at-least-once publishing (solved by idempotency). Naming it unprompted when an interviewer asks "how does the event reliably reach the pipeline?" is a clean staff-level signal.

Retries, backoff, timeouts & DLQs

Retries are how at-least-once is actually implemented, but naive retries cause more outages than they cure. Three rules:

  • Exponential backoff with jitter. Fixed-interval retries from a thousand workers create a synchronized thundering herd that hammers the recovering dependency at exactly the wrong moment. Multiply the delay each attempt and randomize it so retries spread out.
  • Timeouts on everything. A call with no timeout isn't a call, it's a resource leak waiting for a hang. Every network and query call gets a bounded timeout; the timeout is a failure that triggers the retry policy.
  • Bounded retries, then a dead-letter. Retrying forever on a poison message — a record that will never succeed because it's malformed or violates a constraint — blocks the whole partition behind it. Cap the attempts and route the loser to a dead-letter queue.
retry.py
import random, time

def with_retries(fn, key, max_attempts=5, base=0.5, cap=30.0):
    """At-least-once processing. `key` is the idempotency key so a retry
    that actually succeeded server-side but lost the ack is harmless."""
    for attempt in range(max_attempts):
        try:
            return fn(key, timeout=10)          # bounded timeout, always
        except RetryableError as e:
            if attempt == max_attempts - 1:
                dead_letter(key, reason=str(e))  # poison msg -> DLQ, don't block
                raise
            # exponential backoff + full jitter (AWS "Exponential Backoff and Jitter")
            delay = random.uniform(0, min(cap, base * 2 ** attempt))
            time.sleep(delay)
        except NonRetryableError:
            dead_letter(key, reason="permanent")  # 400-class: never retry
            raise

Distinguish retryable failures (timeouts, 5xx, throttling, a lock conflict) from non-retryable ones (schema violation, 4xx, a poison record). Retrying a permanent error just wastes the retry budget and delays the DLQ. The DLQ itself must be monitored and drainable — a DLQ nobody watches is just silent data loss with extra steps.

Antipattern

Retrying a non-idempotent operation. If the retried call double-inserts or double-increments, your reliability mechanism is now a data-corruption mechanism. Retries are only safe on top of the idempotency key — the two are a package deal, never one without the other.

Failure domains, blast radius & restartability

Reliability isn't only "does one task recover" — it's "when something fails, how much goes down with it?" That's the blast radius, and containing it is a design activity, not a monitoring one.

  • Failure domains. A shared upstream (one credentials secret, one Spark cluster, one schema-registry) is a domain: when it fails, everything behind it fails together. Draw them explicitly. The goal is that a bad partition for one source doesn't halt the other twenty.
  • Isolate the poison. Per-source DAGs or per-table tasks (see task-centric vs asset-centric in Chapter 03) mean one broken feed quarantines to its own lane instead of failing a monolithic run.
  • Graceful degradation. If the enrichment API is down, can you serve yesterday's dimension and flag the rows stale, rather than failing the whole load? Partial-but-labeled often beats all-or-nothing.
  • Checkpointing & restartability. A job that must restart from zero after a failure at 90% doesn't scale. Checkpoint progress (processed offsets, last completed partition, a high-water mark) so a restart resumes, not repeats. Idempotency makes the overlap on resume safe.

The observability pillars

Application observability is metrics/logs/traces. Data observability adds a second axis: the pipeline can be green while the data is wrong. A job that "succeeds" but writes zero rows, or yesterday's rows, or rows with a shifted schema, is the failure mode that actually pages you. Watch five pillars:

PillarThe question it answersHow you measure it
FreshnessIs the data recent enough?now() - max(event_time) vs the SLA; last successful load time.
VolumeDid the expected amount of data arrive?Row counts vs a moving baseline; alert on ±X% or a hard floor of 0.
SchemaDid the shape change under me?Column adds/drops/type changes vs the last snapshot; contract check at ingest.
LineageWhat's upstream and downstream of this?Dependency graph across tables/columns (see next section).
DistributionDo the values still look right?Null rate, cardinality, min/max/mean drift, % in an accepted set.

Freshness and volume are the highest-ROI pair — they're cheap to compute and catch the majority of real incidents (a stuck upstream, a silently empty load). Distribution monitoring is closer to the anomaly detection in Chapter 06; you can buy it (Monte Carlo, Metaplane, Soda) or roll your own with control charts on the metrics above. The point in an interview: name the pillars, then say which you'd instrument first and why.

Lineage

When a metric is wrong at 9am, lineage is what turns "somewhere upstream" into "this column, from this source, changed at 2am." Two granularities:

  • Table-level lineage — which tables feed which. dbt gives you this for free from ref()/source(); the DAG is the lineage graph.
  • Column-level lineage — which source columns compute which output columns. This is what lets you scope a schema change or a restatement precisely instead of re-running everything downstream.

OpenLineage (with Marquez as a reference backend) is the emerging open standard for emitting lineage events from Airflow, Spark, and dbt in a tool-neutral way — worth naming as the interoperable answer. On the consumer side, dbt exposures declare the dashboards, ML models, and apps that depend on your marts, so lineage extends past the warehouse to "who actually breaks if this table is late." That last mile is what converts a data incident into a stakeholder communication.

Why interviewers push on lineage

It's the fastest predictor of your incident MTTR. "I'd have column-level lineage plus exposures, so when reconciliation breaks on revenue I know exactly which source and which downstream dashboards are affected, and I can notify owners before they notice." That's L4 blast-radius thinking made concrete.

SLAs, SLOs & error budgets

These three get muddled constantly; keeping them straight is itself a signal. For data:

  • SLI — the measured indicator. "Data freshness = minutes between event time and availability in the mart."
  • SLO — your internal target on that SLI. "Freshness < 2h for 99% of days." This is what you engineer and alert against.
  • SLA — the externally-promised, often contractual version, usually looser than the SLO, with consequences if breached. You set the SLO tighter so you notice before the SLA is at risk.

An error budget falls straight out of the SLO: a 99% freshness target means 1% of the period is your budget to spend on failures, maintenance, and risky changes. Budget intact ⇒ ship faster; budget exhausted ⇒ freeze changes and stabilize. It turns "how reliable is reliable enough?" from an argument into arithmetic.

Airflow SLAs are not SLOs

Airflow's sla= only fires a callback when a task misses a wall-clock duration on a run that executed. It's blind to a DAG that never triggered, an upstream that's late, or output that's present but wrong. A real freshness SLO checks the data — now() - max(event_time) in the served table — independent of whether any job "succeeded." Conflating the two is a classic tell that someone has configured Airflow but never owned an SLA.

freshness_slo_check.sql
-- A real freshness SLI, computed on the DATA, not on job status.
-- Run it as a monitor; page if it breaches the SLO.
SELECT
    max(event_time)                                   AS last_event,
    datediff('minute', max(event_time), current_timestamp) AS staleness_min,
    120                                               AS slo_minutes,
    datediff('minute', max(event_time), current_timestamp) > 120 AS slo_breached
FROM analytics.orders;

Alerting, on-call & incident response

Good instrumentation with bad alerting is worse than no alerting — a flood of noisy pages trains everyone to ignore the one that matters. Design alerts to be:

  • Actionable. Every page maps to a decision. "CPU 80%" isn't actionable; "orders freshness breached SLO, 0 rows in 3h" is.
  • Deduped & grouped. One upstream outage that fails forty tables is one incident, not forty pages. Group by root cause using lineage.
  • Routed & tiered. Page for SLO breaches on tier-1 data; send a ticket or Slack for warnings. Match severity to consumer impact — the exposures from the lineage section tell you the tier.
  • Warn vs block. Same decision as Chapter 06: a failed critical check should halt promotion (circuit breaker), while a soft anomaly warns. Blocking bad data beats alerting on it after it's live.

When something does break, run a repeatable loop rather than improvising:

incident_loop.txt
DETECT   → monitor/SLO breach fires (not a consumer email). Ack, declare.
CONTAIN  → stop the bleeding: pause the DAG, freeze promotion (WAP holds
           bad data in staging), flag affected marts as "stale/suspect".
DIAGNOSE → use lineage to find the changed source/column + the blast radius
           (which downstream exposures are impacted).
REMEDIATE→ backfill or RESTATE the affected partitions idempotently
           (immutable partitions + re-run, per Ch04/05). Reconcile after.
PREVENT  → add the test/contract/monitor that would have caught it earlier;
           write the blameless postmortem with an action item + owner.

The runbook is what makes this executable at 3am by whoever is on-call, not just the author — the alert links to the runbook, the runbook has the exact queries and the rollback command. The blameless postmortem is where reliability compounds: each incident should end with a durable control (a new freshness monitor, a data contract, a reconciliation tolerance) so the same class of failure can't recur silently.

The cost of data downtime

Frame reliability in dollars, not vibes. "Data downtime" — periods where data is missing, wrong, or late — costs decisions made on bad numbers, eroded trust in the platform, and engineer-hours firefighting. The business case for WAP, contracts, and observability is that they convert expensive, trust-destroying silent failures into cheap, loud, contained ones. At staff level you're expected to make that ROI argument, not just build the controls.

Leveling ladder

Reliability is where the ladder is steepest — the same scenario ("make this pipeline dependable") is answerable at every rung, and interviewers climb it deliberately.

LevelWhat you'd say / doWhat it signals
L1 · Foundational"Turn on Airflow retries and email on failure." Knows failures happen; leans on the orchestrator's defaults.Aware of retries; no model of correctness under failure.
L2 · Practitioner"At-least-once with an idempotency key, exponential backoff + jitter, timeouts, and a DLQ for poison messages so one bad record doesn't block the queue."Builds pipelines that survive and recover from ordinary failure safely.
L3 · Senior"Effectively-once via idempotent merges + atomic WAP swaps; freshness/volume SLOs with error budgets checked on the data; actionable, deduped alerting; a detect→contain→restate→prevent runbook."Owns SLAs and incident response; reasons about blast radius and MTTR.
L4 · Staff"Transactional outbox to kill dual-writes at the source; explicit failure domains so a bad feed can't collapse the platform; OpenLineage column-level lineage + exposures driving blast-radius routing; postmortems that harden the platform; the whole thing justified as cost-of-downtime avoided."Architects reliability across teams and systems; measures it in trust and dollars.
Level up, out loud

"The simple version is Airflow retries. That silently drops data on a dual-write and floods you with noise, so in production I'd do at-least-once + idempotency with a DLQ (L2), put real freshness SLOs and WAP promotion on it (L3), and fix the dual-write at the source with an outbox while isolating failure domains (L4) — costs a relay and some plumbing, buys a platform that fails loud and contained instead of quiet and wrong." One arc, four rungs, exactly the through-line from Chapter 01.
