Section D · Production-Grade

Scale & Architecture

What changes when the data is a thousand times bigger: the physical-layout decisions, table formats, and streaming/batch trade-offs that a staff engineer reasons about explicitly — and where each one quietly breaks.

Partitioning & physical layout

At scale, the dominant cost is how much data you read, and that's decided by physical layout long before query time. Partitioning splits a table into directories by a column so the engine can skip whole partitions — partition pruning — instead of scanning everything.

  • Partition by what you filter on, at the right grain. For pipeline data that's almost always event date (event_date=2026-09-11), because nearly every query and every incremental merge is bounded by a date range. Pruning a query from a full-history scan to three days is often a 100× cost cut.
  • The small-files problem. Many tiny files (one per micro-batch, per partition) wreck read performance — the engine pays per-file open/list overhead and loses columnar batching. Streaming and over-frequent writes are the usual culprits.
  • Over-partitioning is the mirror image. Partitioning by (event_date, user_id) yields millions of near-empty directories, catastrophic metadata/listing cost, and worse pruning. Rule of thumb: keep partitions in the hundreds-of-MB-to-GB range, not KB.

The fix for both small files and layout drift is compaction: periodically rewrite many small files into fewer large ones. Inside a partition, clustering / bucketing / Z-ordering co-locates rows by a secondary key (e.g. customer_id) so filters on that key also skip data. Z-order (Delta) and sort-based clustering multi-dimensionally sort within files so pruning works on more than just the partition column.

Say the trade-off

"Partition on the always-filtered low-cardinality column — event_date — and cluster, don't partition, on the high-cardinality one. Then run compaction so streaming's small files don't erode reads." That sentence shows you've felt the small-files pain, not just read about pruning.

File formats & pushdown

The format under the partition matters as much as the partitioning. Analytical pipelines are columnar — Parquet or ORC — not row-oriented (Avro/CSV/JSON), and the reason is two forms of pushdown:

  • Projection pushdown. Columnar storage lets the engine read only the columns a query touches. SELECT amount FROM orders reads one column's worth of bytes, not the whole row.
  • Predicate pushdown. Parquet/ORC store per-row-group min/max statistics (and optionally bloom filters), so a WHERE amount > 1000 skips entire row groups whose max is below the threshold — reading is pruned inside a file, not just across partitions.

Both formats also compress far better than row formats because a column holds homogeneous values (run-length, dictionary encoding). Row formats like Avro still win for the write side — streaming ingest and per-record serialization — which is why a common shape is Avro on the wire/landing, compacted to Parquet for the analytical layer.

Table formats & the lakehouse

Parquet files in a directory are not a table — there's no atomic commit, no snapshot isolation, no safe concurrent write. Open table formats — Iceberg, Delta Lake, Hudi — add a metadata layer over the files that brings ACID transactions, time-travel, and schema/partition evolution to object storage. This is the technical core of the lakehouse, and it's what makes the atomic swap and WAP flow from Chapter 07 real on a data lake.

Two concepts every interviewer probes here:

  • Hidden partitioning (Iceberg): you declare "partition by day(event_time)" and the engine derives the partition value; queries filtering on event_time prune automatically without users knowing the partition scheme — and it can evolve without rewriting old data.
  • MoR vs CoW. Copy-on-Write rewrites whole files on update — fast reads, expensive writes (good for read-heavy marts). Merge-on-Read writes lightweight delete/update deltas and merges at read time — cheap frequent writes, more read cost (good for high-frequency upserts and CDC). Compaction periodically materializes MoR deltas back into base files.
The one-liner that lands

"Table formats give me ACID and time-travel on object storage, so my incremental MERGE (Chapter 05) is transactional, my WAP publish is an atomic snapshot swap, and I can restate a partition and still reproduce any prior version for reconciliation (Chapter 06)." That ties scale back to correctness — exactly the synthesis staff interviews want.

The industry trend — and the reason ELT won (Chapter 02) — is the lakehouse collapsing the old two-tier "lake for data science, warehouse for BI" split into one governed copy. But a managed warehouse is still the right, boring answer for a pure-SQL analytics shop; don't reach for a lakehouse to prove sophistication when Snowflake or BigQuery solves it with less operational surface.

Spark: skew, shuffle, spill, broadcast

Distributed compute at scale lives and dies by the shuffle — moving data across the network to co-locate keys for a join or aggregation. Four failure modes come up constantly:

  • Shuffle cost. Wide transformations (joins, groupBy) shuffle. Minimize them, filter/aggregate before the shuffle, and don't shuffle more columns than you need.
  • Skew. If one key holds 40% of the rows (a null customer_id, a whale account), one task does most of the work while the rest idle — the job runs at the speed of its slowest partition. Fixes: salting the hot key, Spark's adaptive skew join (AQE), or filtering/handling nulls separately.
  • Spill. When a partition doesn't fit in executor memory, Spark spills to disk — correct but slow. It signals skew or under-partitioning; repartition or bump memory/partition count.
  • Broadcast joins. When one side is small (a dimension), broadcast it to every executor and skip the shuffle entirely. Huge win — but broadcasting something too big causes OOM. Set the threshold deliberately; let AQE decide when it can.
The classic tell

"My Spark job is slow" with no mention of the shuffle is junior. "One stage has a straggler task — I'd check the Spark UI for skew, salt the hot key or enable AQE skew handling, and broadcast the small dimension side" is senior. The diagnostic instinct (read the UI, find the straggler) matters more than any single fix.

Streaming architectures

When freshness requirements drop below the batch interval, you move to streaming — and inherit a different set of scale concerns. Kafka is the usual backbone:

  • Partitions are the unit of parallelism and of ordering. Kafka guarantees order within a partition, not across. So the partition key is a correctness decision: key by order_id and all events for an order stay ordered on one partition. Too few partitions caps consumer parallelism; too many strains the cluster.
  • Consumer groups distribute partitions across consumers; a rebalance reassigns them on scale/failure. Offsets are the checkpoint (tie back to restartability in Chapter 07).
  • Retention vs compaction. Time/size retention drops old records; log compaction instead keeps the latest value per key — turning a topic into a changelog you can rebuild state from.

For the processing engine, know the Flink vs Spark Structured Streaming distinction:

Both realize exactly-once sinks the same way conceptually — checkpoint the input position and commit the output transactionally together, which is the streaming twin of the effectively-once/outbox story in Chapter 07. And the watermark, allowed-lateness, and windowing machinery here is exactly the late-arriving-data model from Chapter 04 — streaming state is where those concepts become infrastructure rather than SQL.

Batch vs micro-batch vs streaming: a decision framework

The over-engineering trap (Chapter 01) is reaching for streaming to look advanced. Drive the choice from requirements:

decision.txt
What is the FRESHNESS requirement?  (ask before choosing — Ch01)
  hours / daily        ─► BATCH
       cheapest, simplest, easiest to reconcile & backfill. Default.
  1–15 min             ─► MICRO-BATCH (Structured Streaming / dbt microbatch)
       near-real-time without full streaming ops burden.
  sub-second / seconds ─► STREAMING (Flink / Kafka Streams)
       only if the business truly consumes it that fresh.

Then sanity-check against:
  • Correctness bar   : streaming makes reconciliation & restatement HARDER.
  • Cost              : always-on compute vs scheduled bursts.
  • Ops maturity      : streaming = 24/7 state, checkpoints, backpressure.
  • Late data         : both need watermarks (Ch04); batch absorbs via lookback.

Rule: choose the SLOWEST tier that meets the freshness SLA. Earn the complexity.

Most "real-time" requirements are actually "fresh enough by the time someone looks," which micro-batch serves at a fraction of streaming's operational cost. Reserve true streaming for cases where a human or system acts on the data within seconds — fraud blocks, live ops dashboards, alerting.

Cost/performance engineering & multi-region

At scale, architecture is cost engineering — the design that's 3× cheaper often wins over the one that's 10% faster. The levers:

  • Decouple compute from storage. The modern default (Snowflake, BigQuery, lakehouse): pay cheap object-storage rates for data at rest, spin compute up only when a job runs. Right-size and auto-suspend warehouses; scan less via the partitioning/pushdown above.
  • Materialization strategy. Trade compute for storage deliberately — pre-aggregate hot marts (compute once, read many) vs compute-on-read views for cold data. This is the incremental-vs-full-refresh economics from Chapter 05 at the table level.
  • Spot/preemptible + caching. Run fault-tolerant batch on spot instances (restartability makes this safe); cache reference data and broadcast dimensions rather than re-reading them.
  • Backpressure & throughput. Streaming systems must shed or buffer load gracefully when downstream slows — Kafka's durable log is the buffer; the consumer's lag is the SLI to watch.

For multi-region / DR, know the vocabulary: RPO (how much data you can lose) and RTO (how long recovery takes) drive the design. Cross-region replication of the object store plus reproducible, idempotent pipelines means DR is "re-point compute at the replica and re-run from the last checkpoint" — which only works because the pipeline is idempotent and partitions are immutable. Reliability primitives from Chapter 07 are what make DR cheap; bolting it on later is what makes it expensive.

Schema evolution & zero-downtime migration

The hardest scale problem is changing a live system without breaking the consumers depending on it. Two layers:

  • Schema evolution. Additive changes (new nullable column) are safe and backward-compatible — the whole point of contracts (Chapter 06). Breaking changes (drop, rename, retype) need coordination: expand-then-contract — add the new field, dual-write both, migrate readers, then remove the old. Table formats with id-based schema evolution (Iceberg) make the rename safe at the storage layer; a schema registry with compatibility rules enforces it on the wire.
  • Zero-downtime pipeline migration. To swap a pipeline or a model definition, dual-run / shadow: run the new version alongside the old, writing to a parallel table, and reconcile the two outputs (row counts, aggregates, hash-diffs — the recon toolkit from Chapter 06) until you trust it. Then cut consumers over behind a view or contract, and retire the old path. No flag day, no big-bang risk.
Why shadow-run is the staff answer

"I don't cut over on faith. I shadow-run the new pipeline, reconcile its output against the old for N days within tolerance, then flip a pointer." It reuses reconciliation as a migration safety net, has a built-in rollback (the old path is still live), and turns a scary rewrite into a measured, reversible cutover. That's the L4/L5 move — evolving the platform without an outage.

"Naively I'd date-partition Parquet (L1).
