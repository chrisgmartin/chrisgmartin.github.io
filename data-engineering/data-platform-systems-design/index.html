Data Platform Systems Design — GPU Marketplace

How a Data Platform Engineer designs the internal data platform for a GPU-marketplace company, end to end — from the application space and ingestion through lakehouse storage, data modeling, transformation, serving, governance, and AI enablement. Layered for both learners and senior architects. Built around VastDP, an illustrative platform modeled on Vast.AI, and three reference stacks compared throughout: open-source lakehouse, Databricks, and Snowflake.

How to read this

Start with 00 · Start Here — it defines the running case study (the company, its source systems, the canonical data model, the three reference stacks, and the scale numbers) that every later chapter builds on. Each chapter opens with foundational framing, then climbs to senior design-decision depth. If you already know the modern data stack, jump to 03 · Reference Architectures.

"I need to enable AI on our data" path

00 (case study) → 06 (modeling) → 08 (semantic layer) → 12 (platform for ML) → 13 (AI powering the platform). The semantic layer in 08 is the hinge: it is what makes both self-serve analytics and AI-generated SQL trustworthy.

About this guide. A vendor-aware, layered systems-design reference for building the data platform at a GPU-marketplace company. The running case study, VastDP, is an illustrative platform modeled on the publicly observable shape of Vast.AI — it is not Vast's actual internal architecture. Technology choices are presented as three comparable reference stacks rather than a single prescription. Pair it with Data Engineering for Neoclouds (which covers DE tasks on and inside neoclouds) and the Vast.AI company profile.
