Section C · The Big Trade-offs

Lakes, Warehouses & Lakehouses

Where the data lives, in what format, and who can query it — the storage-and-compute fork that quietly decides your cost, your lock-in, and whether ML and BI can share one source of truth.

Three shapes of storage

Three architectures, on a spectrum from managed-and-structured to open-and-flexible. Know the trade-off each one makes.

The reframe

The lakehouse exists to end a decade-old split: warehouses gave you ACID, governance, and fast BI but locked your data in a proprietary store; lakes gave you cheap, open, any-format storage but no transactions and a tendency to rot into an unqueryable swamp. Open table formats put warehouse-grade guarantees — ACID, time-travel, schema evolution — directly on cheap object storage. That's the whole pitch: one open copy of the data that both BI and ML can trust.

OLTP vs OLAP, row vs columnar

Everything above is OLAP — analytical, scan-heavy, aggregate-many-rows-few-columns. That's a different world from the OLTP source systems (Postgres, MySQL) that serve the app: point lookups and single-row writes, low latency, high concurrency. You don't run analytics on the OLTP database — you replicate out of it (see CDC, Chapter 04) into an OLAP store. The physical reason is layout:

  • Row storage (OLTP) keeps a whole record contiguous — perfect for "fetch this user's row," terrible for "sum revenue across a billion rows," which would drag every column off disk.
  • Columnar storage (OLAP — Parquet, ORC) keeps each column contiguous. An aggregate reads only the columns it touches, and homogeneous columns compress far better (run-length, dictionary encoding). This is why analytical stores are columnar and why Parquet is the lingua franca of the lake.

Being able to say "analytics is scan-heavy, so we store columnar; the source is lookup-heavy, so it's row-oriented — and CDC bridges them" shows you understand why the storage split exists, not just that it does.

Open table formats

The lakehouse's core technology. A table format is a metadata layer over Parquet/ORC files that tracks which files make up a table at each version, giving you ACID commits, time-travel, and schema/partition evolution without a proprietary store. The three contenders:

How to call it in the room

The safe, defensible default is Iceberg for its vendor neutrality, broad engine support, and hidden-partitioning + partition evolution (you can repartition without rewriting the table). Pick Delta if you're on Databricks — the integration is tightest there. Pick Hudi when the workload is upsert-heavy with record-level mutations and low-latency incremental pulls (its original CDC-into-the-lake use case). Naming why — not just the name — is the whole answer. Note the convergence effort (Delta UniForm exposing Iceberg metadata) so you don't sound like you're betting on a single winner.

Partitioning, clustering & small files

Storage layout is where lake/lakehouse designs succeed or quietly rot. The levers:

  • Partitioning — physically split data by a column (usually date) so queries prune whole directories. Partition too coarsely and you scan too much; too finely and you get the small-files problem. Iceberg's hidden partitioning lets you change the scheme later without rewriting query logic.
  • Clustering / Z-ordering — sort or co-locate data within files by frequently-filtered columns so predicate pushdown and file skipping work. Snowflake auto-clustering and Delta Z-order are the named mechanisms.
  • Compaction — merge many small files into fewer large ones. Essential for streaming/CDC ingest, which naturally produces a flood of tiny files.
The small-files problem

Streaming or frequent micro-batch writes create thousands of tiny Parquet files. Query engines pay a fixed per-file cost (open, read footer, plan), so a table of ten thousand 1MB files is dramatically slower and pricier to scan than a hundred 100MB files — even with identical data. The fix is periodic compaction (Iceberg rewrite_data_files, Delta OPTIMIZE). Mentioning this unprompted is a strong seniority signal; it's the classic operational failure of a naive streaming-into-the-lake design.

The medallion layout

The dominant organizing pattern for a lake/lakehouse: progressively refine data through three quality tiers, each a queryable set of tables.

medallion.txt
  BRONZE (raw)            SILVER (cleaned/conformed)      GOLD (curated/served)
  ─────────────          ──────────────────────────      ─────────────────────
  Ingest as-is,     ──▶  Dedup, typed, validated,   ──▶  Business-level marts,
  append-only,           conformed keys, joined,         aggregates, star
  full fidelity,         schema-enforced.                schemas, feature
  replayable.            One source of truth.            tables. BI + ML read.
       │                        │                              │
   CDC / events           dbt / Spark transforms         serving layer below
  • Bronze — raw, immutable, append-only landing (CDC change logs, raw events). Full fidelity so you can always reprocess. Never let consumers query it directly.
  • Silver — cleaned, deduplicated, typed, conformed. The trustworthy single source of truth most transforms build on.
  • Gold — business-ready marts and aggregates, modeled for consumption (star schemas for BI, feature tables for ML).

The MERGE/upsert mechanics that move CDC change logs from bronze to a current-state silver table, and the incremental-model patterns behind gold, live in the companion guide — see Production Data Pipelines · Incremental Processing. Reference the layout here; don't re-teach the merge.

Serving layers

Storage is not consumption. The gold layer feeds several distinct serving patterns, each with its own access shape — a staff-level answer names the serving layer explicitly rather than stopping at "the warehouse."

Storage/compute separation is the enabler for most of this: because data sits once in open object storage, many independent compute engines (a BI warehouse, a Spark ML job, a Trino ad-hoc cluster) read the same tables without copying, and you scale and pay for each separately. That decoupling is the economic argument for the lakehouse — and the reason "one copy, many engines" is worth saying out loud.

Warehouse-first, lake-first, lakehouse

Key the decision to team maturity and workload mix, not to fashion.

Warehouse-first when…
  • Workloads are overwhelmingly SQL & BI, and consumers are analysts, not data scientists.
  • The team is small or SQL-centric and wants zero infrastructure to operate — buy the managed platform.
  • Governance and fast, reliable dashboards matter more than storage cost or format openness.
  • You're early: a managed warehouse (Snowflake/BigQuery) is the fastest path to value. Default for most early-stage analytics platforms.
Lake-first when…
  • You have large volumes of raw, semi-structured, or unstructured data (logs, events, images) where warehouse ingestion would be costly or ill-fitting.
  • ML and data-science workloads dominate and need direct file access from arbitrary frameworks.
  • Cost at extreme scale forces cheap object storage, and you have the engineering muscle to run engines and enforce governance.
Lakehouse when…
  • You need both BI and ML on one governed, open copy of the data — the split-brain of a separate lake and warehouse is the pain you're solving.
  • You want to avoid warehouse lock-in and keep data in an open format (Iceberg/Delta) that many engines can read.
  • Volume and workload diversity justify separating storage from compute and scaling each independently.
  • The increasingly common default at scale — but only once the team can operate the extra moving parts.
The trap

Reaching for a lakehouse when the team is three analysts running dashboards. The open format, the compaction jobs, the engine to operate — all of it is overhead with no payoff if the workload is pure SQL BI at modest volume. As with batch vs streaming: match the architecture to the requirements and the team, not to the reference architecture on a conference slide. Say it plainly: "I'd start warehouse-first and migrate to a lakehouse when ML workloads or storage cost make the open format worth the operational weight."
