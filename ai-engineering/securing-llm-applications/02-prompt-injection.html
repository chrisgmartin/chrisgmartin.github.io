Section B · Threats

Prompt Injection

Direct and indirect injection with the mechanism and the public incidents, why prompt hardening fails, the paths through documents, email, web and tool results, and the Harbourline claim form that tries to change an address.

The mechanism, and the two shapes it takes

Chapter 01 established that the model reads one token stream. Prompt injection is what an attacker does with that fact: they put text in the stream that the model treats as an instruction. Perez and Ribeiro (2022) gave the first systematic treatment, against GPT-3, and named two goals that still organise the field: goal hijacking, which redirects the model from its task to the attacker's, and prompt leaking, which makes it reveal its instructions. They showed that simple handcrafted inputs were enough.

The two shapes differ in who the attacker is, and that decides the damage.

  • Direct injection. The person in the session is the attacker. They type the instruction themselves. The damage is bounded by what that person is allowed to do anyway, provided tool calls carry their authorisation (chapter 01). A customer who talks the agent into changing their own address has done nothing they could not do in the app.
  • Indirect injection. The attacker wrote text that someone else's session later reads: an email, a web page, a PDF, a field in a database. Greshake et al. (2023) named it and showed it working against real applications. The attacker is absent and the victim's privileges do the work. This is a confused-deputy problem, and it is why indirect injection ranks above direct in impact for any system with tools.

The model cannot tell these apart, because to the model both are tokens. The difference lives in your architecture: whose authority the tool call carries, and which tools a given stream of text can reach.

Incidents with the mechanism visible

Two public cases show the mechanism at different layers. Each is cited to a primary source, and the details below are what that source says.

EchoLeak, Microsoft 365 Copilot, 2025

The paper by Reddy and Gujral (September 2025) describes EchoLeak as a zero-click prompt injection in Microsoft 365 Copilot, tracked as CVE-2025-32711. A single crafted email was enough for remote, unauthenticated data exfiltration, with no user interaction. The notable part is the chain: the attack evaded Microsoft's cross-prompt injection classifier, defeated link redaction by using reference-style Markdown, relied on images the client fetches automatically, and used a Microsoft Teams proxy that the content security policy allowed. Four separate controls were in place, and the attack found a gap in each. The lesson for a builder is that a classifier is one layer, and the exfiltration channel, here an auto-fetched image, is a second place to cut. Chapter 05 covers the rendering channel.

The GitHub MCP server, May 2025

Invariant Labs (26 May 2025) showed an agent hijacked through the official GitHub MCP server. An attacker opens an issue on a public repository containing hidden instructions. When the user asks their agent to review that repository's open issues, the agent follows the instructions, reads from the user's private repositories, and publishes what it finds in a pull request on the public repo. The post states that this is not a flaw in the server code, so the fix belongs at the agent level. It also records a precondition worth noting: the user had set tool calls to "Always Allow", so no one reviewed each action. Their suggested mitigations were least-privilege permissions, such as one repository per session, and runtime monitoring. Chapter 04 takes this apart as three properties meeting in one agent.

The same goals appear in the earliest work. Perez and Ribeiro showed in 2022 that a short input could override a GPT-3 application's task and that the same technique could extract its prompt, so the problem was visible in the first customer-facing deployments.

Why hardening the prompt and filtering phrases fail

The two obvious responses are to write a firmer system prompt and to block known phrases such as "ignore previous instructions". Both fail for the same reason: they fight in the attacker's medium.

A firmer system prompt adds more text to the stream. The attacker's text is in the same stream, in the same natural language, weighed by the same model. Neither side has a privilege the model enforces. A phrase filter matches strings, while the attack is semantic. The same intent can be paraphrased, written in another language, split across two chunks, placed in a table cell, or phrased as data, such as a note that appears to come from an adjuster. You cannot enumerate those, and each blocked phrase teaches the attacker the next.

Learned detectors do better than phrase lists, and some defences measure well on a fixed test. Hines et al. (2024) report that spotlighting, which transforms untrusted input so the model can see where it came from, cut attack success from over 50% to under 2% in their experiments. That is a real gain, and chapter 07 covers the technique. But Nasr et al. (2025) bypassed 12 published defences with adaptive attacks, most at over 90% success, and most had reported near-zero. Read a headline number as a rate against a particular attacker, not a guarantee.

Residual rates matter at scale. Take the illustrative three hostile uploads a day from chapter 01. A defence that stops 98% still lets through 3 × 0.02 = 0.06 a day, or about 22 a year. If one success redirects a $9,000 payout, that is a six-figure annual loss from a defence working as advertised. Microsoft's guidance reaches the same conclusion from the other side: layer probabilistic defences, then add deterministic controls so that an attack which gets through has limited effect.

A passing injection test is a statement about your test set

If your red-team prompts were written before your defence, you measured a static attacker. Re-run with prompts adapted to the defence, and report the rate with its interval, as chapter 08 describes.

The Harbourline claim PDF, step by step

This is the guide's recurring attack, described at the level needed to defend it. A claimant uploads a repair estimate through the document uploader. In the file is text no reviewer sees: white on white, or a size too small to read, or a metadata field. In substance it says that the payee's bank details have changed and that the agent should record the new ones. The text carries no exploit, only a plausible instruction in the voice of a business note.

upload ──► extract text ──► claims-intake agent ──► proposed tool call (PDF) (hidden text (reads it as part change payee bank is extracted of the claim) details too) │ control 1: no change-payee tool on this agent ─────────┤ control 2: flag hidden text before the model sees it ──┤ control 3: bank changes go to a verification flow ─────┘ that contacts the payee on file

The attack works because three things hold at once: the extractor reads text a human cannot, the model cannot tell that text from the claim's content, and a write tool exists in the same agent. Remove any one and the chain breaks, and the cheapest to remove is the third. The controls, in order of strength:

  1. No write tool on the agent that reads uploads. The intake agent can read, summarise and propose. A bank-detail change is a separate deterministic workflow that verifies with the contact already on file, and never uses details that arrived in the same session or document.
  2. Surface hidden text before it reaches the model. Compare what is visible with what is extracted, and flag the difference for a human. The sketch below shows the check.
  3. Provenance on every chunk. Mark upload text as unverified third-party content, and refuse tool calls that touch payment data whenever such text is in the context.
  4. Alert on the proposal. Log every proposed bank-detail change with its source session. A change proposed from a session that contained an upload is a high-signal event.

The first control is a design decision and the fourth is monitoring. Neither depends on the model reading the document correctly, which is why they hold when a classifier does not. Chapter 04 redesigns the customer-service agent on the same principle, and chapter 07 assembles the layers.

hidden_text_check.py (sketch)
# Sketch, not run against production files. Assumes PyMuPDF (import fitz).
import fitz

WHITE = 0xFFFFFF

def suspicious_spans(path: str) -> list[dict]:
    """Return text spans a human reader would not see."""
    flagged = []
    doc = fitz.open(path)
    for page in doc:
        for block in page.get_text("dict")["blocks"]:
            for line in block.get("lines", []):
                for span in line["spans"]:
                    text = span["text"].strip()
                    if not text:
                        continue
                    off_page = not page.rect.intersects(fitz.Rect(span["bbox"]))
                    if span["color"] == WHITE or span["size"] < 2 or off_page:
                        flagged.append({"page": page.number, "text": text})
    return flagged

This catches the crude cases only. Text can be hidden behind an image, matched to a pale background that is not pure white, or placed in metadata. Render the page and compare it with the extraction as a stronger check, and treat the flag as one signal, not a gate.

✓ Check yourself

Answer from memory before opening each one.

  1. A customer types an instruction into the chat that makes the agent change their own address. A different customer's uploaded PDF makes the same agent change someone else's payout details. Why is the second the more serious case, and what in the architecture decides it?

    Show answer

    In the first, the attacker holds the authority for the action anyway. In the second, the attacker is absent and the session's privileges are used on their behalf, a confused deputy. Whose authorisation the tool call carries, and whether the agent reading uploads holds a write tool, decide it. See the two shapes.

  2. Which controls did the EchoLeak chain pass through, and what does that say about relying on a single classifier?

    Show answer

    It evaded the injection classifier, defeated link redaction with reference-style Markdown, used auto-fetched images, and went through a proxy the content security policy allowed. Four layers each had a gap. A classifier cuts the rate but does not close the exfiltration channel. See incidents.

  3. A defence stops 98% of hostile uploads and the uploader sees 3 a day. How many get through in a year, and what do you do about the remainder?

    Show answer

    3 × 0.02 × 365 is about 22. Tuning the filter further has diminishing returns; limit what a successful injection can do instead, with no write tool on the reading agent and verification for bank changes. See why hardening fails.

  4. Your team proposes a rule that rejects any input containing "ignore previous instructions". Give two reasons it will not hold, and one thing it is still good for.

    Show answer

    The attack is semantic, so paraphrase, translation or splitting across chunks gets past a string match. The rule also tells the attacker what to avoid. It is still a cheap signal for logging attempts, which shows who is probing. See hardening.

  5. The batch job summarises claims for adjusters, and a downstream agent reads the summaries. Why do those summaries need a provenance tag even though your own model wrote them?

    Show answer

    The model that wrote them read untrusted text and can carry the instruction forward, now looking like internal output. Tag it as derived from untrusted input and treat it that way downstream. See the paths in.

  6. In the claim-PDF walkthrough, which single control would you build first, and what does it cost?

    Show answer

    Removing the write tool from the agent that reads uploads and routing bank changes to a verification workflow. It costs a slower payee-change process, which is acceptable for a rare, high-value action. If payee changes are frequent, tier the review by amount instead of verifying every one. Takeaway

  • Prompt injection works because instructions and data share one token stream; it has two shapes, and indirect injection is the serious one because the victim's privileges do the work.
  • Public cases such as EchoLeak and the GitHub MCP issue show that attacks chain past several controls and that agent-level permissions decided the outcome.
  • Firmer prompts and phrase filters fail because they compete in the attacker's medium; classifiers help but adaptive attacks have bypassed published ones at over 90% success.
  • At scale, a defence that works 98% of the time still lets through dozens of attacks a year, so you must limit what a success can do.
  • Every path that carries text, including tool results and other agents' output, needs a named author and a provenance tag.
  • The strongest control against the claim-PDF attack is architectural: the agent that reads uploads holds no write tool, and bank-detail changes are verified out of band.
