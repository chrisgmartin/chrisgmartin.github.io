Section B · Threats

The Threat Model

Assets, actors and trust boundaries for an LLM system, why the model cannot separate data from instructions, the OWASP Top 10 for LLM Applications mapped to Harbourline's six surfaces, and how to rank what to fix first.

What you are protecting

A threat model starts with what an attacker would want, because the list decides which of the ten OWASP entries you spend a quarter on. Harbourline's list is short. Customer data: names, addresses, claim narratives and payment details for about two million policies. Write actions: the customer-service agent can change an address or a payment method, and the claims-intake agent can route a claim and, in the design this guide attacks, touch payout details. Model assets: the system prompts, the eval sets, and the weights or adapters of anything fine-tuned. The brand and the licence to operate: an insurer that tells a customer a loss is covered when it is not has a regulatory problem, not only a bad answer.

Rank these by what an attacker can turn into money or harm. Write actions come first, because they change real records and are hard to undo, as the surface table notes for the customer-service agent. Customer data is second: a leak is permanent, but it needs a channel to get out. System prompts are last, and they stay last only if they hold no secrets. The exception is a prompt that carries an API key or a rule an attacker could game; then it moves up, and the fix is to take the secret out of the prompt rather than to hide the prompt better.

Who attacks, and what they can already do

Four groups matter, and what separates them is their access, not their skill.

  • Customers. They can type into the chat and upload files. Most are harmless; a few probe for refunds, discounts or the system prompt out of curiosity. Their reach is the front door.
  • Fraudsters. Insurance fraud predates language models. What changes is that the claims inbox and uploader are now read by a system that follows text. A fraudster needs no access to Harbourline, only the ability to submit a claim, which is the one thing the business wants every claimant to do. Expect this group to supply most of the attacks with a financial motive.
  • Insiders. Adjusters edit the summaries that feed the fine-tuning pipeline, and engineers read traces. An insider rarely needs a prompt trick; they need the model to carry out something they are not permitted to do themselves, or they need a poisoned example to survive review.
  • Suppliers. The model vendor, a model hub, an MCP server maintained by a third party, and any contractor whose documents arrive as evidence. They are not hostile by default, but they write text and code that reaches the model with a trusted look.

A fifth group never touches Harbourline at all: the authors of web pages and emails that an agent reads. They matter because the agent acts with someone else's privileges. That is the asymmetry the next chapter builds on, and it is why the threat model has to name who wrote each piece of text, not only who is logged in.

Trust boundaries in an LLM system

In classic appsec you draw a boundary wherever data crosses from a less-trusted party to a more-trusted one, and you validate there. An LLM system has five such crossings, and every one of them feeds the same place.

Only the system prompt is yours, and it ends up in the same stream as everything else. The question for each row is what the text can cause after it lands: which tools the model can call, which records they can write, and where the output can travel. Why the model cannot tell data from instructions

SQL injection has a fix because the database grammar separates code from values: a parameterised query sends the two on different channels, and the engine never parses the value as code. A language model has no such grammar. The chat template flattens system prompt, user turns and tool outputs into one sequence of tokens, and the model predicts the next token from all of it. Roles and delimiters are conventions that training taught it to weigh heavily. Nothing in the runtime enforces them. Greshake et al. (2023) made this the premise of their paper: LLM-integrated applications blur the line between data and instructions, so an attacker can plant a prompt in data the application retrieves later and never talk to the model directly.

The practical consequence is a change of goal. You cannot make the model reliably ignore bad text, and the authoritative sources say so. OWASP's entry for prompt injection says it is unclear whether foolproof prevention exists, given the stochastic way models work. Microsoft's July 2025 write-up on defending against indirect injection says probabilistic defences lower the likelihood of an attack but may not catch every instance, calls deterministic detection of indirect injection an open research problem, and describes its own approach as layered: probabilistic defences plus deterministic controls that limit the impact.

Evidence on the probabilistic layer is sobering. Nasr et al. (2025) ran adaptive attacks, where the attacker tunes the attack to the specific defence, against 12 published defences. Attack success exceeded 90% for most of them, and most had originally reported near-zero success against fixed attack strings. A defence tested only against a static list tells you how it fares against yesterday's attacker.

Plan for the model being steered, then bound what steering can do

Treat "the model follows the attacker's text some of the time" as a property of the component, like a network that drops packets. You still add classifiers and careful prompts, because they cut the rate. You design the system so that a steered model has few useful actions to take, and you size those controls against the attack that gets through, not the one you caught.

The OWASP list as a map of Harbourline

The OWASP Top 10 for LLM Applications 2025 lists ten risks. It has no separate entry for jailbreaks, which this guide treats in chapter 03 alongside prompt injection. The table maps each entry to the surface where it bites hardest at Harbourline and to the chapter that handles it.

OWASP defines excessive agency as a system that can take damaging actions because its outputs were unexpected, unclear or manipulated, whatever the cause: a hallucination, a poor reply to a benign prompt, or injected text. It traces the problem to excessive functionality, excessive permissions and excessive autonomy. That wording matters for the model: LLM01 is how the model gets steered, and LLM06 is what makes steering expensive. If you fix only one, fix LLM06 first, because it limits the damage from every other entry on the list.

Ranking by impact and exposure

You cannot fix ten risks at once, so rank by expected loss per day: attempts per day, times the chance an attempt works with today's controls, times the cost of one success. The numbers below are illustrative, chosen to show the method. Replace them with your own traffic and red-team results.

ThreatAttempts/daySuccess rateCost per successExpected loss/day
Hidden text in a claim upload redirects a payout6,000 claims × 0.05% = 310%$9,0003 × 0.10 × $9,000 = $2,700
Chat social engineering changes an address40,000 sessions × 0.01% = 45%$4004 × 0.05 × $400 = $80
System prompt extracted from the help centre40,000 × 0.1% = 4050%$240 × 0.5 × $2 = $40

The ordering is the point: a quiet attack on a write tool outweighs a noisy attack on a prompt by a factor of 30 or more, even though the prompt leak succeeds far more often. Exposure also differs. The uploader is open to every claimant by design, so it has a steady stream of hostile inputs from people with a financial motive. The nightly batch reads text no attacker typed directly, which makes it easy to forget.

Two caveats flip the ranking. If an attempt can be scaled by a script, multiply the attempts, because a fraud ring runs the same upload a thousand times. And if the leaked prompt contains a credential, the third row's cost per success is no longer $2. Impact is also not linear: one disclosed customer record or one wrongful payout to a regulated party can cost more than the sum of small losses, so give any threat with a regulatory tail a floor in the ranking.

What classic appsec still covers

Most of an LLM system's security is ordinary, and teams under-apply it because the novel parts are more interesting. The rule that carries the most weight: a tool call must run with the end user's authorisation, not the agent's. If the customer-service agent calls an address-change API with a service account that can edit any policy, then every steered model can edit any policy. If the call carries the session's own token and the API checks that the policy belongs to that customer, a steered model can do only what the customer could do by hand. That check is deterministic code that no prompt can talk its way past.

The same goes for the rest: authentication on every tool endpoint, secrets kept out of prompts, rate limits per account, output encoding before anything model-written reaches a browser or a database, tenant filters applied in the retrieval layer as chapter 08 of the RAG guide describes, and logs good enough to reconstruct an incident. Dependency management applies to model files and packages as much as to libraries, which chapter 06 takes up. What classic controls do not cover is the model's judgement: whether it treats a sentence as data or as a command. For that you limit privileges, and the retrieval-side version of that argument is in injection through retrieved text.

✓ Check yourself

Answer from memory before opening each one.

  1. Why can a parameterised query defeat SQL injection while no equivalent exists for prompt injection?

    Show answer

    A database grammar lets the driver send code and values on separate channels, so a value is never parsed as code. A language model receives system prompt, user text and tool output as one token sequence, and role markers are trained habits, not enforced boundaries. See why the model cannot tell data from instructions.

  2. A vendor shows you a prompt-injection filter with a 0.5% attack success rate on its benchmark. What do you ask before you count that as a control?

    Show answer

    Ask whether the attacks were fixed strings or adaptive attacks tuned to the filter. Nasr et al. bypassed 12 defences with adaptive methods, most above 90% success, against reports of near-zero. Then ask what the application can still do when the filter misses. See the one-stream section.

  3. For each of the five trust boundaries, name who writes the text at Harbourline. Which one is easiest to forget?

    Show answer

    User input: the session's user. Retrieved documents: content authors, including customers who upload. Tool results: whoever wrote the returned field. Model and adapters: the vendor, a hub or your training run. MCP servers: their maintainers. Tool results are the usual miss, because a database field feels internal even when a customer typed it. See trust boundaries.

  4. Using the illustrative table, claims-intake injection costs $2,700 a day in expectation and a prompt leak $40. A red team halves the leak's cost per success and doubles its attempts. What changes in the ranking, and what would change it a lot?

    Show answer

    Nothing material: the factors cancel, so the leak stays near $40 a day against $2,700. A credential in the prompt would change it, because the cost per success is then the cost of a stolen credential. Replace the numbers with your own and keep the method. See ranking.

  5. The customer-service agent's address-change tool authenticates with a service account. Why is that the biggest single weakness, and what is the smallest change that fixes it?

    Show answer

    Any steered model then holds the authority of the service account, so injected text can edit any customer's record. Pass the end user's session token and let the API check ownership, so a steered model can do no more than the customer could by hand. See what classic appsec still covers.

  6. The OWASP list has no jailbreak entry. Where would you place a customer who tricks the help-centre assistant into rude replies, and where a fraudster whose upload redirects a payout?

    Show answer

    The rude replies are a jailbreak: the user attacks the model's own safety behaviour, with low impact unless a tool is involved (chapter 03). The payout redirect is indirect injection through LLM01 made costly by LLM06 excessive agency. See the OWASP map.

Takeaway

  • Rank assets by what an attacker can turn into money or harm: write actions first, customer data second, system prompts last unless they hold secrets.
  • Name the author of every piece of text that reaches the context window, because trust follows authorship, not the system the text arrived through.
  • A language model reads one token stream, so no prompt or filter gives a guarantee that it will treat data as data.
  • Probabilistic defences cut the rate of attacks and should be used, but adaptive attacks have bypassed published ones at over 90%, so size your controls for the attack that gets through.
  • Excessive agency (LLM06) is the multiplier on every other entry: limiting what a steered model can do shrinks the harm from all of them.
  • Tool calls must carry the end user's authorisation and be checked by deterministic code, which is ordinary appsec doing the most important job.
