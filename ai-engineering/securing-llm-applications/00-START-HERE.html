Section A · Orient

Start Here

Every security model before this one assumed the program could tell its instructions from its data. A language model cannot, and an application built on one inherits that fact on every surface that reads untrusted text. Start here for why that changes the threat model, the trust boundaries the guide defends, the OWASP list as a map, and the Harbourline surfaces the chapters attack and harden.

Why this is not ordinary application security

Application security has a working assumption so old it is rarely stated: code is trusted and data is not, and the two arrive through different channels. A SQL engine distinguishes the query from its parameters; an operating system distinguishes an executable from a file it opens. A language model has one channel. The system prompt, the user's message, the retrieved policy document, the result a tool returned and the PDF a claimant uploaded all arrive as tokens in one sequence, and the model is trained to follow whatever instructions it finds in that sequence. There is no parser to fix, no escaping that makes a document unable to issue commands, because the capability being exploited is the product feature.

Three consequences follow. The attack surface is everything the model reads, not only what the user types, so a claims agent that reads uploaded documents can be attacked by anyone who can file a claim. Defences that filter inputs for bad strings fail the way signature antivirus failed, because the same instruction can be phrased, encoded or hidden in ways a filter has not seen. And because the model is probabilistic, a defence that holds 99 times in 100 is a defence that fails at 40,000 sessions a day. Security for these systems is therefore mostly architecture: deciding what the model is allowed to do, not what it is allowed to read.

This guide is for engineers who ship LLM features that touch real data and take real actions. It explains each class of attack at the depth needed to defend against it, cites the public incidents so you can read them yourself, and spends its second half on the defences that hold, the ones that only feel like they do, and how to measure the difference. It does not teach attacks for their own sake; the papers it cites do that better and with their authors' ethics statements attached.

The trust boundaries

Draw the system as the model sees it and the boundaries are obvious. Everything in the shaded band is untrusted: the model has no way to know who wrote it, and the application must assume an adversary did.

Two boundaries get less attention than they deserve. The output side is one: a model that can render a Markdown image, call a URL or send an email has an exfiltration channel, and an injection that cannot act is a nuisance where one that can is a breach. The weights are the other: a checkpoint from a hub or an adapter from a fine-tuning run is code you did not write, and chapter 06 treats it that way. The vocabulary

TermMeaning here
Prompt injectionInstructions in untrusted content that the model follows. Direct when the attacker is the user; indirect when they planted it in something the model reads.
JailbreakAn attempt to make the model violate its own safety training. A model-level problem; injection is an application-level one.
Excessive agencyA model with more tools, permissions or autonomy than the task needs, so that a wrong decision becomes a real action.
Lethal trifectaPrivate data, untrusted content and an exfiltration channel in one agent. Any two are manageable; all three are a breach waiting for a prompt.
Confused deputyA trusted component (the agent) tricked into using its authority on behalf of an attacker.
Exfiltration channelAny way output leaves the system without a human reading it: a rendered image URL, a web request, an email, a write tool.
PoisoningAttacking the training or fine-tuning data so the model learns something the attacker wants.
Backdoor, sleeperA trained-in behaviour that appears only on a trigger, and survives ordinary safety training.
Guardrail, classifierA model or rule that inspects inputs or outputs. Reduces attack success; never eliminates it.
Red teamingDeliberate attack by people or tools to find failures before an adversary does.
Attack success rateThe share of attack attempts that achieve their goal. The eval metric of this field; always reported with the attack set and an interval.
Least privilegeEach tool call carries only the permissions that request needs. The defence that does the most work.

The running example: Harbourline Insurance

Harbourline is a fictional mid-size property-and-casualty insurer, about two million policies in the US and UK, shared with the other AI Engineering guides. Its six AI surfaces each read something an attacker can influence, and the guide follows one attack across chapters: a claim PDF whose hidden text tells the intake agent to change where the payout is sent. Takeaway

  • A language model reads instructions and data on one channel, so anything it reads can command it; this is the feature, not a bug to patch.
  • The attack surface is everything the model reads, and the damage happens on the output side: tools, URLs, writes. Defend the actions, not the strings.
  • Probabilistic defences fail at volume; a classifier that holds 99 percent of the time fails hundreds of times a day at Harbourline's traffic.
  • The OWASP Top 10 for LLM Applications is a map of risk categories; rank your own surfaces by the worst action each can take.
  • Least privilege, confirmation of writes and the removal of exfiltration channels do more than any filter; measure the rest with a red team and an attack success rate.
