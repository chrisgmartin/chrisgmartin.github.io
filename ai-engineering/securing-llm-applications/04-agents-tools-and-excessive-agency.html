Section C · Agents and data

Agents, Tools and Excessive Agency

The lethal trifecta, confused deputies, tool permissions and confirmation for writes, MCP server trust and tool poisoning, sandboxing code execution, and Harbourline's customer-service agent.

Three properties you cannot hold together

The decision that matters most in an agent design is made before any tool is written: which of three properties this session will have. Simon Willison named them the lethal trifecta in June 2025. An agent is at serious risk of data theft when it has access to private data, exposure to untrusted content, and a way to communicate externally. Each is a reason someone wanted the agent. Untrusted content is whatever a customer, a web page or a PDF puts in front of it. An outbound channel is any tool, link or rendered image that can carry text to a place the attacker can read. Willison's advice is blunt: avoid the combination, because guardrail products that catch 95% of attacks are a failing grade by web-security standards.

Meta published the same idea as a design rule on 31 October 2025, the Agents Rule of Two. Until prompt injection can be reliably detected and refused, an agent should hold at most two of three properties in one session: it processes untrustworthy inputs, it can reach sensitive systems or private data, and it can change state or communicate externally. If a task needs all three, the agent should not run autonomously, and a human approves the consequential step. Meta says the rule limits impact and does not finish the job: a user who clicks through a warning defeats a compliant design, so it sits on top of least privilege.

The framings differ in one place. The trifecta is about exfiltration, while Meta's third property also counts changing state. That matters at Harbourline, where the worst outcome is a write. In the injection chapter the claim PDF carries hidden text that tries to redirect a payout. The claims-intake agent reads uploaded documents, looks up the policy and the claimant, and can edit claim records. It holds all three, and a better system prompt does not change the count.

Two surfaces hold all three. You cannot remove untrusted input from an intake agent, because reading the customer's documents is the job, so the move is to remove or gate one of the other two for the dangerous steps. The exception is a closed deployment where every input is authored by staff already trusted with the same data. There the count really is lower.

The deputy acts with more authority than the person asking

A confused deputy is a program with real authority that an unauthorised party tricks into using it. An LLM agent is a deputy by construction: it holds credentials the end user does not hold directly, and it decides what to call based on text anyone can influence. If the customer-service agent calls the payments service with a service account that can read any customer, then "show me the payment status for policy 88213" works for whatever policy number appears in the conversation, whoever typed it and wherever it came from. The model cannot check who is asking, because identity is only a claim written in text.

OWASP's 2025 entry on Excessive Agency (LLM06) puts the cause in three places: excessive functionality, excessive permissions and excessive autonomy. Its prevention list reads as a deputy checklist. Execute extensions in the user's context, with the user's authorisation and the minimum scope. Enforce authorisation in the downstream system rather than asking the model what is allowed, which OWASP calls complete mediation. For Harbourline this means the tool call carries the signed-in customer's session token, and the policy service checks that policy 88213 belongs to that customer, exactly as it would for the web app. The agent can be fooled into asking, not into succeeding.

The same principle applies inside MCP. Its security best practices describe a confused deputy in OAuth proxy servers and forbid token passthrough: a server must not forward tokens that were not issued to it, because that breaks audience checks and audit trails. The MCP deep dive covers the protocol; the security rule is that every hop re-checks authority and none inherits it.

Authorisation belongs to the service, not the prompt

Any rule of the form "never change an address unless the customer is verified" written in a system prompt is a request. The same rule enforced as a check in the address service is a control. The test: if an attacker chose the model output, would the control still hold?

Least privilege, one tool at a time

Least privilege for an agent is a per-tool exercise, because each tool is a separate grant. Start with functionality: OWASP advises minimising the extensions an agent has, minimising what each does, and avoiding open-ended ones such as a general shell or a "run any SQL" tool in favour of granular tools. Then permissions: a read tool gets a read-only credential, scoped to the signed-in customer. Then autonomy: which calls may happen without a person.

Harbourline's customer-service agent has four tools.

ToolClassCredentialControl before it runs
Policy lookupRead, own dataCustomer session, read-onlyDownstream ownership check
Payment statusRead, own dataCustomer session, read-onlyDownstream ownership check; masked account numbers in the result
Address changeWrite, reversible with effortCustomer session, narrow scopeConfirmation showing old and new value; rate limit per policy
Payment-method changeWrite, hard to undoNot held by the agentHandoff to a verified web flow with step-up authentication

The last row is the important one. The agent does not hold the credential to change payout or payment details at all. It can start the process by sending the customer to a flow that the model cannot drive, where the customer re-authenticates. That puts the most damaging write out of the model's reach. The cost is friction, since some customers must leave the chat. If your write is low-value and easy to reverse, such as a communication preference, the handoff costs more than it protects and an ordinary confirmation is enough.

Confirmation that is not a rubber stamp

Human approval is the mitigation everyone reaches for and the one most often defeated by use. Invariant Labs' May 2025 demonstration against the official GitHub MCP server shows the failure. An attacker opened an issue in a public repository containing an injection. When the owner asked their agent to review open issues, the agent read it, pulled details from the owner's private repositories, and posted them in a public pull request. The client did ask for confirmation on tool calls. Invariant notes that many users choose "Always Allow", which lets the attack run unnoticed.

Three design rules make a confirmation worth having. First, it fires rarely. Suppose, illustratively, that 3% of Harbourline's 40,000 daily chat sessions reach a write tool: 1,200 prompts a day. If the prompt also appeared for every read, it would appear tens of thousands of times and be approved on reflex. Ask only where an action changes state. Second, it shows the action and not the model's account of it: the old address, the new address, the policy, in a rendering the model cannot style or lengthen. Invariant's tool-poisoning work found that clients often show a simplified view of what the model actually sends, so the dialogue has to be generated from the structured call arguments by your code. Third, it routes to the right person: the customer for a customer-initiated change, an adjuster for a claims-intake write, never the claimant whose PDF is under suspicion.

Meta's caveat applies: a user may approve a warning without reading it, so compliant designs can still fail. Treat confirmation as one layer. For the payout bank details, which are the target of Harbourline's recurring attack, do not rely on it. The intake agent proposes a change to a queue, flagged as coming from a document. A separate process verifies it through a channel the document cannot reach, such as a call-back to the number on file. The flip case is a low-volume expert reviewer who sees the diff in context; there a confirmation works well.

MCP servers are third-party code that writes your prompt

Every tool description from an MCP server is text the model reads as instruction. That makes a server a supplier of prompt content as well as code, and it widens the trust boundary from "the data" to "the tool list". Invariant Labs described three attacks in April 2025 that follow from this.

  • Tool poisoning. Malicious instructions sit inside a tool's description. Users see a simplified view; the model reads the full text. In Invariant's example a harmless-looking arithmetic tool carried hidden steps that made the agent read sensitive local files and pass them out through a parameter, while the agent explained the sum to the user.
  • Rug pulls. A server changes a tool's description after the user approved it. Invariant compares it to a malicious update on a package index.
  • Tool shadowing. A malicious server's description changes how the agent uses a different, trusted tool. In their test a poisoned tool altered how a trusted email tool addressed messages, even when the user named another recipient, without the poisoned tool ever being called.

Package-level risk is not hypothetical. In September 2025 an npm package called postmark-mcp, impersonating Postmark's MCP server, published fifteen ordinary versions and then added a line in version 1.0.16 that blind-copied outgoing mail to an external address. Koi Security found it; Postmark said it had nothing to do with the package. A tool installed because it worked became an exfiltration channel through an update.

The controls follow from the mechanism. Allowlist the servers an agent may load, and review each server as you would a dependency with network access. Pin versions and hash tool descriptions, then fail closed when a hash changes, which defeats the rug pull. Keep servers that handle sensitive data out of the same context as servers you do not control, since shadowing needs a shared context. Run local servers in a sandbox with restricted file and network access, as the MCP security guidance recommends, and show the exact command before a one-click install runs. The harness chapter shows where this configuration lives. The exception to allowlisting is a research or coding assistant whose value is its open tool ecosystem; there, keep private data and secrets out of that session.

Code execution, budgets and the blast radius

A tool that runs model-written code is the ultimate open-ended extension. OWASP's advice to avoid open-ended tools applies at its strongest: run the code in an isolated environment with no credentials, no access to the internal network, no writable path outside a scratch directory, and an egress policy that blocks everything not listed. Harbourline's customer-service agent needs no code execution, so it ships without the tool. If an analyst agent does need it, give it a copy of the data, not the production database, so the exfiltration path has nothing private to carry.

Budgets limit damage when prevention fails. Cap the number of tool calls per session, the number of distinct write calls, and the spend per session. If no honest address-change conversation needs more than 12 tool calls, a cap of 20 loses nothing. Alert on hits: a session at its cap is broken or hostile. For a long-running research agent with unbounded legitimate use, cap only the damaging tools (writes, sends).

Harbourline's customer-service agent, redesigned

The start state held all three trifecta properties, with write tools for address and payment method on a shared service credential. The redesign removes the credential, narrows the tools and moves the dangerous write out of the model's reach.

customer chat ──► model ──► tool gateway (your code) │ read tools ◄───────────┤ customer session token, (own data only) │ ownership check downstream │ address change ◄───────┤ confirmation built from structured │ args, rate limit, step cap 20 │ payment method ✗ └─► handoff link to web flow (no credential) with step-up authentication tool results ──► returned as typed fields, rendered links and images stripped (chapter 05)

Count the properties again. Untrusted input is still present. Private data is still present, but scoped to one customer. State change is limited to one reversible write behind a confirmation, and the irreversible one is gone. An injected instruction in a retrieved page can at worst propose an address change that the customer sees as a diff. Compare that with the start state, where the same instruction could have changed payment details with no prompt. The cost is a handoff step for payment changes and the confirmations. Attack success rates before and after belong to the red-team chapters.

As the confident-and-wrong chapter argues for wrong answers, where a wrong write is costly you change what the system may do, not how careful the model is. Privilege separation and allowlists in code come in chapter 07.

✓ Check yourself

Answer from memory before opening each one.

  1. A colleague says the claims-intake agent is safe because it only reads documents and "writes" are done by a human clicking Submit. The human sees a 3-line summary the agent wrote. What is wrong with this design?

    Show answer

    The summary is model output, so an injected document can shape what the human approves. The approval shows the model's account of the action, not the action. Build the confirmation from the structured arguments in code, and keep high-value fields such as bank details out of the agent's write path. See confirmation.

  2. A system prompt says "only change addresses for verified customers". The address service accepts any authenticated call from the agent's service account. Which side holds the control, and what would an attacker who controls the model output do?

    Show answer

    The control is in the prompt, so it is a request. An attacker who steers the model calls the service directly and succeeds, because the service never checks. Fix it by passing the customer's session and checking ownership and verification in the service. See the deputy section.

  3. You review a design that holds only two of the three Rule of Two properties. A teammate says it is therefore safe from prompt injection. What do you reply, and what extra risk remains?

    Show answer

    Meta frames the rule as limiting impact, not as proof of safety. Injection still occurs and the two held properties can still do harm: an agent with untrusted input and state change but no private data can still make bad writes. Check what the remaining pair can do, and keep least privilege. See the trifecta section.

  4. An MCP server you approved in March now behaves differently, though you changed nothing. Name the attack and the two controls that would have caught it.

    Show answer

    A rug pull: the description or behaviour changed after approval. Pin the server version and hash the tool descriptions, failing closed on a change. A review step when a pinned dependency updates covers the case where the code, not the description, changed. See the MCP section.

  5. Harbourline wants a confirmation on every tool call, read or write, "to be safe". Argue the case against, using the session volume, and say when the broader policy would be right.

    Show answer

    Prompts on every read multiply the count from about 1,200 a day (illustrative) to tens of thousands, and people respond by approving on reflex, as users did with "Always Allow" in the GitHub MCP case. Reserve prompts for state changes. The broad policy is right for a small expert team on a new, high-consequence tool during a pilot. See confirmation.

Takeaway

  • An agent with private data, untrusted content and an outbound or state-changing tool in one session is exposed, and the only reliable fix is to remove or gate one of the three.
  • The model is a deputy that cannot verify who is asking, so authorisation must be checked in the downstream service with the user's own credentials.
  • Least privilege is per tool: read tools get read-only, scoped credentials, and the most damaging write should sit outside the agent's reach entirely.
  • A confirmation only protects when it is rare, built from the structured call, and shown to someone able to judge it.
  • An MCP server supplies prompt text as well as code, so allowlist servers, pin and hash them, and keep untrusted servers out of contexts that hold sensitive data.
  • Budgets on calls, writes and spend do not stop an attack, but they cap what a hijacked session can do.
