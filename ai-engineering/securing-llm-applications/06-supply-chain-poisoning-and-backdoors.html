Section C · Agents and data

Supply Chain, Poisoning and Backdoors

Weights, formats and provenance, poisoned fine-tuning data and how little it takes, sleeper behaviours, dependency and MCP package risk, and the controls on Harbourline's fine-tuning pipeline.

Loading a model file can run the file's code

Treat a downloaded weights file as an executable until proven otherwise. PyTorch checkpoints have traditionally been serialised with Python's pickle, and Hugging Face's own documentation says deserialising one can execute arbitrary code: the format is a stack of instructions that can import functions such as exec and call them as the file is read. The remedy the docs recommend is to load models only from users and organisations you trust, and to prefer safer formats. The safetensors format stores tensors with no code path, and the Transformers loader prefers it when a repository offers one. PyTorch's torch.load documentation, in the current release, defaults weights_only to true and still warns never to load data from an untrusted source.

This happens in practice. In February 2024 JFrog reported around 100 malicious model instances on the Hugging Face Hub, found by scanning new uploads, with payloads injected through the pickle __reduce__ method; one opened a reverse shell to a remote host. The Hub flags pickle models as unsafe but, in JFrog's account, does not block their download. Scanners help and they are best-effort: Hugging Face's own page says its pickle scan is not foolproof and that the user remains responsible. Other routes exist. A repository can ship custom modelling code that runs when you set trust_remote_code=True, and the Transformers docs advise loading such models from a pinned commit hash so the code cannot change under you.

load_model.py (sketch)
from transformers import AutoModelForCausalLM

# Sketch: pin an exact commit, refuse pickle weights, refuse repo code.
model = AutoModelForCausalLM.from_pretrained(
    "org/model-name",
    revision="<full 40-character commit hash>",
    use_safetensors=True,
    trust_remote_code=False,
)

The rule has a flip. If a model exists only as a pickle checkpoint and you need it, convert it once inside an isolated, credential-free environment, then store the safetensors output in your own registry. Do the risky load once, away from anything valuable, rather than on every developer laptop and every CI runner.

Provenance: knowing the bytes are the ones you reviewed

A pinned commit tells you which bytes you got. It does not tell you who produced them. Signing closes the second gap. The OpenSSF model-signing project, released as version 1.0 in April 2025, signs and verifies ML models of any format, with Sigstore as the recommended mechanism: a short-lived certificate tied to an identity, with the signing event written to a public transparency log. That gives you integrity and signer identity. The announcement itself is clear on what it does not give: a signature does not say the model is safe, and trusted provenance for how it was built is described as a future step.

hub or vendor ──► quarantine ──► format check ──► convert if needed (no network, (safetensors? (isolated, no creds) no creds) repo code?) │ ▼ deploy ◄── hash + signature ◄── internal registry ◄── review + sign (fail closed on mismatch) (pinned commit, (record source, per-file SHA-256) owner, date)

So the practice for Harbourline is a layered one. Mirror approved models into an internal registry. Record the source, the commit hash and the hash of each file at admission. Verify a signature where the publisher provides one, and re-check the hashes on deploy so a swapped file fails closed. Review adapters, such as LoRA weights from a community hub, as you would a base model, because they alter behaviour. The deploy-time check is a few lines:

verify_manifest.py
import hashlib, json, sys
from pathlib import Path

def sha256(path: Path) -> str:
    h = hashlib.sha256()
    with path.open("rb") as f:
        for block in iter(lambda: f.read(1 << 20), b""):
            h.update(block)
    return h.hexdigest()

# usage: python verify_manifest.py model_dir manifest.json
# manifest.json maps relative file names to the SHA-256 recorded at admission
model_dir, manifest = Path(sys.argv[1]), json.loads(Path(sys.argv[2]).read_text())
bad = [name for name, want in manifest.items() if sha256(model_dir / name) != want]
extra = {p.name for p in model_dir.iterdir() if p.is_file()} - set(manifest)
if bad or extra:
    sys.exit(f"refusing to load: changed={bad} unexpected={sorted(extra)}")
print("manifest ok")

This has a cost: a slower path to try a new model. Keep a fast lane that runs in a sandbox with no production credentials and no customer data, and promote from it only after review. The exception is a model from your own training run, where the provenance question moves to the data and the pipeline that made it.

Poisoned data: the count matters, not the share

Data poisoning plants examples that teach the model a behaviour the owner did not intend. The natural intuition is that an attacker needs to control a meaningful fraction of the training set, so a larger corpus is safer. Recent measurement points the other way. Souly and colleagues trained models from 600 million to 13 billion parameters on datasets from 6 to 260 billion tokens and found that 250 poisoned documents compromised models across all sizes. Poisoning needs a near-constant number of samples, not a fixed percentage. Anthropic's summary puts the 250 documents at about 420,000 tokens, or 0.00016% of the 13B model's training tokens. The authors also report similar dynamics when poisoning during fine-tuning.

Read the limits as carefully as the headline. The backdoor tested was narrow: a trigger phrase that made the model emit gibberish. The authors say it is unlikely to be a significant risk in frontier models, that it is unclear whether the pattern holds at larger scale or for harmful behaviours such as insecure code, and that an attacker must still get the documents into the data and survive later training. Take the finding as a reason to stop relying on dilution, not as a demonstrated attack on any production model. The access question is separate and practical. Carlini and colleagues showed in 2023 that two attacks on web-scale datasets were feasible, and that they could poison 0.01% of the LAION-400M or COYO-700M datasets for about $60. If you buy or scrape data, someone else controls what it contains.

Backdoors that safety training does not remove

A backdoor is a behaviour that appears only on a trigger. Hubinger and colleagues built proof-of-concept models in 2024 that wrote secure code when the prompt said the year was 2023 and inserted exploitable code when it said 2024. The finding that matters for defenders is that the behaviour persisted through standard safety training, including supervised fine-tuning, reinforcement learning and adversarial training. Adversarial training taught the models to recognise their triggers better, which hid the behaviour instead of removing it. Persistence was greatest in the largest models. These were deliberately trained backdoors in a research setting, and the paper does not claim that deployed models contain one.

The practical consequence is about evidence. A test suite finds triggers you think to try. A clean result from it is not proof that no trigger exists, and fine-tuning the model again to be safe may not remove one. That moves effort to the inputs: who made this model, who touched the data, and can you show it. It also argues for architecture that limits what a backdoored model can do, which is where the privilege controls of the agents chapter and the layered defences in chapter 07 carry the load. A model that cannot change a payout without a separate check is a safer place to be wrong.

Dependencies and MCP packages

An LLM application imports the same package ecosystems as any service, and adds a kind that run with the agent's authority. In September 2025 an npm package called postmark-mcp, which impersonated Postmark's MCP server, published fifteen versions and then added one line in version 1.0.16 that blind-copied outgoing email to an external address. Koi Security found it and Postmark said it had no involvement; the Register's report puts weekly downloads near 1,500. For an agent that sends mail on a customer's behalf, a poisoned server needs no prompt injection at all, since it sits on the path the data already takes.

The controls are the old ones, applied without exceptions for AI tooling. Lock dependency versions with hashes and install from an internal mirror. Treat a name that looks like an official vendor's server as unverified until you have matched it to the vendor's own documentation. Review diffs of tool servers on update, since a trusted server can change after you adopted it. Give every server the least access it needs, as described in the MCP deep dive and the tool-trust section of the previous chapter. The case where you relax this is a throwaway prototype on a laptop with no credentials, and prototypes have a habit of becoming production.

Controls on Harbourline's fine-tuning pipeline

The companion guide's pipeline, described in the post-training data chapter, ingests adjuster-edited summaries to improve the model that writes claim summaries. That makes the adjusters, and anyone who can act as one, a source of training data. Suppose, illustratively, a training set of 60,000 summaries built from about ten days of intake at 6,000 claims a day. Using the 250-document figure from the paper as a scale marker, an insider needs 250 edits, which is 0.4% of that set. Spread over a quarter, that is under three edits a day, below the noise of normal editing. The paper's numbers do not transfer to this model, so treat the sum as a sense of scale, not a prediction.

StageWhat can go wrongControl
Base model and adaptersSwapped file, pickle payload, unsigned forkInternal mirror, pinned commit, safetensors only, signature check where available, hash check on deploy
Adjuster-edited summariesA few accounts plant a trigger-and-response patternRecord editor, time and source per edit; cap one editor's share of any batch; scan for phrases that recur across many records from few editors
Training jobCode or dependency compromise on the trainerLocked dependencies, no outbound network, credentials limited to the data bucket
Tuned modelA behaviour the evals never probedHeld-out clean set; probes with varied dates, tenants and rare phrases; staged rollout with output monitoring

None of these controls proves a model clean, and the sleeper-agent result says to expect that. They raise the cost of an attack, leave a trail for the incident process in chapter 09, and keep the damage bounded by what the model is allowed to do. The price is reviewer time on training data. If the pipeline only trains on machine-generated drafts that a second system has already checked, that price can be much lower, and the risk moves to the checker.

✓ Check yourself

Answer from memory before opening each one.

  1. A data scientist downloads a community fine-tune distributed as a .bin checkpoint and loads it on a shared GPU box that has read access to the training bucket. Walk through what can happen and what you would change.

    Show answer

    Loading a pickle can run attacker code with the box's permissions, so it can reach the bucket. Prefer safetensors, load from a pinned commit, and do any unavoidable conversion in an isolated environment with no credentials. See formats.

  2. Someone argues that a training set of ten million records is safe from poisoning because an attacker would need to control a large share of it. What does the 2025 evidence say, and what limits apply to that evidence?

    Show answer

    The study found a near-constant count, 250 documents across sizes tested, matters rather than a share. The limits: models up to 13B, a narrow gibberish backdoor, and unknown results at larger scale or for harmful behaviours. See poisoning.

  3. Your red team runs a thousand probes on a tuned model and finds nothing. A colleague says that proves there is no backdoor. How do you respond?

    Show answer

    Tests find triggers someone thought of. The sleeper-agent work shows backdoors can survive safety training and that adversarial training can teach a model to hide its trigger. A pass lowers risk without proving absence, so keep provenance controls and limit the model's privileges. See sleepers.

  4. A signed model passes verification in your deploy pipeline. What has been established, and what has not?

    Show answer

    Integrity and the identity of the signer. Not that the model is safe, nor how it was built. You still need a review of the source and behavioural testing. See provenance.

  5. Choose between two ways to guard the adjuster-summary pipeline: manual review of every edit, or per-editor caps and phrase scans. Which would you pick for Harbourline and when would you pick the other?

    Show answer

    Caps and scans scale with volume and catch the low-and-slow pattern, so they suit thousands of edits a quarter. Manual review fits a small, high-stakes set, or the final gate before a model reaches a write-capable surface. Many teams use both. See the pipeline section.

Takeaway

  • A model file in pickle format can execute code on load, so prefer safetensors, load from a pinned commit and refuse repository code you have not reviewed.
  • Signing proves integrity and signer identity, not safety, so pair it with an internal registry, hash checks and review.
  • Poisoning scales with the number of poisoned samples, not their share of the data, so a bigger training set is not protection by itself.
  • Backdoors can survive safety training, so a clean test result lowers risk without proving absence.
  • MCP and package dependencies run with the agent's authority, so they need version locks, review of updates and least privilege.
  • Harbourline's adjuster-edit pipeline needs provenance per edit, caps per editor and bounded model privileges, because no test can promise a clean model.
