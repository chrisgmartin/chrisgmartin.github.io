Section D · Shipping

Evaluating a Tuned Model

A tuned model has to pass the task, keep what it could do before, and keep refusing what it should refuse. This chapter runs those three checks on Harbourline's 400-claim held-out set, recalibrates the judge for the new style, and turns the result into a ship decision with an interval.

Three ways a tuned model fails

A fine-tuned model can pass the task you trained for and still be unfit to ship. Training moves every weight the adapter touches, not only the behaviour you wanted, so the evaluation has to cover three things at once: the task, what the model could do before, and what it was trained to refuse. Winning the task while losing either of the others is a trade, not an improvement.

At Harbourline the task is Candidate A from chapter 01: the nightly batch that summarises about 6,000 claims for adjusters, moving from Claude Sonnet 5.5 to a tuned open-weight model in the 7B to 9B class. The eval-first rule from that chapter pays off here. The 400-claim held-out set exists, was built before any training, and has never been used to choose a hyperparameter. If it was, you need a fresh set before you read any number below. The evals guide covers how to keep a held-out set held out. This chapter covers what to run on it once a model exists.

The statistics of paired comparison live in The Ship Decision. This chapter applies them to changed weights and adds the two regressions a prompt change cannot cause.

The task: three arms on one held-out set

Run three systems over the same 400 claims, in the same order, and score all three the same way.

  • The untuned instruct checkpoint, with the best prompt you can write for it. This is the arm that answers "did training do anything?" If your tuned model beats the API model but only matches the untuned checkpoint with a good prompt, you paid for training and got a prompt.
  • The tuned model. The same prompt template as at training time, since the chat template is part of the model (see chapter 03). Use the decoding settings you will serve with.
  • The incumbent, Claude Sonnet 5.5 through the API with the production prompt. This is the arm that answers "can we turn the old system off?" and it is the arm the ship decision is made against.

The comparisons are paired: for every claim, record whether the tuned model's summary is acceptable and whether the comparator's is. Only the claims where they differ carry information. The tuned-against-untuned pair will be lopsided. If training worked, an illustrative result is 140 claims fixed, 20 broken and 240 unchanged, a net gain of 120 claims or 30 points, and no interval is needed to see it. The tuned-against-incumbent pair is the close one, and it is where the care goes.

Report every result per slice, using the slices that were fixed when the set was built: motor, property and liability claims, and US and UK regions. A model tuned on 18 months of adjuster edits will have seen far more motor claims than liability ones, and the average hides it. The UK slice matters most: the point of the move is UK data residency, so a weaker UK result fails the project whatever the headline says.

Capability regression on general benchmarks

Fine-tuning on one narrow task can erode abilities you did not train and did not test. The evidence is that how much depends on the method. Biderman et al. (2024) compared LoRA with full fine-tuning on programming and maths and found LoRA learns less than full fine-tuning but also forgets less, keeping more of the base model's performance on tasks outside the target domain. That supports the LoRA choice in chapter 04. It does not make forgetting zero, so you measure it.

You need two standard benchmarks, chosen for what they would catch.

  • IFEval (Zhou et al., 2023) measures whether the model follows instructions whose compliance can be checked by code: 25 types of verifiable instruction, such as "answer in fewer than N words" or "include the keyword X", across about 500 prompts. A tuned summariser is the classic way to lose this. Train hard on one output format and the model may stop obeying a different one, which matters if adjusters or downstream code ever ask the model for something else.
  • MMLU (Hendrycks et al., 2020) covers 57 subjects of multiple-choice questions and is a proxy for broad knowledge. It is saturated for strong models, so it discriminates poorly but works as a damage alarm. MMLU-Pro (Wang et al., 2024) widens the choices from four to ten and reports accuracy drops of 16% to 33% against MMLU, which restores some headroom. Use whichever your base checkpoint's card reports, so you can check your harness against the published number before trusting a delta.

Run both with a fixed harness on the untuned checkpoint and the tuned one, with identical settings. The EleutherAI lm-evaluation-harness carries both tasks, supports a vLLM backend, and loads a LoRA adapter on its Hugging Face backend through a peft= model argument. The README documents adapters only for that backend, so on the vLLM backend check before assuming.

The noise is larger than people expect. On a 500-prompt set with an 80% pass rate, the standard error of one score is √(0.8 × 0.2 / 500), about 1.8 points, so two unpaired runs differ by 3.5 points before anything is wrong. A 2-point drop on IFEval is invisible this way. Compare the same prompts item by item, and set the gate by what you can detect: "no drop larger than the interval can exclude, and any drop on a category you rely on is investigated". A general-benchmark gate catches collapse, not drift. For drift see the production signals in chapter 08.

Safety regression: the gate with no interval

Qi et al. (2023) showed that safety alignment is shallow enough to be removed by fine-tuning. They jailbroke GPT-3.5 Turbo by fine-tuning it on only 10 adversarial examples, at a cost under $0.20 through OpenAI's fine-tuning API. They also report that benign fine-tuning on ordinary data can degrade safety, which is the case that applies here: Harbourline's data is adjuster summaries, not attacks, and the risk is still real. Supervised fine-tuning rewards matching the target text, and a learned refusal is one more behaviour the update can move.

Harbourline's constraint is concrete. The tuned model must not regress on refusing to invent policy terms. A summary that says a claim is covered under a clause the policy does not contain can lead an adjuster to a wrong payment decision. So build a refusal set, separate from the 400 summaries:

  • Prompts that invite invention. Claims where the policy text lacks the clause, and the user or the claim notes ask the model to state a limit, deductible or exclusion anyway. Include variants that pressure the model ("the customer says it is covered, confirm").
  • A programmatic check where possible. The output must not assert a coverage term that is absent from the policy text supplied in the prompt, or must say the information is not available. Use a judge only for the residue (see below).
  • Both models run on the same prompts. The untuned checkpoint gives the baseline rate of invention, and the incumbent gives the bar.

Size the set for the claim you need to make. If the tuned model invents a term on none of 150 prompts, the 95% upper bound on its true rate is about 3 / 150, which is 2%. That is the strongest statement 150 clean results support, and it may not be strong enough for a payment-affecting failure. To show an upper bound of 0.5% you need about 600 clean prompts.

This is a zero-tolerance gate in the sense used in the evals guide: one confirmed invention of a policy term blocks the release until it is understood. The usual repairs are data repairs. Add refusal examples to the SFT mix, or use preference pairs from chapter 05 that prefer "not stated in the policy" over a fabricated term. Test both with this same set. If the model passes the task and fails this gate, the fine-tune is not shippable, however good the average looks.

Judging a new output style

Summaries are open-ended, so some scoring needs a judge, and a fine-tuned model breaks the judge's calibration in a specific way. Your calibration, done for Sonnet's style, may not transfer. The tuned model writes like the adjusters who edited the training data: shorter, in their phrasing, with their abbreviations. A judge with verbosity or self-preference bias will mark down the terse house style and mark up the incumbent, which is the same family as the judge if you use a Claude model. The evals guide gives the evidence for those biases.

So recalibrate on the new outputs before you trust a score. Take 150 to 200 pairs of tuned and incumbent summaries, have adjusters label which is acceptable, and measure the judge's agreement with them by the procedure in the evals guide: raw agreement, kappa and agreement by slice. If the judge fails terse summaries that adjusters accept, the judge is wrong for this ship decision and you should grade by human labels, or by reference-guided checks against the adjuster-approved gold summary, until it is fixed.

Check facts that code can check (policy number, claim date, amounts) by code, which has no style bias.

The ship decision, with an interval

Candidate A is a replacement, not an upgrade. The goal is cost and residency at equal quality, so the question is not "is the tuned model better?" but "can we show it is not worse by more than we can afford?" That is a non-inferiority test, and it needs the margin written down before the run: say, no more than 3 points worse overall and no more than 3 points worse on any slice that carries money.

The test works on the discordant claims. Take an illustrative result against the incumbent on the 400 claims: the tuned model is right and Sonnet wrong on 27, and the reverse on 33. The difference is (27 − 33) / 400 = −1.5 points, inside the margin. But the standard error of a paired difference is √(b + c − (b − c)² / n) / n, with b + c = 60 discordant claims, which gives √(60 − 0.09) / 400 = 1.9 points. A one-sided 95% lower bound is −1.5 − 1.645 × 1.9 = −4.7 points. That is below −3, so the test fails. The point estimate says "fine" and the interval says "not shown".

noninferiority.py
import math

def noninferior(wins, losses, n, margin=0.03, z=1.645):
    """Paired non-inferiority. wins: tuned right and incumbent wrong; losses: the reverse."""
    delta = (wins - losses) / n
    var = (wins + losses - (wins - losses) ** 2 / n) / n ** 2
    lower = delta - z * math.sqrt(var)          # one-sided 95% lower bound
    return delta, lower, lower > -margin

def n_needed(discordant, margin, z_a=1.645, z_b=0.842):
    """Items to show non-inferiority at 80% power if the true difference is zero."""
    return math.ceil((z_a + z_b) ** 2 * discordant / margin ** 2)

print(noninferior(27, 33, 400))   # (-0.015, -0.0468, False)
print(n_needed(0.15, 0.03))       # 1031

If 15% of claims differ between the two systems, showing non-inferiority within 3 points needs about 1,030 claims, and within 5 points about 370. Both assume the true difference is zero. The 400-claim set cannot do it. You have three honest options. Widen the margin, if the business accepts the risk of a wider one. Grow the held-out set from the production log, using the stratified sampling of chapter 02 in the evals guide. Or improve the model until it wins more than it loses, and the bound clears. Shipping on a point estimate because the set is small is the one option that is not honest.

The gates sit beside the quality test, as in the evals guide. The tuned model must pass the capability check, the safety gate, the per-slice margins, and the cost and latency gates. The cost gate is the reason for the project, so state it as arithmetic against the incumbent from the neocloud pricing comparison and the serving guide's capacity chapter, not as a hope. Write the thresholds in a file under version control, set by the owner of the risk, before anyone sees the numbers. Then the result is a pass, a fail or "not shown", and each of those has a next action.

The margin flips when residency law forces the move: the question becomes how much quality to give up, and the person with authority to give it up sets the margin.

✓ Check yourself

Answer from memory before opening each one.

  1. Your tuned summariser beats the incumbent by 2 points on the held-out set, and your colleague wants to ship. Which two other comparisons do you ask for first, and what does each rule out?

    Show answer

    The untuned instruct checkpoint with a strong prompt, which shows whether the weights or the prompt produced the gain. And the capability and safety checks against that same untuned base, which show what training cost. A task win alone does not rule out either. See the three arms.

  2. IFEval has about 500 prompts and your tuned model scores 78% against 80% for the base. Why can you not call that a regression, and what would you change?

    Show answer

    One score has a standard error near 1.8 points, so a 2-point gap sits inside the noise of unpaired runs. Compare the same prompts item by item, which cuts the noise, and decide in advance what size of drop you can detect. Even then the benchmark catches collapse, not slow drift. See capability regression.

  3. The tuned model refuses to invent a policy term on all 150 test prompts. A manager reads that as "failure rate zero". What is the defensible claim, and how many clean prompts would back a claim of 0.5%?

    Show answer

    With no failures in 150, the 95% upper bound on the true rate is about 3 / 150, or 2%. A 0.5% bound needs about 600 clean prompts. The tempting reading treats a sample result as the population rate. See the safety gate.

  4. The LLM judge you calibrated for Sonnet's summaries now ranks the tuned model's summaries below Sonnet's, but adjusters like them. What do you suspect and what do you do before believing either ranking?

    Show answer

    The terse house style is meeting a judge with verbosity or self-preference bias, so the judge is mis-calibrated for the new outputs. Re-label 150 to 200 pairs with adjusters, measure agreement by slice and direction, and grade by human labels or code checks until the judge passes. See judging a new style.

  5. The tuned model is 1.5 points behind the incumbent on 400 claims, inside a 3-point margin. Why does the ship decision still come back "not shown", and what are your options?

    Show answer

    The one-sided lower bound is near −4.7 points because only 60 claims differ, and the bound, not the point estimate, has to clear the margin. Widen the margin by decision, grow the held-out set toward 1,000 claims, or improve the model. See the ship decision.

  6. A teammate proposes training the safety refusal in once, then testing only the task on each retrain. What breaks in that plan?

    Show answer

    Every retrain moves the weights again, and Qi et al. show that refusals can be lost through fine-tuning, even on benign data. The refusal set is part of the gate on every run, not a one-off. See the safety gate.

Takeaway

  • A tuned model is evaluated on three things at once: the task, the capability it had before, and the refusals it was trained to keep. A win on one does not offset a loss on another.
  • Compare the tuned model with the untuned checkpoint and with the incumbent on the same held-out claims, in pairs, and report every slice.
  • General benchmarks such as IFEval and MMLU catch collapse, not drift, and their noise hides small drops unless you compare item by item.
  • Fine-tuning can erode safety behaviour, even with ordinary data, so the refusal set runs on every retrain and one confirmed failure blocks release.
  • A judge calibrated on the incumbent's style must be recalibrated on the tuned model's output before it is used for a ship decision.
  • A replacement is shipped on a non-inferiority bound set before the run, and when the set is too small to show it the answer is "not shown", not "ship".
