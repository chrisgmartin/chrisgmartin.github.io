Section C · Training

Supervised Fine-Tuning

Full fine-tuning against LoRA and QLoRA with the memory arithmetic, rank, alpha and target modules, learning rate, epochs and packing, the frameworks as of November 2026, and reading a loss curve for overfitting and forgetting.

Overview

Chapter 03 left Harbourline with about 22,000 claim-to-summary pairs. This chapter turns them into weights on one rented H100: which parameters to train, what that costs in bytes, which settings matter, and how to read the loss curve.

The worked model is Qwen3-8B, which lists Apache-2.0 on its model card and has 8,190,735,360 parameters according to the Hugging Face API in November 2026. Chapter 02 owns the pick. Harbourline volumes are illustrative.

Where the bytes go

Training memory has four parts: weights, gradients, optimiser state and activations. The middle two scale with the number of trainable parameters, which is the whole case for LoRA. The ZeRO paper (Rajbhandari et al., 2019) gives the accounting for mixed-precision Adam: 2 bytes per parameter for BF16 weights, 2 for BF16 gradients, and 12 for the optimiser's FP32 master copy, momentum and variance. That is 16 bytes per parameter, or 131 GB for Qwen3-8B before one activation is stored. An H100 has 80 GB, so a full fine-tune does not fit on one card.

LoRA freezes the base. A frozen weight needs no gradient and no optimiser state, so only its 2 bytes remain, and the adapter is small. QLoRA stores the frozen base in 4 bits.

Activations come on top. With gradient checkpointing, which TRL enables by default, each layer keeps only its input. A micro-batch of 4 sequences at 4,096 tokens is 16,384 tokens, so layer inputs cost 36 × 16,384 × 4,096 × 2 bytes, or 4.8 GB. The logits are the surprise: 16,384 × 151,936 vocabulary entries × 2 bytes is 5.0 GB, and 10.0 GB if the loss upcasts to FP32. The LoRA run therefore needs roughly 17 + 5 + 5 to 10 GB plus one layer's working set. It fits in 80 GB. These are estimates, so read the real peak from torch.cuda.max_memory_allocated().

A pure-BF16 full fine-tune fits on paper and still fails

Dropping the FP32 master copy gives 65.5 GB, which looks feasible. The trouble is rounding. BF16 keeps 7 explicit mantissa bits, so a weight near 0.02 moves in steps of about 0.000122, and an Adam update of 0.00005 is rounded away. Check it: torch.tensor([0.02], dtype=torch.bfloat16) + 5e-5 equals 0.02. The FP32 master copy exists to catch these small updates, and at full fine-tuning rates of 1e-5 to 2e-5 most of them are small.

What LoRA changes, and the four settings that matter

Hu et al. (2021) freeze a weight W and learn ΔW = BA, where A is r × d_in with random Gaussian values and B is d_out × r and starts at zero. The model therefore begins where the base left off, and the update is scaled by α/r. For a 4,096 × 4,096 projection at r = 16 the adapter holds 131,072 values against 16.8 million, 0.78%. After training, ΔW folds into W at no inference cost, which chapter 08 uses.

Target modules. The original paper adapted only the attention query and value projections. Dettmers et al. (2023) found LoRA on all linear layers is required to match full fine-tuning. On Qwen3-8B the three MLP projections hold 78% of each block's linear weights, so attention-only LoRA leaves most of the model without an adapter. Use target_modules="all-linear".

Rank. In the QLoRA ablations, rank made no measurable difference once every linear layer carried an adapter. Biderman et al. (2024) qualify that: on hard targets such as continued pre-training for code and maths, LoRA underperforms full fine-tuning substantially, and full fine-tuning learns a weight change of rank 10 to 100 times higher than typical LoRA settings. On instruction data, higher ranks closed most of the gap. Harbourline's task is a narrow format over knowledge the base already has, so start at r = 16 and run r = 64 once. That adapter is 174.6 M parameters and 2.8 GB of state. If 64 does not beat 16 on the validation slices, keep 16. If neither meets the bar from chapter 01, the task may need capability LoRA cannot add, and a full fine-tune is the next experiment.

Alpha and dropout. With Adam, changing α is roughly the same as changing the learning rate, and Hu et al. set it to the first rank they tried without tuning it. Fix α = 2r, the ratio Biderman et al. used, and sweep the learning rate. QLoRA used dropout 0.1 up to 13B parameters and 0.05 above. Use 0.05, and remove it first if the run underfits.

QLoRA: use it when the BF16 base will not fit

QLoRA stores the frozen base in 4-bit NormalFloat and dequantises each block to BF16 for the matrix multiply. One FP32 scale per 64 weights costs 0.5 bits per parameter, and double quantisation brings that to 0.127. Paged optimisers absorb the memory spikes checkpointing causes on long sequences. With these, Dettmers et al. fine-tuned a 65B model on one 48 GB GPU and matched 16-bit fine-tuning on their tasks.

On Qwen3-8B the saving is 16.4 GB down to 6.1 GB, assuming the embedding table and output head stay in BF16, and Harbourline has 80 GB. QLoRA would trade step time, since every layer dequantises on the fly, for memory it does not need. The slowdown was not benchmarked on this model, so measure it before you decide. QLoRA earns its place on a small card such as a 24 GB workstation, or for a large model: a 70B base in BF16 is 140 GB.

The step arithmetic: 500 of the 22,000 rows go to validation, leaving 21,500. At 32 sequences per step that is 672 steps per epoch and 1,344 for two. Split by claim, not by pair, and keep validation apart from the 400-claim set in building the eval set. Validation loss steers training, and the held-out set decides shipping.

Truncation hurts quietly. TRL keeps the start of anything over max_length. A summary cut short loses its end-of-turn token, so the model sees examples that never finish. If the prompt alone exceeds the limit, the whole completion is masked and the row is dropped. Both effects fall on your longest, hardest claims. Measure the 99th percentile of token length, then set the limit above it or filter long rows deliberately and record how many.

Packing. Without packing, each batch pads to its longest sequence. If claims average 2,000 tokens and a batch pads to 3,500, 43% of positions are padding. packing=True concatenates sequences into fixed blocks, and the default bfd strategy needs FlashAttention 2 or 3. Leave it off for the first run and turn it on when step time is the problem.

A minimal run

The script applies the choices above to a prompt-completion JSONL file. It was smoke-tested end to end for three steps on CPU with a 135-million-parameter model, using MODEL=HuggingFaceTB/SmolLM2-135M-Instruct MAX_STEPS=3. It was not run on an H100 or at 8B scale, so treat this chapter's memory and time figures as arithmetic to confirm. With a prompt and a completion per row, TRL masks the prompt out of the loss. Only the adapter is saved: 43.6 M parameters in FP32 is about 175 MB, against 16.4 GB for a full BF16 checkpoint.

train_sft.py
# train_sft.py: LoRA SFT on claim-to-summary pairs. Tested with trl 1.17.1, peft 0.21.2,
# transformers 5.22.2, torch 2.15.0. Set MODEL and MAX_STEPS to smoke-test on a small model.
import os
import torch
from datasets import load_dataset
from peft import LoraConfig
from trl import SFTConfig, SFTTrainer

MODEL = os.environ.get("MODEL", "Qwen/Qwen3-8B")
MAX_STEPS = int(os.environ.get("MAX_STEPS", "-1"))
cuda = torch.cuda.is_available()

# One JSON object per line: {"prompt": [{"role": "user", ...}], "completion": [{"role": "assistant", ...}]}
# With this layout TRL puts the loss on the completion only, so the claim text is not trained on.
data = load_dataset("json", data_files={"train": "claims_train.jsonl", "validation": "claims_val.jsonl"})

lora = LoraConfig(
    r=16, lora_alpha=32, lora_dropout=0.05,
    target_modules="all-linear",          # every linear layer except the output head
    task_type="CAUSAL_LM",
)

args = SFTConfig(
    output_dir="out/harbourline-sft-lora",
    num_train_epochs=2,
    max_steps=MAX_STEPS,
    per_device_train_batch_size=4,
    gradient_accumulation_steps=8,       # effective batch 4 x 8 = 32 sequences
    learning_rate=2e-4,                  # LoRA tolerates about 10x the full fine-tune rate
    lr_scheduler_type="cosine",
    warmup_steps=0.03,                # a float below 1 is a share of total steps (Transformers 5)
    max_length=4096,
    bf16=cuda,
    model_init_kwargs={"dtype": torch.bfloat16 if cuda else torch.float32},
    eval_strategy="epoch" if MAX_STEPS < 0 else "no",
    save_strategy="epoch" if MAX_STEPS < 0 else "no",
    logging_steps=10,
    report_to="none",
    seed=7,
)

trainer = SFTTrainer(model=MODEL, args=args, train_dataset=data["train"],
                     eval_dataset=data["validation"], peft_config=lora)
trainer.model.print_trainable_parameters()
trainer.train()
trainer.save_model()                      # writes the adapter only

Reading the loss curve

Log training loss every 10 steps and validation loss every epoch. Four shapes cover most runs.

  • Both fall, then flatten together. The run is healthy. Part of the floor cannot be lowered, because two adjusters write different valid summaries of one claim.
  • Training falls, validation turns up. The model is memorising. Illustratively, validation at 0.91, 0.88, 0.93 across three epochs says to keep the epoch-2 checkpoint, then use fewer epochs or more data.
  • Loss spikes or goes to NaN. The learning rate is too high for the batch, or a malformed row produced an empty target.
  • Validation improves but the slices regress. Loss averages over tokens, and the few tokens that decide whether a summary is correct barely move it.

The last case includes forgetting. Biderman et al. found that LoRA learns less than full fine-tuning but also forgets less of the base model's behaviour outside the target domain, and does so better than weight decay or dropout. That makes LoRA the safer default for Harbourline's constraint that the tuned model still refuse to invent policy terms. Safer is not safe: loss will not show a lost refusal, so chapter 07 tests it directly. The ship decision is a paired comparison with an interval, as in the ship decision.

✓ Check yourself

Answer from memory before opening each one.

  1. A colleague plans a full fine-tune of the 8.19 B model on one 80 GB H100 with mixed-precision AdamW. What is the static memory, and what is the smallest change that makes it fit?

    Show answer

    16 bytes × 8.19 B is 131 GB, so it does not fit. LoRA keeps the BF16 base at 16.4 GB and adds 0.7 GB of adapter state, 17.1 GB in all. Pure BF16 gives 65.5 GB but rounds small updates away. See where the bytes go.

  2. Rank 16 and rank 64 reach the same validation loss and per-slice scores. Which do you carry forward, and what would change your mind?

    Show answer

    Rank 16: 43.6 M parameters against 174.6 M, and the extra capacity bought nothing. Choose higher rank if it wins on a slice that matters, or if the target looks like new knowledge, where Biderman et al. found LoRA underperforms. See what LoRA changes.

  3. Over three epochs training loss falls from 0.80 to 0.55 while validation loss is 0.91, 0.88 and 0.93. What happened, which checkpoint do you keep, and what do you check before shipping it?

    Show answer

    The model began memorising in epoch 3, so keep epoch 2. Then run the held-out evaluation by slice and the refusal check, which validation loss does not measure. See reading the loss curve.

  4. You set max_length=1024 and claims average 1,500 tokens. Name two things that go wrong, and the first thing you measure.

    Show answer

    Rows whose prompt alone exceeds the limit have the whole completion masked and are dropped, so the longest claims vanish. Rows cut mid-summary lose the end-of-turn token, so the model learns summaries that do not end. Measure the token-length percentiles. See the settings table.

  5. Peak memory is well above your estimate, and you passed the model to the trainer as a string. What do you check first?

    Show answer

    The load dtype. TRL 1.17.1 loads a model given by name in FP32 unless model_init_kwargs sets dtype, so the base takes 32.8 GB instead of 16.4 GB. See frameworks.

Takeaway

  • Full fine-tuning in mixed precision costs 16 bytes per parameter, 131 GB for an 8B model, because gradients and Adam state are 14 of those bytes.
  • LoRA keeps the BF16 base frozen and trains about 0.5% of the parameters, so static memory drops to about 17 GB and one H100 has headroom.
  • Put LoRA on all linear layers, fix alpha at twice the rank, start at rank 16, and spend the sweep on the learning rate.
  • QLoRA trades step time for memory, so use it when the BF16 base does not fit.
  • Truncation and dtype defaults fail silently, so measure token lengths and pass the dtype explicitly.
  • Validation loss says when to stop, not whether the model is good; the held-out evaluation decides that.
