Serving and Retraining

A tuned model is a file until it is versioned, served and replaced. This chapter decides between merged weights and adapters, surveys provider fine-tuning APIs as of November 2026, and sets how Harbourline releases, watches and retrains the model, including when the base model changes.

Merged weights or adapters

The training run ends with an adapter, and the first serving decision is whether to keep it separate. Both forms are the same model. A LoRA adapter stores, for each targeted weight matrix W, two thin matrices A and B whose product is the update, so the tuned layer computes W·x + B·(A·x). Merging adds B·A into W once and discards the adapter. The merged model has the base architecture and no extra cost at inference. The unmerged one runs two extra small matrix products per adapted layer.

The sizes make the trade concrete. Take Qwen3-8B, whose Hugging Face config gives 36 layers, hidden size 4,096, 32 attention heads and 8 key-value heads of 128 dimensions (so key and value projections are 1,024 wide), and a 12,288-wide feed-forward layer. A rank-16 adapter on all seven projections has 16 × (4,096 + 4,096) × 2 for the query and output projections, 16 × (4,096 + 1,024) × 2 for key and value, and 16 × (4,096 + 12,288) × 3 for the feed-forward ones. That is about 1.21 million parameters per layer and 43.6 million over 36 layers, which is about 87 MB in BF16. The base is about 16 GB in BF16 (roughly 8 billion parameters × 2 bytes). So an adapter is about 0.5% of the model.

That 0.5% is the reason to keep adapters when you have many of them and the reason to merge when you have one. Candidate A has one task and one adapter, so merge it: the served artefact is an ordinary checkpoint, every engine in the serving guide's engines chapter can load it, and there is no adapter machinery to operate. Merge into BF16 weights, quantise afterwards if you quantise (see its quantisation chapter), and run the evaluation from chapter 07 on the artefact you will serve, not on the one you trained. Merging and quantising both change the numbers a little, and the eval has to see the final file.

Keep the adapters separate when one base serves several behaviours. If Harbourline later tuned a second adapter for another line of business, or one per region, two adapters of 87 MB cost almost nothing next to a second 16 GB model, and they share the base weights and the KV-cache memory of a single deployment.

Serving many adapters from one base

Batching is the idea behind multi-adapter serving. A GPU is efficient when it processes many requests at once, and requests for different adapters cannot normally share a batch, because each has a different W. S-LoRA (Sheng et al., 2023) keeps the base computation shared and applies each request's small adapter product separately, so one batch can mix adapters. Its abstract claims serving thousands of adapters on a single GPU or across several, and up to 4 times the throughput of Hugging Face PEFT and of vLLM with naive LoRA support. Those are its numbers on its benchmarks, and a reason to try the design, not a forecast for yours.

vLLM supports this directly, as of its current documentation. The server flag --enable-lora turns it on, --lora-modules name=path registers adapters at start-up, and --max-lora-rank must be set to the highest rank among your adapters, since a much higher value wastes memory. A client picks an adapter by putting its name in the model field of the request. Requests with adapters run alongside base-model requests on the same server.

serve-adapters.sh (sketch)
# Sketch: flag names from the vLLM LoRA documentation; paths and names are illustrative.
vllm serve BASE_MODEL_ID \
  --enable-lora \
  --max-lora-rank 16 \
  --lora-modules claims-summary=/models/adapters/claims-summary-v3

# A client then asks for the adapter by name:
#   {"model": "claims-summary", "messages": [ ... ]}

vLLM can also load and unload adapters at run time, through the /v1/load_lora_adapter and /v1/unload_lora_adapter endpoints, but only if you set VLLM_ALLOW_RUNTIME_LORA_UPDATING=True, and its documentation warns that this is a security risk to use only in isolated, fully trusted environments. Treat that endpoint as an admin interface, not as a deployment mechanism. A rollout that anyone on the network can trigger is not a rollout.

The flip is cost. Multi-adapter serving is a cost and operations saving when you have many adapters with uneven traffic. For one adapter on a nightly batch it adds a flag and a failure mode for no gain, so it stays off.

Three consequences follow. First, a provider-tuned model carries the provider's lifecycle. OpenAI's fine-tunes die with their base models, and the base is dated. Open weights you hold do not deprecate, which weighs in favour of the route in this guide. Second, a provider API gives you a tuned model but not the inference-time control you get from owning the stack: you cannot choose the quantisation, the batch policy or the region beyond what the vendor offers. Third, for Candidate A the residency goal decides it. The constraint is UK data residency, and a vendor's tuning service is a processor for your training data, so the question for legal is where the data and the tuned model live. If a provider region satisfies that, a provider fine-tune is a legitimate shortcut, and the cost model is the one in chapter 01, with a per-token surcharge in place of GPU hours.

Versioning, canary and rollback

A tuned model is the product of five inputs: the base checkpoint, the training data, the training code and settings, the merge or quantisation step, and the eval that passed it. If any is unrecorded you cannot reproduce the model or explain a regression. Store one manifest per release: the base model's revision hash, the data snapshot identifier, the adapter hash, the eval report with its gates, and the serving configuration. The model's name in production is a version of that manifest, never "latest".

[train] → [eval gates: ch07] → [manifest + artefact] ↓ [shadow: run on nightly batch, not shown to adjusters] ↓ [canary: ~5% of claims to the new model, edit rate watched] ↓ [full rollout] [rollback: re-point to previous manifest]

Harbourline's nightly batch is a gift for staging because nothing is interactive. Run the new version in shadow on a full night's 6,000 claims alongside the current one, compare the outputs by the paired method of the evals guide, and only then give it a slice of the real queue. A 5% canary is 300 claims a night. The signal that matters is the one adjusters already produce: how much they edit the summary. An edit rate that rises against the incumbent's, within a night or two, is the rollback trigger, and it should be written before the canary starts. The evals guide's rollback section covers the mechanics, and the serving guide's operations chapter covers the serving side.

Rollback needs the previous artefact to be warm and the routing to be a configuration change. Keep the last two released versions loaded or one command from loaded, and make the switch a flag. If rolling back means rebuilding a container, the canary was theatre.

Drift and retraining triggers

A tuned model is frozen against the world at the moment of training. The data it learned from, 18 months of adjuster-edited summaries, stops being the data it sees. Claim wording shifts, a new claim type appears, the policy wordings change, adjusters change their house style. None of that shows in the held-out set, because that set is also frozen. You find out in production, and the evals guide's drift chapter lays out the signals. For a tuned model the useful ones are three.

  • Adjuster edit rate on summaries, by slice. A slow rise is the drift signal, and a step change usually means an upstream format change or a bad release.
  • Input shift. The share of claims of each type and region against the training mix, and the share containing wording the training data never had. A claim type with 2% of the training data and 15% of tonight's queue is a trigger by itself.
  • Refusal-set and held-out re-runs. Re-run the chapter 07 gates monthly against a fresh sample, because the production log, not the frozen set, is where the answer lives.

Retraining is not free, so set the triggers instead of a calendar alone. A reasonable pair: retrain when an edit-rate or input-shift trigger fires, and otherwise review quarterly. The data supply sets the practical floor. Harbourline's 40,000 pairs over 18 months is about 2,200 a month, about 1,200 a month after the filtering of chapter 03. At a quarter, that is about 3,700 new filtered pairs, 17% on top of the 22,000 you hold. That may not move the model much, which is an argument for a longer cadence unless a trigger fires. The cost of a run comes from chapter 06. The cadence flips when claims change faster than your data: a regulatory change to a form, or a new product line, makes the old data wrong rather than merely old, and the answer is to retrain on new data with the stale pairs removed.

When the base model changes

An adapter is a difference from one specific set of base weights. It was fitted so that W plus the update behaves well, and on a different W the same update means something else. A new release of the base, even from the same family and the same shapes, makes the old adapter at best untested and at worst wrong, so the adapter does not move. The data does. You rerun training on the new base with the same filtered pairs, which is why the data and its manifest are the real asset, and you rerun every gate in chapter 07.

That decision comes in two kinds. A security or licence fix, or a base your engine no longer supports, is forced. A better base is optional, and the question is the one in chapter 02: does it beat your current tuned model on the held-out set after you tune it? Do not upgrade because a release is new. A tuned 8B model that passes its gates is a working system, and a base change restarts the cost.

Candidate B in this guide, the claims-intake agent, never had this problem, since a prompt and retrieval carry across a base change with only a re-run of the evals. That portability is a real, recurring benefit of not fine-tuning, and it belongs in the cost of Candidate A.

✓ Check yourself

Answer from memory before opening each one.

  1. Harbourline has one adapter, for the nightly batch, and a colleague wants multi-adapter serving "for flexibility". What do you ask, and what would change your answer?

    Show answer

    Ask what the second adapter is. With one adapter, merging gives a plain checkpoint that every engine loads and no adapter code to operate. Several adapters with uneven traffic on one base would flip it, since each costs about 87 MB against 16 GB for a second model. See merged weights or adapters.

  2. Why can requests for different adapters not simply share a batch the way requests for one model do, and what do S-LoRA-style systems do instead?

    Show answer

    Each adapter implies a different effective W, so a plain batch cannot mix them. The shared base computation is done once for the whole batch and the small per-adapter products are applied separately, so mixed adapters share a batch. See serving many adapters.

  3. Your legal team prefers a managed fine-tuning API. Which facts about November 2026 do you check first for each of OpenAI, Google and Anthropic?

    Show answer

    Whether the route is open. OpenAI has closed it to new organisations and shuts GPT-4.1 fine-tunes on 14 January 2027. Google lists Gemini models for tuning, so check region and residency terms. Anthropic's documentation lists no fine-tuning for current Claude models. See the provider table.

  4. The new version scores well on the gates but you are unsure about a full rollout. What does a shadow run on the nightly batch tell you that the held-out set cannot?

    Show answer

    It tests the current queue, not the frozen sample, so it shows input shift and real format changes, and it can be compared claim by claim with the live version. The canary then adds the adjuster edit rate. See versioning, canary and rollback.

  5. Edit rate has risen slowly for three months with no release. Name two causes you would test and the data you need for each.

    Show answer

    Input shift, tested by comparing today's claim-type and wording mix against the training mix, and changed adjuster style or policy wording, tested by sampling recent edits. Edit rate by slice separates the two. See drift and retraining triggers.

  6. A new release of the base family appears, with the same shapes. Someone proposes loading the existing adapter onto it. Why is that wrong, and what carries over?

    Show answer

    The adapter is a difference fitted to the old weights, so on new weights it means something else even if it loads. The data, manifest and gates carry over, so you retrain on the same pairs and rerun the evaluation. See when the base changes.

Takeaway

  • An adapter is about 0.5% of the size of its base. Merge a single adapter into a plain checkpoint and keep adapters separate only when several share one base.
  • Evaluate the exact artefact you serve, after merging and any quantisation, not the one you trained.
  • vLLM serves many adapters from one base and selects them by model name, and its runtime-loading endpoint is for trusted environments only.
  • As of November 2026, OpenAI has closed fine-tuning to new organisations and is shutting GPT-4.1 fine-tunes, Google tunes Gemini models, Bedrock tunes Nova and Llama models, and Anthropic documents no fine-tuning of current Claude models.
  • Version every release as a manifest of base, data, adapter, eval report and serving configuration, canary it on the nightly batch, and make rollback a configuration change.
  • Retrain on triggers, edit-rate rise and input shift, with a review cadence behind them. A new base means retraining on the same data, not moving the adapter.
