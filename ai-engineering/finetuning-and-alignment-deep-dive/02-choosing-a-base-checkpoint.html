Section B · Deciding and preparing

Choosing a Base Checkpoint

What pre-training leaves you: base, instruct and reasoning checkpoints, the scale and data behind them, context and knowledge cutoff, licences and their terms as of November 2026, and how to shortlist and test candidates.

What pre-training leaves you

A checkpoint is one point in a pipeline, and which point you start from decides how much of the assistant you have to build. The Llama 3 paper describes the stages. Pre-training on a large text corpus produces a model with, in the paper's words, "a rich understanding of language" that "does not yet follow instructions or behave in the way we would expect an assistant to." Post-training then aligns it over several rounds, each of supervised fine-tuning on instruction data followed by Direct Preference Optimization, and adds capabilities such as tool use on the way.

Vendors publish different cuts of that pipeline, and the names are not standard.

  • Base. The pre-trained model only. It continues text and has no habit of answering. Qwen's model card for the Qwen3.5-9B base says its intended uses are fine-tuning and in-context learning experiments, not direct conversation.
  • Instruct or chat. The base after post-training. It follows instructions, uses a chat template, and carries whatever safety behaviour the vendor trained in.
  • Reasoning or hybrid. An instruct model that can spend output tokens thinking first. Qwen3-8B exposes a switch, enable_thinking, in its chat template. Thinking is on by default, and setting the flag to false produces no think content.

Start Harbourline's summariser from the instruct checkpoint. With about 22,000 pairs you are teaching a task and a house style, and LIMA's result says that is enough for style. You are not rebuilding instruction following, refusal behaviour or tool use, and the instruct model already carries those from several rounds of vendor post-training on far more data than you hold. Starting from base would make you own all of it, and the refusal behaviour matters here, because chapter 07 has to show the tuned model still refuses to invent policy terms.

Start from base when you need control of the template and the whole output distribution, for example a model that must emit a strict token format that no instruct template accommodates, and when you have enough varied data to teach everything. The exception to the exception is a vendor-quality instruct model whose habits fight your target. If a chatty, hedging instruct model keeps adding preamble that your summaries must not have, tuning can remove it, but you pay in regression risk that you can measure on the held-out set.

For the nightly batch, run reasoning off. Thinking tokens are output tokens, so they cost latency and GPU time on every one of 6,000 claims, and classifying and summarising a claim does not need a chain of deliberation. Test that on the held-out set instead of assuming it. If a slice such as liability scores much lower with thinking on, you have found a cost worth paying on that slice only.

Scale and the data behind it

Parameter count is a poor proxy for capability, and the reason is training tokens. Hoffmann et al. (2022) found that for compute-optimal training, model size and training tokens should scale equally: double the parameters, double the tokens. Their 70B Chinchilla model was trained on four times the data of the 280B Gopher, to test that rule at a fixed compute budget.

Llama 3 shows what happens when you spend on the serving side instead. The paper says the flagship 405B model, trained on 15.6T tokens, is approximately compute-optimal for its budget, but that the smaller models were trained "for much longer than is compute-optimal", and that the result is that they "perform better than compute-optimal models at the same inference budget." The whole pre-training corpus is about 15T tokens, against 1.8T for Llama 2. Take the 8B model as having seen that corpus: 15T divided by 8B is roughly 1,900 tokens per parameter. The equal-scaling rule would call for far fewer.

Two things follow for the shortlist.

  1. A recent 8B or 9B checkpoint is much stronger than the same size from two years ago, so compare by release date and by your eval, not by size alone.
  2. The knowledge a checkpoint holds came from that pre-training. Fine-tuning will not add much to it, as chapter 01 showed, so a checkpoint weak on insurance vocabulary or UK English stays weak on them after 22,000 summaries. Probe for that in the bake-off.

Context window and knowledge cutoff

Read the context figure as the longest sequence the model was trained to handle, and read your own need as the training and serving sequence length, which is a memory cost. The claims in Harbourline's batch average a few thousand tokens, so even the smallest window here is ample, and a long window costs you in training memory only if you set the sequence length to it.

Model cards state these differently, so quote the one you read. As of November 2026:

The cutoff matters less than it looks. A summariser works from the claim in front of it, so a model that has never heard of last month's regulation still summarises correctly. It matters for anything the model must know unaided: a new vehicle model, a recent statute, a changed name. Anything the nightly job needs from outside the claim should arrive through retrieval, so the cutoff costs you nothing. If a card does not state a cutoff, ask the model about events across several months and find where its answers stop.

Licences, as of November 2026

The licence decides whether the tuned model can ship at all, and it is the one property a bake-off cannot show. Read the card for each candidate on the day you choose, because licences change between releases of the same family.

CheckpointLicence on the cardTerms that bite

Ministral 8B Instruct 2410Mistral Research LicenseCommercial use needs a separate agreement with Mistral

The last row is the trap. "Mistral" is not a synonym for Apache: the card for this 8B checkpoint says to contact the company for commercial use. Other Mistral releases were not checked for this chapter, so read each card. Apache 2.0 itself is light: it grants a perpetual, royalty-free patent licence from each contributor, requires you to keep notices and mark modified files, and gives no right to the licensor's trademarks. The patent grant ends for anyone who sues over the work for infringement.

For Harbourline the 700 million user clause is irrelevant, since the model serves an internal batch. The naming and attribution terms are not: a Llama-derived summariser inside a claims system is a model whose name must begin with "Llama", and that is a product decision somebody has to accept. Apache checkpoints remove the question. A licence that is cheap to comply with is worth a few points on an eval, and it is worth more if you plan to distil or merge later.

Tokenizer fit

The tokenizer sets how many tokens a claim becomes, and so the cost, the latency and the sequence length of every example. Vocabularies differ widely. The Llama 3 paper reports a vocabulary of 128K tokens. Qwen3-8B's tokenizer has 151,669 entries and Qwen3.5-9B's has 248,077, and Gemma 4 E4B's has 262,144. A larger vocabulary can pack text into fewer tokens, especially in other languages, at the price of a bigger embedding table.

Claims text is hard for a tokenizer. It is full of strings built for machines: policy numbers, registration plates, VINs, postcodes, amounts. These split into many short pieces, which costs tokens and makes exact copying harder. Measure it on your own text. The script below counts tokens for a synthetic claim note, whose identifiers are invented, and for one policy number. It ran with transformers 5.22.2 in November 2026. The Llama repository is gated behind a licence acceptance, so the script skips it unless you are signed in.

tokfit.py
import sys
from transformers import AutoTokenizer

NOTE = (
    "FNOL 14/03/2026 09:42. Insured reports rear-end collision on the A406 near Hanger Lane. "
    "Policy HL-UK-4471-0382-A, vehicle VIN WVWZZZ1KZAW123456, reg AB12 CDE. "
    "Third party vehicle: Ford Transit, reg XY19 ZZZ. Excess 250 GBP, claim reserve 3,480.00 GBP. "
    "Insured address 12 Example Road, London AB1 2CD. Adjuster notes whiplash alleged by "
    "third party; contact solicitor Ref. 2026/ML/55812. No police attendance."
)
for name in ["Qwen/Qwen3.5-9B", "Qwen/Qwen3-8B"] + sys.argv[1:]:
    try:
        tok = AutoTokenizer.from_pretrained(name)
    except Exception as e:                      # gated or missing repo
        print(f"{name:22s} not loaded: {type(e).__name__}")
        continue
    n = len(tok(NOTE, add_special_tokens=False)["input_ids"])
    k = len(tok("HL-UK-4471-0382-A", add_special_tokens=False)["input_ids"])
    print(f"{name:22s} vocab={len(tok):7d} note={n:3d} tokens ({len(NOTE.split())} words)  policy-id={k} tokens")
Qwen/Qwen3.5-9B        vocab= 248077 note=162 tokens (58 words)  policy-id=14 tokens
Qwen/Qwen3-8B          vocab= 151669 note=162 tokens (58 words)  policy-id=14 tokens
google/gemma-4-E4B     vocab= 262144 note=161 tokens (58 words)  policy-id=15 tokens

The three tokenizers agree to within a token on this note: about 2.8 tokens per word, and 14 or 15 tokens for a 17-character policy number. A bigger vocabulary did not help on this English text, and Qwen3 and Qwen3.5 gave identical counts. One note is a tiny sample, so run it on 200 real notes before you rely on it. For Harbourline the useful reading is the policy-number line: a model that spends 14 tokens on an identifier is one that can drop a character when copying it, and your held-out set should check exact identifier reproduction as its own item.

Shortlist, then a bake-off before any training

Filter first by what a bake-off cannot show: the licence, a size that fits your hardware, a context window above your need, and support in your training and serving stack. On the size filter, Qwen3-8B has 8.2B parameters, and in BF16 at two bytes each that is about 16 GB of weights. Qwen3.5-9B lists 10B parameters in its tensor metadata because it carries a vision encoder, so budget about 20 GB and expect a larger download. Either leaves most of an 80 GB H100 for the LoRA training state that chapter 04 sizes.

From the filter Harbourline's shortlist is Qwen3-8B, a text-only model under Apache-2.0 with 8.2B parameters, 36 layers and 32 query and 8 key-value attention heads, and the newer Qwen3.5-9B, February 2026, Apache-2.0, which adds a vision encoder that a text-only summariser does not use. Gemma 4 E4B, also Apache 2.0, has about 8B parameters counting embeddings but 4.5B effective. Llama 3.1 8B Instruct stays on the list as the licence contrast. The rest of this guide uses Qwen3-8B as its working example, because chapters 04 to 06 size their memory and cost on it. That is a provisional pick, not a result: nothing has been scored yet.

The bake-off is the cheap experiment that replaces opinion. Run each instruct candidate, untouched, on the held-out set built in the eval-set chapter, with the same prompt and the same few-shot examples that chapter 01 told you to tune first. At 4,000 input and 400 output tokens per claim, 400 claims are 1.6M input tokens and 0.16M output tokens per model. That is small. The real cost is the grading, which the evals guide covers.

Read the result in three ways.

  • Weakest slice, not the mean. Rank on the worst of motor, property, liability, US and UK. A model that wins on average and fails UK liability fails the job.
  • Gap to the API model. The distance from Sonnet 5.5 on each slice is the headroom tuning must cover. A 2-point gap is a different project from a 20-point gap.
  • Failure type. Format errors and over-long answers are what tuning fixes. Wrong facts about a claim are not.

The bake-off ranks starting points and does not predict final scores. The best untuned model is usually the best tuned one, but not always: a weaker model with more headroom can catch up. When two candidates are within the noise of a 400-item set, which for a pass rate near 90% is about 3 points either way overall and wider on a 70-item slice, run a short LoRA pass on the same few thousand examples for each and compare them again, since slice results on a small set carry wide intervals. The data for that pass is the subject of the next chapter.

✓ Check yourself

Answer from memory before opening each one.

  1. A teammate says the 405B model was trained on 15T tokens, so an 8B model from the same family must have seen far less. Is that right, and what does the answer imply about picking a checkpoint by parameter count?

    Show answer

    No. Llama 3 trained its smaller models far beyond the compute-optimal token count, on a corpus of about 15T tokens, because that gives a better model at a fixed inference budget. Size alone says little, so compare checkpoints by release date and by your own eval. See scale and data.

  2. You have 22,000 summary pairs. Argue for starting from the instruct checkpoint rather than the base, and say what would change your mind.

    Show answer

    The instruct model already follows instructions, uses a template and carries refusal behaviour from large-scale post-training, and 22,000 pairs teach a style without rebuilding that. It would change if you needed a strict output token format the instruct template cannot produce, and had enough varied data to teach the whole assistant. See what pre-training leaves you.

  3. A colleague proposes Ministral 8B because "Mistral models are Apache". What do you check, and what do you find on that card?

    Show answer

    Read the licence on the model card for that exact checkpoint. This one is under the Mistral Research License, and commercial use needs a separate agreement. Licences vary between releases from one vendor. See licences.

  4. The bake-off puts model X first on mean score and model Y second, but Y is far better on UK liability. Which do you carry forward, and what do you run to be sure?

    Show answer

    Judge on the weakest slice, so Y is likelier to be right if X fails UK liability. If the scores are within noise, run a short LoRA pass on the same subset for both and compare again, since untuned rank does not always predict tuned rank. See the bake-off.

  5. A model has a 262K context window and its card gives no knowledge cutoff. Does either matter for the nightly claims summariser, and why?

    Show answer

    Neither much. Claims run a few thousand tokens, so the window is ample, and a summariser works from the claim, so the cutoff matters only for facts the model must recall unaided, which retrieval should supply. See context and cutoff.

  6. Two tokenizers give 14 and 15 tokens for the same policy number. Why should that number shape the held-out set rather than the shortlist?

    Show answer

    The two tokenizers differ by one token, so it does not separate the candidates. What it shows is that identifiers cost many tokens each, so any model can drop or alter a character while copying one. The held-out set should score exact identifier reproduction as its own item. See tokenizer fit.

Takeaway

  • Start from the instruct checkpoint unless you need to own the template and can teach the whole assistant, because instruct models carry instruction following and refusal behaviour that a narrow dataset cannot rebuild.
  • Parameter count does not measure capability, because Llama 3 trained its small models for far more tokens than compute-optimal; compare by release date and by your own eval.
  • Fine-tuning will not add much knowledge, so a checkpoint that is weak on your vocabulary at the start stays weak afterwards.
  • Read the licence on the card for the exact checkpoint on the day you choose, since vendors ship permissive and restrictive licences within one family.
  • Measure tokenizer fit on your own identifiers and amounts, and put exact reproduction of identifiers in the held-out set.
  • Run an untouched bake-off on the held-out set before any training and rank on the weakest slice, because the licence, the gap to the API model and the failure types decide the project.
