Section B · Deciding and preparing

When to Fine-Tune

Prompting, retrieval and fine-tuning as three different tools: what each changes in the model's behaviour, the cost model of each, the eval-first rule, and the decision for Harbourline's two candidate systems.

Three tools that change different things

The question "should we fine-tune?" gets answered badly because it is asked as a choice between three rivals. Prompting, retrieval and fine-tuning change different parts of the system, and the right one is the one that matches where the failure sits.

A prompt changes the instructions and examples the model conditions on. Retrieval changes which facts are in that input: the model reads them instead of recalling them. Fine-tuning changes the weights, which shifts the model's behaviour on every input, with nothing added to any request. That last property is the whole attraction and the whole risk. The change is free to apply per call and expensive to make, to check and to undo.

LeverWhat it changesCost of one changeFixes
PromptInstructions, examples, output schemaMinutes; ships like codeThe model could do it but was not told how, or in what shape
RetrievalThe facts in the context windowA re-index; no trainingThe model lacks a fact, or the fact changes faster than a release cycle
Fine-tuningWeights: style, format, narrow task skillA data pass, a training run and a full re-evaluationThe model is told clearly, still does it inconsistently, or does it too slowly or dearly

The order follows the cost column. Start at the top and move down only when a measured failure survives the cheaper tool. Anthropic's prompt-engineering guide frames the same precondition: it assumes you already have a definition of success, a way to test against it and a first draft prompt, and its advice is to establish those first. OpenAI's optimisation guide says the prompt-engineering process "may be all you need" for many use cases, and presents fine-tuning as an addition for specific tasks.

failure observed on the eval set │ ▼ can a clearer prompt or examples fix it? ── yes ──▶ prompt, re-measure │ no ▼ is a fact missing or stale in the context? ─ yes ─▶ retrieval, re-measure │ no ▼ is it behaviour: format, style, narrow skill, or is the cost/latency of the big model the problem? │ yes ▼ fine-tune, with the eval set already built

Retrieval is the tool people skip when they should not. If the failure is "the model did not know the deductible on this policy", no amount of tuning on yesterday's policies fixes it, because the next policy edit makes the weights stale. The contract that makes retrieval reliable is in the retrieval contract.

What fine-tuning reliably changes

The evidence points one way. Models acquire most of their knowledge in pre-training, and post-training mostly teaches them how to use it. LIMA (Zhou et al., 2023) fine-tuned a 65B LLaMa model on only 1,000 curated prompt-response pairs, and in a human study its answers were equivalent or preferred to GPT-4's in 43% of cases. The authors read this as evidence that almost all knowledge is learned in pre-training and a small amount of instruction data teaches the output style. Gekhman et al. (2024) tested the knowledge side directly. Examples that introduce facts the model does not already know are learned more slowly than examples consistent with what it knows, and once the model does fit them, its tendency to hallucinate rises with the number of such examples. Ovadia et al. (2023) compared the two routes for injecting knowledge and found that retrieval consistently outperformed unsupervised fine-tuning, both for facts the model had seen and for entirely new ones.

The mechanism explains the pattern. A training step on a summary nudges every weight that contributed to that summary's tokens. If the summary's style is something the network can already produce, the nudge makes the style likelier. If the summary asserts a fact the network has no representation for, the only way to lower the loss is to memorise the string, and the network learns to produce confident fact-shaped text. That is a hallucination habit, not knowledge.

So the reliable wins are these:

  • Format and structure. Consistent schemas, house sections, a fixed length. OpenAI lists consistent formatting and handling novel inputs among the uses.
  • Style and tone. Matching how adjusters write, in the vocabulary adjusters use.
  • Narrow task skill. Classification, extraction and summarisation of one document type, where the target behaviour is stable and examples are plentiful.
  • Cost and latency. A small tuned model can replace a large prompted one. OpenAI's documentation names this: train a smaller, cheaper, faster model to excel at one task where a larger model is not cost-effective. Shorter prompts also save tokens, though prompt caching has weakened that argument for stable prefixes.

What it does not reliably change is fresh knowledge, which belongs in retrieval, and the reasoning ceiling. No source checked for this chapter measures the second claim directly, so treat it as a prior to test: an 8B model tuned on 22,000 summaries should get better at summarising claims, and you should not expect it to start reasoning like a model several times its size. Your eval set is where you find out. Also expect forgetting. LoRA Learns Less and Forgets Less (Biderman et al., 2024) reports that LoRA underperforms full fine-tuning on programming and maths but better preserves the base model's performance outside the target domain. Either way, a tuned model moves on tasks you did not train on, which is why chapter 07 tests for regression.

The cost model, including owning a model

Each tool has a different cost shape, and fine-tuning's is the least visible. Prompting costs tokens on every call, which grows with traffic. Retrieval adds an index, a retriever and the extra context tokens per call. Fine-tuning moves cost from per call to up front, and then adds the bills that the training run does not show.

  • Data. Collecting, cleaning and reviewing examples, covered in chapter 03. For most teams this is the largest line.
  • Training runs. Cheap for LoRA on one GPU and several times that for a full fine-tune; chapter 06 does the arithmetic. You will run more than one, because the first run exposes data problems.
  • Evaluation, repeated. Every new checkpoint is a new model to qualify, and every base-model update restarts the work.
  • Serving. GPUs that bill whether or not requests arrive, plus the engineering to keep them up. The Serving Open-Weight Models guide covers it.
  • Ownership. Someone is on call for the model, watches for drift, and retrains. This is the cost that decides most cases.

A provider can also change the terms under you. As of November 2026, OpenAI's deprecations page says its self-serve fine-tuning platform is being wound down. From 7 May 2026 organisations that had never run fine-tuning could not create jobs. Active existing customers lose the ability to create new jobs on 6 January 2027. Inference on fine-tuned models continues until the underlying base model is deprecated. If you build on a hosted tuning service, the exit is part of the cost model. Open weights remove that dependency and replace it with the serving bill.

The eval-first rule

Build the held-out set before you touch weights. Training makes everything look like progress: the loss falls, the samples read well, and the first impression of a tuned model is almost always better than it deserves. Without a fixed set that the tuning data never touches, you cannot tell a real gain from a model that learned the style of the examples you happened to read. Building the eval set covers how to build and protect it; this chapter needs the consequences.

  1. Set the target first. Write the pass bar per slice before any run, so the result cannot move the bar.
  2. Measure the cheap baselines. Run the strongest prompted model, then a well-prompted version of the model you would tune, with the same examples in context. The gap between them is the most that tuning has to buy.
  3. Exhaust the prompt. Iterate on instructions, few-shot examples and a schema until gains flatten. A model tuned to beat a lazy prompt has beaten nothing.
  4. Only then spend on data. If the gap is zero, stop. If it is real, you now have the number the tuned model must close.

The exception is a set you cannot build. If nobody can say what a correct answer looks like, tuning on examples will bake in whatever the examples disagree about. Fix the labelling first, using agreement measures from the evals guide.

The decision for Harbourline's two candidates

All figures in this section are illustrative inputs, except the prices, which come from the vendors' pages in November 2026.

Candidate B: the claims-intake agent's tone and output format

The intake agent reads a first notice of loss and returns a structured record in a house tone. Suppose the team builds a 300-conversation held-out set, with a target of 95% valid output schema and 95% on a tone checklist. A prompt with a schema, three worked examples and retrieval of the relevant procedure passes the schema on 296 of 300 (98.7%) and the tone checklist on 289 of 300 (96.3%). Both clear the bar.

Decision: do not fine-tune. The failure the tuning would fix does not exist. A prompt change ships in minutes and rolls back in minutes, and tuning would add a model to own for no measured gain. The longer prompt costs little: at Sonnet 5.5's cache-hit rate of $0.10 per million tokens, 6,000 extra prompt tokens on each of 6,000 intake calls a day is 36 million cached tokens, or $3.60 a day before cache writes. This is the contrast case that later chapters refer back to.

Candidate A: the nightly batch

The batch classifies and summarises about 6,000 claims a night. Assume 4,000 input tokens and 400 output tokens per claim. Sonnet 5.5 costs $2 per million input tokens and $10 per million output tokens, and the Batch API halves both, to $1 and $5. A nightly job can wait, so use the batch rate.

output  6,000 x   400 =  2.4M tokens x $5/M  = $12.00

open-weight 8B on one H100, 2 hours a night (assumed), $3.99/GPU-hour

The H100 rate is the on-demand figure in the site's neocloud pricing table, and the two hours is a placeholder that the serving guide replaces with a measured throughput. Against a saving of about $10,000 a year, the ownership cost in the previous section is larger. Take a tenth of one engineer's year, say $20,000 on an assumed loaded cost of $200,000, and the model costs more than it saves.

Decision: build the eval set and run the bake-off, and fund training only if the data-residency constraint is binding. Cost alone does not justify tuning at 6,000 claims a night. The case rests on the requirement that UK claims data stay in the UK, which a hosted API may or may not satisfy on terms Harbourline's counsel accepts. If the API can meet it, stay on the API. If it cannot, the open-weight route is the only route, and the question becomes whether a tuned 7B to 9B model matches Sonnet 5.5 on the 400-claim set, in every slice, motor, property and liability, US and UK. The rest of this guide takes that path.

When the decision flips

Each conclusion above has a condition that reverses it.

  • Volume. At ten times the volume, 60,000 claims a night, the same arithmetic gives a saving near $100,000 a year, which pays for the owner. If GPU time scales with volume, each claim-a-night saves about $1.70 a year ($28.02 a night over 6,000 claims, times 365, divided by 6,000). Break-even against a $20,000 owner is then about 11,700 claims a night. Recompute it with your measured tokens and GPU hours.
  • Prompt ceiling. If the baseline plateaus below the bar however the prompt is built, and the failure is stylistic or structural, tuning becomes the only lever left. Candidate B would flip here if the schema pass rate stalled at 85%.
  • Latency. If an interactive surface needs responses in a time the large model cannot deliver, a small tuned model can be the fix, whatever the cost.
  • Knowledge that changes. If the failure is a stale or missing fact, tuning is wrong at any volume. Fix retrieval.
  • No stable target. If the correct output keeps changing because the policy or the template changes monthly, each change is a retrain. A prompt absorbs the same change in minutes.

The interview-prep view of the same trade is in latency and cost at scale. The next step for Candidate A is choosing what to tune, in the next chapter.

✓ Check yourself

Answer from memory before opening each one.

  1. The help-centre assistant quotes the wrong deductible after a policy form was revised last month. A colleague proposes fine-tuning on the new forms. What do you say?

    Show answer

    The failure is a missing or stale fact, which tuning handles poorly. Models learn new facts slowly through fine-tuning and may become more prone to hallucinate as they fit them, and the next revision makes the weights stale again. Fix the index so the model reads the current form. See what fine-tuning changes.

  2. Your tuned 8B model scores higher than the prompted base model on the examples you read during development. Why is that not yet evidence, and what would make it evidence?

    Show answer

    Developer-read samples are the ones the tuning was shaped around, so improvement on them may be style matching. Evidence needs a held-out set built before training, with pass bars fixed in advance and the prompt-only baselines measured on it. See the eval-first rule.

  3. Candidate B passes its eval with a prompt, and the team still wants to tune "to make the prompt shorter". Give two reasons that argument is weak and one condition under which it holds.

    Show answer

    Cached prompt prefixes bill at a small fraction of the input rate, and tuning adds a model to own and re-qualify. It holds if the prompt cannot be cached, such as a prefix that varies per call, or if the prompt is so long that it hurts latency or exceeds the context budget. See the decision.

  4. Candidate A's nightly volume doubles to 12,000 claims. Does the cost case for tuning now stand on its own? Show the arithmetic you would redo first.

    Show answer

    Barely. API cost doubles to $72 a night, about $26,300 a year. Four GPU hours at $3.99 is about $5,800 a year, so the saving is about $20,500 against an assumed ownership cost of $20,000. That is break-even with no margin, so measure real token counts and GPU hours before deciding. See when the decision flips.

  5. Which costs of owning a tuned model does the training run itself not show, and which of them is likeliest to decide a close case?

    Show answer

    Data preparation, repeated evaluation of each checkpoint, idle GPU time while serving, and the person who owns drift and retraining. Ownership, meaning the engineering time, usually decides a close case because it recurs every month and does not shrink with volume. See the cost model.

Takeaway

  • Prompting changes what the model is told, retrieval changes what it can read, and fine-tuning changes how it behaves on every input; match the tool to where the measured failure sits.
  • Fine-tuning reliably improves format, style, narrow task skill and cost or latency through a smaller model, and does not reliably add knowledge, which retrieval handles better.
  • Fine-tuning moves cost from every call to an up-front investment, and then adds data work, repeated evaluation, serving and an owner, which together decide most close cases.
  • Build the held-out set and the cheap baselines before touching weights, so the gap tuning must close is a number and not a feeling.
  • Harbourline does not fine-tune the intake agent, because a prompt with retrieval already meets its eval, and it pursues the nightly batch only because data residency makes the API route uncertain.
  • Every conclusion has a flip condition: more volume, a prompt ceiling, a latency need, or a stable target moves the answer toward tuning, and changing facts or policy moves it away.
