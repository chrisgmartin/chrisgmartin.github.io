Section C · Training

Preference Alignment

Reward models and PPO, DPO and its variants, GRPO and reinforcement learning with verifiable rewards, rejection sampling, collecting preferences from Harbourline's adjusters, and the reward hacking to watch for.

Overview

Chapter 04 trains the model to imitate adjusters' summaries. Harbourline's adjusters also did something imitation cannot use: over eight weeks they picked the better of two summaries about 6,000 times. This chapter decides whether that signal is worth a second training stage, and if so how to use it.

Why SFT alone plateaus

SFT maximises the likelihood of one reference summary, token by token. Two summaries can both be acceptable and still score very differently against that reference. The objective also only ever sees good outputs, so it has no way to say "this wording is worse than that one".

Preference data supplies the missing signal. Stiennon et al. (2020) tested it on summarisation: their 1.3B model trained with human feedback was preferred to the reference summaries 61% of the time, while a supervised model ten times its size reached 43%. Tajwar et al. (2024) analysed why. Methods that sample from the model's own outputs, or push down the likelihood of bad responses (a "negative gradient"), beat plain maximum-likelihood training.

The reward-model pipeline and why teams moved off it

Ouyang et al. (2022) set the template behind InstructGPT. First fine-tune on demonstrations. Then collect rankings of model outputs and train a reward model to predict which output a human prefers. Then optimise the SFT model against it with PPO, with a KL penalty to keep it near the start.

The cost is the machinery: PPO keeps a policy, a frozen reference, a reward model and a value model, and samples from the policy during training. The Llama 3 authors state their choice plainly: they used SFT, rejection sampling and DPO rather than more complex reinforcement learning algorithms that tend to be less stable and harder to scale. For an 8B model on one rented GPU that argument is stronger, so the rest of this chapter starts from DPO.

DPO: the preference loss without a reward model

Rafailov et al. (2023) show that the RLHF objective has a closed-form optimal policy, so the reward model can be written in terms of the policy itself. The result is a classification loss on pairs. For a prompt x, a chosen summary yw and a rejected one yl:

loss = -log sigmoid( beta * [ log pi(yw|x) - log pi_ref(yw|x) ] - beta * [ log pi(yl|x) - log pi_ref(yl|x) ] )

Each bracket measures how much more likely the tuned model makes a summary than the reference does. The loss falls when the chosen summary gains likelihood relative to the rejected one. There is no sampling and no reward model. The "implicit reward" TRL logs is β times that log ratio.

The reference must be the SFT model. DPO pulls the policy back toward the reference, so a base model as reference would drag the tuned model away from everything chapter 04 taught. With LoRA, merge the SFT adapter into the weights, save, and train a fresh adapter on top. TRL's error message for an adapter model plus a new adapter config says to merge and unload the adapter first. When ref_model is None, TRL uses the model's state before DPO started.

Beta. β sets how hard the pull back is. In TRL, a higher value means less deviation from the reference, and the default is 0.1. The DPO paper used 0.1 for most tasks and 0.5 for TL;DR summarisation, which is Harbourline's task, so sweep both.

What to watch. At step zero the policy equals the reference, both brackets are equal, and the loss is the log of 2, 0.693. In a one-step smoke test the logged loss was 0.6931. TRL also logs rewards/accuracies, the share of pairs where the chosen summary has the higher implicit reward, and rewards/margins. Held-out accuracy climbing is the sign that training generalises; a margin that grows while it stalls is memorisation.

The two scripts below run the Harbourline recipe. Both were smoke-tested on CPU with a 135-million-parameter model for one to three steps, and have not been run at 9B scale. Run merge_sft.py first.

merge_sft.py
# merge_sft.py: fold the SFT adapter into the base weights so DPO can start from the SFT model.
import os, torch
from peft import AutoPeftModelForCausalLM
from transformers import AutoTokenizer

adapter, out = "out/harbourline-sft-lora", "out/harbourline-sft-merged"
model = AutoPeftModelForCausalLM.from_pretrained(adapter, dtype=torch.bfloat16)
model.merge_and_unload().save_pretrained(out)
AutoTokenizer.from_pretrained(adapter).save_pretrained(out)
train_dpo.py
# train_dpo.py: LoRA DPO on adjuster preference pairs, starting from the merged SFT model.
# Tested with trl 1.17.1, peft 0.21.2, transformers 5.22.2, torch 2.15.0.
import os
import torch
from datasets import load_dataset
from peft import LoraConfig
from trl import DPOConfig, DPOTrainer

START = os.environ.get("START", "out/harbourline-sft-merged")
MAX_STEPS = int(os.environ.get("MAX_STEPS", "-1"))
cuda = torch.cuda.is_available()

# {"prompt": [user message], "chosen": [assistant message], "rejected": [assistant message]}
data = load_dataset("json", data_files={"train": "pairs_train.jsonl", "validation": "pairs_val.jsonl"})

args = DPOConfig(
    output_dir="out/harbourline-dpo-lora",
    beta=0.1,                            # pull back to the SFT model; the DPO paper used 0.5 for summarisation
    learning_rate=5e-6,                  # TRL's default for full DPO is 1e-6; LoRA needs more. Sweep 5e-6 to 5e-5
    num_train_epochs=1,
    max_steps=MAX_STEPS,
    per_device_train_batch_size=2,
    gradient_accumulation_steps=16,      # 2 pairs x 16 = 32 pairs per update
    max_length=4096,
    bf16=cuda,
    model_init_kwargs={"dtype": torch.bfloat16 if cuda else torch.float32},
    eval_strategy="no" if MAX_STEPS >= 0 else "steps",
    eval_steps=50,
    logging_steps=10,
    save_strategy="no" if MAX_STEPS >= 0 else "epoch",
    report_to="none",
    seed=7,
)
trainer = DPOTrainer(model=START, args=args, train_dataset=data["train"], eval_dataset=data["validation"],
                     peft_config=LoraConfig(r=16, lora_alpha=32, lora_dropout=0.05,
                                            target_modules="all-linear", task_type="CAUSAL_LM"))
trainer.train()
trainer.save_model()

Each row of the pairs file holds a prompt and two one-message lists, chosen and rejected. A pair is two sequences, so micro-batch 2 means four per forward pass, plus a no-gradient reference pass. Hold out 600 of the 6,000 pairs and let TRL report accuracy on them.

ORPO, KTO and SimPO: what each one changes

Each variant removes one thing DPO needs. Which removal helps depends on what you are short of: a stage, a reference model's memory, or pairs.

MethodWhat it changes from DPOData neededStatus in TRL 1.17.1
DPOBaseline: log-ratio against a reference modelPairsStable trainer
ORPOAdds an odds-ratio penalty to the SFT loss, in one stage, with no reference model (Hong et al., 2024)PairsUnder trl.experimental
KTOReplaces pairs with a per-output good-or-bad label, using a prospect-theory utility (Ethayarajh et al., 2024)Binary labelsStable trainer
SimPOReward is the length-normalised average log-probability, so no reference model; adds a target margin (Meng et al., 2024)PairsVia the experimental CPO trainer, loss_type="simpo"

ORPO folds SFT and preference learning into one run from the base model, giving the chosen response a strong adaptation signal and the rejected one a weak penalty. That saves a stage but merges two experiments into one, so a bad result is harder to attribute, and it sits in TRL's experimental module, which can change without deprecation.

KTO needs only a label that an output was good or bad. Harbourline's review tool probably holds many more of those than pairs, such as an adjuster accepting a summary unedited. The KTO authors report matching or exceeding preference-based methods from 1B to 30B parameters using this weaker signal.

SimPO uses the average log-probability of a response as the reward, which is close to the quantity used to generate, and subtracts a target margin. Dropping the reference model saves its forward pass, and length normalisation targets the bias in the hacking section. The SimPO authors report that without the normalisation the model drifts toward longer, lower-quality sequences.

GRPO, verifiable rewards and rejection sampling

When the right answer can be checked by a program, you can skip human preferences. DeepSeek-AI (2025) trained R1-Zero with GRPO, a method from the DeepSeekMath paper. For each question it samples a group of outputs (16 in R1-Zero), scores each, and computes the advantage as the reward minus the group mean, divided by the group's standard deviation. The group baseline replaces PPO's value model, which cuts memory. The rewards were rules: accuracy, checked by matching a boxed answer or running a compiler, and format. The authors avoided neural reward models because they were susceptible to reward hacking.

Harbourline has a checkable half. The classification fields, such as claim type, loss date and amount, can be compared with structured data. The prose quality of a summary cannot. GRPO fits the first and not the second. TRL's GRPOTrainer samples 8 generations per prompt by default, so generation, not the weight update, dominates the cost. Do not start here. It earns a place if SFT and DPO still leave field errors that a program can score.

Rejection sampling is the cheapest way to get an on-policy signal. Sample K candidates per prompt from the SFT model, score them, keep the best, and run SFT on the winners. Llama 2 did this with a reward model, and Llama 3 paired it with DPO. At Harbourline the scorer could be the judge you calibrated in the evals guide. It reuses chapter 04's script. The risk is the scorer: Gao et al. (2022) found best-of-n sampling overoptimises a proxy reward too, so whatever the judge prefers, such as length, is what the winners will have.

Collecting preferences from adjusters

Treat the preference interface as an instrument. Show the claim, then the two summaries in random order, with options for "tie" and "both wrong" and a one-tap reason such as "invented a fact" or "missing amount". Randomise order, since position bias is not only a judge problem.

Measure agreement before you trust the labels. Have two adjusters label an overlap of about 10% of pairs, roughly 600. For scale, Ouyang et al. report labelers agreeing with each other 72.6 ± 1.5% of the time, 77.3% for held-out labelers, and cite 73% researcher agreement from Stiennon et al. If Harbourline lands near 73%, then with balanced choices chance agreement is 50% and kappa is (0.73 − 0.50) / (1 − 0.50) = 0.46, moderate. A model cannot be expected to agree with one adjuster much more often than adjusters agree with each other. Drop the contested pairs from training. Training on pairs adjusters would split on adds noise, and TRL's label_smoothing option for flipped labels documents a range of 0 to 0.5 and recommends 0.1, so it is a patch for light noise, not for 27%.

How many pairs? Llama 2's reward models used over a million comparisons, for general chat. A single narrow task needs far fewer, and no source tells you how many. Find out with a learning curve: train on 1,500, 3,000 and 5,400 pairs, and plot held-out pair accuracy. If it still climbs at 5,400, collect more. If it has flattened, the limit is label noise or the signal, not quantity.

Last, check where the pairs came from. Tajwar et al. found on-policy data works better. If the candidates in the review tool came from the current Sonnet pipeline rather than your SFT model, the pairs are off-policy. They teach the tuned model to prefer one API-model summary over another, not to fix its own mistakes. Once chapter 04's model exists, have it generate the pairs for the next batch.

Reward hacking and length bias

Any learned preference signal can be gamed, and the cheapest game is length. Singhal et al. (2023) found that a purely length-based reward reproduced most of the downstream improvement RLHF showed over SFT, and traced the dominant source to reward models and the length bias in preference data. Park et al. (2024) showed DPO exploits length too, without a reward model at all. Gao et al. (2022) fit the general curve: for best-of-n the gold reward follows d(α − βd), where d is the square root of the KL distance from the starting policy. It rises, peaks, then falls.

At Harbourline, a longer summary is a riskier summary

Adjusters will often pick the fuller summary, since it feels complete. A DPO model learns that and drifts long. Each added sentence is another chance to state a policy term the claim file does not contain, which is the failure chapter 07 must rule out. Log mean summary length at every checkpoint, compare tuned and untuned models inside length buckets, and apply the controls in the judge-bias section.

Controls: compare at matched length, use a higher β or an earlier checkpoint, try SimPO's length normalisation, and stop on held-out pair accuracy and length trend together, not on the training margin.

When SFT is enough

Preference tuning adds a stage, a hyperparameter, a reference model's memory and a new regression to test. It pays only when SFT's remaining errors are choices between acceptable outputs. It does nothing for missing knowledge or a wrong field, which are data and capability problems.

Test before you build. After SFT, have adjusters compare the SFT model's summary with the approved summary on the 400 held-out claims, blind. If failures cluster in missing fields or wrong amounts, fix the training data. If they are in style or emphasis, DPO is aimed at the right target.

Then account for the noise in your own measurement. With 400 paired comparisons the standard error on a 50% win rate is the square root of 0.25 / 400, which is 0.025, so the 95% interval is ±4.9 points. A DPO model must beat the SFT model by more than that, a win rate above about 55%, before the held-out set can tell the difference. The ship decision covers intervals properly. If the realistic gain is smaller than the interval, you cannot detect it, and the stage is not worth its risk.

One exception favours doing it anyway. Chapter 04's SFT cannot teach a model what not to say. Harbourline needs the tuned model to refuse to invent policy terms, and a preference pair where the rejected answer invents a term is exactly the negative signal SFT lacks. A few hundred such pairs, deliberately constructed, may do more than six thousand style pairs. That is a hypothesis for chapter 07 to test, not a result. Candidate B, the intake agent's tone, needs no training of either kind.

✓ Check yourself

Answer from memory before opening each one.

  1. Two summaries of the same claim are both factually right, and adjusters consistently prefer the shorter one. Explain why SFT on the approved summaries cannot reliably learn that preference, and what a DPO pair adds.

    Show answer

    SFT only sees one good output per claim and scores it against that reference, so it never learns that another acceptable wording is worse. A pair gives an explicit contrast: the loss pushes the chosen summary's likelihood up relative to the rejected one's. See why SFT plateaus.

  2. Your held-out pair accuracy is 71%, and two adjusters agreed on 73% of the overlap pairs. Is the model underperforming?

    Show answer

    No. Adjusters disagree with each other on 27% of pairs, so that agreement rate is a rough ceiling for agreement with any one adjuster. A model at 71% is close to it. See collecting preferences.

  3. After DPO the adjuster win rate over the SFT model is 60%, but mean summary length rose from 180 to 260 tokens. What do you do before reporting the win?

    Show answer

    Compare the two models within length buckets, so a longer summary is only compared with a summary of similar length, and check for invented policy terms in the longer outputs. If the win shrinks inside buckets, it was length. See reward hacking and length bias.

  4. You have 400 held-out claims and DPO improves the adjuster win rate over SFT to 53%. Can you ship the DPO model on that evidence? Show the arithmetic.

    Show answer

    No. The standard error at 50% is the square root of 0.25 / 400, which is 0.025, so the 95% interval is ±4.9 points and 53% is inside the noise around 50%. The gain is not distinguishable from no gain, and the stage added risk. See when SFT is enough.

Takeaway

  • SFT imitates one reference summary and never sees a worse one, so it cannot learn preferences among acceptable outputs, which pairs can teach.
  • DPO turns pairs into a classification loss against a reference model, with no reward model and no sampling, which makes it the practical default for a 9B model on one GPU.
  • The reference model must be the merged SFT model, and beta sets how far the tuned model may move from it; sweep 0.1 and 0.5 for summarisation.
  • Preference data is bounded by adjuster agreement, and length is the cheapest way to game it, so measure both before and after training.
  • Preference tuning is wasted when SFT's errors are missing data or wrong fields, or when the expected gain is smaller than the evaluation interval.
