Section A · Orient

Start Here

Running an open-weight model is a capacity problem dressed as a machine-learning problem: the questions are how many bytes move per token, how many requests share each pass, and what that costs per million tokens against an API price. Start here for why Harbourline is doing it, the four numbers every chapter measures against, and the vocabulary.

Why run the model yourself

An API is the right default for almost every team. Someone else owns the GPUs, the upgrades and the on-call rota, and the price per million tokens already includes the utilisation they achieve by pooling thousands of customers. Three things move a workload off the API: a volume high enough that the rented GPUs would be busy most of the day, a constraint on where data may go that a vendor contract cannot satisfy, or a latency or customisation need the API does not offer, such as a fine-tuned adapter the vendor will not host. Cost alone rarely does it on its own, because a self-hosted GPU that sits at 20 percent utilisation costs more per token than the API it replaced.

This guide is for the engineer who has one of those three reasons and must now make the thing work: pick a model, fit it into GPU memory with room for requests, make a decode step fast, choose an engine, size a deployment against a latency objective, and keep it running. Each chapter explains the mechanism first, because every optimisation in serving is a consequence of where a decode step spends its time, and an engineer who knows that can reason about a new technique the week it appears. Chapter 01 does the build-or-buy arithmetic for both Harbourline workloads and says which reason tipped each one.

The four numbers

Serving is measured with four quantities, and a design that improves one usually spends another. Time to first token (TTFT) is the wait before the first output token appears, dominated by prefill: the pass over the whole prompt. Time per output token (TPOT), also called inter-token latency, is the gap between tokens once streaming starts, dominated by decode. Throughput is output tokens per second across all requests on a GPU, what a batch is for. Goodput is the share of that throughput delivered inside the latency objective; a GPU producing 3,000 tokens a second at a TTFT of four seconds has high throughput and, for an interactive assistant, almost no goodput.

Where the bytes go

A GPU's memory is the budget everything else is paid from. The weights take a fixed share: two bytes per parameter in BF16, one in FP8, about half a byte at four-bit. What remains holds the key-value cache, the per-token state every request keeps for the whole conversation, plus activations and the engine's working space. The number of requests that can run at once is the free memory divided by the KV cache a request needs, and that is why nearly every serving technique is either a way to shrink the weights, shrink the cache, or reuse one pass across more requests.

one 80 GB GPU, 70B-class model ┌──────────────────────────────────────────────────────────────────────────────┐ │ weights BF16: 140 GB (does not fit) FP8: 70 GB INT4: ~35 GB │ │ ──────────────────────────────────────────────────────────────────────────── │ │ KV cache = (80 GB − weights − working space) ÷ KV bytes per token │ │ → the number of concurrent tokens you can hold │ │ ──────────────────────────────────────────────────────────────────────────── │ │ activations + engine working space (a few GB) │ └──────────────────────────────────────────────────────────────────────────────┘ shrink weights (ch. 03) · shrink or share the cache (ch. 04) · more tokens per pass (ch. 05)

Decode is memory-bound: for each new token the GPU reads every weight once and every cached key and value for the request, and does comparatively little arithmetic with them. Batching many requests into one pass reads the weights once for all of them, which is where throughput comes from and why the cache, not compute, is usually the ceiling. Chapter 02 does this arithmetic for the model Harbourline chose, and the paging that makes the cache usable is explained in PagedAttention from First Principles.

The vocabulary

TermMeaning here
Open-weight modelA model whose weights can be downloaded and run under a licence. Not the same as open source: the training data and code may not be published and the licence may restrict use.
PrefillThe pass over the whole prompt that fills the KV cache. Compute-heavy; sets TTFT.
DecodeOne forward pass per generated token, reusing the cache. Memory-bound; sets TPOT.
KV cacheThe keys and values every layer computed for every token so far, kept so they are not recomputed. Grows with context length.
QuantisationStoring weights (and sometimes activations or the cache) in fewer bits. Trades a measured accuracy loss for memory and bandwidth.
Continuous batchingAdding and removing requests from the running batch at every decode step instead of waiting for a batch to finish.
Prefix cachingReusing the KV cache of a prompt prefix that many requests share, such as a system prompt.
Speculative decodingGuessing several tokens cheaply and verifying them in one pass of the large model; faster when the guesses are usually right.
Tensor and pipeline parallelismSplitting one model's layers across GPUs by slicing each matrix (tensor) or by assigning whole layers (pipeline).
EngineThe serving software: vLLM, SGLang, TensorRT-LLM, TGI, llama.cpp. Owns batching, the cache and the API.
Constrained decodingMasking the next-token distribution so output follows a grammar or JSON schema.
GoodputThroughput that arrives within the latency objective. The number to size against.

Takeaway

  • Self-hosting pays when volume keeps GPUs busy, when data may not leave, or when the API cannot host what you need; cost alone at low utilisation argues the other way.
  • TTFT, TPOT, throughput and goodput are the four numbers; a batch job and an assistant weight them differently and are configured differently on the same hardware.
  • GPU memory is the budget: weights first, then the KV cache, and the cache decides how many requests run at once.
  • Decode is memory-bound, so every optimisation shrinks the weights, shrinks or shares the cache, or spreads one pass over more tokens.
  • Keep the arithmetic traceable: the memory picture in chapter 02 is the source of every capacity and cost number later in the guide.
