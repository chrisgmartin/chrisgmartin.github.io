Section D · Running it

Engines and Formats

vLLM, SGLang, TensorRT-LLM, TGI, llama.cpp and Ollama, MLX: features, formats and compatibility as of November 2026, and how Harbourline chose.

Overview

Chapters 04 and 05 described techniques. This chapter asks which software implements them, in what file format the weights arrive, and what you give up by choosing one engine over another. The seven projects covered are vLLM, SGLang, TensorRT-LLM, Hugging Face TGI, llama.cpp, Ollama and MLX-LM. They fall into two groups: engines built for GPU servers with many concurrent users, and engines built for one user on one machine. Harbourline's deployment is the first kind. The second kind appears here because developers will run it on laptops, and chapter 07 returns to that.

Everything in the feature table is read from each project's own documentation in November 2026. "Documented" means the page says so for some configuration, not that every combination works. Projects ship faster than guides are written, so treat the table as the checklist of questions to ask a current version, not as a verdict. None of the engines was benchmarked for this chapter. Speed rankings between engines move with every release and with the workload, and you should run your own test, described in the last section.

Weight formats: what is on disk

The format decides who can load the file, whether loading copies it, and whether quantization is baked in.

  • safetensors. Hugging Face's format for storing tensors "safely (as opposed to pickle)" while staying fast through zero-copy loading. A reader can open a file and fetch single tensors or slices of them, which matters when each of two GPUs needs only its shard of a weight. It stores tensors and nothing that executes, so loading an untrusted checkpoint cannot run code. The safetensors project lists transformers, MLX and llama.cpp's converter among its users. Quantized checkpoints, such as AWQ, GPTQ or FP8 variants, are usually safetensors files whose tensors are the packed integers and scales, so the format does not tell you the precision. Read the config.
  • GGUF. The single-file format of the llama.cpp ecosystem. One file holds typed key-value metadata (hyperparameters, tokenizer) and the tensors, aligned to 32 bytes by default so the file can be memory-mapped. Its tensor types include F32, F16, BF16 and quantized types from Q4_0 to Q8_0, the K-quants and the IQ variants. Because it carries everything, it is the easiest format to hand to someone. It is little-endian by default, with big-endian supported. vLLM lists GGUF support in its quantization table, and Ollama builds models from GGUF files or safetensors directories.
  • Compiled engine plans. TensorRT-LLM has historically compiled a model into a GPU-specific artefact, tied to the GPU type and library versions that built it. Its current documentation describes a PyTorch-native, modular architecture and includes a migration guide for the removal of the TensorRT backend, so check what your version loads before you plan around a build step.

Quantization from chapter 03 and format are separate decisions. A GPTQ INT4 model can be a safetensors file for vLLM, and a Q4_K_M model is a GGUF file for llama.cpp, and the two are not interchangeable even when both are "4-bit". When someone says "the model is quantized", ask which method, which format and which engine has a kernel for it.

The seven, in one paragraph each

vLLM is the origin of paged KV cache (Kwon et al., 2023, reporting 2× to 4× throughput over earlier systems at the same latency) and the engine whose feature list is broadest. It serves an HTTP API with completions, chat completions, responses and embeddings endpoints, and its quantization page covers AWQ, GPTQ, FP8, INT8, INT4 via llm-compressor, bitsandbytes, GGUF, NVIDIA Model Optimizer, TorchAO and more. SGLang started as a language for LLM programs with a runtime built on RadixAttention, which keeps the KV cache of earlier requests in a radix tree. Its paper reports up to 6.4× throughput over contemporary systems across tasks including agent control, JSON decoding, retrieval-augmented generation and multi-turn chat. Its docs list the widest range of speculative methods, and it has run on NVIDIA, AMD, Intel, TPU and Ascend hardware.

TensorRT-LLM is NVIDIA's library. It leads on NVIDIA-specific numerics: FP8 per tensor, block and rowwise scaling on Hopper, NVFP4 and FP8 KV cache on Blackwell, W4A16 and W4A8 AWQ and GPTQ, and it documents FP8 doubling performance and halving memory against 16-bit on H100 and later. It runs only on NVIDIA GPUs. TGI was Hugging Face's server. Its documentation now says it is in maintenance mode, accepting only minor fixes, and recommends vLLM and SGLang, and llama.cpp or MLX for local use. Treat it as something you may inherit, not something you should start with.

llama.cpp is a C/C++ runtime for GGUF models across Metal, CUDA, Vulkan, SYCL, HIP and CPU. Its server provides OpenAI-compatible routes, parallel decoding with continuous batching, speculative decoding, grammar and JSON-schema constraints, LoRA adapters and prompt caching. It is the one engine that runs on almost anything. Ollama wraps that kind of runtime in a model manager: a Modelfile, a model kept loaded for five minutes by default, and an API with structured outputs through a JSON-schema format field. MLX-LM runs and fine-tunes models on Apple silicon, with quantization, LoRA and prompt-cache files. Its server docs say outright that it is not meant for production, since its security checks are minimal and a quantized KV cache disables batching.

The shape is clear even with gaps. The three server engines each cover every column. TGI covers them but is closed to new features. The local tools cover what a single user needs and thin out where concurrency begins. A "yes" in a column also hides interactions, and the vLLM entry shows one: speculation and LoRA do not combine in its feature list, which matters if the adapters in serving and retraining arrive later. Structured output has its own chapter, 09, and the mechanism behind prefix caching and paged blocks is in the paged attention guide.

"OpenAI-compatible" covers the happy path only

The routes match; the edges do not. Ollama's compatibility page says logprobs are unsupported and that tool_choice is missing on chat completions. Extensions such as guided decoding, adapter selection and engine metrics use each engine's own fields. A client that sticks to the standard fields moves between engines in an afternoon. One that uses engine extensions does not, so wrap them in one module.

How Harbourline chose

The requirements come from the guide's two workloads. Serve a 70B dense model in FP8 on two H100s in a UK region. Keep the shared 1,200-token prompt cached, since chapter 04 showed it saves 80 ms per request. Force valid JSON for the nightly claims batch. Expose a standard chat endpoint so the gateway and existing clients do not change. Leave room for adapters and speculation later. That leaves three real candidates: vLLM, SGLang and TensorRT-LLM. TGI is out because it is in maintenance mode, and the local tools are out because they are not built for concurrent production traffic.

Harbourline picks vLLM as the default. The deciding reasons are documentation reach, since its quantization and feature pages cover the FP8 W8A8 path on Hopper, prefix caching, structured output backends, LoRA and speculation in one place; the standard endpoints; and a hardware table that does not tie it to one vendor. Those are reasons about risk and hiring, not about speed. The decision is provisional until the test below.

The test costs one day. Stand up vLLM and SGLang on the same two GPUs with the same quantized weights. Run the Harbourline help-centre evaluation set on both and compare answers, since engines differ in sampling and numerics. Replay a recorded day of Workload B prompts at the illustrative peak of 1.5 requests/s, and record p95 TTFT, tokens/s per stream, prefix hit rate and preemption count. Pick on those numbers and write down the date and version, because the result is a snapshot.

The case for a different choice

  • SGLang if the workload becomes agent loops and branching prompts with large shared and re-used prefixes, or if EAGLE-3 speculation is a priority, since its docs list the most speculative methods and a large structured-output set.
  • TensorRT-LLM if the fleet is all NVIDIA, moving to Blackwell, and a platform team can own the version coupling, so that NVFP4 and FP8 KV and NVIDIA's tuned kernels pay for the extra moving parts.
  • llama.cpp if the target is CPUs, Apple or mixed hardware rather than H100s, or a single-tenant edge box.
  • Stay on TGI only if it is already deployed and works; plan the migration to vLLM or SGLang rather than adopting it fresh.

The recommendation also flips on the team, not just the engine. If nobody can read a CUDA trace, the engine with the largest community answers more of your questions. Capacity planning in chapter 08 is written engine-agnostic for that reason: the inputs are measured tokens per second at a batch size, whichever engine produced them.

✓ Check yourself

Answer from memory before opening each one.

  1. A contractor hands you "the 4-bit model" as a single .gguf file and asks you to serve it on vLLM next to your FP8 safetensors checkpoint. What do you check before agreeing, and what would you do differently for a production H100 deployment?

    Show answer

    Check that your vLLM version lists GGUF for Hopper and which quantization type the file holds, since K-quants and integer types differ in kernel support. For production H100 serving, prefer a checkpoint in a format the server's own kernels are tuned for, such as FP8 or AWQ safetensors. See formats.

  2. Why does loading from safetensors differ from loading a pickle-based checkpoint, in both safety and loading behaviour?

    Show answer

    Safetensors holds tensors only, so loading cannot execute code, while unpickling can run arbitrary code. It also supports zero-copy loading and reading slices, so each GPU can read just its shard. See formats.

  3. A new colleague proposes TGI because "Hugging Face maintains it, so it will track new models." What do you tell them?

    Show answer

    TGI's own documentation says it is in maintenance mode, accepting only minor fixes and documentation work, and points users to vLLM, SGLang, llama.cpp and MLX. New features, models and kernels will land elsewhere. See the engines.

  4. Your client code calls the engine with response_format for JSON mode, a custom adapter field and the OpenAI logprobs parameter. You want to test SGLang as a challenger next week. Where will it break?

    Show answer

    The standard fields should transfer, but the adapter field and any guided-decoding extensions are engine-specific, and logprob support varies by endpoint and server. Isolate engine-specific fields in one module and test each one on the challenger. See the feature table.

  5. Harbourline chose vLLM on documentation breadth. Name two measured results on the day-long replay that would make you switch to SGLang or TensorRT-LLM, and one that would not.

    Show answer

    A materially lower p95 TTFT at the same quality on the evaluation set, or a higher prefix hit rate with fewer preemptions, would justify switching. A small tokens/s gain inside run-to-run noise would not, since it does not repay the migration. See how Harbourline chose.

Takeaway

  • Safetensors holds tensors without executable code, GGUF is a self-contained single file for the llama.cpp family, and neither tells you the quantization method on its own.
  • vLLM, SGLang and TensorRT-LLM are the production candidates for GPU servers, and each documents quantization, speculation, prefix caching, LoRA and structured output.
  • TGI is in maintenance mode, and its maintainers point to vLLM and SGLang.
  • llama.cpp, Ollama and MLX-LM are tools for one user on one machine, and MLX-LM's own docs say its server is not for production.
  • OpenAI-compatible means the standard routes match; engine-specific extensions break the swap and belong behind one module.
  • Harbourline defaults to vLLM for documentation breadth, then confirms with a one-day replay against SGLang, because engine rankings move with each release.
