Section C · Making it fast

Attention and KV-Cache Optimisations

FlashAttention as an IO-aware exact kernel, paged and prefix caching, KV-cache quantization, chunked prefill and sliding windows, and what each buys at Harbourline's prompt shapes.

Overview

Chapter 02 showed that decode is limited by bytes moved, and chapter 03 shrank the weights until a 70B model fit on two H100 80 GB GPUs. This chapter covers what is left: how attention is computed, how the cache is shared, and how many bytes each cached token costs.

Paged allocation, the base layer of every modern engine, is taught in the paged attention guide and is assumed here. Five techniques sit on top of it, each with its mechanism, its Harbourline numbers, and the case where it does nothing.

All figures use Llama 3.3 70B. The Llama 3 paper gives the 70B architecture as 80 layers, 64 query heads and 8 KV heads, and the Llama 3.3 model card says it uses grouped-query attention. With a head dimension of 128, the cache costs 2 × 80 × 8 × 128 × 2 bytes = 327,680 bytes, or 320 KiB, per token in BF16. A Workload B request of 3,250 tokens holds about 1.07 GB of cache. The pool left after FP8 weights on two GPUs is about 68 GB, which holds 207,500 tokens, or 64 such requests.

FlashAttention: the same answer, fewer trips to memory

Standard attention writes the full score matrix to GPU memory, reads it back for the softmax, writes the probabilities, and reads them again for the multiply by V. For one Harbourline prompt of 3,250 tokens, one layer and 64 heads at 2 bytes, the scores alone are 3,250² × 64 × 2 B = 1.35 GB. Four passes through HBM move 5.4 GB. At 3.35 TB/s that is 1.6 ms per layer and about 130 ms over 80 layers on one GPU, or about 65 ms when tensor parallelism gives each of two GPUs half the heads. This assumes four passes and no overlap. The term is quadratic in prompt length and pure memory traffic.

FlashAttention (Dao et al., 2022) removes the term. It splits Q, K and V into tiles that fit in on-chip SRAM, computes scores for one tile at a time, keeps running softmax statistics so earlier tiles can be rescaled, and writes only the output. The paper calls it an IO-aware exact attention algorithm: it counts HBM reads and writes, not just FLOPs, and computes the same function as standard attention.

The three versions differ in how well they use the GPU, not in what they compute.

  • FlashAttention-2 (2023) repartitions work across thread blocks and warps. The authors report about 2× over the first version, reaching 50 to 73% of theoretical peak FLOPs on A100 where the first reached 25 to 40%.
  • FlashAttention-3 (2024) targets Hopper. It overlaps data movement and tensor-core work asynchronously and interleaves matrix multiplies with softmax. The authors report 1.5 to 2.0× over the previous version on H100, FP16 at up to 740 TFLOPs/s (75% utilisation) against about 35% for FlashAttention-2, and FP8 close to 1.2 PFLOPs/s.

The FP8 path is the one place where "exact" needs a caveat. It quantizes inside the kernel, so its output differs from the BF16 kernel. The authors report 2.6× lower numerical error than a baseline FP8 attention, which is not zero error.

In decode the query is one token, so no N × N matrix exists and the gain is small. It pays in prefill, which sets Workload B's time to first token. The engine selects the backend from the GPU, so check its start-up log on the H100s to confirm it picked the Hopper kernel. On A100 fleets the best kernel is the second version.

Prefix caching: the shared 1,200 tokens

A token's key and value vectors depend on every token before it. That is why a cache can only be reused for a prefix: two requests that begin with the same token ids have identical KV for those positions, and the first position where they differ invalidates everything after. vLLM documents automatic prefix caching as reusing the KV cache of existing queries when a new query shares the same prefix, and notes that it reduces prefill time, not decoding time. SGLang builds the same idea on a radix tree (RadixAttention), and TensorRT-LLM stores filled blocks in a radix search tree with reuse on by default. Sharing works on whole blocks of a fixed token count, so a partial block at the end of the shared prefix is recomputed.

At Harbourline, every Workload B prompt starts with the same 1,200-token system prompt, followed by retrieved passages that differ per question. The shared head is 40% of an average 3,000-token prompt. Three numbers follow, using 13,000 sessions a day and an illustrative prefill rate of 15,000 tokens/s for the pair, about 2.1 PFLOP/s at 140 GFLOP per token, roughly half the pair's dense FP8 peak.

  • Compute. 1,200 × 13,000 = 15.6 million of 39 million prefill tokens a day are skipped. That is about 17 minutes of the pair's day. Prefix caching does not move the cost line at this volume.
  • Latency. Each request skips 1,200 / 15,000 s = 80 ms of prefill, out of about 217 ms for 3,250 tokens. Against an 800 ms p95 budget that is headroom for queueing.
  • Memory. The prefix is stored once. At an illustrative peak of 1.5 requests/s, each lasting about 9 s (0.8 s to first token, then 250 tokens at 30/s), about 14 streams are in flight. Sharing replaces 14 copies of 393 MB with one, saving 13 × 393 MB = 5.1 GB of the 68 GB pool.
kv_budget.py
# Llama 3.3 70B, two H100 80 GB, FP8 weights
LAYERS, KV_HEADS, HEAD_DIM = 80, 8, 128
POOL_GB = 68                      # 2 x 72 GB usable, minus 70 GB weights, minus ~6 GB activations and graphs
PROMPT, ANSWER, SHARED = 3000, 250, 1200
SESSIONS_PER_DAY = 13_000
PREFILL_TOK_S = 15_000            # assumed prefill rate for the pair; measure yours

def kv_per_token(bytes_per_value):
    return 2 * LAYERS * KV_HEADS * HEAD_DIM * bytes_per_value   # K and V

for name, b in (("BF16 KV", 2), ("FP8 KV", 1)):
    per_tok = kv_per_token(b)
    tokens = POOL_GB * 1e9 / per_tok
    print(f"{name}: {per_tok:,} B/token, pool {tokens:,.0f} tokens, "
          f"{tokens / (PROMPT + ANSWER):.0f} requests of {PROMPT + ANSWER:,} tokens, "
          f"{tokens / 32_000:.1f} requests of 32,000 tokens")

saved_tokens = SHARED * SESSIONS_PER_DAY
print(f"prefix hit saves {saved_tokens:,} of {PROMPT * SESSIONS_PER_DAY:,} prefill tokens a day "
      f"({SHARED / PROMPT:.0%}), {saved_tokens / PREFILL_TOK_S / 60:.0f} GPU-pair minutes, "
      f"{SHARED / PREFILL_TOK_S * 1000:.0f} ms of TTFT per request")
streams = 14
print(f"14 streams share one prefix copy: saves {(streams - 1) * SHARED * kv_per_token(2) / 1e9:.1f} GB of KV")

Multi-turn sessions add a second prefix, turn one's prompt and answer. Both hits need nothing variable before the shared text.

One timestamp in the first line turns the cache off

If the system prompt begins with the date, the user's name or a request id, the first differing token ends the match and the 1,200 shared tokens are recomputed every time. Put variable text last and watch the engine's prefix hit-rate metric rather than assuming it works.

The cache also lives per replica. Hugging Face's TGI v3 notes warn that with several replicas behind a load balancer a user's next request may land on a replica without the prefix, and suggest sticky sessions, with the caveat that they may be unnecessary. Harbourline's single replica avoids this, but the second replica in chapter 08 will not. API-side prompt caching is in latency and cost at scale. Block hashing and eviction are in the paged attention guide.

KV-cache quantization: half the bytes per token

The KV cache can be quantized separately from the weights, and it is a different bargain: weights are read once per step regardless of batch, while the cache is read once per sequence and grows with context. FP8 KV halves the cost per token from 320 KiB to 160 KiB. That doubles the pool in tokens (207,500 to 415,000) and halves the cache bytes each decode step reads.

vLLM exposes it as --kv-cache-dtype fp8, with fp8_e4m3 and fp8_e5m2 variants. Two details matter for quality. With no calibration all scaling factors default to 1.0, and the docs recommend calibrating scales on a dataset with llm-compressor. Per-attention-head scales work only with the Flash Attention backend and need that calibration. A separate flag keeps chosen layers, such as sliding-window layers, at native precision. TensorRT-LLM lists FP8 KV on Hopper and Blackwell.

What does it buy at Harbourline? Less than the headline suggests. Workload B at peak holds 14 streams of 3,250 tokens, 14.9 GB of cache in a 68 GB pool, so capacity is not the constraint. Workload A holds more: at an average 1,650 tokens of context, the BF16-KV pool fits about 125 concurrent claims and the FP8-KV pool about 250. Idealised step time is (70 GB of weights + cache read) / 6.7 TB/s, about 20.5 ms either way, because doubling the sequences while halving the bytes reads the same 68 GB. That is about 6,100 against 12,200 tokens/s. Workload A needs 1.8 million output tokens in four hours, which is 125 tokens/s. Both ceilings are far above it, and both are bandwidth-only upper bounds; chapter 08 uses measured throughput.

So at Harbourline's prompt shapes the recommendation is to leave the cache in BF16. The case where it flips is long context: a 32,000-token document costs 10.5 GB of cache in BF16, so the pool holds 6 such requests and FP8 KV holds 13. If Harbourline moved claim-file summarisation onto this model, FP8 KV would be the first thing to enable. Before doing so, run the Harbourline evaluation set on both settings, including long-context questions, because the error is not visible in perplexity on short text.

Chunked prefill: keeping decode steady

The SARATHI paper states the problem: prefill saturates GPU compute even at small batch sizes, while decode leaves it mostly idle. If an engine runs a whole 3,250-token prefill as one step, every other stream waits. At the assumed 15,000 tokens/s that step takes about 217 ms, against a stream budget of 33 ms per token (30 tokens/s).

Chunked prefill splits the prompt and mixes each chunk with the running decodes. SARATHI describes chunked prefills plus decode-maximal batching, and reports up to 1.25× end-to-end throughput on LLaMA-33B on A100. In vLLM V1 the scheduler serves pending decodes first, then fills the remaining token budget with prefill, splitting a prompt that does not fit. The budget is max_num_batched_tokens, and the docs state the trade directly: smaller values give better inter-token latency, larger values give better time to first token.

Setting it for Harbourline is arithmetic. A decode step with 14 streams takes about 12.7 ms (70 GB of weights plus 14.9 GB of cache over 6.7 TB/s). To keep every step under 33 ms, a chunk can add (33 − 12.7) ms × 15,000 tokens/s, about 300 tokens. An uncached 3,250-token prompt then takes 11 chunks and about 360 ms to first token, against about 230 ms unchunked. With the prefix hit, 2,050 tokens take 7 chunks and about 230 ms. The new request pays about 130 ms more so that fourteen others do not stall, which fits the 800 ms budget.

Prefix caching and chunking pay for each other

A prefix hit removes four of the new request's eleven chunks, so tune the token budget with prefix caching on and benchmark on a warm cache. The scheduler is covered in the paged attention guide.

The setting flips for Workload A, which has no stream-rate target: use a large budget, since vLLM's docs suggest values above 8,192 for throughput.

Sliding windows: a model property, not a switch

With sliding-window attention each token attends only to the previous W tokens. Mistral 7B uses W = 4,096. Because layers stack, information still travels W × k tokens by layer k, a theoretical span of about 131,000 tokens at the last layer. The cache keeps only the last W positions in a rolling buffer, position i at slot i mod W. The Mistral paper reports an 8× smaller cache at 32,000 tokens with no loss in quality.

This does nothing for Harbourline: Workload B's 3,250-token requests fit inside one 4,096 window. The Llama 3 architecture as published has no window, and a window cannot be bolted onto a trained model without retraining, since the model learned to use the whole context. It matters when you choose a model: some architectures window some layers, so the per-token cache is smaller than the formula above. Compute it from the model's own config, layer by layer, and do not reuse 320 KiB. Engines handle the mixed case: vLLM can skip FP8 on sliding-window layers, and TensorRT-LLM frees blocks that leave a layer's window.

The techniques that reduce work (FlashAttention, prefix caching) pay at Harbourline's volumes. Those that reduce capacity pressure (FP8 KV, windows) do not, because 68 GB is generous for 14 streams. Chapter 05 moves from storing the cache to spending each memory-bound step on more than one token.

✓ Check yourself

Answer from memory before opening each one.

  1. A colleague says FlashAttention-3 is faster because it approximates softmax. What is wrong with that, and where does the speed come from?

    Show answer

    The algorithm is exact. The speed comes from moving less data through HBM and from using Hopper's asynchronous tensor cores and tensor memory accelerator more fully. Only the FP8 path is lossy. See FlashAttention.

  2. Harbourline adds the current date and the customer's first name as the first line of the help-centre system prompt. Prefix-cache hit rate falls from near 100% to near zero. Why, and what is the fix?

    Show answer

    Keys and values depend on all earlier tokens, so a match must start at position zero and stops at the first differing token. A first line that varies per request ends every match at once. Move the variable text after the shared 1,200 tokens. See prefix caching.

  3. Workload B has 14 streams in flight at peak. A teammate proposes FP8 KV cache to "double our capacity". Using the numbers in this chapter, do you agree?

    Show answer

    No. Peak use is 14 × 1.07 GB = 14.9 GB of a 68 GB pool, so capacity is not binding and FP8 KV would add quality risk for nothing. It would matter at contexts near 32,000 tokens, where the pool holds 6 requests in BF16. See KV-cache quantization.

  4. You set max_num_batched_tokens to 16,384 on the interactive deployment and p95 time to first token improves but users report stuttering streams. What happened, and what do you change?

    Show answer

    A large budget lets one prefill occupy a whole step, so running streams stall for the length of that step: better TTFT, worse inter-token latency. Reduce the budget to about the size that keeps the step under the per-token budget, here about 300 tokens at the assumed prefill rate. See chunked prefill.

Takeaway

  • FlashAttention is exact attention that avoids writing the N × N score matrix to HBM; it speeds up prefill, not decode.
  • A KV cache can only be reused as a prefix, so prefix caching depends on keeping variable text out of the head of the prompt.
  • At Harbourline, the shared 1,200-token prompt saves 40% of prefill tokens and about 80 ms of TTFT per request, but only about 17 GPU-minutes a day.
  • FP8 KV halves the cache per token, and pays only when the pool is the constraint, which for Harbourline means contexts near 32,000 tokens.
  • Chunked prefill trades the new request's TTFT for the other streams' steadiness, and its token budget should be derived from the per-token latency target.
  • Sliding windows belong to the trained model, so compute cache cost from its config.
