Structured Output and Constrained Decoding

Grammar-constrained decoding, JSON schema enforcement, tool-call formats, what it costs in latency and quality, and the libraries that do it as of November 2026.

When the output feeds a machine

Harbourline's nightly batch reads about 6,000 first notices of loss and writes, for each, a record the adjuster queue can load: a loss type from a fixed list, an urgency from one to four, a list of missing documents. A person can forgive a stray sentence before the JSON. A loader cannot. There are three ways to get valid records from a model. You can ask in the prompt and validate after, you can constrain generation so invalid tokens cannot be produced, or you can fine-tune until the model rarely strays. The first two are this chapter. The third is in the fine-tuning guide.

Take the arithmetic of validating alone. If 2% of outputs fail to parse, an illustrative rate, that is 120 records a night. Re-asking costs one more call of about 1,800 tokens each, 216,000 tokens a night, which is trivial for a batch with a four-hour window. A retry loop is a fine answer there. It is a poor answer for the interactive path, where a failed parse adds a whole generation to the user's wait, and for agents, where a malformed tool call stalls a multi-step run. Constraining costs per token on every request, so it pays where a failure costs more than that.

How constrained decoding masks logits

At each step the model produces one logit for every token in its vocabulary, 128,000 for Llama 3. Sampling turns them into probabilities. Constrained decoding inserts a step before that: compute which tokens may legally come next, set the logits of all others to negative infinity, and sample from what remains. The model is unchanged. Only the choice among its outputs is restricted. How the sampler picks a token is the subject of the token-generation guide.

logits (128k) ---> mask ---> softmax ---> sample ---> token ^ | | grammar state (automaton) | +---- advance state with the token <-+ state after {"loss_type":" allows: "fire" "water" "theft" ... every other token's logit = -inf

The hard part is that grammars speak in characters and models speak in tokens. A token can span several characters, and a single JSON string value can be tokenised many ways, so the engine must test each of the 128,000 tokens against the automaton's current state. Done naively that is a scan of the vocabulary per step. The libraries differ in how they avoid it. XGrammar's paper splits the vocabulary into tokens whose validity does not depend on the parser's stack, which are checked ahead of time, and context-dependent tokens, checked at runtime, and reports up to a 100× speedup over earlier grammar engines. llguidance's README claims about 50 µs of single-core CPU time per token for a 128k tokenizer, and 1.5 ms for the full mask of a typical JSON schema. Those are the authors' figures, to be reproduced on your own schemas.

Put them against the decode step from chapter 08. A step with 39 streams takes 33 ms. If masks were computed one after another at 50 µs each, 39 streams cost 39 × 50 µs ≈ 2 ms, about 6% of the step. Engines overlap this CPU work with GPU compute, which is the point of co-designing grammar and engine that the XGrammar abstract describes, so the observed cost is often smaller. The cost that does show up is the first request with a new schema, when the grammar is compiled. vLLM's tool-calling documentation says that, for a named function, compiling the grammar adds several seconds the first time before it is cached. A schema that changes per request defeats that cache.

Enforcing a JSON schema

In vLLM a client asks for a schema through the OpenAI-compatible response_format with type json_schema, or through structured_outputs in extra_body, which also accepts choice, regex, grammar and structural_tag. The server's backend defaults to auto, which picks one for the request; the documentation names xgrammar and guidance. Older guided_* fields were removed in v0.12.0. This is a sketch against Harbourline's claim record, not a tested pipeline:

triage.py (sketch)
from typing import Literal
from openai import OpenAI
from pydantic import BaseModel, Field

class Triage(BaseModel):
    loss_type: Literal["fire", "water", "theft", "collision", "other"]
    urgency: int = Field(ge=1, le=4)
    missing_documents: list[str]

client = OpenAI(base_url="http://gateway.internal/v1", api_key="unused")
resp = client.chat.completions.create(
    model="harbourline-70b",
    messages=[{"role": "user", "content": notice_text}],
    max_tokens=600,
    response_format={"type": "json_schema", "json_schema": {
        "name": "triage", "schema": Triage.model_json_schema()}},
)
choice = resp.choices[0]
if choice.finish_reason == "length":      # cut off mid-JSON: not valid
    raise RuntimeError("raise max_tokens or shorten the schema")
record = Triage.model_validate_json(choice.message.content)

Three details matter. First, finish_reason must be checked: a constraint guarantees that every prefix is valid, not that the output is complete, so a response that hits max_tokens stops mid-object and will not parse. Second, schema coverage is partial. llguidance says it supports "a large subset" of JSON Schema, and the JSONSchemaBench paper was written because little had been done on systematically comparing the behaviours of Guidance, Outlines, llama.cpp, XGrammar, OpenAI and Gemini across 10,000 real-world schemas. Run your schemas against your engine and keep the validator after it, for any keyword the backend ignores. Third, the guarantee is syntactic. The mask cannot stop the model from choosing "theft" for a flood. The Literal list makes a wrong answer look right, so the accuracy check from the evals guide still applies.

Tool calls

A tool call is structured output with a convention on top: a function name and arguments, in a format the model was trained on. Open-weight models differ in that format, so vLLM needs --enable-auto-tool-choice and a --tool-call-parser matched to the model, such as hermes or llama3_json, and it takes a chat template that renders tool messages. Pick the parser for the weights you serve and re-check it when the model changes (chapter 10).

What tool_choice does about validity is easy to miss. With auto, the model writes its call as free text and the parser extracts it, so a malformed call is possible. With required, or a named function, vLLM uses the structured-output machinery, so the arguments match the schema, at the cost of the grammar compile on first use. For a state-changing tool such as a Harbourline address update, use the constrained modes and still validate the arguments against business rules before executing. Whether the call should happen at all belongs to the agents and tools chapter of the security guide.

Use the engine-native path first. It is the one your engine's maintainers test with its scheduler, and it keeps the request shape portable across engines. Reach for a library when your engine lacks a feature you need, a grammar format in particular, or when you run outside a server, for instance a batch job calling a model through Transformers. The libraries are changing quickly, so pin versions and re-run your schema suite on each upgrade. The vLLM page also notes that lm-format-enforcer is deprecated, which is an example of a backend disappearing under a deployment.

What constraining costs

Latency. The per-token mask is small if it is overlapped, the first-use compile is seconds, and a schema that varies per request pays it every time. Reuse a fixed schema, or enumerate a few. Quality. Setting disallowed logits to negative infinity renormalises the probability over what remains, so a token the model rated very unlikely can become the likeliest legal choice, and the model has no way to say it disagrees. Tam et al. report a significant decline in reasoning ability under format restrictions, larger as the restrictions tighten. Note that this finding comes from their tasks and models, and engines have changed since.

The practical remedy is order. Fields generate in the order the schema lists them, so put a free-text reasoning field before the answer fields, and the model thinks before it commits to a loss type. Costing the extra tokens at 100 or so a record on 6,000 records is 600,000 tokens a night, still small. When the reasoning must be long, split into two calls: a free-text analysis, then a constrained extraction of its conclusion.

A valid record is not a correct record

Constrained output removes parse errors and leaves wrong answers in place, and it makes the wrong ones harder to spot because they look right. Keep the eval on the Harbourline set, and track the validity rate and the accuracy separately, so an improvement in one cannot hide a drop in the other.

Constrain, validate, or both

Constrain when the caller is a machine with no retry path: a tool call that mutates state, an interactive path with a latency budget, or a model small enough that its raw format failures are common. Validate after the fact when the failure rate is low and retries are cheap, as in the nightly batch, when the schema uses features your backend lacks, or when the task needs long reasoning that a grammar would cut off. In practice do both: constrain the shape, then validate the semantics with code, such as an urgency consistent with the loss type, and retry or route to a person on failure. The flip is a model fine-tuned on the exact schema, which may reach a failure rate where the mask is no longer worth its overhead. Measure that rate on the eval set rather than assuming it.

✓ Check yourself

Answer from memory before opening each one.

  1. Describe what happens to the logits and the probabilities at one decode step when a JSON grammar is active and the output so far is {"urgency":.

    Show answer

    The engine finds the tokens that can legally follow, here digits or whitespace, sets every other logit to negative infinity, and renormalises over the rest. Sampling then picks among the survivors, and the automaton advances by the chosen token. See the mask.

  2. A response with a schema returns HTTP 200 and fails to parse. What do you check first, and why can it happen when the constraint is on?

    Show answer

    Check the finish reason. A constraint guarantees valid prefixes, so a generation cut off by the token limit stops mid-object. Raise the limit or shorten the schema. See enforcing a schema.

  3. A team enables constrained decoding and the accuracy of the loss-type field drops, while parse errors go to zero. Offer two explanations and one change for each.

    Show answer

    The mask forces a legal but unlikely token the model would not have chosen, and tighter formats lower reasoning quality, so add a reasoning field before the answer or split into two calls. Or the zero parse errors reveal errors that used to be retried away, so compare accuracy on the same records with retries counted. See what constraining costs.

  4. Why does tool_choice set to auto not give the same guarantee as required on the same server?

    Show answer

    With auto the model writes the call as free text and a parser extracts it, so it can be malformed. required and named choices use structured outputs, so the arguments match the schema. See tool calls.

  5. The nightly batch has a 2% parse-failure rate and four hours to spare. A colleague wants constrained decoding on it. Make the case against, and name what would change your mind.

    Show answer

    Retrying 120 records costs about 216,000 tokens, which the window absorbs, while the mask adds compile and per-token overhead and may lower reasoning quality. That judgement flips if the failure rate rises, retries began to fail repeatedly, or a downstream step could not tolerate a retry delay. See constrain or validate.

Takeaway

  • Constrained decoding masks the logits of tokens the grammar forbids, so the model's weights are untouched and only its choices are restricted.
  • The mask guarantees syntax, not truth: check the finish reason for truncation, and keep evals for accuracy separate from the validity rate.
  • The cost is a per-token mask that engines overlap with GPU work, plus a first-use compile that a per-request schema pays every time.
  • Tool calls with auto choice can be malformed, while required and named choices go through the structured-output machinery.
  • Prefer the engine-native path, add a library only for a capability the engine lacks, and pin versions because this area moves fast.
  • Constrain where a failure is expensive, validate where a retry is cheap, and do both for anything that changes state.
