Section D · Running it

Operating in Production

Per-request observability, KV-cache and queue metrics, canary model upgrades, serving fine-tuned adapters, placing guardrails, and the incidents open-weight serving produces.

What to record on every request

A self-hosted model gives you the signals a vendor API hides, and you pay for that with the duty to look at them. Start with one structured log line per request, written by the gateway so that it covers the queue before the engine as well as the engine: a request id, the model and adapter name, the engine image, prompt tokens, completion tokens, time in queue, TTFT, mean inter-token latency, the finish reason and a flag for whether the request was preempted. The finish reason matters most. A rise in length means truncated answers or runaway generations, and nothing else surfaces it.

Beside the logs sit the engine's own gauges and histograms. vLLM serves them at /metrics, and these are the ones to chart for Harbourline's help-centre assistant:

The thresholds are starting points from the arithmetic in chapter 08, not vendor guidance. The 33 ms is 1/30 s. Track the output rate of the whole fleet through vllm:generation_tokens and vllm:prompt_tokens as well, so cost per million tokens is a dashboard line and not a quarterly surprise. GPU-level health such as memory errors and temperature comes from your platform's exporter, not the engine, so confirm the host has one before you rely on it.

Upgrading the model, the tokenizer and the engine

There are three things that change under a live service, and each can fail silently. A new model version changes the answers. A new tokenizer changes what a token is. A new engine release changes the scheduler, the kernels and sometimes the default flags. The upgrade path is the same for all three: stand up a second deployment next to the first, send it a copy of real traffic, compare, shift a small share, and keep the old one until the new one has carried a full peak. Because each model is its own pod set (chapter 07), rollback is moving the gateway's weights back and costs no deployment. The decision rules for judging the new model on the eval set are in model and prompt changes. What is specific to serving is the list of things that move with it.

The tokenizer deserves its own check, because it changes numbers that your plan treats as constants. Say a new model tokenises Harbourline's help-centre text into 10% more tokens, an illustrative figure. A 3,000-token prompt becomes 3,300 and the 250-token answer 275, and the KV cache per request grows from 1.065 GB to 1.16 GB. The per-replica batch that the 30 tokens-per-second floor allows was 39 in chapter 08, from 20.8 GB per GPU of cache reads at 0.5325 GB per request on each GPU. At 0.58 GB per GPU it is 35. A 30 token-per-second floor also buys fewer words. Prefill takes 10% longer, and every per-token price, prompt budget and max-model-len in your configuration changes meaning. Also re-check the things tied to the vocabulary: the chat template and stop tokens, the tool-call parser, and the compiled grammars of chapter 09.

For the canary, compare per version, from the logs above: finish-reason mix, tokens per answer, TTFT and inter-token latency percentiles, preemptions, schema validity rate and the eval score on the labelled set. Run the chapter 08 load test on the new image before it takes traffic, since a release that is correct but 20% slower consumes a replica's worth of headroom. Pin the engine image by digest, so that "the same version" cannot change under you.

Serving fine-tuned adapters

If Harbourline fine-tunes with low-rank adapters, one base model can serve several of them. In vLLM, --enable-lora turns it on, --lora-modules name=path registers adapters at startup, and a client picks one by putting its name in the model field. Requests for different adapters and for the base model run side by side in the same batch. Set --max-lora-rank to the largest rank you will serve, because the documentation warns that setting it much higher wastes memory, and that memory comes out of the KV budget you sized in chapter 08.

The same page describes loading and unloading adapters at runtime through /v1/load_lora_adapter and /v1/unload_lora_adapter, gated by VLLM_ALLOW_RUNTIME_LORA_UPDATING, and says plainly that the feature is insecure and belongs only in an isolated, fully trusted environment, not production. For a production fleet, ship an adapter as a new deployment, with the canary above, so that every adapter version has an owner and a rollback. How adapters are trained, merged and retired is the job of the fine-tuning guide's serving chapter.

Where guardrails sit

A guardrail is a check on what goes into or comes out of the model, and the serving stack offers three places for one. The gateway can check the input before the engine is reached: length, a banned pattern, a classifier for prompt injection. It can check the output after the engine returns. And the engine itself can constrain the output, which is the structured-output machinery of chapter 09. Each costs something different. An input check adds to TTFT directly, so a guard model of 8B parameters in front of a 70B adds its own prefill to the 800 ms budget. An output check on a streamed answer faces a choice: hold the answer until it passes, which breaks the 30 tokens-per-second experience, or stream and be unable to retract what the user has already read.

Put cheap deterministic checks at the gateway, put the classifier on the path only where a miss is expensive, and keep guard models on their own GPUs so a guard spike cannot starve the main model's batch. What to check, and why prompt injection cannot be filtered away, is the subject of the security guide.

The incidents this stack produces

The long prompt. Harbourline's uploader accepts policies of up to 300 pages. At an assumed 500 tokens a page, that is 150,000 tokens, past the 128k context in the model card, so the engine rejects it. A request at the 128,000 limit would hold 128,000 × 327,680 bytes = 42 GB of cache, 62% of the 68 GB budget, and even a 32,000-token request holds 10.5 GB, enough to push a busy replica into preemption. Set --max-model-len to a value your budget can carry, reject larger requests at the gateway with a clear error, and route long documents to a batch path with its own capacity.

Cache thrash. When the cache fills, vLLM pauses some requests and, in its default V1 mode, recomputes them later. The recomputation is work that produces no new tokens, so preemptions push throughput down at the moment load is highest, and TTFT with it. The documented levers are to raise gpu_memory_utilization, lower max_num_seqs or max_num_batched_tokens, or raise the tensor-parallel size. The prefix cache can thrash too: if the prompts' shared prefix is evicted by varied traffic, the hit rate falls and prefill cost returns. Watch the hit rate against its baseline.

The stuck request. A generation that never reaches a stop token, a repetition loop, or a client that disconnected still holds a batch slot and its cache. With no cap on max_tokens, a runaway can hold a slot for as long as the context allows; at 30 tokens per second, 100,000 tokens is nearly an hour. Cap max_tokens at the gateway, set timeouts, and test that your engine releases a request when the client goes away rather than assuming it.

The node. A GPU or host fails and takes a tensor-parallel pair with it. That is what the second replica is for, and the readiness check must exercise a real generation, not only a port.

✓ Check yourself

Answer from memory before opening each one.

  1. Throughput on a replica falls 30% during the morning peak while CPU and GPU look busy and no request errors. Which metric do you check, and what mechanism explains the fall?

    Show answer

    The preemption counter, with KV cache usage. A full cache makes the engine pause requests and recompute them later, so GPU time goes on repeated work and fewer new tokens come out. See the incidents.

  2. A model upgrade passes the eval set, yet two days after rollout the replicas queue at traffic they handled before. What changed that the eval set could not show, and how would you have caught it?

    Show answer

    The new tokenizer produces more tokens for the same text, so prefill and KV cache per request grow and the SLO batch ceiling falls. A canary that compared tokens per request and ran the load test would show it. See upgrading.

  3. Why is it a mistake to alert on mean TTFT from the engine's histogram alone?

    Show answer

    The SLO is a p95 as the user sees it, which includes gateway queue time that the engine histogram starts after, and a mean hides the tail. Alert on the gateway's p95. See what to record.

  4. A team proposes loading adapters at runtime so data scientists can ship without a deployment. What does the vLLM documentation say about that, and what do you offer instead?

    Show answer

    It calls the runtime update endpoints insecure and for isolated, fully trusted environments only. Offer a deployment per adapter version through the normal canary, so each has an owner and a rollback. See adapters.

  5. You must add a safety classifier to the help-centre assistant without breaking an 800 ms TTFT budget that currently sits near 560 ms. Where do you place it and what do you check?

    Show answer

    Run it on its own GPU, on the paths where a miss is expensive, and measure its added latency at p95 against the 240 ms of spare budget. If it does not fit, run it in parallel with the model. For streamed output you must choose between holding the answer and being unable to retract it. See guardrails.

Takeaway

  • Log one line per request at the gateway, including queue time, TTFT and finish reason, and chart the engine's queue, KV usage, preemption and latency metrics next to it.
  • A tokenizer change alters token counts, KV size and the batch the SLO allows, so a model upgrade needs a load test and a canary, not only an eval score.
  • Serve adapters as versioned deployments; the runtime load endpoints are documented as unsafe for production.
  • Guardrails cost TTFT, so keep cheap checks at the gateway, put classifiers where a miss is expensive and keep guard models off the main model's GPUs.
  • Long prompts, a full cache and unbounded generations are the usual causes of an incident, and each has a cap or a limit you can set before it happens.
  • A runbook that maps symptom to metric to first action is what turns the dashboard into a response.
