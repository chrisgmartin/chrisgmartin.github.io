Section C · Making it fast

Quantization

The precision ladder from BF16 to INT4, weight-only against weight-and-activation methods, GPTQ, AWQ, GGUF and FP8, calibration data, what accuracy you lose and how to measure it, and fitting a 70B-class model on Harbourline's GPUs.

The precision ladder

The previous chapter showed that a decode step is a weight read, so the cheapest way to speed it up is to make the weights smaller. A 70B-parameter model has 70 × 109 weights, and the bytes per weight set the memory bill:

FormatBits70B weightsWhat it keeps
FP3232280 GBFull range and precision. Training master copy; rarely served.
BF1616140 GBFP32's range with fewer mantissa bits. The release format of many open models and the quality baseline.
FP8 E4M3870 GBA float with 4 exponent and 3 mantissa bits, so range and relative precision survive coarsely. Hopper and newer run it natively.
INT8870 GB256 evenly spaced levels per scale. Fine when values are well behaved; outliers hurt.
INT4435 GB plus scales16 evenly spaced levels per scale. Needs small groups and care.

FP8 has two encodings, E4M3 and E5M2, proposed in Micikevicius et al. (2022). E5M2 trades mantissa for range and E4M3 the reverse. The paper reports that FP8 post-training quantization worked on language models trained in 16 bits that did not quantize well to INT8. The reason is where the resolution sits: a float spends its levels densely near zero and sparsely at large magnitudes, while an integer grid is uniform, so one large value stretches it and starves the small values. The next section measures that.

Scales, absmax and zero-point

Mapping a float tensor to integers needs a scale. In absmax (symmetric) quantization, scale = max|w| ÷ qmax, where qmax is 127 for INT8 and 7 for INT4, and each weight becomes q = round(w ÷ scale), clipped. The dequantized value is q × scale. Zero-point (asymmetric) quantization uses the range [min, max] instead: scale = (max − min) ÷ (2bits − 1) and an integer offset so that zero maps exactly. It wastes fewer levels when values are lopsided, as activations can be; weights are roughly symmetric, so absmax is the usual choice for them.

A worked case. Weights [0.12, −0.5, 0.03, 0.9] with INT8 absmax: scale = 0.9 ÷ 127 = 0.00709, giving q = [17, −71, 4, 127] and dequantized values [0.1205, −0.5032, 0.0284, 0.9], so the largest error is 0.0032. Quantize the same four to INT4: scale = 0.9 ÷ 7 = 0.129, and 0.12 rounds to q = 1 (0.129) while 0.03 rounds to 0. The small weights are lost, and the cure is the scale granularity. One scale for a whole tensor is cheap and fragile. One per output channel is the common default for FP8 and INT8 weights. One per group of 32 to 128 weights is what makes INT4 usable, and it costs memory: a 16-bit scale per 128-weight group adds 16 ÷ 128 = 0.125 bits per weight.

The script below runs on a synthetic slab of weights with a standard deviation of 0.02 and 8 outliers 25 times larger, and prints the error relative to the weights' own spread. It uses only the standard library.

absmax.py
import random
from math import sqrt

def quant_absmax(w, bits, group):
    """Symmetric absmax quantization with one scale per `group` consecutive weights."""
    qmax = 2 ** (bits - 1) - 1                       # 127 for INT8, 7 for INT4
    out = []
    for i in range(0, len(w), group):
        block = w[i:i + group]
        scale = max(abs(x) for x in block) / qmax
        for x in block:
            q = max(-qmax - 1, min(qmax, round(x / scale)))
            out.append(q * scale)                    # dequantized value
    return out

random.seed(0)
w = [random.gauss(0, 0.02) for _ in range(8192 * 16)]    # one weight slab, std 0.02
for i in random.sample(range(len(w)), 8):
    w[i] *= 25                                           # a few outliers

std = sqrt(sum(x * x for x in w) / len(w))
print("bits  group   relative RMS error")
for bits, group in [(8, len(w)), (8, 128), (4, len(w)), (4, 128), (4, 32)]:
    d = quant_absmax(w, bits, group)
    rms = sqrt(sum((a - b) ** 2 for a, b in zip(d, w)) / len(w))
    print(f"{bits:>4}  {group:>6}  {rms / std:8.4f}")

Output from running it with Python 3:

bits  group   relative RMS error
   8  131072    0.1235
   8     128    0.0082
   4  131072    0.9793
   4     128    0.1294
   4      32    0.0989

With one scale for the whole slab, INT4 loses essentially all the information (0.98, an error as big as the signal) because the outliers set a coarse grid. Groups of 128 bring INT4 to 0.13 and groups of 32 to 0.10, and INT8 per group is nearly clean at 0.008. This is a synthetic slab, not Llama's weights, so read it as the shape of the effect.

Weight-only against weights and activations

You can quantize the weights alone, or the weights and the activations they multiply. The notation is W4A16 (4-bit weights, 16-bit activations) or W8A8. The choice follows the roofline.

Weight-only (W4A16, W8A16). The kernel loads the small weights, unpacks them to 16 bits in registers, and multiplies at 16-bit speed. Bytes read fall, arithmetic does not. That is exactly what a memory-bound decode step needs: INT4 at about 4.2 bits is 36 GB instead of 70 GB for FP8, so the weight read per GPU falls from 10.4 ms to about 5.4 ms. It does little for compute-bound prefill, and the unpacking can slow it. In vLLM's hardware table, AWQ, GPTQ and the Marlin kernels run on Hopper, and Marlin "always runs with 16-bit activations".

Weights and activations (W8A8). Both operands are 8-bit, so the matrix multiply itself runs on the 8-bit tensor cores. On the H100 SXM that is 1,979 TFLOPS dense for FP8 against 989.5 for BF16, so prefill gets up to twice the compute as well as half the bytes. The vLLM documentation says FP8 weight and activation quantization is accelerated on GPUs such as the H100, with FP8 compute on compute capability 8.9 and newer (Ada, Hopper, Blackwell), while Ampere only gets weight-only FP8 through Marlin. It also claims a 2x cut in model memory and up to 1.6x higher throughput.

The catch is activations. They have large outlier channels that weights lack, which is what LLM.int8() (Dettmers et al., 2022) found: it keeps the outlier feature dimensions in a 16-bit multiply and the other 99.9 percent of values in 8 bits. SmoothQuant (Xiao et al., 2022) takes the other route and moves the difficulty offline, rescaling activations down and the matching weights up in a mathematically equivalent transformation, so W8A8 INT8 works, with a reported speedup of up to 1.56x and 2x less memory.

So, for the Harbourline pair: use FP8 W8A8 as the default, since it speeds both phases and has the best accuracy record, and pick INT4 weight-only when memory is the binding constraint. The exception is hardware: a pair of A100s has no FP8 tensor cores, and there W4A16 or INT8 is the choice.

GPTQ, AWQ, GGUF, FP8 and what each one is for

  • GPTQ. Frantar et al.'s GPTQ (2022) is a one-shot post-training method that quantizes the weights layer by layer, adjusting the weights not yet quantized to compensate for the rounding error using a small calibration set. The paper reports 3 or 4 bits per weight with negligible accuracy loss, and a 175B model quantized in about four GPU hours.
  • AWQ. Activation-aware Weight Quantization (Lin et al., 2023) observes that protecting about 1 percent of salient weight channels greatly reduces error, picks those channels from the activation magnitudes rather than the weights, and scales them up before quantizing, with no backpropagation or reconstruction.
  • GGUF k-quants. The llama.cpp format stores quantized blocks with their scales in one file. Its quantize README lists, for Llama 3.1 8B, Q4_K_M at 4.89 bits per weight, Q5_K_M at 5.70, Q6_K at 6.56 and Q8_0 at 8.50. The "4" in the name is not the cost: scaled to 70B, Q4_K_M is 70 × 109 × 4.89 ÷ 8 ≈ 43 GB, not 35. An importance matrix computed on calibration text lowers the loss. GGUF is the format for llama.cpp and Ollama, and vLLM can load it, but the engines chapter covers which engine fits a production server.
  • FP8 on Hopper and Blackwell. vLLM's recommended FP8 recipe, FP8_DYNAMIC, uses static per-channel weight scales and dynamic per-token activation scales. The documentation says it needs no calibration data and that simple round-to-nearest recovers accuracy, which makes it the lowest-effort option on the ladder.

Embedding and output-head matrices are usually left in 16 bits; the vLLM recipe above ignores lm_head. For Llama 3.3 70B that head is 128,256 × 8,192 = 1.05 × 109 parameters, which is 2.1 GB at BF16 against 1.05 GB at FP8, so "70 GB" in FP8 is really about 71 GB in practice.

Calibration data

GPTQ, AWQ and static activation scales need to see typical inputs to choose their scales and compensations. The calibration set is a sample of text run through the model once. It matters for the same reason a held-out set does: methods fit to it. Calibrating on generic web text tunes the scales for web text, not for policy questions full of deductible tables and clause numbers.

For Harbourline, calibrate on the real prompt shape: the system prompt, retrieved policy chunks, and questions, drawn from a sample that is not in the evaluation set from the eval-set chapter. Otherwise the quantized model is fit to the exam. FP8 with dynamic scales needs no calibration data, one reason it is the default.

Measuring the loss

Perplexity is the usual first check, and it is not enough. It averages the next-token loss over every token of a text, most of which are easy, so a model can stay within a fraction of a percent of baseline perplexity while getting a rare, important token wrong more often: a digit in a deductible, a clause number. Kurtic et al.'s study, "Give Me BF16 or Give Me Death?", ran over 500,000 evaluations across the Llama 3.1 family and reports that FP8 W8A8 is effectively lossless across model sizes, well-tuned INT8 W8A8 loses roughly 1 to 3 percent, and INT4 weight-only is more competitive than expected. Treat that as a prior and verify it for your model.

The check that decides is the Harbourline labelled set, run on the BF16 baseline and each candidate with identical prompts and decoding. Compare item by item, not by average. Suppose, illustratively, that on 400 items INT4 turns 22 correct answers wrong and 9 wrong answers right. The net loss is 13 items, 3.25 points. An exact two-sided sign test on the 31 changed items gives p ≈ 0.03, so the drop is unlikely to be noise, which the two accuracy percentages alone (88.0 and 84.8) do not show. The paired method is the one in the ship decision chapter.

Then slice it. Quantization hurts unevenly, so split the results by deductibles and limits, exclusions, identifiers, long prompts and any structured-output cases, and look for the slice where flips concentrate. If INT4 loses on identifiers only, keep FP8 where memory allows.

Fitting 70B on two H100s with KV headroom

Weights are the first claim on memory and the KV cache gets the rest. Two H100 80 GB GPUs hold 160 GB. Leaving 10 percent unallocated, take 0.90 × 80 = 72 GB usable per GPU, 144 GB for the pair, and subtract an assumed 3 GB per GPU for activations and CUDA graphs, 6 GB in all. The cache costs 327,680 B per token (chapter 02), so a 3,250-token request takes 1.065 GB. The table shows the arithmetic, with weights at 16, 8 and 4.16 bits per weight:

FormatWeightsLeft for KV (144 − 6 − weights)Tokens (÷ 327,680 B)Requests of 3,250 tokens
BF16140.0 GB−2.0 GBnone0
FP870.0 GB68.0 GB207,52063.9
INT4, groups of 12836.4 GB101.6 GB310,15995.4

The INT4 row assumes a 16-bit scale and a 4-bit zero-point per 128 weights. BF16 does not fit with any headroom: even at 100 percent of memory only 160 − 140 − 6 = 14 GB would remain, about 13 requests, and with the 90 percent convention the weights alone overrun the budget. FP8 holds about 64 concurrent requests at the full 3,250 tokens, the batch the last chapter used. INT4 holds about 95 and halves the weight read. Now the cache limits the batch, which is the case for the techniques in chapter 04: an FP8 cache halves the 320 KiB per token and doubles the 64 to about 127 requests.

Which one for Harbourline? FP8, because it is lossless on the evidence above, speeds prefill as well, and 64 concurrent requests is several times the roughly ten concurrent streams Workload B peaks at. It flips to INT4 if the 400-item set shows no loss and you want one GPU, not two: 36.4 GB of weights leaves 72 − 36.4 − 3 = 32.6 GB, about 31 requests on a single H100, half the hourly bill with no inter-GPU all-reduce, at the price of lower peak capacity.

✓ Check yourself

Answer from memory before opening each one.

  1. INT4 weight-only quantization cuts the decode weight read roughly in half versus FP8, yet barely changes time to first token. Why?

    Show answer

    Decode is memory-bound, so fewer bytes per step helps directly. Prefill is compute-bound and, with 16-bit activations, still multiplies at 16-bit speed after the weights are unpacked, so it gains nothing and may lose a little to the unpacking. See weight-only against weights and activations.

  2. A weight tensor has typical values around 0.02 and one outlier at 0.5. With a single INT4 absmax scale for the whole tensor, what happens to the typical weights, and what fixes it?

    Show answer

    The scale is 0.5 ÷ 7 = 0.071, so a weight of 0.02 becomes round(0.28) = 0 and almost all typical weights vanish. Per-group scales confine the outlier to its own group of 32 to 128 weights, at about 0.125 bits per weight extra for a 16-bit scale per 128. See scales, absmax and zero-point.

  3. A vendor shows the INT4 model within 0.5 percent of baseline perplexity and says it is ready to ship. What do you run before agreeing, and why can perplexity mislead?

    Show answer

    Run the labelled set on both models, compare per item, and slice by deductibles, identifiers and exclusions. Perplexity averages over mostly easy tokens and can hide errors on the rare ones that carry a deductible or clause number. See measuring the loss.

  4. On the 400-item set, a quantized model turns 22 right answers wrong and 9 wrong answers right. A colleague notes the accuracy only moved from 88.0 to 84.8 percent and calls it noise. How do you respond?

    Show answer

    Only the 31 changed items carry information, and a two-sided sign test on 22 against 9 gives p ≈ 0.03, so the drop is unlikely to be chance. See measuring the loss.

  5. The team wants to keep BF16 on the two H100s for maximum quality: "140 GB fits in 160 GB." What is wrong with that plan?

    Show answer

    The KV cache needs memory too. After the reserve and overhead nothing is left, and even with every byte spare only about 13 requests fit. See fitting 70B on two H100s.

  6. You are choosing between FP8 on two GPUs and INT4 on one for Workload B, and both pass the quality set. What decides it?

    Show answer

    Capacity and risk against cost. One GPU halves the bill and avoids the all-reduce but holds about 31 requests rather than 64, so check it against the peak concurrency and the p95 TTFT budget. INT4 wins if the peak fits in 31 with room; FP8 wins if it does not. See the fit table.

Takeaway

  • Quantization shrinks the bytes a decode step reads, so it speeds the memory-bound phase directly: 70B is 140 GB in BF16, 70 GB in FP8 and about 36 GB in INT4 with group scales.
  • Absmax scaling lets one outlier ruin the grid, which is why INT4 needs per-group scales and why scale granularity matters more than the bit width alone.
  • Weight-only schemes speed decode; weight-and-activation schemes such as FP8 W8A8 speed prefill as well, because the multiply runs on 8-bit tensor cores.
  • FP8 on Hopper is the default: the evidence for Llama 3.1 is that it is effectively lossless, and the dynamic recipe needs no calibration data.
  • Perplexity is not an acceptance test. Run the labelled set on baseline and candidate, compare items pairwise, and slice by the failures that cost Harbourline money.
  • On two H100s, BF16 70B leaves no KV room, FP8 holds about 64 requests of 3,250 tokens and INT4 about 95, so the cache, not the weights, then sets the batch.
