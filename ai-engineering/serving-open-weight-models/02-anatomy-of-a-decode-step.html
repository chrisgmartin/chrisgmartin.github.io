Section B · Decide and understand

Anatomy of a Decode Step

Prefill and decode, why decode is memory-bound, KV-cache size arithmetic, MQA and GQA, time to first token and time per output token, and the roofline that explains every optimisation that follows.

Two phases with opposite costs

A request to a decoder-only model runs in two phases that stress different parts of the GPU. In prefill the model reads the whole prompt in one pass and writes a key and a value vector for every prompt token into the KV cache. In decode it generates one token per step: each step feeds back the last token, attends over every cached key and value, and appends one new pair. NVIDIA's inference-optimisation overview describes prefill as a highly parallel matrix-matrix operation that saturates the GPU, and decode as a matrix-vector operation that underuses its compute because the data movement dominates.

The consequence is that two numbers you care about have different physics. Time to first token is mostly prefill, and prefill scales with prompt length. The gap between later tokens is decode, and it scales with how many bytes a step must read. A change that helps one often does nothing for the other, which is why the rest of this guide keeps asking which phase an optimisation touches.

The running example is the same pair of H100 80 GB GPUs serving Llama 3.3 70B in FP8 for Harbourline's help-centre assistant, with a prompt of about 3,000 tokens and an answer of 250. Two GPUs split each layer between them (tensor parallelism), so each reads half the weights per step. The arithmetic below is a floor, the time the hardware needs if nothing else gets in the way. Real engines land above it, and the capacity chapter replaces floors with measurements.

Why decode is memory-bound

Each generated token has to pass through every weight once. A dense model does about 2 floating-point operations (one multiply, one add) per parameter per token, so a 70B-parameter model does 2 × 70 × 109 = 140 GFLOP per token. In decode at batch size 1 those weights are read from memory, used for 2 operations each, and discarded. The ratio of operations to bytes read is the arithmetic intensity. For BF16 weights at 2 bytes it is 2 FLOP ÷ 2 B = 1 FLOP per byte. For FP8 weights at 1 byte it is 2 FLOP per byte.

Compare that with what the chip can do. From NVIDIA's H100 page, an H100 SXM has 3.35 TB/s of memory bandwidth and lists 1,979 TFLOPS for BF16 and 3,958 for FP8, both with structured sparsity. Dense numbers, which a normal model uses, are half: 989.5 TFLOPS BF16 and 1,979 TFLOPS FP8. The ridge point, where the chip turns from bandwidth-limited to compute-limited, is peak FLOPS ÷ bandwidth:

  • BF16: 989.5 × 1012 ÷ 3.35 × 1012 = 295 FLOP per byte.
  • FP8: 1,979 × 1012 ÷ 3.35 × 1012 = 591 FLOP per byte.

Decode at batch 1 runs at 1 to 2 FLOP per byte, about 300 times below the ridge. Put times on it for the FP8 pair. Each GPU reads half of the 70 GB of weights per step: 35 × 109 B ÷ 3.35 × 1012 B/s = 10.4 ms. The arithmetic for the same step, 70 GFLOP per GPU at 1,979 TFLOPS, is 0.035 ms. The memory read takes about 300 times longer than the maths, so the GPU's compute units idle almost the whole step. A single stream therefore tops out near 1 ÷ 10.4 ms ≈ 96 tokens a second at the floor, however many TFLOPS the card has.

The way out is batching. When B sequences decode together, one weight read serves B tokens, so intensity rises to about B FLOP per byte for BF16 (2B ÷ 2) and 2B for FP8. The weights stop being the bottleneck near B ≈ 295, the ridge for both formats. Below that, adding a sequence costs almost nothing in weight traffic, which is why batching is the main throughput lever and why the batching interview chapter starts there. What does grow with every added sequence is its KV cache read, covered next.

Prefill sits on the other side. A 3,000-token prompt uses each weight for 3,000 tokens in one pass, so its intensity is in the thousands of FLOP per byte, well past the ridge. It is compute-bound: 3,000 × 140 GFLOP = 420 TFLOP. The pair's dense FP8 peak is 3,958 TFLOPS, so the floor is 0.106 s; at a more realistic 40 percent of peak it is 0.27 s. The attention score computation adds under 6 percent at this length. TTFT for Workload B is then this prefill plus whatever time the request waits in the queue, against the 800 ms p95 budget.

KV cache per token and per request

Decode attends over every earlier token, and recomputing their keys and values each step would be quadratic, so the engine stores them. The size per token is 2 (keys and values) × layers × KV heads × head dimension × bytes per element. The same formula appears in NVIDIA's overview, written with heads times head dimension. For Llama 3.3 70B, whose configuration has 80 layers, 8 KV heads and a head dimension of 128 (read from the mirrored config.json, as the official repository is gated), with a 16-bit cache:

2 × 80 × 8 × 128 × 2 B = 327,680 B per token, which is 320 KiB.

The whole guide uses this number. At FP8 it halves to 160 KiB. For one Workload B request, 3,000 prompt tokens plus a 250-token answer is 3,250 tokens: 3,250 × 327,680 B = 1.065 GB. The shared 1,200-token system prompt alone is 1,200 × 327,680 B = 393 MB. A 128,000-token context, the model's maximum, would be 128,000 × 327,680 B = 41.9 GB for a single request.

Two things follow. First, the cache is capacity: whatever the weights leave of the 160 GB divides by 1.065 GB to give the concurrent requests you can hold, which the quantization chapter computes. Second, the cache is bandwidth: every decode step reads every active sequence's whole cache. At 64 requests of 3,250 tokens that is 64 × 1.065 GB = 68 GB per step, or 34 GB per GPU because the 8 KV heads split across the two GPUs. That read takes 34 × 109 ÷ 3.35 × 1012 = 10.2 ms on top of the 10.4 ms for weights.

The step time is therefore about 10.4 + 10.2 = 20.6 ms at 64 streams, giving 64 ÷ 0.0206 = 3,100 tokens a second in total and 48 tokens a second per stream. At 32 streams the KV read is 5.1 ms, the step is 15.5 ms, throughput is 2,060 tokens a second and each stream gets 64. Doubling the batch raised the step by 33 percent and throughput by 50 percent. That is batching working, and the sub-linear step growth is the weights being shared. Both batch sizes meet the 30 tokens-per-second SLO, which needs a step at or under 33 ms, and the gap between the floor and that budget is the headroom for everything real hardware adds: kernel overheads, the all-reduce between the two GPUs, scheduling.

Once the batch is large, the KV cache is the cost

Weight traffic is a fixed cost per step, shared by every sequence. KV traffic is a per-sequence cost, so it takes over as batch and context grow. At 64 streams it is already the larger part of the step, which is why every technique in the attention and cache chapter shrinks, shares or avoids it, and why paged attention exists to stop wasted cache memory from capping the batch.

MQA and GQA as KV reducers

Multi-head attention gives every query head its own key and value head. Shazeer's multi-query attention (2019) shares one key-value head across all query heads, which shrinks the cache and the bandwidth cost of incremental decoding and costs minor quality. Ainslie et al.'s grouped-query attention (2023) sits between: query heads form groups and each group shares one key-value head, giving quality close to multi-head with speed comparable to multi-query, and a multi-head checkpoint can be uptrained into it with a fraction of the original compute.

Llama 3.3 70B has 64 query heads and 8 KV heads, so eight query heads share each pair. What that is worth, per token at 16 bits:

  • Multi-head (64 KV heads): 2 × 80 × 64 × 128 × 2 B = 2,621,440 B, 2.5 MiB. One Workload B request would hold 8.5 GB, and 64 of them 545 GB, more than three times the pair's total memory.
  • Grouped-query (8 KV heads, the real model): 327,680 B, 320 KiB.
  • Multi-query (1 KV head): 40,960 B, 40 KiB. Eight times smaller again.

The saving is in the KV heads only. The attention weights shrink slightly, a small share of the 70B parameters, so the weight-read cost of decode barely changes. The gain is the cache: 8 times less capacity and 8 times less read traffic per sequence than multi-head. That is why a 70B model fits 64 concurrent streams on two cards at all. The exception that matters is model choice: when you shop for a model, its KV heads and layer count determine serving cost as much as its parameter count, so read them off the config before comparing two models of the same size.

TTFT, TPOT, throughput and goodput

Four metrics describe a serving system, and quoting one without the others hides the trade between them. Definitions below follow NVIDIA's benchmarking metrics and the vLLM metrics design page.

  • Time to first token (TTFT). From request arrival to the first output token. It contains queueing, tokenisation, prefill and the first decode step. vLLM measures it from arrival at the front end.
  • Time per output token (TPOT), or inter-token latency (ITL). The average gap between later tokens: (end-to-end latency − TTFT) ÷ (output tokens − 1). NVIDIA treats ITL and TPOT as the same quantity. vLLM exposes both a per-request TPOT and a per-streamed-event inter-token latency that matches TPOT only when each event carries one token. Know which your dashboard shows.
  • Throughput. Output tokens per second summed over all concurrent requests. The per-user rate is about 1 ÷ TPOT.
  • Goodput. DistServe's definition is the highest request rate the system can serve while meeting both a TTFT limit and a TPOT limit for most requests. It is throughput that counts only requests that were good enough.

Harbourline's SLO translates directly: p95 TTFT ≤ 800 ms, and a stream of at least 30 tokens a second means TPOT ≤ 1 ÷ 30 = 33 ms. A request with TTFT 0.35 s and TPOT 25 ms for 250 tokens has end-to-end latency 0.35 + 249 × 0.025 = 6.6 s, which meets both limits.

The cost of mistaking throughput for goodput is easy to show with illustrative numbers. Suppose the pair completes 3.0 requests a second when saturated, but past 2.0 requests a second the queue pushes p95 TTFT beyond 800 ms. Throughput says 3.0. Goodput says 2.0. Capacity planning that uses 3.0 over-promises by half, and tuning that pushes the batch size up to raise throughput can lower goodput by breaking the TPOT limit. The speculative decoding and batching chapter returns to this trade.

The roofline, with Harbourline on it

A roofline plots attainable work against arithmetic intensity: a sloped line set by memory bandwidth, then a flat roof set by peak compute. Everything left of the ridge is bandwidth-limited and everything right of it is compute-limited. Here are the Workload B phases on the H100's BF16 roofline:

attainable TFLOPS 989 | ___________________________ compute roof | _____/ (989.5 dense BF16) | _____/ | ____/ slope = memory bandwidth, 3.35 TB/s | ____/ | ____/ |/ +--*-----*--------------|-------------------------*------> FLOP per byte 1 64 295 3,000 decode decode ridge prefill batch 1 batch 64 3,000-token prompt

The picture explains the order of the rest of the guide. Decode sits far left, so what moves it is fewer bytes: smaller weights (quantization), smaller or shared KV (chapter 04), or more tokens per byte read, either through bigger batches or by checking several draft tokens in one weight read (chapter 05). Prefill sits right, so what moves it is more FLOPS or fewer prompt tokens to compute, such as prefix caching. The ridge at roughly 295 tokens in flight per step is the target a decode batch rarely reaches before the KV cache fills memory.

The roofline is a bound, not a forecast. Real kernels reach a fraction of peak bandwidth and compute, which is why measured step times will exceed the floors here. Use it to decide what to try, and a benchmark to decide what you got. The recommendation flips for very long contexts or very large batches: there, attention reads so much KV that the sequence's cache, not the weights, owns the step time, and the left-hand slope's lesson applies to the cache instead.

✓ Check yourself

Answer from memory before opening each one.

  1. On the FP8 pair, a single stream decodes at batch size 1. What sets the time per token, roughly how long is it, and why would a GPU with twice the TFLOPS and the same bandwidth not help?

    Show answer

    Reading the weights sets it: 35 GB per GPU ÷ 3.35 TB/s ≈ 10.4 ms, against about 0.035 ms of arithmetic. The step spends nearly all its time waiting for memory, so extra FLOPS sit idle. See why decode is memory-bound.

  2. Going from 32 to 64 concurrent streams raised the step time from 15.5 ms to 20.6 ms. Why did it not double, and what part of the step did grow?

    Show answer

    The 10.4 ms weight read is paid once per step and shared by every sequence, so it did not grow. Only the KV read grew, from 5.1 ms to 10.2 ms, because each sequence adds its own cache to read. See KV cache per token and per request.

  3. A candidate model has 48 layers, 8 KV heads, a head dimension of 128 and a 16-bit cache. How many 8,192-token requests fit in 40 GB of cache, and what would it be with full multi-head attention at 64 KV heads?

    Show answer

    Per token: 2 × 48 × 8 × 128 × 2 B = 196,608 B. Per request: 8,192 × 196,608 B ≈ 1.61 GB, so 40 ÷ 1.61 ≈ 24 requests. With 64 KV heads the cache is 8 times larger and only 3 requests fit. See MQA and GQA.

  4. A change to the help-centre assistant grows the average prompt from 3,000 to 12,000 tokens. What happens to TTFT, and which phase is responsible?

    Show answer

    Prefill is compute-bound and its FLOPs grow with prompt length, so TTFT rises about fourfold: the 0.27 s floor at 3,000 tokens becomes about 1.1 s at 12,000, past the 800 ms p95 budget before any queueing. Attention adds a little more, since it is quadratic. See the prefill paragraph.

  5. A teammate raises the maximum batch size and reports that tokens per second per GPU rose by 40 percent. Customers say answers feel slower. What do you look at, and which metric should the team report instead?

    Show answer

    A bigger batch lengthens the step, so TPOT rises and per-stream speed falls even as total throughput climbs. Check p95 TPOT against the 33 ms limit and p95 TTFT against 800 ms, and report goodput, the request rate that meets both. See the metrics.

  6. Two 70B-class models have the same parameter count, but one has 80 layers with 8 KV heads and the other has 80 layers with 64 KV heads. Which is cheaper to serve at long context, and by how much?

    Show answer

    The 8-KV-head model: its cache per token is 8 times smaller, so it holds about 8 times as many concurrent requests and reads 8 times less KV per step. The weight cost is nearly the same, so the gap grows with context and batch. See MQA and GQA as KV reducers.

Takeaway

  • Prefill is compute-bound and sets TTFT; decode is memory-bound and sets TPOT, so an optimisation helps one phase and usually not the other.
  • At batch 1 a decode step does 1 to 2 FLOP per byte against a ridge near 295 to 591, so it spends about 10 ms reading weights on the FP8 pair and a fraction of a percent of that on maths.
  • Batching shares one weight read across all sequences, which is why throughput rises faster than step time until the KV cache fills memory.
  • KV cache per token is 2 × layers × KV heads × head dimension × bytes, 320 KiB for Llama 3.3 70B at 16 bits, so one 3,250-token request holds about 1.07 GB.
  • Grouped-query attention cuts that cache by the ratio of query heads to KV heads, 8 times for Llama 3.3 70B, and a model's KV heads matter as much as its parameter count.
  • Report goodput, the rate that meets both the TTFT and TPOT limits, not throughput alone.
