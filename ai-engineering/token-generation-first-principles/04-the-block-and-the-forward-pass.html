Section B · Inside the model

The Block and the Forward Pass

Chapter 03 built attention for one layer. This chapter adds the rest of the block, counts Llama 3.1 8B's parameters term by term, converts them into FLOPs and H100 milliseconds, and shows what mixture-of-experts changes.

One block, in the order the data flows

Chapter 03 built attention for one layer. A layer is more than attention. Llama 3.1 8B repeats one block 32 times, and the block has two sub-layers, each wrapped in the same pattern: normalise, transform, add the result back onto the input.

x (4,096 numbers per token: the residual stream) │ ├──────────────┐ │ RMSNorm │ attention (GQA, RoPE) chapter 03 │ │ └──────(+)─────┘ x = x + attention(norm(x)) │ ├──────────────┐ │ RMSNorm │ SwiGLU feed-forward this chapter │ │ └──────(+)─────┘ x = x + ffn(norm(x)) │ next block (32 in total), then final RMSNorm, then the output head

Two choices here are easy to get wrong when reading the code. First, the norm sits inside each residual branch, before the transform, not after the addition. This is pre-norm. Xiong et al. showed that with the norm inside the branch, gradients at initialisation are well behaved, which lets you drop the learning-rate warm-up that post-norm Transformers need. The side effect is that the residual path itself is never normalised, so it carries the raw sum of every layer's contribution. That is the "residual stream" of chapter 02: each sub-layer reads a normalised copy and writes a delta onto the stream.

Second, RMSNorm is LayerNorm without the mean subtraction. For a vector x of length d it computes x / sqrt(mean(x²) + ε) × g, where g is a learned scale per dimension and ε is 10-5 in this model's config. Zhang and Sennrich proposed it on the argument that re-centring is dispensable and re-scaling is what matters, and reported running-time savings of 7% to 64% against LayerNorm in their experiments. It has one weight vector of 4,096 numbers per norm and no bias.

The feed-forward network, where the capacity sits

Attention moves information between positions. The feed-forward network (FFN) works on each position alone: it takes the 4,096-number vector, expands it into a wider space, applies a non-linearity, and projects back. No token sees another token here. They are also the largest block of weights in the model.

The original Transformer FFN had two matrices and a ReLU. Llama uses SwiGLU, from Shazeer's 2020 note on gated variants. It has three matrices, and the output of one path gates the other:

ffn(x) = W_down ( SiLU(W_gate x) ⊙ (W_up x) ) W_gate : 4,096 → 14,336 SiLU(z) = z · sigmoid(z) W_up : 4,096 → 14,336 ⊙ is element-wise multiplication W_down : 14,336 → 4,096

Shazeer reduced the hidden width by a factor of two thirds when swapping in a gated variant, so that three matrices cost the same as two. Matching a 16,384-wide two-matrix FFN would give 10,923. Llama 3.1 8B uses 14,336, which is 3.5 times the model width and about 31% more FFN parameters than parity. Meta's paper lists 14,336 in its hyperparameter table without giving the reason, so treat the choice as deliberate but unexplained.

Counting the 8.03 billion parameters

The hyperparameters in the table below are Table 3 of the Llama 3 paper and match the config.json fields of the 8B checkpoint. Everything else follows from them. The shapes: queries project to 32 heads of 128 dimensions, keys and values to only 8 heads of 128 (the grouped-query attention of chapter 03), and the output projection maps the 4,096 concatenated head outputs back to 4,096.

params.py
# Llama 3.1 8B: hidden 4096, ffn 14336, 32 layers, 32 heads, 8 KV heads, vocab 128256
d, f, L, H, Hkv, V = 4096, 14336, 32, 32, 8, 128256
hd = d // H                                  # head dimension, 128

attn = d*(H*hd) + 2*d*(Hkv*hd) + (H*hd)*d    # W_q + (W_k + W_v) + W_o
ffn  = 3 * d * f                             # gate, up, down
norm = 2 * d                                 # two RMSNorm scale vectors
block = attn + ffn + norm

embed, head, final_norm = V*d, V*d, d        # untied: separate input and output matrices
total = embed + L*block + final_norm + head
print(f"{attn:,} {ffn:,} {block:,} {total:,}")

The total is 8.03 billion, which the name "8B" rounds down. Three things follow from the table. The FFN holds 70% of all parameters (32 × 176.2 million = 5.64 billion), attention holds 17%, and the two vocabulary matrices hold 13%. A model's size is mostly its feed-forward layers. Second, grouped-query attention saves little in parameters: full multi-head attention would raise Wk and Wv from 8.4 million to 33.6 million per layer, a 25 million difference across 32 layers of a 8,030 million total. Its saving is in the KV cache, which chapter 06 sizes. Third, the output head is a separate matrix because this model does not tie input and output embeddings (tie_word_embeddings is false). Some models tie them and save the second 525 million.

At two bytes per parameter in BF16, the weights occupy 16.06 GB, or 14.96 GiB. Every decode step in chapter 06 starts from that number. Quantisation attacks it directly: 4-bit weights bring the floor down by roughly a factor of four, at a cost in accuracy that the serving guide measures.

FLOPs per token: 2N, plus attention over context

Every weight in a matrix multiplication takes part in one multiply and one add per token. So the forward pass costs about two floating-point operations per parameter per token. Kaplan et al. write this as Cforward ≈ 2N + 2·nlayer·nctx·dmodel, where N excludes the embedding lookup (a table read, not a matrix product) and the second term is attention over the context.

For this model that is 2 × 7.5 billion matmul parameters = 15.0 GFLOPs per token, or 16.06 GFLOPs if you simply double the headline count. The two numbers differ by 7% and the second is the one people quote. The attention term depends on how much context there is:

Context lengthAttention term, per tokenRelative to 15.0 GFLOPs

At a few thousand tokens the 2N rule is accurate to a few per cent. At 131,072 tokens attention costs more than twice everything else combined, because it grows with context while the matrices do not. The formula is an upper bound for causal attention, since a token only attends to earlier positions and the average is about half. Setting the attention term equal to 15.0 GFLOPs gives a crossover near 57,000 tokens of context. Quadratic cost across a whole sequence is the subject of chapter 03; the point here is the per-token view, where the weights set a fixed floor and the context adds a variable amount on top.

What a forward pass costs on an H100, in time

FLOPs are not time. A GPU has two limits, and a forward pass runs into whichever it reaches first. NVIDIA lists the H100 SXM at 3.35 TB/s of memory bandwidth and 1,979 TFLOPS of BF16 tensor throughput, with a footnote that this figure is with sparsity. The dense figure is half, about 989 TFLOPS, and that is the one to use for ordinary weights. Divide one by the other and you get 295 FLOPs per byte moved, the ridge point. Work with fewer FLOPs per byte than that waits on memory; work with more waits on compute.

A BF16 weight is two bytes and costs two FLOPs per token it serves. With one token in flight, each byte read buys one FLOP, 295 times below the ridge. With B tokens sharing one read of the weights, it buys B. So the arithmetic is simple enough to do by hand:

decode, one token (batch 1) memory-bound time ≈ weights / bandwidth = 16.06 GB / 3.35 TB/s = 4.8 ms ceiling: about 205 tokens/s compute used: 15.0 GFLOPs / 4.8 ms = 3 TFLOPS of 989 (0.3%) prefill, 2,000 tokens in one pass compute-bound FLOPs = 2,000 × 15.0 GFLOPs = 30 TFLOPs time at peak = 30 TFLOPs / 989 TFLOPS = 30 ms time at an assumed 50% of peak = 61 ms

The 50% figure is an assumption for illustration; real kernels land somewhere below peak, and chapter 06 uses the same figure. The 4.8 ms is a floor: it ignores the KV cache read, kernel launch overhead and communication. The shape of the result is the durable part. Processing the prompt is cheap per token because 2,000 tokens share one read of the weights, and generating is expensive per token because one token pays for the whole read. A 2,000-token prefill takes about 13 decode steps' worth of time while doing 2,000 times the work.

Batch 1 decode uses well under 1% of the chip

This is why serving engines batch requests together. Adding sequences to a decode step costs almost no extra weight traffic, so throughput rises almost linearly at first, until the batch nears 295 tokens or the KV cache fills memory. The flip side: if you serve one user at a time on an H100, you pay for a 989 TFLOPS machine and use 3.

Mixture of experts: active against total parameters

A dense model sends every token through every FFN weight. A mixture-of-experts (MoE) model replaces the single FFN in each block with many smaller FFNs, the experts, and a small router that picks a few of them per token. Attention stays dense. The consequence for the arithmetic above is that two numbers now describe the model. Total parameters set the memory the weights occupy. Active parameters set the FLOPs per token, so the 2N rule becomes 2 × active.

Take Qwen3-235B-A22B. Its FLOPs per token are about 2 × 22 billion = 44 GFLOPs, roughly three times Llama 3.1 8B and a fraction of what a dense 235-billion model would need (470 GFLOPs). Its weights still need 470 GB in BF16, so it does not fit on one 80 GB GPU even at 4 bits per weight, which would still take about 118 GB. You buy compute efficiency and pay in memory.

The decode floor behaves differently from the dense case, and this is where the intuition breaks. At batch 1 the router picks 8 of 128 experts in each layer, so only a small share of the FFN weights is read and the step is fast. But different tokens pick different experts. If routing were uniform, a batch of 64 tokens would touch 1 − (1 − 8/128)64 = 98% of the experts in each layer, which means the step reads nearly all the weights. A real router is not uniform, so this overstates the effect, but the direction holds: MoE gives its speed advantage at small batch, and as batches grow the memory traffic approaches that of the full model. Whether a given MoE model is cheaper to serve than a dense one of similar quality depends on your batch size, which is a serving question taken up in capacity, cost and SLOs.

✓ Check yourself

Answer from memory before opening each one.

  1. Without looking at the table, derive the FFN parameters in one Llama 3.1 8B layer. Then say what fraction of the total they make up and why that fraction is not the same as the fraction of FLOPs spent on FFN at a 131,072-token context.

    Show answer

    Three matrices of 4,096 × 14,336 give 176,160,768 per layer, and 32 layers give 5.64 billion of 8.03 billion, or 70%. At long context the attention term grows with context length while the FFN FLOPs do not, so FFN's share of FLOPs falls well below 70%. See Counting the 8.03 billion parameters and FLOPs per token.

  2. A colleague says the model has 8 billion parameters, so a forward pass is 16 GFLOPs. Where is that right, and where is it wrong?

    Show answer

    It is right to within 7% at short contexts: 2N with N including the embedding is 16.06 GFLOPs, and 15.0 without the lookup. It is wrong at long context, where attention adds 2 × layers × context × width per token, 34 GFLOPs at 131,072 tokens. See FLOPs per token.

  3. Why does a 2,000-token prompt take about 60 ms to prefill while each generated token takes about 5 ms, when the model does 2,000 times more arithmetic in the first case?

    Show answer

    Prefill shares one read of the weights across 2,000 tokens, so it is limited by compute. A decode step at batch 1 reads all 16 GB for one token and is limited by memory bandwidth, about 4.8 ms. See What a forward pass costs on an H100.

  4. Grouped-query attention cuts keys and values from 32 heads to 8. How many parameters does that save in this model, and why do people care about it anyway?

    Show answer

    Full multi-head K and V would be 33.6 million per layer instead of 8.4 million, a saving of 25 million per layer, 805 million in total, about 10% of the model. The larger effect is a four times smaller KV cache, which is what limits batch size at decode. See Counting the 8.03 billion parameters.

  5. Qwen3-235B-A22B decodes one token at batch 1 much faster than a dense 235B model would. Why does that advantage shrink when you serve 64 concurrent requests?

    Show answer

    Different tokens activate different experts. With 8 of 128 experts per token and uniform routing, 64 tokens touch about 98% of them, so the step reads nearly all 470 GB of weights. Memory traffic, not active FLOPs, sets the step time. See Mixture of experts.

Takeaway

  • A block is pre-norm RMSNorm, attention, add, pre-norm RMSNorm, SwiGLU feed-forward, add. The residual stream is never normalised and every sub-layer writes a delta onto it.
  • The feed-forward network holds 70% of Llama 3.1 8B's 8,030,261,248 parameters, attention 17% and the two vocabulary matrices 13%.
  • A forward pass costs about 2 FLOPs per parameter per token, plus an attention term that grows with context and, on Kaplan's upper-bound formula, passes the weights' cost near 57,000 tokens.
  • At batch 1 an H100 decodes this model at about 4.8 ms per token, set by reading 16 GB of weights, using under 1% of its compute.
  • Prefill is compute-bound and decode is memory-bound, which is why batching raises throughput almost for free until the batch nears 295 tokens.
  • For a mixture-of-experts model, active parameters set FLOPs and total parameters set memory. The speed advantage fades as batch size grows and more experts are touched.
