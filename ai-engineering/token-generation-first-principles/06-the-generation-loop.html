Section C · Generation

The Generation Loop

Chapter 05 turned logits into one token. This chapter repeats that: prefill against decode, why the KV cache exists and what it costs for the Harbourline prompt and a 131,072-token context, stop conditions, and the latency arithmetic for a 300-token answer.

One token at a time

A decoder-only model is trained to predict the next token given all the previous ones, so generating a reply means running it repeatedly on its own output. Each pass takes the sequence so far, runs the forward pass, turns the last position's logits into a token with the procedure in chapter 05, appends that token, and goes round again. The probability of a whole answer is the product of the per-step conditional probabilities, which is why a single early token can send the rest somewhere else.

prompt tokens ──► PREFILL: one forward pass over all P tokens, in parallel │ builds K and V for every position (the cache) ▼ logits for the last position ──► sample ──► token 1 (first out) │ ┌───────────────────────┘ ▼ DECODE step t: forward pass for ONE new token, reading the cache ──► logits ──► sample ──► token t ──► append K, V to the cache repeat until a stop condition (end token, stop string, max tokens)

The two phases have different costs because they have different shapes. Prefill pushes P tokens through the weights at once and is limited by compute. Each decode step pushes one token and is limited by how fast the weights and cache can be read. Chapter 04 worked that out for an H100: about 61 ms to prefill 2,000 tokens at an assumed half of peak, and 4.8 ms for each decode step at batch 1. The rest of this chapter builds on those two numbers.

Why the KV cache exists

In the causal attention of chapter 03, the key and value vectors at position i depend only on tokens 1 to i. When the next token arrives, the keys and values of every earlier token are unchanged. Recomputing them is waste, so the engine stores them. A decode step then computes the query, key and value for the one new token, appends the key and value to the cache, and attends over everything cached.

Count what it saves on the Harbourline request. Take a 2,000-token prompt and a 300-token answer. The prompt is an illustrative round figure: the 1,200-token system prompt, the two retrieved passages and the question. Chapter 01 counts a real one. Without a cache, generating token t reruns the whole sequence so far, which is 2,000 + t tokens. Summed over 300 steps:

without cache, step t reruns 2,000 + t tokens, for t = 0..299: Σ (2,000 + t) = 300 × 2,000 + 300 × 299 / 2 = 644,850 token-forwards with cache: 2,000 (prefill) + 300 (one per step) = 2,300 token-forwards ratio: 644,850 / 2,300 ≈ 280 times less work

The first form shows the shape of the cost. Without a cache the work is roughly n × P + n²/2 for n output tokens, and it is quadratic in the output length for a fixed prompt. With a cache it is linear: each step adds one token of weight traffic and one more row of cached keys to read. The cache does not remove attention's quadratic cost over a whole sequence, since each new token still attends to everything before it. It removes the recomputation on top of that.

What the cache costs in memory

Each token adds one key and one value vector in every layer, for each of the 8 KV heads of 128 dimensions. In BF16:

kv_cache.py
layers, kv_heads, head_dim, bytes_per = 32, 8, 128, 2
kv_token = 2 * layers * kv_heads * head_dim * bytes_per     # K and V
print(kv_token)                                              # 131072 bytes = 128 KiB

print(2_000 * kv_token / 2**20)         # 250.0 MiB   Harbourline prompt
print(2_300 * kv_token / 2**20)         # 287.5 MiB   after a 300-token answer
print(131_072 * kv_token / 2**30)       # 16.0 GiB    a full 131,072-token context

weights = 8_030_261_248 * 2             # BF16 bytes
print((80e9 - weights) // (131_072 * kv_token))   # 3.0 full-length sequences beside the weights on 80 GB

A Harbourline request holds about 250 MiB of cache after prefill and 288 MiB at the end of the answer. That is small beside the 15 GiB of weights, and it is why chat at a few thousand tokens batches well. A full 131,072-token context holds 16 GiB, slightly more than the weights themselves, and an 80 GB card has room for three such sequences after the weights are loaded, before activations and any overhead. Long context therefore costs twice: attention work grows, and every concurrent long conversation takes a slice of memory that could have served many short ones.

Grouped-query attention is what keeps these numbers manageable. With all 32 heads storing keys and values, the figure would be four times larger: 512 KiB per token and 64 GiB for a full context. The Kwon et al. paper that introduced PagedAttention gives the same formula for OPT-13B, 800 KB per token, and builds a memory manager around the observation that this cache, not the weights, limits how many requests fit. The PagedAttention guide follows that argument through, and its worked example shows the savings.

Stop tokens and max tokens

The loop ends for one of three reasons, and an application should know which. The model can emit an end token, a special vocabulary entry it learned to produce when a turn is complete. The Llama 3.1 8B Instruct generation config lists three ids that count as an end: 128001, 128008 and 128009, and the engine stops when any is sampled. You can supply stop strings, which halt generation when the text matches. Or the budget runs out: max tokens, a hard count of new tokens.

The last is a safety valve, and it fails quietly. Anthropic's API reports why generation stopped in stop_reason, with end_turn for a natural stop, stop_sequence for one of your strings and max_tokens when the cap was hit. In Harbourline's claims extraction, max tokens is 400. If the model needs 450 tokens of JSON, the output ends mid-object with no error from the sampler, and a parser downstream sees a truncated string. Check the stop reason before parsing, and size the cap from the schema: measure the longest valid output on real claims and add a margin. Where a provider counts reasoning tokens against the same cap, as Anthropic does for extended thinking, the cap must cover the thinking too, or the visible answer is what gets cut.

A cap that is too generous has a cost as well. It is the worst-case time for a runaway loop, and the worst-case KV allocation the engine may reserve for the request. The flip case is open-ended chat, where a tight cap truncates good answers; there, set the cap from the longest answer you would accept and treat hits on it as a metric.

TTFT, TPOT and the arithmetic of 300 tokens

Two numbers describe a streamed response. Time to first token (TTFT) is how long the user waits before anything appears. Time per output token (TPOT) is the gap between tokens after that. They differ because they measure different phases: TTFT includes queueing, network and the whole prefill, while TPOT is one decode step. Total time follows:

TTFT = network + queue + prefill(P tokens) + first decode step total = TTFT + (n - 1) × TPOT

For the Harbourline chat on one H100, ignoring network and queueing, with the 2,000-token prompt and a 300-token answer:

QuantityWorkingValue
Prefill2 × 7.5B × 2,000 / (0.5 × 989 TFLOPS)61 ms
TPOT, batch 1(16.06 GB + 0.28 GB of cache) / 3.35 TB/s4.9 ms
TTFT floor61 + 4.966 ms
Total for 300 tokens61 + 300 × 4.91.52 s

The 0.28 GB of cache is the average over the answer: about 2,150 tokens at 128 KiB each. These are floors for the hardware and the 50% prefill assumption, not benchmarks. Real engines add kernel overheads, scheduling and sampling, and a hosted API adds network and queue time, so measure your own. What survives is the structure. Decode dominates: 1.46 s of the 1.52 s is the 300 steps, and prefill is 4% of the total. Doubling the prompt to 4,000 tokens adds about 61 ms. Doubling the answer to 600 tokens adds about 1.5 s. That is the reason a shorter answer is a bigger latency lever than a shorter prompt, and why the latency chapter of the interview guide asks you to record both numbers per surface.

Streaming changes what the user sees, not how long generation takes. Anthropic's streaming API sends server-sent events, with a content_block_delta event for each increment of text, so the first words appear at about the TTFT and the rest follow at the TPOT. The chat benefits because 66 ms to first word feels instant while 1.5 s of blank screen does not. The claims extraction does not, because a parser needs the complete object and nothing is gained by receiving half of it earlier. There streaming adds overhead and no benefit, so Harbourline leaves it off.

What this means for serving

Everything above assumed one request on the card. A real server runs many, and the trade-offs follow from the two bottlenecks. Decode is limited by memory reads, and the weight read is shared, so adding requests to a step is cheap. But each added request brings its own cache to read. On the same arithmetic, with every sequence at 2,150 tokens:

BatchStep timePer-user speedAggregate
14.9 ms205 tokens/s205 tokens/s
85.5 ms183 tokens/s1,463 tokens/s
327.5 ms134 tokens/s4,275 tokens/s
6410.2 ms98 tokens/s6,288 tokens/s

Going from 1 to 64 requests multiplies aggregate throughput by 31 while slowing each user by about half. Compute is not the limit at any of these sizes: at batch 64 the arithmetic needs about 1 ms of the 10 ms step. The growth of the step comes from the cache reads, 18 GB at batch 64 against 16 GB of weights. That is the whole case for shrinking and managing the cache: quantising it, sharing prefixes, paging it so no request reserves memory it does not use. The serving guide's anatomy of a decode step takes each of those in turn.

Aggregate throughput is not the user's experience

A capacity plan that targets the largest batch the memory allows will hit a latency target before it hits a memory limit. Set the per-user TPOT you promise first, then find the batch size that meets it. The flip case is the nightly batch job, where no one is waiting and the largest batch that fits is the right answer.

✓ Check yourself

Answer from memory before opening each one.

  1. Compute the KV cache for a 6,000-token conversation on Llama 3.1 8B in BF16, and say which fields of the config you used.

    Show answer

    2 × 32 layers × 8 KV heads × 128 head dimension × 2 bytes = 131,072 bytes per token, so 6,000 tokens take 786 million bytes, about 750 MiB. The fields are num_hidden_layers, num_key_value_heads, head dimension (hidden size over attention heads) and the dtype. See What the cache costs in memory.

  2. Without a KV cache, how does the work to generate n tokens from a prompt of P grow, and what does the cache change about it?

    Show answer

    Roughly n × P + n²/2 token-forwards, quadratic in output length. With a cache it is P + n, linear in the tokens processed. For P = 2,000 and n = 300 that is 644,850 against 2,300. Attention over the growing sequence is still quadratic in total; the cache only removes recomputation. See Why the KV cache exists.

  3. A user complains the chat feels slow. TTFT is 70 ms and TPOT is 5 ms, and answers average 600 tokens. Which lever helps most, and what does shortening the system prompt by 500 tokens buy?

    Show answer

    Total is about 70 ms + 599 × 5 ms = 3.1 s, nearly all decode, so shorter answers help most. Cutting 500 prompt tokens saves roughly 15 ms of prefill at the compute rate used here, and little else. See TTFT, TPOT and the arithmetic of 300 tokens.

  4. Claims extraction returns a JSON string that fails to parse about once in a few hundred calls. Name two causes in the generation loop, and the check that separates them.

    Show answer

    The cap of 400 tokens was reached and the object was cut off, or the model produced malformed JSON that no mask prevented. Read the stop reason: max_tokens means truncation. See Stop tokens and max tokens and the masking section of chapter 05.

  5. Why does the per-user speed fall as batch size rises on a memory-bound decode step, even though the weights are read only once per step?

    Show answer

    Each sequence adds its own cache to read, about 282 MB at 2,150 tokens, so the bytes per step grow with the batch while the weight read stays fixed. At batch 64 the cache is about 18 GB, more than the weights. See What this means for serving.

Takeaway

  • Generation is a loop of forward pass, sampling and append, which ends on an end token, a stop string or the token cap, and the application should record which.
  • Prefill processes the prompt in parallel and is compute-bound. Decode produces one token per pass and is memory-bound, so the two phases have different costs and different levers.
  • The KV cache stores each token's keys and values so earlier tokens are never recomputed. For a 2,000-token prompt and a 300-token answer it cuts the work by about 280 times.
  • Llama 3.1 8B holds 128 KiB of cache per token, 250 MiB for the Harbourline prompt and 16 GiB for a full 131,072-token context.
  • Time to first token is dominated by prefill and queueing. Total time for a normal answer is dominated by decode steps, so answer length is the bigger latency lever.
  • Batching raises aggregate throughput by sharing the weight read, but each added request brings its own cache, so per-user speed falls and memory eventually caps the batch.
