Section D · Scale and practice

Reading a Model Card

Chapter 07 covered why models have their shape and what thinking and image tokens cost. This chapter turns that into a practical skill: reading a config.json and model card, computing weight memory and KV cache from them, separating claimed from effective context, and checking the licence. It reads Llama 3.1 8B and Qwen3.8-27B side by side.

Overview

A model card tells you what the vendor wants you to believe. The config.json beside it tells you what the weights are, and from a dozen of its fields you can compute the memory a model needs before you download a byte. This chapter reads two configs side by side: Llama 3.1 8B, the worked model of this guide, and Qwen3.8-27B, a current open-weight model released in 2026 (as of November 2026). It then separates claimed from effective context and covers the licence and data statements.

The fields that matter

Most of a config is plumbing. Eight groups of fields carry the numbers you need, and each has a way to mislead you.

FieldWhat you compute from itThe trap
hidden_size, num_hidden_layersWidth and depth; with the two below, the parameter countMultimodal configs nest these inside text_config
intermediate_size, vocab_sizeFeed-forward and embedding parametersCheck tie_word_embeddings: tied halves the embedding cost, untied doubles it
num_attention_heads, num_key_value_heads, head_dimKV cache bytes per token (below)A missing KV-heads field means one per head. head_dim need not equal hidden size divided by heads
layer_types and any linear_* keysHow many layers keep a per-token cacheA hybrid model caches only its full-attention layers
rope_theta or rope_parameters, rope_scalingHow position is encoded and whether it was stretchedLlama has rope_theta; Qwen nests it in rope_parameters
max_position_embeddingsThe context the vendor claimsA claim, not a measurement

Qwen3.8-27B shows most of these traps. Its head_dim is 256, but dividing the hidden size 5,120 by its 24 heads gives 213.3, so a script that assumes the usual relation computes the wrong attention shape. Its rotary base lives under rope_parameters, its dtype key is dtype, and 48 of its 64 layers are not softmax attention at all.

Weight memory and KV cache from the config

Weight memory is parameters times bytes per parameter. Llama 3.1 8B at two bytes is 16.06 GB, which leaves 63.9 GB on an 80 GB H100 SXM (NVIDIA lists 80 GB and 3.35 TB/s). Qwen3.8-27B at two bytes is 55.56 GB, leaving 24.4 GB. Quantisation shrinks that; the config gives only the shipped precision.

The KV cache per token is the formula from chapter 03, with one correction for hybrids. For each layer that keeps a per-token cache, store K and V for every KV head:

bytes per token = cached layers × 2 (K, V) × KV heads × head_dim × bytes per value Llama 3.1 8B : 32 × 2 × 8 × 128 × 2 = 131,072 bytes (128 KiB) Qwen3.8-27B : 16 × 2 × 4 × 256 × 2 = 65,536 bytes ( 64 KiB) Qwen, naive : 64 × 2 × 4 × 256 × 2 = 262,144 bytes (wrong: 4 times too high)

Qwen's 48 Gated DeltaNet layers keep a recurrent state of fixed size per sequence instead of a growing cache. That state is not in the formula, and it was not measured for this chapter, so treat the Qwen figures as the growing part only.

Multiply by sequence length. A Harbourline chat turn of about 1,900 tokens needs 249 MB of cache on Llama and 125 MB on Qwen. A full-length sequence needs 131,072 × 131,072 bytes = 16 GiB on Llama, and 262,144 × 65,536 bytes = 16 GiB on Qwen, which is a coincidence of the two designs. Dividing the memory left after the weights by those figures gives the planning numbers below, ignoring activations and runtime overhead, which will cut them.

One H100 80 GB, BF16Llama 3.1 8BQwen3.8-27B

The last row reads every weight once per token at 3.35 TB/s, a batch-1 bound that ignores cache reads. The paging that makes these cache numbers achievable is the subject of the PagedAttention guide. For Harbourline the arithmetic says the 27B model fits one card with about three quarters of the concurrency of the 8B, at roughly 3.5 times the time per token. Whether the 27B's quality justifies that is an eval question; the neocloud pricing table has H100 hourly rates.

A script that prints these numbers

This script reads any dense or hybrid decoder config of the kinds above. It unwraps text_config, handles the renamed keys, counts only full-attention layers when layer_types exists, and derives the parameter count for dense models. It raises a KeyError on a config it does not understand instead of printing a plausible wrong number.

config_numbers.py
"""Print the memory numbers a model's config.json implies. Usage: config_numbers.py config.json [total_params]"""
import json
import sys

DTYPE_BYTES = {"bfloat16": 2, "float16": 2, "float32": 4}
H100_BYTES = 80e9          # H100 SXM memory, 80 GB
H100_BW = 3.35e12          # H100 SXM memory bandwidth, bytes per second


def read(path, total_params=None):
    cfg = json.load(open(path))
    cfg = cfg.get("text_config", cfg)            # multimodal configs nest the language model
    h, L = cfg["hidden_size"], cfg["num_hidden_layers"]
    heads = cfg["num_attention_heads"]
    kv_heads = cfg.get("num_key_value_heads", heads)
    head_dim = cfg.get("head_dim", h // heads)
    width = DTYPE_BYTES[cfg.get("torch_dtype") or cfg["dtype"]]
    types = cfg.get("layer_types")               # hybrid models mix attention kinds
    full = sum(t == "full_attention" for t in types) if types else L
    rope = cfg.get("rope_theta") or cfg["rope_parameters"]["rope_theta"]
    ctx = cfg["max_position_embeddings"]

    if total_params is None:                     # dense Llama-style count, term by term
        ff, v = cfg["intermediate_size"], cfg["vocab_size"]
        attn = h * heads * head_dim * 2 + h * kv_heads * head_dim * 2     # Q, O, K, V
        per_layer = attn + 3 * h * ff + 2 * h                             # SwiGLU MLP, 2 norms
        embed = v * h * (1 if cfg.get("tie_word_embeddings") else 2)      # input + output
        total_params = L * per_layer + embed + h                          # + final norm

    kv_tok = full * 2 * kv_heads * head_dim * width    # K and V, per token, whole model
    weights = total_params * width
    print(f"layers {L} ({full} with a per-token KV cache), hidden {h}, heads {heads}, "
          f"kv heads {kv_heads}, head dim {head_dim}, rope theta {rope:,.0f}")
    print(f"params {total_params:,}  dtype bytes {width}  weights {weights / 1e9:.2f} GB")
    print(f"KV cache per token {kv_tok:,} bytes ({kv_tok / 1024:.0f} KiB)")
    print(f"KV cache at {ctx:,} tokens {kv_tok * ctx / 2**30:.1f} GiB")
    print(f"KV cache at 1,900 tokens {kv_tok * 1900 / 1e6:.0f} MB")
    free = H100_BYTES - weights
    print(f"H100 80 GB: {free / 1e9:.1f} GB left after weights = "
          f"{free / (kv_tok * ctx):.1f} sequences at full context, "
          f"{free / (kv_tok * 1900):.0f} at 1,900 tokens")
    print(f"batch-1 decode floor (weights / bandwidth) {weights / H100_BW * 1e3:.1f} ms per token")
    if types:
        print(f"naive count (every layer cached) would say {L * 2 * kv_heads * head_dim * width:,} bytes per token")


if __name__ == "__main__":
    read(sys.argv[1], int(sys.argv[2]) if len(sys.argv) > 2 else None)

Claimed context against effective context

max_position_embeddings is the longest position the model was trained or extended to handle. It is not a quality guarantee. Meta's paper describes how Llama's number came about: pretraining ran at an 8K window, and the final stage extended it to 128K in six increments using about 800 billion tokens, because attention cost grows quadratically with length. Each increment was accepted when short-context scores had fully recovered and the model solved needle-in-a-haystack retrieval perfectly at that length.

RULER (Hsieh et al., 2024) asks for more. It adds multiple needles, multi-hop variable tracking and aggregation, and defines the effective length as the longest length where a model's score stays above a fixed threshold, the score of Llama 2 7B at 4K, which was 85.6. Llama 3.1 8B Instruct claimed 128K and scored as follows.

Context length4K8K16K32K64K128K
RULER score, Llama 3.1 8B95.593.891.687.484.777.0

The score passes the threshold at 32K and fails at 64K, so RULER reports an effective length of 32K against a claimed 128K. The paper's wider finding is that almost all models fell below the threshold before their claimed length, and that only about half of the 17 models tested kept satisfactory performance at 32K.

Qwen3.8-27B claims 262,144 natively. Its README says that going further needs YaRN scaling, which the notable open-source engines implement as static scaling, and warns that it is "potentially impacting performance on shorter texts", so it advises changing the config only when you need the length. The card gives no long-context benchmark.

The practical rule has two parts. For capacity planning use the claimed length, because the cache must hold what you let users send. For quality use the length you actually send, measured on your task. Harbourline's chat turn is about 1,900 tokens, far inside any limit, so the claimed length matters for the cap you set on pasted documents, not for the quality of the usual turn. It flips for a claims agent that stuffs 60,000 tokens of policy history into one prompt: there, run your own needle and multi-hop tests at that length before trusting the headline. Chapter 02 explains why length degrades quality.

Licence, usage terms and training data

A model you cannot legally ship is not a candidate. Read three things on the card, in this order.

The licence. Llama 3.1 uses a custom licence. It grants a royalty-free licence to use, modify and redistribute, with conditions. If you distribute the models or a product containing them you must pass on the agreement and prominently display "Built with Llama". If you use the materials or their outputs to create, train, fine-tune or improve a model that you distribute or make available, its name must begin with "Llama". If, on the 23 July 2024 release date, your products had more than 700 million monthly active users, you need a separate licence from Meta. The Acceptable Use Policy is incorporated by reference, and the licence ends if you sue Meta over the materials. Qwen3.8-27B is Apache 2.0, a standard permissive licence with no display, naming or user-count conditions. This is a reading aid, not legal advice.

The training-data statement. The Llama 3.1 card says "a new mix of publicly available online data", more than 15 trillion tokens, and a knowledge cutoff of December 2023, and calls the model static. The Qwen3.8-27B README as read for this chapter states no training-data description, token count or knowledge cutoff. Without one you cannot rule out that it has seen your benchmark.

A December 2023 cutoff means the model knows nothing about terms Harbourline changed since, or about policy HL-UK-4471-220. The facts must arrive in the prompt, which is the job of retrieval and the reason the embeddings chapter exists.

✓ Check yourself

Answer from memory before opening each one.

  1. A teammate sizes Qwen3.8-27B's cache as 64 layers × 2 × 4 × 256 × 2 bytes. What did they miss?

    Show answer

    Only the 16 full-attention layers keep a per-token cache: 65,536 bytes, a quarter of theirs. See weight memory and KV cache.

  2. A config lists 40 layers, 40 attention heads, no num_key_value_heads field, hidden size 5,120 and BF16 weights. Compute the KV cache per token, and say what changes if the field is present with value 8.

    Show answer

    With no KV-heads field every head has its own K and V, so the head dimension is 5,120 / 40 = 128 and the cache is 40 × 2 × 40 × 128 × 2 bytes = 819,200 bytes per token. With 8 KV heads it is 40 × 2 × 8 × 128 × 2 = 163,840 bytes, a fifth. See weight memory and KV cache.

  3. A vendor's card says "128K context" and shows a perfect needle-in-a-haystack chart. Your task is to answer questions that combine facts from three places in a 100,000-token claims file. What do you do before you trust it?

    Show answer

    Treat the chart as evidence of single-fact retrieval only. Build a test at 100,000 tokens with your own multi-hop questions, as RULER does with variable tracking and aggregation, and compare against a shorter-context baseline. RULER measured Llama 3.1 8B at 77.0 at 128K against 95.5 at 4K. See claimed against effective context.

  4. You are choosing between Llama 3.1 8B and Qwen3.8-27B to self-host the help-centre chat on one H100. Memory alone does not decide it. What does the arithmetic rule in, what does it rule out, and what must you still measure?

    Show answer

    Both fit: 16.06 GB and 55.56 GB leave room for roughly 257 and 196 concurrent 1,900-token sequences. Neither is practical for several full-length sequences on one card. The batch-1 decode floor is about 4.8 ms against 16.6 ms per token, so latency favours the 8B. Whether the 27B's answers are good enough to justify roughly 3.5 times the time per token is an eval question. See weight memory and KV cache.

Takeaway

  • A handful of config fields give you weight memory and KV cache per token before you download the model. The arithmetic for Llama 3.1 8B gives 16.06 GB of weights and 131,072 bytes of cache per token.
  • Configs mislead in predictable ways: nested text_config, renamed keys, a missing KV-heads field that means full multi-head attention, and a head_dim that is not hidden size divided by heads.
  • On a hybrid model only the full-attention layers keep a per-token cache. Qwen3.8-27B needs 65,536 bytes per token, not the 262,144 a naive count gives.
  • A claimed context length is a configuration value, not a measurement. RULER put Llama 3.1 8B's effective length at 32K against 128K claimed, and a perfect needle test shows only that a single fact can be retrieved.
  • Licence terms and training-data statements are part of the model choice. Llama 3.1's licence adds display, naming and user-count conditions that Apache 2.0 does not, and a missing data statement means you cannot rule out benchmark contamination.
