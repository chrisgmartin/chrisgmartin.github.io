Section B · Inside the model

From Text to Tokens

The first step from text to a sampled token is a lookup in a frozen vocabulary. This chapter covers how byte-level BPE and its relatives cut text into ids, what vocabulary size costs, why numbers, identifiers and other languages fragment, how special tokens and chat templates frame a request, and Harbourline's prompt counted with real tokenizers.

What the model actually receives

A customer types What is my deductible for windscreen damage on policy HL-UK-4471-220? and the model never sees a letter. It sees a list of integers, each an index into a fixed vocabulary, and everything downstream is arithmetic on rows of a matrix indexed by those integers. The tokenizer is trained separately from the network and then frozen, so its choices are baked into the model: what counts as one unit, how much text fits in the window, how many units you are billed for, and what information is split apart before the network sees it.

The rest of the guide starts from that list of ids: chapter 02 turns each one into a vector.

Byte-level BPE and how the merges are learned

Byte pair encoding was adapted to neural translation by Sennrich et al. in 2015 to handle rare words as sequences of subword units. The training loop is simple. Start with every word as a sequence of single symbols. Count every adjacent pair of symbols across the corpus, weighted by word frequency. Merge the most frequent pair into a new symbol, record the merge, and repeat until the vocabulary reaches the size you chose. The toy below runs on nine Harbourline words.

bpe_toy.py
from collections import Counter

corpus = "claim claim claim claims claims claimed policy policy policies".split()
words = Counter(tuple(w) for w in corpus)       # each word as a tuple of symbols

def pair_counts(words):
    pairs = Counter()
    for word, n in words.items():
        for a, b in zip(word, word[1:]):
            pairs[(a, b)] += n
    return pairs

def merge(words, pair):
    out = Counter()
    for word, n in words.items():
        new, i = [], 0
        while i < len(word):
            if i < len(word) - 1 and (word[i], word[i + 1]) == pair:
                new.append(word[i] + word[i + 1]); i += 2
            else:
                new.append(word[i]); i += 1
        out[tuple(new)] += n
    return out

for step in range(1, 6):
    pair, n = pair_counts(words).most_common(1)[0]
    words = merge(words, pair)
    print(f"merge {step}: {pair[0]!r} + {pair[1]!r} -> {pair[0] + pair[1]!r}  (seen {n}x)")
print(dict(words))
merge 1: 'c' + 'l' -> 'cl'  (seen 6x)
merge 2: 'cl' + 'a' -> 'cla'  (seen 6x)
merge 3: 'cla' + 'i' -> 'clai'  (seen 6x)
merge 4: 'clai' + 'm' -> 'claim'  (seen 6x)
merge 5: 'p' + 'o' -> 'po'  (seen 3x)
{('claim',): 3, ('claim', 's'): 2, ('claim', 'e', 'd'): 1, ('po', 'l', 'i', 'c', 'y'): 2, ('po', 'l', 'i', 'c', 'i', 'e', 's'): 1}

The pair c l ties with l a at six, and this code breaks ties by first appearance. Encoding a new string replays the merges in the order learned, so a frequent word becomes one token and a rare word falls into pieces that were frequent elsewhere.

Two changes turn this into what production models use. First, bytes instead of characters. The GPT-2 paper observes that a byte-level BPE needs a base vocabulary of only 256 symbols, so any Unicode string can be encoded and nothing is ever unknown. Second, pre-tokenisation. Left alone, BPE would learn many variants of common words such as dog. and dog!, so GPT-2 prevents merges across character categories, with an exception for spaces. Modern tokenizers use a regular expression that cuts the text into chunks before any merge applies. Llama 3.1's pattern separates contractions, letter runs, digits in groups of one to three, punctuation runs and whitespace runs, and merges never cross a chunk boundary. That is why digits, spaces and punctuation behave as they do below.

SentencePiece and Unigram

SentencePiece is a library, not an algorithm. Kudo and Richardson (2018) describe a tokenizer that trains directly on raw sentences with no word-level pre-splitting, so it suits languages without spaces. It treats whitespace as an ordinary symbol, written ▁, which is why Llama 2 and Mistral tokens look like ▁policy. Mistral 7B v0.1 ships a SentencePiece model and a 32,000-entry BPE vocabulary.

Unigram, proposed by Kudo in 2018, reverses the direction. It starts from a large seed vocabulary of frequent substrings and prunes it. A sentence's probability is the product of its subwords' probabilities, the best segmentation comes from the Viterbi algorithm, and probabilities are fitted with expectation-maximisation. Pruning drops the subwords whose removal costs the least corpus likelihood, never single characters. Because it is probabilistic, Unigram can sample several segmentations of one sentence, which Kudo used as training-time noise. BPE gives one per string.

Vocabulary sizes, and what a bigger one costs

A larger vocabulary packs more characters into each token, so sequences are shorter, attention is cheaper and more text fits in the window. It also enlarges two matrices, the input embedding table and the output projection, each vocabulary by hidden size. For Llama 3.1 8B that is 128,256 × 4,096 = 525,336,576 parameters each, about 0.53 billion, and the model does not tie them. Together they are about 1.05 billion of the 8.03 billion parameters, about 13% (chapter 02).

The Llama 3 paper says the 128K vocabulary combines 100K tokens from tiktoken with 28K added to support non-English languages, and that compression on a sample of English rose from 3.17 to 3.94 characters per token against the Llama 2 tokenizer. The table comes from tokenizer and configuration files fetched in November 2026.

Past some point added tokens are rare and barely trained. Larger wins when traffic is multilingual or code-heavy, where small vocabularies fragment text most.

Why numbers, identifiers and whitespace tokenise the way they do

Merges are learned from frequency, so anything common is cheap and anything arbitrary is expensive. Harbourline's policy identifier is arbitrary by design. Here are the pieces for three tokenizers, produced by running them.

'HL-UK-4471-220'
  llama3.1    8  ['HL', '-', 'UK', '-', '447', '1', '-', '220']
  o200k       8  ['HL', '-', 'UK', '-', '447', '1', '-', '220']
  qwen3      12  ['HL', '-', 'UK', '-', '4', '4', '7', '1', '-', '2', '2', '0']

Three mechanisms are visible. The regular expression cuts digit runs into groups of up to three, left to right, so 4471 becomes 447 and 1. The grouping depends on position, not value, which is one reason models are error-prone at long arithmetic and at copying numbers exactly. Qwen3 and Mistral emit one token per digit, which is longer but consistent. Hyphens are separate tokens because punctuation sits in its own chunk. For retrieval, a dense embedding sees this identifier as eight to twelve meaningless fragments, the failure the RAG guide's embeddings chapter describes, and the reason exact-match lookups belong in a lexical index.

Whitespace follows the same logic. In byte-level BPE, Ġ is the visible name of the space byte, and a leading space attaches to the word after it. strawberry and strawberry are different strings: in the Llama 3.1 tokenizer the first is three tokens and the second is one. Runs of spaces collapse into one token, so indented code is cheap: four spaces and return came out as three tokens in every tokenizer tested.

Tokens per word by language, and the bill

The vocabulary is learned from a corpus, so a language that was rare in it gets fewer merges and more fragments. Petrov et al. (2023) report that the same text translated into different languages can differ in tokenisation length by up to 15 times, even in tokenizers built for multilingual use. Ahia et al. (2023) tied it to money: vendors charge per token, so speakers of some languages pay more for the same content.

The Harbourline question, without the policy number, was run through three tokenizers. The translations are the author's and one sentence is a tiny sample, so the ratios are indicative only.

The Hindi row falls from 66 tokens on cl100k_base to 24 on o200k_base, a vocabulary change worth a factor of nearly three. Harbourline's traffic is mostly English, but a Hindi question pays the multiple on every turn, output included. At 1,421 tokens a request (counted below), a million input tokens covers about 700 requests. If the same instructions cost twice the tokens in another language, that falls to about 350, and the window holds half as much conversation. Measure your real traffic with your real tokenizer.

The strawberry failures are a tokenisation artefact

Ask a model how many times r appears in strawberry and it may say two. It is not a reasoning failure in the usual sense. The Llama 3.1 tokenizer cuts the word to str, aw, berry, and o200k_base cuts it to st, raw, berry. The model receives three ids, and each id is a vector with no letters inside it. To count the letter it must have learned, from text, which letters make up each token, which is shaky for a split like this. The same mechanism explains failures at reversing strings and at counting characters in the policy number.

Give character-level work to code. If Harbourline's claims extraction must verify that a policy number matches HL-(UK|US)-\d{4}-\d{3}, a regular expression does it, and asking the model to check character by character is the wrong tool. Asking the model to spell the word out before counting can help, but it spends output tokens to work around an input representation. The rule flips when exactness is not required, as in paraphrasing a customer's message.

Special tokens and chat templates

Vocabularies reserve ids for control symbols that never come from text. The Llama 3.1 vocabulary holds 256 of them: <|begin_of_text|> (id 128000), header markers, and <|eot_id|> (id 128009), which ends a turn. A chat template turns a list of role-tagged messages into one string with these markers. Here is Llama 3.1's, rendered for a system message S and a user message Q:

<|begin_of_text|><|start_header_id|>system<|end_header_id|>

S<|eot_id|><|start_header_id|>user<|end_header_id|>

Q<|eot_id|><|start_header_id|>assistant<|end_header_id|>

The template adds 15 tokens around the two messages, and its final lines open the assistant turn so the model's next token is the first word of the reply. Three failure modes follow. The first is a wrong template: an instruct model served with a different format can degrade quietly, with no error. The second is a doubled start token: Hugging Face's documentation warns that templates already include special tokens, so tokenising a rendered string with default settings can add them twice. Pass add_special_tokens=False or let apply_chat_template tokenise directly.

The third is injection through text. Encoding the string hi <|eot_id|> with the Hugging Face Llama 3.1 tokenizer and it came back as ids 6151, 220, 128009: the literal text in a user's message became the real end-of-turn token. tiktoken refuses by default, raising an error for disallowed special tokens unless you pass allowed_special. So behaviour depends on the library. If the serving path parses them, a Harbourline customer who pastes control strings can end a turn early or forge a role boundary. Strip or escape such strings before templating, and test your own stack, since this depends on the tokenizer library and version.

Counting Harbourline's prompt

The help-centre prompt has three parts: a system prompt, two retrieved passages, and the question. The system prompt is an illustrative text written for this guide, 973 words of rules, style and escalation instructions, and the two passages are short stand-ins for a policy schedule and a wording section. The counts describe this text only. The script takes the system prompt, the question and then the passages as file arguments.

count_tokens.py
import sys
import tiktoken
from transformers import AutoTokenizer

system = open(sys.argv[1]).read().strip()
question = open(sys.argv[2]).read().strip()
context = "\n\n".join(open(p).read().strip() for p in sys.argv[3:])
user = f"CONTEXT\n{context}\n\nQUESTION\n{question}"
body = system + "\n\n" + user                     # the text, with no chat framing

print(f"characters {len(body)}  words {len(body.split())}")
for name in ("o200k_base",):
    enc = tiktoken.get_encoding(name)
    print(f"{name:12s} vocab {enc.n_vocab:>7,}  tokens {len(enc.encode(body)):>5,}")

for repo in ("NousResearch/Meta-Llama-3.1-8B-Instruct",):
    tok = AutoTokenizer.from_pretrained(repo)
    plain = len(tok(body, add_special_tokens=False)["input_ids"])
    chat = tok.apply_chat_template(
        [{"role": "system", "content": system}, {"role": "user", "content": user}],
        add_generation_prompt=True, tokenize=True)
    chat = chat["input_ids"] if hasattr(chat, "keys") else chat
    print(f"{repo.split('/')[1]:28s} vocab {len(tok):>7,}  text {plain:>5,}  chat-templated {len(chat):>5,}")

Run in a fresh virtual environment with tiktoken, transformers and jinja2, using an ungated mirror of the gated Llama tokenizer files, it prints: The output:

characters 6723  words 1145
o200k_base   vocab 200,019  tokens 1,422
Meta-Llama-3.1-8B-Instruct   vocab 128,256  text 1,406  chat-templated 1,421

The system prompt alone is 1,187 Llama 3.1 tokens, the "about 1,200" this guide uses. The question and passages add about 220 and the chat template 15. The whole request is 1,421 tokens, and the two tokenizers differ by about 1% on this English prose. A rough count with the wrong tokenizer is fine for English and unreliable for other languages, code and identifiers. Count with the tokenizer of the model you call.

The 1,421 tokens are what prefill processes before the first output token, and they set a floor on cost, worked through in Latency and Cost at Scale.

✓ Check yourself

Answer from memory first.

  1. Two engineers count the same prompt, one with o200k_base and one with the Llama 3.1 tokenizer, and the counts differ by 16 on 1,400 tokens. Why is that unremarkable for English, and for which input would you expect it to become a problem?

    Show answer

    Both are byte-level BPE vocabularies trained on large, mostly English corpora, so common English words are single tokens in each. They diverge on non-English text, code and identifiers: the Hindi sentence differed by more than a factor of two between cl100k_base and o200k_base. See Tokens per word by language.

  2. A colleague says the model "can't count letters because it isn't smart enough". What is a more accurate explanation, and what do you build for a claims form that needs the check?

    Show answer

    The input is token ids, and a token is one vector with no letters in it, so the model must infer spelling from training data. The tempting answer, a capability limit, misses the representation. For the form, use code such as a regular expression on the policy number. See The strawberry failures.

  3. Your serving code renders the chat template to a string and then calls the tokenizer on it with default settings. Quality drops slightly and no error appears. What is the likeliest cause, and how do you confirm it?

    Show answer

    The start-of-text token is probably present twice. Decode the first ten ids and look for two <|begin_of_text|> entries, then tokenise with special-token addition off. See Special tokens and chat templates.

  4. Harbourline wants the help-centre assistant to answer in six languages and has budgeted from an English token count. What do you tell them, and what would make you accept the budget anyway?

    Show answer

    Counts run higher in most other languages, from 1.8 to 3.2 times in this sample on Llama 3.1 and up to 15 times in published work, so measure per language with the production tokenizer. Accept the English budget if non-English traffic is small enough that a 3× multiplier on it stays inside your margin. See Tokens per word by language.

Takeaway

  • A tokenizer is a frozen, corpus-trained function from a string to integer ids, and the model never sees characters.
  • Byte-level BPE learns merges by repeatedly joining the most frequent adjacent pair, after a regular expression splits the text into chunks that merges cannot cross.
  • A larger vocabulary shortens sequences but adds two vocabulary-by-hidden-size matrices, about 1.05 billion parameters in Llama 3.1 8B.
  • Identifiers, digits and non-English text fragment because merges follow frequency, so cost, context and retrieval behave worse on them than on English prose.
  • Letter-level failures come from the input representation, so give character work to code.
  • Use the exact chat template and tokenizer of the model you call, and treat control strings in user text as an injection risk. Harbourline's help-centre request is 1,421 tokens under Llama 3.1, of which the system prompt is 1,187.
